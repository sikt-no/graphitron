# A structural guard gives case-folded name comparison one legitimate home

The launcher-method census case-folded its uniqueness key for years on a rationale borrowed by analogy from the projection address census, where the fold is justified (a generated class name becomes a file name, and case-insensitive filesystems collide) but where method names never were. The only thing holding the line against further spread was a review-only javadoc instruction ("Do not add either by analogy" in `RoutineWriteRelation`), and it is precisely what failed: a review-only label is an invitation. The tree's existing pattern for this failure mode is `TableNameComparisonCaseGuardTest`: one legitimate home for a case comparison, a structural scan forbidding the shape elsewhere, and touching the guard's assertion as the deliberate review point. A sibling guard should give generated-name case folding its one legitimate home (the projection address census, whose filesystem rationale `Rejection.InvalidSchema.CaseFoldCollision`'s javadoc carries) and fail the build when a name census elsewhere folds its key by analogy. Depends on the launcher census dropping its fold first, or the guard is born with two homes.

## The invariant, at altitude

A case fold is minted only where two namespaces meet; the fact model states this rule for the store side, and this item is its plan-side half. The one boundary the generator's own names cross is Java identifier to file stem: a class address becomes a file path, and case-insensitive filesystems (APFS, NTFS) collapse case there. Two populations cross that same boundary today, each with its own gate: authored GraphQL type names, folded by `GraphitronSchemaBuilder.rejectCaseInsensitiveTypeCollisions` into the typed `Rejection.InvalidSchema.CaseFoldCollision`, and minted projection unit addresses, folded by the projection address census. Method names never cross it, so a folded method-name comparison is not a collision check; it is the rejection of pairs whose emitted names are distinct, which R889 establishes is a bug. The guard turns that argument into a build failure:

- **Minted method names: zero homes.** No statement may fold or case-insensitively compare a minted method name.
- **Minted unit addresses: one home.** The fold is derived once, on the minted-name type itself, and census keys consume the derived value.

The principles-architect review of the first draft reshaped this item: the draft excluded the census's two *files* from the scan, defending a location, where the precedent guard (`TableNameComparisonCaseGuardTest`) defends a *type* (`TableRef.sameTable` is the canonical predicate and the guard excludes its body). The plan below lifts the fold onto the minted-name type first, so this guard gets the same footing.

## Plan

1. **The type-level home first: `UnitRef.fileStem()`.** One derived accessor on the minted-name type, the unit's address as a case-insensitive filesystem sees it (the folded `fqcn()`, `Locale.ROOT`). Its javadoc is where the filesystem rationale lives, with a resolvable `{@link}` to `Rejection.InvalidSchema.CaseFoldCollision`. This is the same single-mint rule the tree already enforces one derivation up: `PackageImportDirectionTest.unitRefsAreMintedOnlyByThePlansNamingVocabulary` pins that unit refs are minted only by `GeneratedUnits`; "the fold of a unit address is computed only on `UnitRef`" is that rule applied to the derived value.

2. **Re-key the projection address census on it.** Three sites spell their own fold today and stop doing so: `ProjectionRelation`'s constructor backstop and `ProjectionCommands.AddressCensus.add` fold `unit().fqcn()`, and the validator mirror's `record()` folds an intermediate `simpleName` string, a third spelling of the same key that quietly disagrees with the other two about what it folds (simple name versus full address). All three consume `fileStem()`. After this step no census spells a fold; deleting the accessor is a compile error at every census, which is a stronger gate than any roster assertion (this is why the first draft's exclusion-rot assertion is gone: the type lift makes it unnecessary).

3. **The guard.** `MintedNameCaseFoldGuardTest`, a `@UnitTier` structural scan in test package `no.sikt.graphitron.plan`, beside the censuses it polices; shape cloned from `TableNameComparisonCaseGuardTest` (recursive walk, pattern list, exclusion, vacuity assertion, offending-sites failure message), with the scan root single-sourced through `GuardScope.locateRepoRoot()` like the rest of the guard family, resolving the whole module main tree (`graphitron/src/main/java`): the precedent's `rewrite` subtree would miss the `plan` package where every census lives. One excluded file: `command/UnitRef.java`, the accessor's own body. A type, like `TableRef`, not a place.

4. **The forbidden shape**, spelling-closed and stated honestly in the guard's javadoc, like the precedent. Within one statement, a fold spelling (`.toLowerCase(`, `.toUpperCase(`, `.equalsIgnoreCase(`, `.compareToIgnoreCase(`) co-occurring with a minted-name anchor: `.unit()`, `UnitRef`, `UnitMethodRef`, or `.fqcn()`. Statement-bounded by `[^;]*`, which crosses newlines but never a `;`: the launcher census's key build spanned a line break (`(… + "#" + row.unit().methodName())` newline `.toLowerCase(ROOT)`), and the shapes that must *not* trip, camelling a first character out of an accessor landed in a local variable (`render/TableLocal.java`, `render/PathFragments.java`), sit behind a semicolon. The anchor set is deliberate: the first draft anchored on `.methodName()` and `.simpleName()`, but `.methodName()` is also spelled by the authored-name refs (`JoinCondition`, `AuthoredMethodRef`), a namespace where a fold can be legitimate, and `.simpleName()` is javapoet vocabulary across ~33 main-source files, so either anchor makes the guard fire a message about name censuses at code that is doing something else, and a false positive with a wrong message invites exclusion-list widening. `.fqcn()` stays in the set although a handful of types beyond `UnitRef` spell it (`EnumMappingResolver.EnumValidation.Valid`, `RecompileSet`'s nodes): each is a Java class address, the file-stem rule covers all of them, so a hit there is review-worthy under the same rule rather than noise. A method-name fold that reaches through neither `.unit()` nor a ref type in the statement escapes, the same intermediate-variable trade the precedent makes; the guard is a tripwire against analogy-borrowing, not a data-flow analysis.

5. **Pattern-sanity fixtures.** A second test method in the same class runs the same scan function over embedded text-block snippets: each forbidden orientation trips (including the newline-spanning launcher key build and `ProjectionRelation`'s pre-lift fold, both lifted verbatim from the pre-fix tree), and the legitimate shapes do not (separate-statement camelling; a single-statement javapoet `simpleName()` camelling, pinning the dropped anchor). This pins the statement-boundedness and the anchor set, the parts most likely to rot, without waiting for a real regression to probe them.

6. **Javadoc.** `RoutineWriteRelation`'s prohibition sentence (post-R889 wording) gains the guard as its enforcement, named in prose as `{@code MintedNameCaseFoldGuardTest}` (a `{@link}` cannot resolve a test symbol from main javadoc, and the reference gate would fail it). The `AddressCensus` javadoc in `ProjectionCommands` and `ProjectionRelation`'s class javadoc point their key at `{@link UnitRef#fileStem()}`, where the rationale now lives. The guard's own javadoc states the rule at the altitude of the invariant section above, and carries its retirement clock in one sentence: the guard polices the transitional plan surface and retires when the address census re-sources onto the store, where the fold rule already has its own statement and enforcers.

7. **Quarantine, not endorsement.** The census's author-facing collision text still splices a folded simple name that names no generated class (`AddressCollision.foldedSimpleName`, and `byFoldedName`, an identity function whose comment apologises for it), the projection twin of the defect R889 repairs on the launcher side. That repair is R891 (`projection-collision-typed-arm`), filed with this spec; the guard javadoc's mention of the census words the exclusion accordingly.

## What the scan deliberately does not cover

Stated in the guard's javadoc, so the honest-scope precedent carries over:

- **Raw-string folds.** `GraphitronSchemaBuilder.rejectCaseInsensitiveTypeCollisions` folds authored GraphQL type names into file stems. That is the *same* boundary and the same rule (Java identifier to file stem), over the authored population rather than the minted one, and it already has its own gate, the typed `CaseFoldCollision` rejection. It is out of *scan* scope for the mechanical reason only: it folds a raw registry key (`entry.getKey()`), no minted-name anchor appears in the statement, so the scan never sees it. The guard javadoc says exactly this; the first draft called it "a different namespace boundary", which the code contradicts.
- **Intermediate-variable evasion.** An anchor landed in a local and folded in a later statement escapes the scan, the same trade the precedent guard makes; the guard is a tripwire against the analogy-borrowing failure mode, not a data-flow analysis.
- **Other spellings.** `String.CASE_INSENSITIVE_ORDER`, hand-rolled char-wise folds. Closed list, stated.

## Verification done while writing this spec

The fold-with-minted-anchor co-occurrence sites in today's main tree are exactly four: the two projection-census sites step 2 re-keys (`ProjectionRelation` constructor, `ProjectionCommands.AddressCensus.add`) and the two launcher folds R889 removes (`LauncherRelation` constructor, `LauncherCommands` ~line 1160). The `record()` fold in `ProjectionCommands` (~line 573) folds an intermediate `String`, invisible to the scan, and is retired by step 2 regardless. The `simpleName()` uses in `render/` (`TableLocal`, `PathFragments`) are first-character camelling; they stop being a false-positive risk once `.simpleName()` leaves the anchor set, and their separate-statement shape is pinned in the fixtures anyway. No `equalsIgnoreCase`/`compareToIgnoreCase` co-occurs with any minted-name anchor today. Accessor-spelling census: `.fqcn()` is spelled by `UnitRef` plus a handful of other class-address types (`EnumMappingResolver`, `RecompileSet`), `.methodName()` also by the authored-name refs `JoinCondition` and `AuthoredMethodRef`, `.simpleName()` by javapoet `ClassName` across ~33 main-source files; the anchor-set reasoning in step 4 follows from this census.

## Reviewer findings

### Round 1 (2026-09-01, Spec -> Ready, reviewer session 01KbabzLipk5gnooagRqCVhV)

Verdict: withhold. One blocking finding on question two that spills onto question one, and three non-blocking notes.

The goal reads clearly and I could restate it without the phase list: nothing changes for a consumer of graphitron, and that is the honest answer for a `testing` item. What changes is that the failure mode the launcher census demonstrates, a fold borrowed by analogy from a census where the fold is justified, stops being reachable by a contributor, because the build fails instead of a javadoc sentence asking politely. The diagnosis holds against the tree: I ran the proposed pattern set over `graphitron/src/main/java` and the co-occurrence sites are exactly the four the plan names, `.simpleName()` really is javapoet vocabulary across exactly 33 main-source files, `.methodName()` really is spelled by the authored-name refs, and dropping both from the anchor set really does take `render/TableLocal` and `render/PathFragments` to zero hits. Lifting the fold onto `UnitRef` rather than excluding two files is the right correction to the first draft, and it puts this guard on the same footing as `TableNameComparisonCaseGuardTest`. What blocks sign-off is one site in step 2 that cannot consume the accessor as step 1 defines it.

**Finding 1 (question two: architecture fit; question one: consumer-visible outcome). The validator mirror cannot consume `fileStem()` as defined, and step 2 asserts that it does.**

`ProjectionCommands.addressCollisions` mints its refs from `new GeneratedUnits("")` (line 524). That placeholder is not incidental: `addressCollisions(GraphitronSchema)` takes only the schema, and `GraphitronSchemaValidator` holds no output package to pass, so the mirror has nothing to fill it with. With an empty output package `GeneratedUnits.packageName("types")` returns `.types`, leading dot and all, so `fqcn()` on a mirror ref returns `.types.FilmCategory` and `fileStem()` would return `.types.filmcategory`. Three consequences the plan does not account for.

First, the accessor's stated contract is false at that site. Step 1 defines `fileStem()` as the unit's address as a case-insensitive filesystem sees it, and puts the filesystem rationale in its javadoc. `.types.filmcategory` is no file's address, because the mirror's refs deliberately carry no real package. The third site would consume a value whose documented meaning does not apply to it.

Second, it is a silent author-facing regression, which is why this reaches question one. `AddressCollision.foldedSimpleName` is the key verbatim (`byFoldedName` is the identity function step 7 names), and `GraphitronSchemaValidator.validateProjectionUnitAddresses` splices it into the located error: `mints the generated projection unit name '<key>' (case-folded)`. An author with a real collision reads `'filmcategory'` today and would read `'.types.filmcategory'` after step 2. No test in the tree pins that message or that validator arm at all, so the change ships unnoticed. Step 7 knowingly leaves the splice defect to R891, which is Backlog; it does not say the defect gets worse while R891 waits.

Third, it weakens step 2's own load-bearing argument. "After this step no census spells a fold; deleting the accessor is a compile error at every census" is the reason the first draft's exclusion-rot assertion is gone, and that argument needs all three sites to want the same derived value. Two do. The third wants a package-independent grain, which is why it folds a simple name today. The plan reads that divergence as accidental ("quietly disagrees"), where it in fact follows from how the mirror is constructed.

What would satisfy the finding: the plan decides this fork rather than asserting past it, and says what an author's collision error reads after the item lands. Arms I can see, without picking one. (a) The mirror keeps a simple-name-grain key, which wants either a second derived accessor on `UnitRef` at that grain or an open-coded fold left standing, and in the second case the guard needs the exclusion-rot assertion back. (b) R891's message repair moves into this item or ahead of it, so the key change lands on text that no longer splices the raw key. (c) The mirror is given the real output package, which changes how the validator is constructed and wants its own justification.

**Non-blocking.**

- The precedent guard is line-based. `TableNameComparisonCaseGuardTest.scan` reads `Files.readAllLines` and matches per line, so its `[^;\n]*` bound is belt-and-braces. Step 4's `[^;]*` deliberately crosses newlines, which I confirmed is necessary (`LauncherCommands:1169` and `LauncherRelation:54` both span a line break), so the clone has to match whole-file content and derive the line number from the match offset. Step 3's clone list does not mention this, and the offending-sites failure message it does name is the part that depends on it.
- `[^;]*` crosses braces as well as newlines. Running the proposed pattern set over today's tree, `ProjectionRelation:22` matches a second time in the anchor-to-fold orientation by running from the `if` condition into the `throw` body, no semicolon intervening. Today that is a duplicate hit on a site the guard already flags, so it costs nothing. The general shape, a fold in the first statement of a block whose condition names a unit ref or the reverse, is a false-positive class the honest-scope section does not name beside the intermediate-variable trade.
- The `LauncherCommands` fold is at lines 1169-1170; line 1160 is the `new GeneratedUnits("")` above it. The "~" makes this harmless, and I have left it alone; noting it only because the verification section is otherwise exact.

### Round 2 (2026-09-01, Spec -> Ready, reviewer session 01PoH8mZNjUBpgprWJY223pk)

Verdict: withhold. The plan body is unchanged since round 1 (the only commit touching this file since the revision that lifted the fold onto `UnitRef` is round 1's findings), so round 1's blocking finding stands unanswered. I re-derived it from the code rather than taking it on trust, and it holds on every mechanical claim. Two new non-blocking notes below, one of which step 6 activates.

**Finding 1 (question two, spilling onto question one) stands: step 2's "all three consume `fileStem()`" is false at the validator mirror.**

Independently confirmed, in today's tree:

- `ProjectionCommands.addressCollisions` mints from `new GeneratedUnits("")` at line 524, and `addressCollisions(GraphitronSchema)` takes only the schema, so the mirror has no output package to pass.
- `GeneratedUnits.packageName(String)` is `subPackage.isEmpty() ? outputPackage : outputPackage + "." + subPackage`, so with an empty output package the `types` sub-package resolves to `.types`, and `UnitRef.fqcn()` (`packageName.isEmpty() ? simpleName : packageName + "." + simpleName`) returns `.types.FilmCategory`. A `fileStem()` defined as the folded `fqcn()` returns `.types.filmcategory` there.
- The mirror's `record()` folds a `simpleName` string, and the three call sites feed it `typeClass(...).simpleName()`, `nestingUnit(...).simpleName()` and `pivotUnit(...).simpleName()`. Consuming the accessor means passing the ref instead, at a grain the site does not want.
- The key reaches an author verbatim: `AddressCollision.foldedSimpleName` is the map key (`byFoldedName` returns its argument), and `GraphitronSchemaValidator.validateProjectionUnitAddresses` (line 121, splice at line 131) puts it in `mints the generated projection unit name '<key>' (case-folded)`. Grepping the tree for `addressCollisions` and for the message text finds no test on that arm, so the text change would ship unpinned.

One narrowing that does not rescue the step. All three mirror mints land in `SUB_TYPES` (`typeClass`, `nestingUnit` and `pivotUnit` all call `unit(SUB_TYPES, ...)`), so the fqcn grain and the simple-name grain agree about *which* names collide; only the message text changes. That makes the regression cosmetic rather than behavioural, and it is still a change to author-facing text that the plan does not name, decided by whoever implements step 2 rather than by the spec. The blocking half is the second one round 1 gave: an implementer handed this plan redesigns at that site, because the accessor as step 1 defines it does not fit it. Round 1's three arms (a second grain-appropriate accessor, pulling R891's message repair forward, or giving the mirror a real output package) are the fork; the spec should pick one and say what an author's collision error reads after the item lands.

Everything else in the plan checks out against the tree. Running the step-4 pattern set (the four fold spellings, the anchor set `.unit()` / `UnitRef` / `UnitMethodRef` / `.fqcn()`, bounded by `[^;]*`, both orientations) over `graphitron/src/main/java` returns exactly the sites the verification section claims: `LauncherCommands:1169` and `LauncherRelation:54` (both newline-spanning, both removed by the launcher item), `ProjectionCommands:496`, and `ProjectionRelation:22` twice. Every symbol the spec names exists as named: `GuardScope.locateRepoRoot()` is public precisely so a guard in another test package can share the anchor, the test package `no/sikt/graphitron/plan` already exists, `PackageImportDirectionTest.unitRefsAreMintedOnlyByThePlansNamingVocabulary` is at line 311, `Rejection.InvalidSchema.CaseFoldCollision`, `GraphitronSchemaBuilder.rejectCaseInsensitiveTypeCollisions`, `TableRef.sameTable`, and `RoutineWriteRelation`'s "Do not add either by analogy" sentence are all present. The precedent guard's shape is as described, excluding `model/TableRef.java` by trailing-path match and asserting a positive scanned-file count.

**Non-blocking.**

- Step 6 activates a false-positive class. The scan reads raw source, so comment regions are scanned too, and a javadoc block contains no semicolons at all: an anchor named in a doc comment reaches across `[^;]*` into the first fold spelling in the code below it. I confirmed this with the proposed patterns against a synthetic `/** ... {@link UnitRef#fileStem()} */` immediately above a method whose first statement folds. No such pair exists in the tree today, but step 6 is the step that puts `{@link UnitRef#fileStem()}` into `ProjectionCommands` and `ProjectionRelation`, two scanned files. This is the same family as round 1's block-crossing note; either the scan strips comments before matching, or the honest-scope section names it, or step 6 keeps the link and the nearest fold apart. Whichever, an implementer should know before writing step 6.
- `fileStem` reads against the tree's own vocabulary for the thing it names. `GeneratedUnits.toRelativeJavaPath(String fqcn)` maps an fqcn to a path, whose stem is the simple name and whose package segments are directories; an accessor called `fileStem()` that returns the folded whole fqcn therefore names a path, not a stem. Folding the whole address is fine for the collision purpose (the package segments are constant across the population), so this is naming, and I raise it only because it is the same conflation that lets step 2 read the mirror's simple-name grain as a "third spelling of the same key". Whatever the fork above resolves to, the accessor's javadoc should say which of address or stem it returns.
