# A client-supplied tenant key routes by the tenant column database value, not its converted Java form

## Goal

In a database-per-tenant build, two tenant values that the tenant column stores as the same database value name the same tenant, wherever the value came from. Today the generated router compares tenant keys by their Java form, so when a jOOQ converter maps the column to a Java type with more spellings than the database type, a client value that binds correctly in the SQL is refused by the router or silently matches no tenant. sis's `INSTITUSJONSNR_EIER` is `INTEGER` in Oracle and `String` in Java through `IntegerToStringConverter`: `eierOrganisasjonskode: "0194"` binds as `194`, yet routing fails with "Tenant '0194' is not permitted for this request" because the request's tenant set holds `"194"`. After this lands, every tenant key graphitron receives, from a client argument, a decoded id, a `@tenant` value, a filter slot, the consumer's `RequestTenants` or the runtime's `DataSource` map, is put through the column's converter and back before it is compared, so `"0194"` and `"194"` are one tenant. A value the column cannot bind (`"abc"` on that column) is a client error; a value it binds by coercion names the tenant the SQL would read, since the key follows the bind. Builds whose tenant column has no converter route as today, except that an unreadable tenant value becomes a client error rather than a server error.

(Terms: the *tenant column* is the column named by `<tenantColumn>`, which decides which database a row lives in; a *tenant key* is one value of it, used to pick the `DataSource`; *routing* is choosing that `DataSource` for a field; *canonical* here means the Java value a read of the column would return for that database value.)

The schema shape, from the converter-backed fixture this item adds (the sis shape: a numeric column the catalog binds to `String`):

```graphql
type Query {
    sites(ownerOrg: String! @field(name: "owner_org")): [OrgSite!]!
    sitesNarrowable(ownerOrg: String @field(name: "owner_org")): [OrgSite] @tenantFanOut
}
```

With tenant `"186"` hosted and permitted, `sites(ownerOrg: "0186")` is refused today and returns tenant 186's sites after; `sitesNarrowable(ownerOrg: "0186")` returns an empty list today, presented as complete, and returns tenant 186's sites after.

## Evidence

Reported from sis on 2026-10-15 (fs-plattform branch `sis/upgrade-graphitron`). sis already normalises its own side: `GraphqlEngines` builds the runtime source map and `RequestTenants` with `replaceFirst("^0+", "")`, a hand copy of the converter's equality. In Graphitron 9, sis's `QueryInspector.identifiserInstitusjonsnrEier` stripped leading zeros from every tenant it derived before routing, so `"0194"` and `"194"` were the same institution. Whether clients rely on this is not verified from traffic; the defect stands without it, because the SQL and the router disagree about one value.

## Where keys meet today

All of this is emitted by `ConnectionRuntimeClassGenerator` into the consumer's `schema` package. The tenant key type `K` is the column's Java type, read off the catalog by `TenantScopeClassifier` into `TenantScopes.Configured.tenantType`.

- **Client-sourced keys** all pass through `TenantConnections.namedTenant(Object...)`, directly or through `divinedTenant`, which refuses a fold that names no tenant. `namedTenant` folds every bound value with `agreeOnTenant` (raw `equals`, before any coercion) and then types the agreed value with `tenantKeyOf`. `tenantKeyOf` is already the shared coercion seam: its javadoc says it is "shared by the routing fold and the fan-out narrowing so a value names the same tenant whichever reads it", and it parses a `String` for an `Integer`/`Long` key. The fan-out narrowing (`fanOutDomain(env, Object[])`) calls `tenantKeyOf` per named value and then `retainAll`s against the request domain, which is where `"0194"` silently empties the result. The per-row lookups (`HandleMethodBody.emitGroupDispatch`, for `node`/`nodes`/`_entities`) group on the raw decoded value and call `divinedTenant` per group.
- **Keys compared** after that: `entryFor`'s `tenants.contains(key.get())` (the one enforcer every keyed acquisition goes through), `permits`, `fanOutDomain`'s hosted/requested intersection, and the runtime's `sourcesByTenant.get`.
- **Consumer-supplied keys**: the `GraphitronRuntime` constructor map (copied into `sourcesByTenant`), and `RequestTenants` (tenant set and default tenant).
- **Keys read off rows** (`handDown`, the parent-row read in `TenantDslEmitter`, `tenantLoaderName`) are the converter's `from` of a database value, canonical by construction.

So the gate is not one site: the agree-fold and the narrowing compare before `entryFor` ever runs. The one site every client-sourced leaf already passes through, or can be made to, is `tenantKeyOf`. Consumer-supplied keys enter at two constructors.

## Implementation

**Capture: the column's database type is a catalog fact.** `JooqCatalog` reads one more fact off each live `Field` where it builds a `ColumnEntry` (the `findColumn` reduction and its siblings that construct the record): the *database type*, the Java type of the value jOOQ exchanges with the database, `field.getConverter().fromType().getName()`. With no converter jOOQ reports its `IdentityConverter`, whose `fromType()` is the bound type, so the fact is always present and equals `columnClass` on an unconverted column. `ColumnEntry` gains it as `databaseType`; its one reader in this item is the classifier, which already reads `ColumnEntry`. It is not written to the store: `ColumnFacts`, `JooqFactCapture` and `sql_column` are unchanged, because nothing in this item reads the fact from the store, and a store column with no reader is a fact admitted because it was available. A later reader that wants it in the store (hover, the node-id landing defects) adds the column with its use site.

The converter's identity is deliberately not captured. jOOQ wraps every plain `Converter` in an adapter: on the fixture catalog `CONVERTER_ORG.ORG_CODE.getConverter().getClass()` is `org.jooq.ContextConverter$1`, the same class every converter-backed column reports, sis's `IntegerToStringConverter` included, and jOOQ exposes no accessor for the converter it wraps. A captured class name would therefore say only "some converter", which the database type differing from the bound type already says.

**Classification: one representative column, and an agreement that makes it representative.** `TenantScopeClassifier.classify` reads `databaseType` off `ColumnEntry`, as it reads `columnClass` today. `TenantScopes.Configured` gains the representative column as the existing `TableRef` (from `JooqCatalog.TableEntry.toTableRef`) and `ColumnRef` (from the entry's `allColumnRefs()`), which together render `<Tables>.<TABLE>.<COLUMN>` through `CatalogRefs.constantsClass(TableRef)`, `TableRef.javaFieldName()` and `ColumnRef.javaName()`: the first tenant-scoped table in the catalog's schema-then-table order, the order `tenantScopedTables` already keeps.

One representative is only sound if every table's column compares values the same way, so `TenantColumnTypeDisagreement` widens from the bound type to the pair (bound type, database type). `TableSite` gains the database type, the distinct-key set keys on the pair, and the message changes from "disagreeing Java types" to naming both per table. This compares Java types, not `sql_type`, so `varchar` beside `text`, or `NUMBER(4)` beside `NUMBER(5)` under one converter, still agree, while a `varchar` bound to `String` beside a `bigint` converted to `String` is rejected: the two would canonicalise `"0186"` differently, which is the disagreement one representative cannot absorb.

*What the agreement does not check.* Two tables that map the column through two different converters between the same pair of types agree under this check, and the representative's converter then decides equality for both. The classifier cannot tell them apart, for the reason the capture paragraph gives, and no behavioural comparison is available without sample values. The assumption this leaves is the one the configuration already states: `<tenantColumn>` names one column, so it names one equality. A jOOQ build reaches two converters on one column only by two `<forcedType>` entries matching the same column name with different converters, which is a configuration that already gives the one column two meanings in the generated model. The manual states the assumption.

**Runtime: one round trip, at every entry, in every multi-tenant build.** `TenantConnections` gains `public static K canonicalTenantKey(Object value)`: the value coerced through the representative column's `DataType` and then put through its converter and back, `converter.from(converter.to(type.convert(value)))`. The `DataType` and converter are read once into static fields from `<Tables>.<TABLE>.<COLUMN>`, with a private generic helper capturing the converter's wildcard so the round trip type-checks in Java 17, and the class carries the same `@SuppressWarnings({"deprecation", "removal"})` `NodeIdEncoder` carries for `DataType.convert`. It is emitted in every multi-tenant build: for a column without a converter the round trip is jOOQ's identity converter, so there is one emitted shape and no predicate for an emitter to fork on, at the cost of a virtual call per key. It is public so a consumer can key its own tenant state by the same equality graphitron uses.

*How the column reaches the emitter.* `ConnectionRuntimeClassGenerator.generate(String, SessionHooks, TypeName tenantKeyType)` is the multi-tenant entry today, and `multiTenant` is `tenantKeyType != null`. Its third parameter becomes the representative column as a rendered `CodeBlock` (`<Tables>.<TABLE>.<COLUMN>`) beside the key type, `generate(String, SessionHooks, TypeName tenantKeyType, CodeBlock tenantColumn)`, both null for a single-tenant build or both present; `generate` throws when exactly one is. The three-argument overload is removed rather than kept as a column-less multi-tenant form, since that form would emit the old shape and is the second shape this item rules out; `generate(String, SessionHooks)` and `generate(String)` stay as the single-tenant forms. `GraphQLRewriteGenerator` renders the column from `TenantScopes.Configured` where it reads `tenantType` today and passes both. The four unit-tier classes that compile and drive a multi-tenant runtime from a bare key type today, `TenantScatterSubstrateTest`, `TenantAuthorizationSubstrateTest`, `SessionHookImplGeneratorTest` and `TenantRuntimeKeyTypeTest`, move to a real fixture column of the key type they already use: `FILM.TITLE` (`String`, no converter) for the `String` keys and `FILM.FILM_ID` (`Integer`) for the `Integer` ones, both on the `java.class.path` `EmittedCodeHarness` compiles against. Their keys are already values of those types, and an unconverted column's round trip is the identity for a value of its type, so their behavioural assertions do not change. `TenantRuntimeKeyTypeTest.multiTenantCarrierShipsTheRoutingStatics` also asserts rendered text of the bodies this item replaces (`if (key instanceof java.lang.Integer typed)`, `tenantKeyOf`'s old parse); those lines go with the bodies they pin, and behaviour is pinned at the execution tier instead.

*What the column cannot bind.* `DataType.convert` is lenient: on jOOQ 3.20.11 `SQLDataType.INTEGER.convert("abc")` returns `null` rather than throwing, and it throws `DataTypeException`, not an `IllegalArgumentException`, for an input type it has no conversion for. So `canonicalTenantKey` follows the shape `ConnectionHelperClassGenerator`'s cursor decode already takes for the same leniency: it treats a `null` from either step of the round trip on a non-null input as unbindable, catches `IllegalArgumentException | DataTypeException` from the coercion and the converter (a converter refusing a value, as `OrgCodeStringConverter.to` does for `"abc"` through `NumberFormatException`, raises one of the two), and throws `IllegalArgumentException` naming the value in every one of these cases. A `null` input is the same `IllegalArgumentException`; graphitron's own callers never pass one, since the agree-fold and the narrowing skip null leaves before they reach a key and the constructors refuse a null key. Any other exception from a converter propagates unchanged: it is a fault in the consumer's converter, not a fact about the client's value, and folding it into a client error would hide it.

*What the column binds by coercion.* `convert` is also lossy: `SQLDataType.INTEGER.convert("1.5")` is `1`, and `"1e2"` is `100`. The tenant key accepts these as the tenant they coerce to, because the key follows the bind. Every other place graphitron binds a client value to this column coerces it the same way: the node-id decode (`NodeIdEncoder.decode<Type>` sets the column from `getDataType().convert(segment)`), the generated filters, which bind a value at the receiving column's `DataType`, and `NodeIdEncoder.requireColumnAgreement`, whose javadoc collapses `"01"` and `1.0` onto one key. A request carrying `filmId: "1.5"` on an `ID` argument over `film_id` therefore filters on `film_id = 1` in its SQL, and routing it to tenant 1 is the router agreeing with that SQL, which is this item's goal. Refusing it would be a strictness rule the router applies and the `WHERE` clause beside it does not, which is the same disagreement in the other direction. It reaches nothing a request could not already reach: the canonical key is checked against the request tenant set like any other, so `"1.5"` reaches tenant 1 only when the request may read tenant 1.

- `tenantKeyOf` becomes a call to `canonicalTenantKey` that turns its `IllegalArgumentException` into the generated client-error type: "Tenant value '<v>' is not a value of the tenant column." The coercion through the `DataType` replaces today's hand-written `Integer`/`Long` parse, so the wire-to-key rule now comes from the column, as the node-id decode's does. This settles the unbindable-value question for every path, `"abc"` and today's `NumberFormatException` alike: a client error, raised before the request-set check, so it reveals nothing about which tenants exist. In the narrowed fan-out it is raised before `retainAll`, so an unbindable value can no longer empty the domain and come back as a complete empty list.
- `agreeOnTenant` is typed on `K` (`K agreeOnTenant(K current, Object candidate)`) and puts each leaf through `tenantKeyOf` before comparing, so `"0194"` beside `"194"` (two slots, a list argument, a batch) agrees instead of raising "Tenant bindings disagree". `namedTenant` returns the fold's `K` with no cast and no second coercion, and `divinedTenant` with it; the disagreement message prints canonical values. Keys read off a parent row also pass through this fold and pay one round trip per fetch, which is cheaper than a second entry point every emitter would have to choose correctly.
- `RequestTenants`' constructor canonicalises the set and the default tenant before the membership check, so `withDefault(Set.of("0194"), "194")` is valid and `tenants()` returns canonical keys.
- `GraphitronRuntime`'s canonical constructor, which every other form delegates to, canonicalises the map's keys into `sourcesByTenant` in configured order, and throws `IllegalArgumentException` naming both keys when two canonicalise to one tenant. `tenantKeys()` and the mount's `Optional<K>` tenant then carry canonical keys. This renames the consumer's keys where they were not canonical; the manual says so and points at `canonicalTenantKey` for state the consumer keys itself.

With both ends canonical, `entryFor`, `permits`, `fanOutDomain`, `timedOutTenants` and the source lookup compare like with like and do not change. The per-row grouping in `HandleMethodBody` keeps grouping on the raw decoded value: two spellings of one tenant become two groups that canonicalise to one key and run on the one pinned connection, which is correct, so it is left alone.

**Behaviour for an unconverted column** is today's routing with three refinements a client can observe, all of which put the router on the rule the column's `DataType` already applies to the same value in the SQL: a tenant value the column cannot bind (`"abc"` on an `ID` argument over an integer column) is a client error rather than today's `NumberFormatException` server error, and in a narrowed fan-out it is that client error rather than an empty list; a value the column binds by coercion that the old `Integer.valueOf`/`Long.valueOf` parse refused (`"1.5"`, `"1e2"`, `" 186 "`) names the tenant it coerces to, the one the `WHERE` clause reads; and a value of another Java type the `DataType` coerces (a `Long` for an `Integer` column) is accepted rather than refused as the wrong Java type. A value the old parse accepted names the same tenant as before.

**Known divergence, handed to a follow-up.** `NodeIdEncoder.requireColumnAgreement` defines two writers to one column as agreeing when `type.convert(a)` equals `type.convert(b)`, which for a converter-backed column compares the Java spellings, the equality this item retires from routing. After this lands, `"0186"` and `"186"` name one tenant but still conflict as two writes to one `owner_org`-shaped column. Moving that check onto the same round trip needs its own two-writer fixture on a converter-backed column and is filed as the Backlog item "Two-writer column agreement compares converter-backed values by their database value", which also decides whether the round trip becomes one emitted primitive both classes share.

## User documentation (first-client check)

In `docs/manual/how-to/tenant-scoping.adoc` §1, the sentence "The tenant key's Java type is read off the catalog (all tables must agree) …" keeps its first half, and its agreement clause becomes:

> All tables carrying the column must agree on its Java type and on the Java type of the database value behind it, so a column a converter maps to `String` on one table cannot be a plain `varchar` on another. Graphitron compares keys through the converter of the first table carrying the column, so map the column through one converter everywhere: two different converters between the same types cannot be told apart at build time, and the first table's then decides for both.
>
> Tenant keys are compared by the value the column stores. When a converter maps the column, graphitron puts every key through it and back before comparing: with an `INTEGER` column mapped to `String`, a client sending `"0194"` reaches the same tenant as one sending `"194"`, exactly as the SQL does. The keys you supply get the same treatment. Register your `DataSource` map and build `RequestTenants` with whichever spelling you have, and graphitron reduces them to the column's form; your mount, `tenantKeys()` and `RequestTenants.tenants()` report that form. To key your own state the same way, call `TenantConnections.canonicalTenantKey`. Two map keys that name one tenant are refused when the runtime is built.
>
> A tenant value the column cannot store, such as `"abc"` on a numeric column, is a client error. A value the column stores by coercion names the tenant the query itself reads: on an integer column `"1.5"` is bound as `1` in the SQL, so it reaches tenant 1, and only if the request may read tenant 1.

## Other solutions we've considered

- **Canonicalise only in `entryFor`.** It is the one enforcer for acquisition, but the agree-fold and the fan-out narrowing compare keys before it runs, so `"0194"` beside `"194"` would still disagree and a narrowed fan-out would still come back empty.
- **`DataType.convert` alone**, the rule `requireColumnAgreement` uses. It coerces a value *to* the bound type and leaves a value already of that type as it is, so for a column converted to `String` it never reaches the database type and canonicalises nothing. It is the first step of the round trip, not a substitute for it.
- **Emit the round trip only for a converter-backed column**, behind a flag on `Configured`. It saves one virtual call per key and costs a predicate every emit site re-tests, a field that means something only when the flag is set, and a second emitted shape to pin.
- **Read the database type off the live `Field` inside the classifier.** The classifier holds only `JooqCatalog`'s reduced `ColumnEntry`; reaching past it would put a live-catalog read outside the one reduction that owns them.
- **Capture the converter's class and add it to the agreement.** jOOQ wraps every plain `Converter` in `org.jooq.ContextConverter$1`, so the class read off the live `Field` is that adapter for every converter-backed column and the comparison would always agree. Reaching the wrapped converter means reading the adapter's synthetic `val$converter` field, an anonymous class inside jOOQ with no public accessor, which a jOOQ upgrade can rename or restructure without notice; a check that silently stops checking on upgrade is worse than a stated assumption.
- **Write the database type to `sql_column` as well.** No reader in this item reads it from the store; the store admits a fact because a reader needs it. The reader that does (hover, the node-id landing defects) adds the column with its use site, and the capture is then one line beside `binding_type`'s.
- **Require canonical consumer keys and validate them**, refusing `"0194"` in the source map rather than reducing it. The consumer can compute the canonical form (through its own column's converter, or `canonicalTenantKey`), so this is a real option; it loses because canonicalising at the constructors is an ordinary boundary decode, it lets sis delete its hand copy of the converter's equality outright, and the renaming it implies is reported through `tenantKeys()` and the mount rather than hidden.
- **A consumer-supplied normalisation hook.** It restates a rule the converter already states, and a consumer who forgets it gets today's behaviour.
- **Compare `sql_type` in the agreement check**, as the multitable ordering rule in `FieldBuilder` does. That rule needs one SQL type per position to order by; routing needs one equality, and comparing type names would reject `varchar` beside `text`, a common and harmless spread.
- **Refuse a lossy coercion on the tenant key**, so `"1.5"` is a client error while `"0186"` is accepted. It needs a rule the column does not state: `"0186"` to `186` is no more value-preserving than `"1.5"` to `1` as a round trip, so telling them apart means a hand-written per-type strictness test (an exact `BigDecimal` comparison for integral database types, something else for the rest), the kind of parse this item replaces with the column's own coercion. And it would make the router stricter than the `WHERE` clause, the node-id decode and `requireColumnAgreement` beside it, which all bind `"1.5"` as `1`: the SQL-and-router disagreement this item exists to remove, pointed the other way. Whether graphitron should refuse lossy coercion everywhere it binds a client value is a real question, but it is one question for every binding site, not a routing rule.
- **Leave it to the consumer**, with sis documenting a breaking change. The build would keep a state where the SQL and the router disagree about one value, which is the defect itself.

## Reviewer findings

### Round 1 (2026-10-15, Spec -> Ready, reviewer session 01K4dGN7wytRaSVmEM1jJuim)

Verdict: withhold. One blocking finding, on question one (a claim about the code that does not hold) with a question-two consequence. The goal reads on its own: a client value that the SQL binds to tenant 186 reaches tenant 186, and the consumer's own keys get the same equality. Every symbol, test and fixture name the spec cites exists as named, the capture and classification plan extends shapes already in the tree, and the representative-column-plus-agreement argument is sound. The blocker is the runtime primitive.

**1. `DataType.convert` does not fail on a value it cannot read, so the round trip as specified does not deliver the stated client-error contract on an unconverted column, and it truncates.** The spec says `canonicalTenantKey` is `converter.from(converter.to(type.convert(value)))` and that "a value it cannot read throws `IllegalArgumentException` naming the value", and it rests "an unreadable tenant value becomes a client error" for every multi-tenant build on that. Run against jOOQ 3.20.11, `SQLDataType.INTEGER.convert("abc")` returns `null` and `SQLDataType.INTEGER.convert("1.5")` returns `1`. For a column without a converter the identity converter passes both straight through. So on `TenantDivinedRoutingExecutionTest`'s `Integer` fixture, after this lands:

- `"abc"` canonicalises to `null` without throwing. In the agree-fold the outcome depends on where the fold tests for null, which the plan does not say: the "binding value is absent" `NoSuchElementException` (a server-side failure with the wrong message), a "disagree" client error naming `null`, or a leaf that silently drops out. In `fanOutDomain(env, narrowing)` it puts `null` into `keys`, `retainAll` empties the domain, and the field returns an empty list presented as complete: the defect class this item exists to remove. Today the same input fails loudly with `NumberFormatException`.
- `"1.5"` (and `"1e2"`, `" 186 "`) canonicalise to a different tenant, where today they are refused. That is the opposite of the spec's "a value the column cannot hold is a client error". The "Behaviour for an unconverted column" paragraph presents the coercion change as a benign widening (`Long` for `Integer`) and does not mention it.

The converter-backed fixture hides this: on `owner_org` the `DataType` is `DataType<String>`, so `convert` is a no-op and `OrgCodeStringConverter.to` throws `NumberFormatException` itself. The only unreadable-value test in the plan therefore cannot catch it. `DataType.convert` can also throw `DataTypeException`, which is not an `IllegalArgumentException`, for an input type it has no conversion for, and the `tenantKeyOf` catch as written would let that escape as a server error.

The leniency is not news to this tree. `ConnectionHelperClassGenerator`'s cursor decode already says so in a comment ("jOOQ's DataType.convert is lenient: an uncoercible wire token yields null rather than throwing"), then null-checks and catches `IllegalArgumentException | DataTypeException` into the client-error type. That is the shape the round trip should extend (question two) rather than restate wrongly.
