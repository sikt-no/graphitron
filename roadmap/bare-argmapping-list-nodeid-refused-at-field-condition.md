# A list of node ids' key column reaches a List parameter at a @condition through argMapping

## Goal

A consumer can hand a list of node ids to a field-level or argument-level `@condition` through `argMapping`, in the spelling that stays, and have the method receive the decoded key column values as a `List`: the entry names the column past the slot, `argMapping: "samlinger: samlingIder.samling_id"`, or descends through an input object onto the list, and the parameter is a `List` of that column's Java type. Today, on trunk at `47ab77d5`, neither form of that spelling works. The entry naming the column is refused as "a list of input objects". The entry descending onto the list builds and hands the method the encoded wire ids, undecoded, in a `List<Integer>`: a wrong value with no refusal, which is what the projection rules exist to prevent. The two spellings that do work for a list, a parameter named after the argument and an entry that stops on it, are the whole-slot contract that is being withdrawn (see The ruling), so a consumer has no spelling to move to before it goes.

Reported in [GitHub issue 583](https://github.com/sikt-no/graphitron/issues/583), where the consumer dropped `@nodeId` and decodes by hand inside the condition, losing the client error a bad id gets at every other `@nodeId` site. The circular refusal that issue reports, the entry stopping on the list told to declare the column's own type, no longer reproduces: R1204 stood that verdict aside at these two sites and the entry now builds. That unblocks the reporter with a spelling that is going; this item is what gives them the one that is not.

## What happens today

The shape is a root field with a list of node ids and a single node id, read together by one condition because the predicate is an `EXISTS` that needs both:

```graphql
films(
    languageIds: [ID!]! @nodeId(typeName: "LanguageNode") @reference(path: [{key: "film_language_id_fkey"}])
    originalId: ID! @nodeId(typeName: "LanguageNode") @reference(path: [{key: "film_original_language_id_fkey"}])
): [Film!]! @condition(condition: {className: "...", method: "...", argMapping: "..."})
```

Rows 11 to 13 below put the same list inside an input object, `films(in: FilmPick)` with `languageIds` a field of `FilmPick` carrying the same two directives.

Three vocabulary items first. A *whole-slot binding* is a parameter bound to the whole of a `@nodeId` argument or input field, by its name or by an `argMapping` entry that stops on it (`"p: languageIds"`, called *bare* below). A *projection* is an entry that hands over one key column, spelled by naming the column past the slot (`"p: languageIds.language_id"`, *dotted*) or by descending through an input object onto a `@nodeId` input field. The *walk* is the classifier that still emits condition glue; the *store* is the fact store that is replacing it.

Probed through the build's validate pass on trunk at `47ab77d5`, against the sakila catalog, with a condition method on the classpath for each row. Rows 1 to 9 keep the numbers the first probe gave them, at `a66d14f`, so the reviewer round below still reads; rows 10 to 13 are new. Rows 2 and 11 were also run through `generate` and their condition glue read. No generated query was executed.

A single id opened the same way is the control: `"p: originalId.language_id"` onto an `Integer` builds, onto a `String` draws the store's `NODE_ID_KEY_COLUMN_TYPE_DISAGREEMENT` and nothing else, and with a column the key does not have draws the store's `ARGMAPPING_KEY_COLUMN_UNRESOLVED` and nothing else.

So the projection of a list is the one binding with no working spelling: rows 4 and 13 are refused by a rule about lists of input objects that was never asked about a list of node ids, and row 11 gets past every judge and is then emitted as an ordinary nested read. Rows 10 and 12 show the store already holds both forms as projections, since its type rule is raised only from a stored projection row and its remedy is the `List`.

A separate fact, which bounds any workaround and this item's reach: a `@nodeId(typeName:)` argument whose node table is not reachable from the field's table by one foreign key or a written `@reference` path is refused in every spelling, with or without `override: true`. Run again on trunk at `032de1aa`: by parameter name the store refuses it (`NODE_ID_LANDS_ON_TABLE`), and through any `argMapping` entry, stopping on the argument or naming a column past it, the walk does ("no foreign key found between tables"). With a multi-hop `@reference` path written on each argument the by-name spelling builds, with and without `override: true` (at `a66d14f`). The reporter's schema is of this kind, a membership table between the field's table and the list argument's node, with no path written, so the spellings named in the Goal reach them only once the paths are written, or once R1205 lands for a condition carrying `override: true`. This item changes nothing about routes.

## Who judges the binding, and what each says

Four readers meet the one binding, and the store is the only one that reads a list projection right.

* **The walk's whole-slot rule.** `ConditionResolver.installNodeIdDecode` hands a whole-slot parameter the decoded key: the key column's own type at a one-column key, a jOOQ `RowN` at a composite key, either wrapped in `List` for a list slot. It applies to a bare `argMapping` entry and to a parameter named after the slot alike, and `ProjectedKeyReads.installRailOwns` lets it win at render. `docs/manual/reference/directives/condition.adoc` documents this as the contract. Rows 1, 2, 5 and 9 build on it, and row 3's first refusal is its.
* **The walk's rule about lists.** `FieldBuilder.conditionReadThroughList` refuses any condition path that continues below a list, on the reading that the list is one of input objects with no single value under it. A key column named past a list of node ids is such a path, so rows 4 and 13 are refused here, by a message that describes something else.
* **The retiring projection readers.** `ArgmappingProjectionDefects` and `ResolvedKeyProjections` read `intent_argmapping_projection_defect` and `intent_resolved_node_key_projection`, views of the `intent_` family that is being dissolved. They infer a one-column projection for every entry that names no column and compare the column's type with the parameter's erased class, so `List<Integer>` reads as `List`. Two things follow at these sites since R1204. The type verdict stands aside at a field-level and an argument-level `@condition` (`authorDefects`), the store judging those parameters, which is why row 2 builds and why a wrong type draws one refusal and not two. And the projection relation the glue reads, `ResolvedKeyProjections`, still has no row for a list projection onto a `List`, its type predicate being the list-blind one: `ConditionGlueRenderer.nestedExtraction` finds no projection for row 11 and renders the cast. What is left of the refusals here is the list deferral that is row 3's second message, the bare composite of row 6 and the unwired site of row 8.
* **The store's occurrence family.** `graphitron_argmapping_landing.receives` states what an entry hands over: `WHOLE` for a bare entry, `COLUMN` for a dotted one or one descending onto the slot. `graphitron_occurrence_node_id_slot_projection` holds the key column each projecting entry takes, beside a slot whose `list_depth` is the id's own, and `graphitron_occurrence_node_id_shape` gives it `KEY_VALUE` where the parameter is a `List` of the column's type. The store's type judgment for a projected column, `NODE_ID_KEY_COLUMN_TYPE_DISAGREEMENT`, covers `@condition` as well as `@service` and is list-aware: it raised nothing against rows 4, 11 and 13 and asked rows 10 and 12 for the `List`.

The store is where this is going, and its rows already carry the ruling below: `graphitron_occurrence_node_id_shape` holds no row for the by-name `List<Integer>` and `Integer` parameters above, no decode shape fitting a whole key on a parameter of the column's own type, and a slot with no shape is what the store refuses at a `@service`.

## The ruling

`docs/architecture/explanation/defects-as-facts.adoc` states it: a parameter bound to the whole of a `@nodeId` slot takes the node's record or a tuple of its key, at a `@condition` as at a `@service` (Alf, 2026-11-14; Filip, 2026-11-20), and a key column's value is a projection asked for by naming the column, a `List` of it off a list of ids. The refusal of a whole-slot parameter of the column's own type ships when the walk no longer renders conditions; R876 holds it on branch `wip/r876-condition-arity-at-flip`, because until then the walk defers an input-field `@condition` projecting its own key column and refusing earlier leaves that site no shape that generates.

So the spelling this item makes work is the projection, in its three written forms over a list: the column named past the slot, the descent onto the list, and both. It adds nothing to the whole-slot contract the walk still serves: no bare or by-name binding that is refused today starts building, and none that builds today is refused here.

## Plan

1. **A list projection is emitted on the live condition glue.** Condition glue is still the walk's (`ConditionGlueRenderer` with `ProjectedKeyReads`); the store's `ConditionEmitter` has no caller in main sources until R876's condition flip, which moves every caller at once and keeps no per-occurrence fallback, so a partial flip is not available. `ProjectedKeyReads` gains one read shape: each id of the list decoded into the node's record and the projected column read off each, the list absent or `null` reaching the method as `null` as a single projected id does. One shape serves rows 4, 11 and 13, the written forms differing only in where the wire list sits, which the sink already derives from the row.
   The rows that read needs come from the store's own projection population, `graphitron_occurrence_node_id_slot_projection` with its slot's `list_depth` and its decode shape, not from `intent_resolved_node_key_projection`: that view has no row for the pair (its type predicate is the list-blind one), and it is dissolving, so it takes no list axis and `KeyProjection` gains no component sourced from its `leaf_is_list`. `ResolvedKeyProjections` reads every field-level and argument-level `@condition` entry from the stored population, the single ids with the lists, and not the list rows alone: one reader taking the same kind of entry from two populations keyed differently would merge them in Java, and the `intent_` family is not a shape to build on. This is the condition half of R876's node "The argMapping readers read the landing, and the candidate and match go". Its routine entries stay on the view, as they are today.
   The readers that stay on the view until that node, named so the split is stated and not discovered: `ArgmappingProjectionDefects.primitiveParameters` and `unemittableProjections`, and `NodeIdDecodeCoverageFacts.projectedInstalls`. The last counts a condition entry's decode as installed only where the view has a row; rows 2 and 11 pass it today, on the walk's own ledger row for the id as far as reading shows, so it is expected to stay quiet, and it is the reader to look at first if "nothing in this build decodes it" appears on a list projection.
   The read is walk-tier code added from a stored fact, which `docs/architecture/explanation/pipeline-overview.adoc` allows on the terms that it is deleted when its tier flips. It is named here and is to be named in R876's node "The walk's read path is gone" in the implementing commit.
2. **The two refusals standing in front of it go.**
   * `FieldBuilder.conditionReadThroughList` no longer fires on a path whose list level is a list of node ids opened with a key column (rows 4 and 13); a list of input objects with a descent below it is still refused, by the same message.
   * `ArgmappingProjectionDefects.listDeferred` no longer defers at the field-level and argument-level condition sites, its "which parameter binding does not emit yet" being untrue there once step 1 lands. Nothing it catches at those sites goes unrefused when it stops: what it defers there, wherever the parameter's type resolved, is a list id onto a parameter of the column's own type, which the whole-slot rule refuses where the entry is bare (row 3, then refused once) and the store refuses where it projects (rows 10 and 12). The input-field site stays as it is, unwired on the walk, and closes at the flip.
3. **Docs.** `docs/manual/reference/directives/condition.adoc`: the projection bullet gains the list forms and says the projection is the spelling for a key column's value; the whole-slot bullet says a parameter of the column's own type still builds there and is going, with the record or tuple as what stays. `docs/manual/reference/directives/routine.adoc` already says a list of node ids is not projected at a routine parameter (`ROUTINE_NODE_ID_LIST_UNSUPPORTED`); that stays true, and where the condition page points at that section it says a list is projected at a `@condition` and a `@service` and not at a routine.

No stand-aside of a retiring verdict is added, and no message changes. The type verdict already stands aside at these sites, and a second report of an unknown column or of a composite key with none named never reaches an author, the store's verdict stopping the build before `ArgmappingProjectionDefects` is read; the view and its remaining arms retire with R876's landing-readers node, which lists the store counterparts they still wait on. The remedy clause an earlier draft changed, "bind a parameter of the column's own type" on an entry naming no column, now fires only at the input-field site and at a child routine, where a parameter does take the column's value, so it is left as it is.

## Workaround today

Bind the list whole: name the condition method's parameter after the GraphQL argument, or write an `argMapping` entry that stops on the argument (`"samlinger: samlingIder"`), with the parameter a `List` of the key column's type. Either way the ids are decoded before the method runs. Each `@nodeId(typeName:)` argument must reach its node's table from the field's table, by a single foreign key or a written `@reference` path, and `override: true` keeps those paths from adding predicates of their own. It is a stopgap: the condition flip refuses both spellings, and the projection is the one that stays.

Do not reach a list of node ids by descending through an input object in `argMapping` until this lands: that is row 11, and the method receives the ids undecoded.
