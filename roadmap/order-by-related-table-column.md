# @order: sort by a column on a to-one related table via path, or by a method-supplied expression

## Goal

An `@order` or `@defaultOrder` entry can sort by a value that does not live in a column of the field's own table, without denormalizing it into that table. Two forms cover the two shapes such a value takes. When the value is a column on a table reached through to-one hops, the author names the column and a `path:` in the same `ReferenceElement` shape as `@reference(path:)`. When the value has to be derived from several related rows, the motivating case of GitHub issue #562 (order `Utdanningsinstans` by the `navn_spesifikasjon` of its latest `Utdanningsinstansnavn`, of which each instance has many), the author supplies the sort key as an expression through `method:`, a static Java method with `@externalField`'s calling convention: it takes the field's table and returns a `Field<?>`. Either way each parent row has exactly one sort key, and graphitron keeps owning direction, keyset pagination and the cursor.

## The gap

`@order(fields: [{name: ...}])` resolves every `FieldSort.name` against the field's own table (`OrderByResolver.resolveOrderEntries` calls `ctx.catalog.findColumn(tableSqlName, colName)`), so a column on a joined table is a build rejection. The only workaround today is copying the value into the main table.

## Proposed surface

`FieldSort` gains two optional arguments, `path:` and `method:`, and `name:` becomes optional (`String` instead of `String!`). An entry sets exactly one of `name:` and `method:`; `path:` is only valid beside `name:`.

### `path:`: a column on a to-one related table

Add an optional `path: [ReferenceElement!]` to `FieldSort`, reusing the existing input type and its `table:` / `key:` semantics, so there is one way to say "walk from here to that table" across the schema. From the sakila fixture, where `film.original_language_id` is a nullable FK to `language`:

```graphql
enum FilmOrderByField {
    TITLE             @order(fields: [{name: "TITLE"}])
    ORIGINAL_LANGUAGE @order(fields: [{
        name: "NAME",
        path: [{key: "film_original_language_id_fkey"}]
    }])
}
```

The hop runs from `film`, which holds the FK, to `language`, which it references, so it is to-one. A film with no original language gets a `NULL` key, which sorts last (R1112).

`name` is resolved against the table the path lands on; with no `path:` nothing changes. The same argument belongs on `@defaultOrder` since both directives share `FieldSort`. `index:` and `primaryKey:` are table-scoped and stay own-table only.

The path is always written out: there is no inferred or empty form, so a column name never silently changes table.

A `condition:` on any hop of an ordering path is rejected, and the message points at `method:`. The rule for which related row counts then lives in one place, the method, and the to-one proof stays purely catalog-derived. Admitting a condition later is a small extension: under the emission below it would sit inside the sort key's subquery, where filtering the related row out yields a `NULL` key instead of dropping the parent.

### `method:`: a sort key the author derives

Add an optional `method: ExternalCodeReference` to `FieldSort`. It names a static method with exactly `@externalField`'s convention: its sole parameter is the jOOQ table class of the field's table, it receives the alias the generated query uses, and it returns a `Field<?>` that is that row's sort key. `method` is required inside the reference (there is no GraphQL field name to default it from, as `@externalField` does). `argMapping:` is rejected, as it is on `@externalField`; a parameterised sort key (for example "the name valid on a date argument") is a later extension, not part of this item.

```graphql
enum QueryUtdanningsinstanserOrderByFieldInput {
    NAVN @order(fields: [{method: {className: "no.sikt.fs.Ordering", method: "gjeldendeNavn"}}])
}
```

```java
public static Field<String> gjeldendeNavn(Utdanningsinstans t) {
    var n = UTDANNINGSINSTANSNAVN.as("n");
    return DSL.field(DSL.select(n.NAVN_SPESIFIKASJON).from(n)
        .where(n.UTDANNINGSINSTANS_ID.eq(t.ID))
        .orderBy(n.ARSTALL_FRA.desc()).limit(1));
}
```

The rule for which related row counts (the latest, an approved one, any filter the reporter's `condition` would have expressed) lives once, in jOOQ, inside the method; it is not restated per enum value, and the same method can back an `@externalField` when the value should also be selectable. `direction:` applies to the returned expression as it does to a column. `collate:` is accepted and behaves as it does for a column: today `OrderByResolver` reads it and no emitter renders it, for columns too, and that gap is not this item's. The cardinality rule below does not apply to a method: a `Field<?>` is one value per row by type. A method returning several rows per parent fails at runtime in the database, as a scalar subquery does; the build cannot see inside the method and does not try.

`method:` with `path:` is rejected (the method already receives the field's table and can reach anything from it). `index:` and `primaryKey:` stay as they are.

For a consumer that would rather keep the rule in the database, a view with a unique key on the parent's id (for example `utdanningsinstans_gjeldende_navn`) plus a jOOQ synthetic foreign key to it makes the hop to-one, and the `path:` form then serves the same case with no code. `order.adoc` documents this as the no-code alternative.

## Emission: a sort key the field's table does not hold is an expression

Both forms reach SQL the same way, as a static method call that takes the alias the site already orders on and returns a `Field<?>`. No site changes its `FROM` clause, and the two forms share one model arm and one emission path: a `method:` entry calls the author's method, and a `path:` entry calls a method graphitron emits with the same signature.

- A `method:` entry renders as `<className>.<method>(<alias>)`.
- A `path:` entry renders as `<field>SortKey<n>(<alias>)`, a call to an emitted `static Field<?> <field>SortKey<n>(<Table> table)`. `<n>` is the entry's ordinal among the field's sort-key entries, counted across its fixed order, its default order and every named order of its `@orderBy` enum, so each entry has its own method. The body declares one alias per hop and returns `DSL.field(...)` around `PathFragments.scalarInnerSelect`, the correlated single-column subselect a single-valued `@reference` field already projects. Its `ScalarSubselect` correlates through `ParentCorrelation.OnFkSlots` on the first hop, which every ordering path has, since `On.Predicate` and `On.Lateral` hops are rejected. Every hop is proven to-one, so the subquery returns at most one row (its `.limit(1)` is then inert), and a parent with no related row gets `NULL`.
- The hop aliases are the method's own locals. They are minted with `PathFragments.generateAliases` and materialised through `PathFragments.emitTableExpression`, and each is declared under the SQL alias `table.getName() + "_" + <local>`, the scheme `ProjectionUnitRenderer`'s subselect terms already use. The locals are scoped to the method body, so they cannot meet a site's own locals or another entry's. The SQL aliases always extend the outer alias, so an inner alias never shadows the one the correlation reads. Two entries that reach the same table mint the same inner alias in two separate subqueries, which is harmless. `JoinStep.Hop.alias()`, which `BuildContext.parseExplicitPath` mints from its `fieldName` argument, is not read on this route.
- The method is hosted on the unit that renders the field's order, so every call renders unqualified, as the `@orderBy` helper's call already does. For a root launcher, a batched rows method, an `@orderBy` helper or `TypeFetcherGenerator.buildOrderByCode`, that unit is the parent's `Fetchers` class. For an inline child list it is the projection unit. A field's order is rendered in exactly one of the two, because a field is classified either as an inline child list or as one of the others. The name has one formula, `GeneratedUnits.sortKeyMethod(owner, fieldName, ordinal)`, beside `inputRowsMethod(owner, fieldName)`, the precedent for a helper hosted on whichever unit consumes it. Both the call sites and the emitter spell the name from it.
- Because both forms render as a call expression, every existing order rendering hosts them without a statement slot. That covers the `List.of(...)` parts `OrderByFragments` renders (the inline child list's `.orderBy(...)` among them), and the switch arms and base return of the `@orderBy` helper bodies.
- At every site the sort key goes into the `ORDER BY` and the seek as the call itself. It goes into the cursor columns (the connection's `extraFields`, the `@orderBy` helper's `OrderByResult.columns`) as the call aliased under a reserved name. `ReservedAliases` gains that name's formula, keyed by the entry's ordinal (for example `__sk_<n>`). `ConnectionHelper.pageRequest` merges `extraFields` into the selection by `Field.getName()`, so a reserved name means the sort key is never dropped in favour of a selected column with the same name (every sakila table has a `last_update`), and `encodeCursor` reads back exactly this value. The `ORDER BY` and seek repeat the call rather than naming the alias, because PostgreSQL does not resolve an output alias inside `WHERE`.
- Sites reached, each by rendering the call against the alias it already orders on: root lists and connections (`RootLauncherRenderer`, including the discriminated single-table interface root), `@splitQuery` batched lists and connections including the `ROW_NUMBER()` window and seek (`BatchedRowsFragments`), inline child lists (`ProjectionUnitRenderer`'s multiset arm, whose `.orderBy(...)` renders through `OrderByFragments.fixedSortParts`), the `@orderBy` helper bodies (`TypeFetcherGenerator.buildSingleArgOrderByBody` and `buildListArgOrderByBody`, which already receive the table alias as a parameter), and `TypeFetcherGenerator.buildOrderByCode`. `totalCount` is unaffected, since nothing is joined.
- Rejected at classification, naming the field and the shape: a multitable interface or union participant (`FieldBuilder.foldParticipantOrderings` folds per-participant `ColumnRef` slots positionally and types each slot from a participant column, so an expression slot is its own item), and a site whose ordered alias is not of the field's jOOQ table class (a routine result), where neither a method's parameter nor the path's start table applies.

A correlated subquery per row is cheap for a to-one path (an indexed key lookup) and is evaluated for the sort in any case; a method's cost is its author's.

## The cardinality rule

An ordering path must never change the cardinality of the row set it orders: every hop must be to-one, so each parent row yields exactly one sort key. This is `JoinStep`'s "no unintended row multiplication" invariant applied without its list-field escape hatch, because an ORDER BY has no meaningful fan-out, and aggregating to pick a key would invent a semantics the author did not write. It is checked at build time rather than left to the subquery's `.limit(1)`, which would silently pick an arbitrary row.

A hop is to-one when the columns on its target side cover a candidate key of its target table: `On.ColumnPairs.targetSideColumns()` checked with `MatchedKeys.firstCovered` against `Hop.targetTable()`. Slot orientation is fixed at synthesis (`BuildContext.resolveFkSlots`), so one check covers both to-one shapes without branching on FK direction: child to parent (the target side is the parent's primary key) and a one-to-one extension (the target side is the extension table's FK columns, under a unique key). Nullability does not matter here, unlike R1106's identifying keys: an equality join never matches a `NULL`, so a unique key with nullable columns still admits at most one target row per origin row. Anything else is to-many and is rejected.

Consequences, stated so the reviewer does not have to derive them:

- Every hop names a `key:` or a `table:`, and no hop carries a `condition:` (see `### path:` above). An `On.Predicate` hop (condition only) or an `On.Lateral` hop (a routine call) carries no key to prove uniqueness from and is rejected. An `On.ColumnPairs` hop keyed by `Keying.NameMatchedKey` matches the target's primary key by construction and passes the same check.
- The classification is catalog-derived at build time, not author-asserted; there is no opt-out argument.
- A parent with no related row still appears: the subquery finds no row, so the sort key is `NULL`. R1112 makes a `NULL` key sort last in both directions and makes the seek return such rows, for every nullable order column; this item inherits that and adds no nulls rule of its own.

The rejection names the field coordinate, the enum value, the offending hop, and the direction in which it fans out (for example "hop 1 `utdanningsinstans` to `utdanningsinstansnavn` via `<key>` is to-many: one parent has many `utdanningsinstansnavn` rows; an ordering path may only follow to-one hops"). A to-many relation is the `method:` form's case, and the rejection message says so: it points at `method:` and at the view-plus-synthetic-key alternative.

## Tiebreaker rule

R1106 owns tiebreaking. A single-table connection whose listed columns contain no identifying key of the field's table gets the table's row key appended, in the direction of the last listed entry. The row key is the primary key, else the `@node` key, else a unique key whose columns are all `NOT NULL`. The appended key goes on the order, the cursor and the seek. Two places decide it: `OrderByResolver.complete` for static orders, and the block that `TypeFetcherGenerator.buildRowKeyCompletion` emits for a list-valued `@orderBy` argument. This item adds one rule to that test and nothing else:

- Only own-table column entries count toward identifying a row. A column reached through `path:` never counts, even when it is the related table's primary key: a to-one hop lets many parent rows share one related row, so a related-table column cannot tell parents apart. A `method:` entry never counts either, because the build cannot see what the expression returns. An order made only of path or method entries therefore always gets the row key appended.
- The test decides by entry kind, not by column name. `OrderByResolver.complete` compares SQL column names, so it reads only own-table entries. The generated check compares `Field.getName()`, which a sort key's reserved alias (see Emission) never matches, so it holds by construction there; a test pins it.
- Everything else is R1106's as shipped: which shapes are completed (connections only, not plain lists or multitable participants), the row-key choice, the direction, and the `connection-order-not-unique` lint finding for keyless tables.

## Plan

1. **SDL and docs.** In `directives.graphqls`, `FieldSort.name` becomes `String`, and `FieldSort` gains `path: [ReferenceElement!]` and `method: ExternalCodeReference` with doc strings. `docs/manual/reference/directives/order.adoc` and `defaultOrder.adoc` document both forms, the to-one rule and its rejection, the method convention, the rejected shapes and the view-plus-synthetic-key alternative, cross-linking `reference.adoc` and `externalField.adoc`; `docs/manual/how-to/sort-results.adoc` gains a section on sorting by a related value.
2. **Model.** `OrderBySpec.Fixed`'s entries become a sealed entry type with two arms: `ColumnOrderEntry` as today (own-table column), and a sort-key entry carrying a sealed key (`path` steps plus the landing `ColumnRef`, or a `MethodRef`), collation, direction, and its ordinal among the field's sort-key entries, from which the emitted method's name and the reserved cursor alias are both minted (see Emission). Consumers switch exhaustively; no nullable fields stand in for the arms.
3. **`path:` resolution.** In `OrderByResolver.resolveOrderEntries`, resolve the elements through `BuildContext.parseExplicitPath` (start = the field's table, `isList` false so a self-referential `{key:}` walks to-one; the `fieldName` it mints `Hop.alias()` from goes unread, per Emission; its error messages are reused, and its terminal-table verdict does not apply, since the landing table is whatever the last hop reaches), then look `name` up on the landing table.
4. **To-one check.** One function over a resolved `JoinStep.Hop`, per the cardinality rule, built on `MatchedKeys.firstCovered`. Computed from the jOOQ catalog, not stored.
5. **`method:` resolution.** The `FieldSort` element is a nested input value, which `FieldBuilder.parseExternalRef` (it reads a directive argument off a `GraphQLFieldDefinition`) does not reach, so `OrderByResolver` reads `className`, `method` and `argMapping` from the element and applies the `argMapping` rejection itself, then calls `ServiceCatalog.reflectExternalField` with the field's `TableRef`, the same reflection `@externalField` uses. Its rejections are prefixed `@externalField`, so this call site names the directive it was reached from instead (a directive-label parameter or a re-prefix at the call).
6. **Validation**, at classification through the existing `OrderByResolver` rejection route. That route needs to carry a reason first: `resolveOrderEntries` returns `null` on any failure and its callers synthesise one generic message, so it returns a result that names what failed. It rejects a non-to-one hop, an `On.Predicate` or `On.Lateral` hop, a `condition:` on any hop (pointing at `method:`), an unknown column on the landing table, an unresolvable path, a missing method or class, a wrong parameter or return type, `argMapping:`, `method:` with `name:` or `path:`, neither `name:` nor `method:`, `path:` without `name:`, and the two rejected shapes under Emission.
7. **Tiebreaker.** Restrict `OrderByResolver.complete`'s identifying-key test to `ColumnOrderEntry` arms, per the Tiebreaker rule.
8. **Emission**, per the Emission section. `GeneratedUnits.sortKeyMethod(owner, fieldName, ordinal)` mints the emitted method's name. `TypeFetcherGenerator` emits one `<field>SortKey<n>` per `path:` entry onto the parent's `Fetchers` class, beside the field's `@orderBy` helper. `ProjectionUnitRenderer` does the same onto the projection unit for an inline child list. One shared renderer turns a sort-key entry into its call: an unqualified call to the emitted method for `path:`, the author's method for `method:`, plus its reserved-alias form for the cursor columns. Every order rendering calls it: `OrderByFragments.fixedSortParts` (which the inline child list's `.orderBy(...)` also goes through) and `fixedColumnParts`, `buildSingleArgOrderByBody`, `buildListArgOrderByBody` and `buildBaseReturnExpr`. The renderers that render the call unqualified take the coordinate's field name for that.
9. **Editor.** In `graphitron-lsp`: `DirectivePolicy.METHOD_BINDING_DIRECTIVES` gains `order` and `defaultOrder`, so `FieldSort.method` is checked like `@externalField`'s. `FieldSort.name` with a sibling `path` answers silent (no completion, no diagnostic) instead of checking the name against the field's own table; completing it against the landing table needs a stored `FieldSort` path relation and is a follow-up Backlog item. `ReferenceElement.key` inside `FieldSort` completes from the enclosing type's bound table as it does elsewhere, which is imprecise but raises no false finding, since its diagnostics are existence checks. `DriftDetectionTest`'s note on `name: String!` is updated.
10. **Fact store.** `graphitron_ast_default_order_field_entry.name_ref` and `graphitron_default_order_field_entry.name_ref` drop `NOT NULL` (`graphitron_ast_order_field_entry.name_ref` is already nullable), and the default-order comment that says an element without a name is not a `FieldSort` is rewritten; otherwise a `@defaultOrder` with a `method:` entry is not transcribed at all. `method:` is already captured by `graphitron_ast_code_reference_entry`, since `GraphitronCodeReferenceEntries` walks every `ExternalCodeReference` value at any depth. The `path:` elements are already rows of `graphql_ast_value_entry`; no `FieldSort` path relation is added, because nothing reads one yet. The editor follow-up adds it with its first consumer, keyed by the `FieldSort` element's position, not by a `@reference` application as `graphitron_ast_reference_element_entry` is.

## Tests

- Pipeline-tier classification: accepted to-one path (child to parent), accepted one-to-one extension hop including one whose unique FK columns are nullable, rejected to-many hop (message names the hop and direction and points at `method:`), rejected `condition:` on a hop, alone and beside a `key:`, unknown column on the landing table, unresolvable `key:`, `path:` without `name:`, and both rejected shapes (multitable participant, routine-result alias).
- Pipeline-tier tiebreaker on a connection: path-only order (row key appended even when the path column is the related table's primary key), a path column whose name equals one of the field's own key columns (row key still appended), `method:`-only order (row key appended), and an own-table key beside a path entry (nothing appended). The same cases through a list-valued `@orderBy` argument, where completion happens in the generated helper.
- Pipeline-tier `method:` classification: accepted method, missing class or method, wrong parameter type, non-`Field` return, `argMapping:` rejected, `method:` with `name:`, `method:` with `path:`, neither set.
- Compilation tier: each site in Emission compiles with a path and a method entry, including a path entry in an `@orderBy` enum value (the helper's switch arm) and in the field's `@defaultOrder` (the helper's base return). One order with two path entries whose first hops reach the same table (`film_language_id_fkey` and `film_original_language_id_fkey`) compiles, as does a `@splitQuery` field whose own path aliases share an initial with the ordering path's. A path column named like a selected own-table column (`last_update`) keeps both in the selection.
- Execution-tier `path:`: films ordered by original language name against the sakila fixtures (the fixture gains films with an original language if it has none), as a connection forward and backward, as a `@splitQuery` child connection and as an inline child list; a film with no original language; duplicate sort keys resolved by the appended primary key.
- Execution-tier `method:`: a connection ordered by a correlated "latest related row" expression over a to-many relation in the sakila fixtures (for example customers by the date of their latest rental), forward and backward pagination, a parent with no related row, and two parents with equal sort keys resolved by the appended primary key.
- Editor: `FieldSort.name` beside a `path` raises no finding; `FieldSort.method` naming a missing method raises one.
- Fact store: a `@defaultOrder` with a `method:` entry is transcribed, with a `NULL` `name_ref` and a `graphitron_ast_code_reference_entry` row.

## Other solutions we've considered

- **Pick one row per hop** (`ReferenceElement` gains an ordering, and a to-many hop that carries one counts as to-one). Rejected: the `LIMIT 1` a single-row read emits caps the whole correlated subquery, not one hop, so on a multi-hop path "first row at hop 1, then continue" renders as "order the final rows by hop-1 columns, keep one"; the rule for which row counts would be restated at every enum value and field path that uses it; and the same element would mean "choose a row" on a single field, "make this hop to-one" in an ordering path, and nothing on a list field.
- **Let the author assert that a hop's `condition:` selects one row.** Rejected: it trades the catalog-derived cardinality rule for an unchecked claim whose failure is silent (duplicated parents, broken page counts and cursors).
- **Order by a GraphQL field** (`{field: "gjeldendeNavn.navnSpesifikasjon"}`, reusing a single-valued field's own row choice). Rejected: it introduces a second naming system into `@order`, which names database columns, and ties ordering to how the field is delivered (`@splitQuery`, services).
- **`LEFT JOIN` the path into each site's `FROM`.** Rejected: the root launcher has no join hook (`.from(tableLocal)`), the batched and inline sites assemble their `FROM` in three different places, the `@orderBy` helper receives only the field's alias, and every one of them would need a `LEFT JOIN` emitter that does not exist (`JoinFragments` emits inner joins). The join's aliases would also share the field's own `fieldName_stepIndex` namespace. The subquery form reaches every site through the alias it already has and shares its emission with `method:`.
- **Render the `path:` subquery inline at each site, declaring its hop aliases ahead of the order.** Rejected: `scalarInnerSelect` reads aliases the caller has already declared, and most order renderings have no statement slot. They are expressions inside `List.of(...)`, a switch-expression arm and a `return`. Each site would need its own declaration placement, and a naming rule to keep the declared locals off the site's own `generateAliases` locals and off another entry's. An emitted method gives the declarations a scope of their own and makes the path form the same call shape as `method:`.

## Implementation notes

What landed follows the plan; these are the places it had to choose, for the In Review reader.

- **Model.** `OrderBySpec.Fixed`'s component is renamed `entries` (it no longer holds only columns), of the sealed `OrderEntry` with `ColumnOrderEntry` and `SortKeyEntry(SortKey key, collation, direction, ordinal)`; `SortKey` is `Path(hops, column)` or `Method(MethodRef.StaticOnly)`. `SortKeyEntry.nullable()` is always true, per the round-3 reviewer note. The multitable fold reads column entries only and throws a generator-bug error on a sort key, which the resolver refuses there first.
- **Where the method name reaches the renderers.** `render` may not import the plan's naming vocabulary, so the producers mint the refs onto the command rows: `command.SortKeyMethod(entry, UnitMethodRef)`, carried by `Ordering.Columns` (launcher rows, owner the parent's fetchers class) and `CallWrap.Multiset` (owner the projection unit), each checked to cover exactly the order's path entries. `SortKeyFragments` renders the call, the cursor column under `ReservedAliases.sortKey(ordinal)` (`__sk_<n>`), and the emitted method. The `@orderBy` helper and the single-table interface child's legacy fetcher spell names through `GeneratedUnits.sortKeyMethod` directly. The fetchers class emits the methods its launcher rows carry plus the ones its helpers render, collected inside the helper loop's existing branches so no new leaf dispatch enters `generators/` (`CommandSeamRatchetTest`); the interface child registers its own as companion methods.
- **Ordinals.** One counter per field: the `@orderBy` enum's values are resolved before the base order, so they take the low numbers.
- **The routine-result refusal** is decided on the field's table: `JooqCatalog.isTableValuedFunction`. A function result has no foreign keys for a path and is not a catalog table class a method takes.
- **`condition:`** is refused as written, from the path elements, before `parseExplicitPath`: a condition-only element has no key to resolve a target from, so its resolution error would name the wrong problem. The post-resolution check on `Hop.filter` and `On.Predicate` stays as the backstop.
- **`reflectExternalField`** gains a directive-label overload, so the nameability rejection names `@order` or `@defaultOrder`.
- **Editor.** `LspVocabulary.namesRelatedColumn` is the one predicate; diagnostics, completion, hover, definition and references each answer silent on it. The stored path relation that would let them answer against the landing table is R1114.
- **Fixtures.** `init.sql` gives films 1, 2, 3 and 5 an original language (data only), and adds `stint_badge`, a one-to-one extension of `stint_person` whose unique foreign key admits `NULL`, for the pipeline case the plan names. The `method:` execution case orders by the store of a film's latest stocked copy (`FilmSortKeys.latestStockStore` over `inventory`) rather than a customer's latest rental, because the fixture seeds no rentals; it covers the same ground: a to-many relation, a tie the appended key breaks, and parents with no related row.
- **Store legality test.** `EntryLegalityTest`'s "missing required field withdraws the application" case was measured on `FieldSort.name: String!`, which no longer holds; it now stands on `ErrorHandler.handler: ErrorHandlerType!`, and a new case pins that a `method:` element is transcribed with a `NULL` `name_ref` and its code-reference row.

Evidence: `SortKeyOrderPipelineTest` (classification, refusals, completion), `SortKeyOrderExecutionTest` (every site, forward and backward walks), `DiagnosticsTest` (the two editor cases), `EntryLegalityTest` (the store case), and the sakila example compiling every fixture at Java 17.
