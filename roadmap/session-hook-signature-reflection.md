# Session hooks are reflected routine calls, not string-bound callables

The claims payload is stringly typed end to end, and the string is not merely the Java carrier: it is also how the payload reaches the database, so a consumer whose connect routine takes a user-defined type has no supported way to call it. `GraphitronFacadeGenerator.generate` hardcodes the owned factory's leading parameter as `ClassName.get(String.class)`, `GraphitronConnectionInstrumentationGenerator.instrumentation` reads it back as `String` from the `graphQLContext` under the emitted `CLAIMS_KEY` constant, the `SessionHook.connect` signature emitted by `ConnectionRuntimeClassGenerator.sessionHook` is `(Connection, String claims)`, and `ConnectionRuntimeClassGenerator.functionHookImpl` binds the payload with `cs.setString(1, claims)` into a hand-assembled `{ call <fn>(?) }`. Nothing casts, so the parameter arrives typed `varchar` and a routine declared `connect(app.claims)` does not resolve against it; whether it works at all depends on the pgjdbc `stringtype` setting deciding to send the parameter as unspecified and letting Postgres infer the composite from its text representation. That is a fragile accident, not a contract, and it inverts the project's own posture everywhere else on this boundary: the tenant key's Java type is read off the catalog so a mis-typed map is a compile error, and contextArguments are typed from the consumer's declared parameter type so a wrong value is a compile error at the factory call site, while the one payload that carries identity, the security-load-bearing value, is an untyped blob that fails (if at all) inside the database at a cast.

## Approach: the signature is already a catalog fact

The consumer has *already* named the routine. `<connect><call>` is a pointer into the database, and everything about the call shape is a property of what it points at, so further `<sessionState>` elements describing the payload type or the handle would make the author restate facts the catalog holds, and admit restating them wrongly. This item resolves the named routines against the catalog and reads their signatures: parameter names, IN/OUT direction, Java types, return type. That is how the generator already treats the database (`@routine`'s reference says "the routine's shape (table-valued) is read off its jOOQ kind, not declared"; the tenant key's Java type is read off the column), and it is the difference between typed code the author configures and typed code the author merely *gets*.

`JooqCatalog.findNonTableValuedRoutine` already does the hard half and throws the answer away. It locates the generated per-routine class for exactly the population a session hook draws from, a procedure or scalar function that is not table-valued, instantiates it, and verifies `org.jooq.Routine.getName()` against the SQL name so a naming-strategy mismatch degrades to a miss rather than a false positive. It then discards the resolved routine and returns `JooqCatalog.RoutineResolution.NonTableValuedRoutine`, whose only payload is a prose `detail` string used to give `@routine` a better rejection message.

Binding then follows for free: a UDT-typed parameter on a generated jOOQ routine class is already typed as the generated `UDTRecord`, and jOOQ already binds it. Calling the routine *through its generated class* rather than through an assembled callable string is what makes UDT support fall out, instead of needing `PGobject`/`setObject` plumbing and a `Schema.getUDTs()` lookup of our own. R234 (UDT records as input backings) is not a prerequisite, though the two should agree on how a UDT surfaces in the model. The resolved signature is a codegen-time snapshot, exactly like every other catalog read: the build checks against the snapshot, and a routine altered after codegen fails at execution rather than at build. That is the established posture, but the security framing invites a reader to expect more, so the docs should say it in one sentence.

**Freedom to redesign rather than extend.** There are no known users of the function-hook form, and the tree confirms it has never run end to end: both plugin executions in `graphitron-sakila-example` configure the `<variables>` sugar, `SessionHookExecutionTest` drives that sugar's emitted hook, and no connect/disconnect fixture routine exists in `graphitron-sakila-db`. The form is unit-tier only (`SessionStateConfigTest`, `SessionHookImplGeneratorTest`, `SessionStateWarningsTest`). So the author-facing surface changes outright with no dual-sourcing; the additive-then-cutover discipline still governs *within* the reactor, which is what the slicing below buys.

**Two provenances, never one record.** `SessionStateConfig` is decoded in `AbstractRewriteMojo.buildSessionStateConfig` from the POM, before the pipeline, with no `JooqCatalog` in scope; its javadoc says all rejections live in `SessionStateConfig.from` precisely because a `pom.xml` defect has no SDL coordinate. The reflected signature is a different population from a different walk, so it must not land on that record: a config record merging "what the author wrote" with "what the catalog says" is the stored-merge shape the fact model tells us to split. This is also the deeper reason `<handle>` is wrong, and the trap to avoid while deleting it: `<handle>` is a *derived* fact declared at the authored boundary, and replacing it with a different derived fact at the same boundary repeats the mistake. So `SessionStateConfig` stays exactly the decoded POM fact, a separate resolver sibling to `RoutineDirectiveResolver` holds the catalog and produces a `ResolvedSessionHooks` carrier, and the emitter consumes only the resolved carrier, never the raw config.

**Carrier: share the resolution seam, not `RoutineRef`.** The Backlog body proposed riding the existing `RoutineRef` / `ParamSource` family; this spec revises that. The resolution seam *is* genuine single-sourcing, and the capture-boundary containment invariant wants it there: `JooqCatalog` is the canonical holder of raw jOOQ types, so reading `getInParameters` / `getOutParameters` / `getReturnParameter` inside it and handing out value-typed facts is right, and no live `org.jooq.Routine` escapes. The *binding carrier* is not shared. `ParamSource.RoutineParamSource permits Arg, SourceColumn`, and its javadoc pins the guarantee that the routine emitter's switch has no unreachable arms; `Arg` carries a `PathExpr` over a field's GraphQL argument slots and `SourceColumn` a `ColumnRef` of the chain's previous node, while a session hook has no field, no argument slots, no chain and no previous node. Riding it there means either a third arm the `@routine` emitter must reject as unreachable, breaking that guarantee, or reusing `Arg` to mean something else. The call surfaces differ too: `RoutineRef` holds a `Routines`-facade convenience method returning `Table<R>`, a session hook calls the per-routine generated class and needs OUT/return. Session hooks get their own small carrier whose single source arm today is "the request boundary".

## Implementation

Four slices. Each has its own behaviour delta and its own enforcing tier, and the ordering is not bookkeeping: S1 lands unconsumed, S2 proves execution against the real database while the config and facade still hold still, and S3 and S4 then change the two author-facing surfaces independently. R640's stated dependency is satisfied by S1 plus S3, not by S4.

### S1: resolution carries the signature

* `JooqCatalog`: promote non-table-valued routine resolution to a first-class outcome. It returns a sealed result carrying the generated routine `ClassName`, the ordered IN parameters (jOOQ name, Java `TypeName`, reflected setter), and the handle (type plus how it is read). Failure arms: not in catalog, ambiguous overload with candidates, ambiguous qualification, no generated routines at all, unbindable signature. Each arm maps one-to-one onto a `Rejection` variant with a stable code, in the register `Rejection.unknownTable` and `BuildContext.candidateHint` already model, so a build failure is a projection of a located row rather than prose composed at the detection site.
* No null-as-miss. `findNonTableValuedRoutine` returns `null` for a miss and gets away with it as a private single-caller helper whose result is immediately mapped to a `Rejection`; giving it a second caller would make null-as-miss a shared contract, which is the out-param smell at the seam being widened. Fold it into the new method and keep `@routine`'s existing `NonTableValuedRoutine(detail)` message as a rendering of the resolved arm, so that message is unchanged.
* Two forks the generated shape imposes (checked against `RentalCountForCustomer` in `graphitron-sakila-db`'s jOOQ output). Each IN parameter generates *two* setters, a value form (`setPCustomerId(Integer)`) and an expression form (`setPCustomerId(Field<Integer>)`); resolution picks the value form using the same `org.jooq.Field`-parameter filter `resolveTableValuedFunction` already applies. And the handle is read two ways: a `RETURNS <type>` function carries a `RETURN_VALUE` parameter read through `AbstractRoutine.getReturnValue()`, inherited and not generated, while an OUT parameter gets a generated getter. `setValue` is protected on `AbstractRoutine`, so generated accessors are the only external path and the fork is unavoidable; the resolved arm records which read applies so the emitter does not re-derive it.
* Accessor names are reflected and verified against the parameter's Java type, never reconstructed from jOOQ's naming transform, mirroring how `resolveTableValuedFunction` reflects the convenience method rather than guessing its name.
* Qualification ambiguity is an arm, not a first-hit: the canonical `Pk_Ras.Connect` is parsed by `parseQualifiedTableName` as schema `Pk_Ras` + routine `Connect`, but written as package `Pk_Ras` + procedure `Connect`. Both readings are attempted; a name resolving under both is ambiguous.
* Oracle package routines: teach the probe the generated package location (verify jOOQ's layout at implementation; the current probe looks only at `<schema>.routines.<PascalName>`). Both the package form and the ambiguity arm are properties of *resolution*, not of session hooks, which is why they sit here.
* Overload addressing: `<call>` accepts an optional parenthesised argument-type list (`app.mount_identity(app.claims)`). A bare overloaded name is the ambiguous-overload rejection naming candidates.
* Naming hazard: two types are already called `RoutineResolution`, `JooqCatalog`'s catalog outcome and `no.sikt.graphitron.rewrite.model.RoutineResolution`, the FROM-source axis on `QueryTableField` registered in `HierarchyKindRegistryTest` as a walked fact. Pick a distinct name, and check whether a new sealed model type in this area owes a registry entry.

### S2: the hook executes through the generated routine class

Keeps `(Connection, String claims)`, the config, the facade and the carrier exactly as they are; changes only the emitted body and its preconditions, so this slice is provable end to end on its own.

* `functionHookImpl` / `functionDisconnect`: instantiate the generated routine class, set each IN parameter through its value-form setter, `execute(configuration)`, then the resolved handle read, replacing `CallableStatement` and `setString`.
* **Which `Configuration`.** The `DSLContext` the instrumentation publishes is `DSL.using(connection, runtime.dialect())` with `GraphitronTransactionProvider` set on its *live* configuration, the transaction-demarcation seam. If the hook ran through that configuration, "both halves run outside any transaction" would stop being structural and become prose. The hook builds its own provider-free configuration per call. State this in the plan and pin it, because it is the one way this slice could silently weaken the state contract.
* **How the dialect reaches the hook.** `PinnedConnection.acquire` is static and receives no dialect, nor does `afterSettle`. Baking it into the generated hook's constructor from `runtime.dialect()` is the obvious answer and is a real ripple through `PinnedConnection`.
* **What the hook declares as `throws`.** Today `SessionHook.connect` / `disconnect` declare `SQLException`, `acquire` / `release` / `afterSettle` catch `Throwable` so fail-closed survives, and the instrumentation catches `SQLException` narrowly. jOOQ throws unchecked `DataAccessException`. Fail-closed still holds, but `SessionHook` is a consumer-visible generated interface with the fail-closed contract hanging off it, so the declared signature is a decision to make, not a consequence to accept.
* A resolution miss fails the build naming what was probed; add the `<routines>true</routines>` precondition in the spirit of `JooqCatalog.verifyTablesClassPresent`. Silently falling back to a string bind would revert identity plumbing to the weaker form, a security-relevant regression rather than a convenience.
* **Fixture and first execution coverage land here.** `graphitron-sakila-db/src/main/resources/init.sql` gains a composite payload type, a composite handle type, a connect routine taking the payload and producing the handle, a disconnect routine bound to it, and RLS policies on a probe table reading what connect mounted. Both directions composite, so the fixture proves typed IN *and* typed OUT binding. `graphitron-sakila-example/pom.xml` gains a plugin execution configuring the function-hook form into its own output subpackage, following the isolation pattern the federation and multitenant executions already use, leaving the sugar's coverage untouched. The autocommit and per-settle re-fire contract is re-proven here against real PostgreSQL.
* The integrity-gradient doc rewrite attaches to this slice.

### S3: signature-derived handle

* Delete `<handle>` from `SessionStateBinding` and from `SessionStateConfig.Unmount.PairedDisconnect`, and with it the "declared on both or neither" cross-check in `SessionStateConfig.from`. Keep `<stateSurvivesTransactions>` and `Unmount.UnmountFree`: both are claims about what a routine body does, which no signature reveals.
* Replace boolean agreement with a type check across two resolved signatures: connect's OUT-or-return type must satisfy disconnect's handle parameter. Stronger than the invariant being deleted, which is the test for whether the trade is worth making.
* `PinnedConnection`'s handle field, `SessionHook.disconnect`, and the re-fire retype to the resolved handle type.
* When writing the new mismatch rejection, do not inherit the spelling of the messages being deleted: `SessionStateConfig.from` renders the flag as an attribute (`<connect handle="true">`) while `SessionStateBinding` binds it as a nested element.

### S4: N typed parameters

Widest consumer blast radius, and the only slice with a genuinely open ergonomics question, so it is deliberately last and not gated behind S2's emitter work.

* **Resolve the factory signature once into an ordered list of typed slots.** After this item the emitted factory has four parameter groups under three ordering rules (the leading slot, hook IN parameters in declaration order, the fan-out tenants slot, contextArguments alphabetical), and R640 adds a *filter* on the last group. Today `GraphitronFacadeGenerator.buildExecutionInputFactory` single-sources the two factories' shape with a pair of `if`s and a loop while `appendFanOutTenantsParam` / `appendContextArgParams` hand-assemble the matching javadoc in parallel. Adding a third group plus a filter would make the ordering a convention that the parameter emitter, the javadoc emitter, the `graphQLContext` write loop, the dev-goal surface, the MCP `execute` tool and the manual each have to agree on independently. Instead: one ordered list of slots, each carrying name, `TypeName`, and provenance; parameters, null-checks, `graphQLContext` puts and `@param` javadoc all fold over it, and R640's "hook-mounted arguments are not factory parameters" becomes a filter over the list rather than a fourth rule.
* **A minted record, not a tuple.** "Tuple" invites `Object[]` or `List<Object>`, which would re-erase what the reflection just established and put casts back into an emitted body. Emit a record whose components are the reflected IN parameters with their generated types (a UDT parameter's component is the generated `UDTRecord`), minted once through the plan's naming vocabulary under the single-mint regime. `SessionHook.connect`, `PinnedConnection`'s retained field, `PinnedConnection.acquire`, `TenantConnections`, and the `graphQLContext` key then all type off one name, and "the re-fire re-runs connect with the same payload" stays structural instead of becoming a comment. `CLAIMS_KEY` is replaced by a `SESSION_ARGS_KEY` constant, keeping the single-constant property it exists for.
* A single `text` parameter reproduces today's `(String claims, ...)` factory signature exactly, which is why the `<variables>` sugar and the raw-JWS cryptographic-fence pattern need no special case: they are signatures that happen to be one string.
* The mojo-configuration and dev/MCP doc rewrites attach to this slice.

## Open decisions for the reviewer

* **Four slices in one item, or four items.** The principles consult recommends splitting into four items, on the argument that each has an independent behaviour delta and an independent enforcer, and that R640 is unblocked by S1 plus S3 alone. This spec keeps one item with four slices, because the four are sequential refinements of one mechanism with one thesis and the repo supports multi-phase plans (status stays `Ready` while phases remain), so four sign-off cycles would multiply workflow overhead for one design. Reviewer's call; if it splits, the seam is exactly the four headings above and R640's `depends-on` narrows to the resolution and handle items.
* **How a POM-sourced located violation keys into diagnostics.** S1 wants resolution failures to be located facts with candidate hints rather than prose, but a `<sessionState>` defect has no SDL coordinate, which is the very reason `SessionStateConfig` throws `IllegalArgumentException` from a constructor today. What the coordinate becomes (the POM element path? a synthetic build-config coordinate?) is a design question, not an implementation detail.
* **The dead claims parameter under `SessionStateConfig.None`.** The owned factory takes `String claims` even with no `<sessionState>`, and nothing reads it. Deriving the parameter list from the hook says it should not exist. Recommendation: drop it in S4. Honest caveat: that changes an emitted signature for consumers on the owned path *without* session state, outside the function-hook form's blast radius and therefore outside the "no known users" licence this item otherwise leans on.
* **`<devDatabase><claims>` and the MCP `execute` tool.** `GRAPHITRON_DEV_CLAIMS` and `<allowClaimsOverride>` supply one inline-or-`@file` string. Most likely to want to stay string-ish, since an agent composing a composite literal is worse than one composing JSON; a defensible answer is that the dev seam accepts a JSON object and maps it onto the reflected parameters by name.
* **Oracle resolution without Oracle execution proof.** `R468`'s Oracle execution coverage is blocked on a container. S1's package resolution is unit-testable against a generated catalog but not execution-provable here. Confirm that is acceptable against the "every invariant has an enforcer" posture.
* **Fact-store deferral.** `graphitron_routine` captures the *authored* `@routine` directive and there is no `sql_routine` relation, so routine signatures stay a walk-side catalog read. Given this item's thesis is "the signature is already a catalog fact", the deferral should be stated rather than left for a reviewer to ask about; capturing routine signatures as a fact relation is a separate item if wanted.

## User documentation (first-client check)

Draft replacement for the function-hook subsection of `docs/manual/reference/mojo-configuration.adoc` § Session identity. If this does not read more simply than what it replaces, the design is wrong.

> **Function-hook form.** Name consumer-authored database routines. `connect` mounts identity; `disconnect` unmounts it. Graphitron reads the routines' signatures from the jOOQ catalog, so the payload's type, the number of arguments, and whether a handle is produced are all facts you declare once, in the database:
>
> ```xml
> <sessionState>
>   <connect><call>app.mount_identity</call></connect>
>   <disconnect><call>app.unmount_identity</call></disconnect>
> </sessionState>
> ```
>
> The generated factory's parameters follow the connect routine's IN parameters. A routine taking one `text` parameter gives you `newOwnedExecutionInput(String claims, ...)`; a routine taking a composite type gives you `newOwnedExecutionInput(ClaimsRecord claims, ...)` with typed field setters, and passing the wrong shape is a compile error rather than a cast failure inside the database. If connect produces an OUT value or returns one, graphitron captures it and binds it to `disconnect`; the two signatures must agree on its type, and the build fails naming both if they do not.
>
> Signatures are read from your jOOQ codegen output, so altering a routine means re-running codegen; a routine changed underneath a build fails at execution, like every other catalog change.
>
> If the name is overloaded, address the overload you mean: `<call>app.mount_identity(app.claims)</call>`.

Also rewrite: the "Producing the claims payload" and integrity-gradient sections of `docs/architecture/reference/runtime-extension-points.adoc`, `docs/security.adoc`, and the owned-path paragraph of `docs/manual/how-to/tenant-scoping.adoc`. The integrity gradient improves rather than merely being corrected: the cryptographic fence is a routine taking `text` it verifies in-database, the enforced fence is a routine taking a composite behind a definer-rights package, and the gradient becomes readable off the signature.

## Tests

* **S1, unit.** One case per resolution arm, including both ambiguity arms, the package form, the two-setter pick, and both handle-read forms. Verifiable against the existing fixture routines (`rental_count_for_customer`, `create_secure_note` in `init.sql`) before any new DDL exists. `@routine`'s current rejection message is pinned unchanged.
* **S2, execution.** The function-hook form's first execution-tier proof, in the shape `SessionHookExecutionTest` establishes for the sugar: an RLS-scoped read sees only permitted rows, a mutation's post-commit read-back still does (exercising the settle re-fire), identity is absent after disconnect, and a composite payload and composite handle round-trip through the real emitted hook. Plus `SessionHookImplGeneratorTest` for the emitted jOOQ call shape and the provider-free configuration.
* **S2, compilation.** Generated sources for the new fixture execution compile at `<release>17</release>` in `graphitron-sakila-example`.
* **S3, unit.** `SessionStateConfigTest`'s handle-mismatch case becomes a signature type-mismatch rejection case; the config-shape rejections that survive keep their coverage.
* **S4, pipeline.** `GraphitronFacadeGeneratorPipelineTest` asserts the `newOwnedExecutionInput` slot list against a reflected multi-parameter signature, including the degenerate one-string case that must reproduce today's signature.
* **Warnings.** `SessionStateWarningsTest` still fires `session-state-convention-fence` where it should; check whether reflected signatures let it become more precise, since a routine taking a verified token is not the same exposure as one taking bare JSON.

## Retired vocabulary

* `CLAIMS_KEY` (constant and its `no.sikt.graphitron.request.claims` value), replaced by `SESSION_ARGS_KEY`.
* The `<handle>` configuration element, and `handle` as a component of `SessionStateConfig.Unmount.PairedDisconnect`.
* "opaque claims payload" / "the opaque claims" as the description of the connect parameter, in emitted javadoc and in prose. The word `claims` itself is *not* retired: the `<variables>` sugar's `<claim>` mapping and the dev-goal `<claims>` config both name a genuine claims document.
* `RoutineResolution.NonTableValuedRoutine` as a prose-only arm, once S1 folds it into the shared resolution.
