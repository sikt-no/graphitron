# Session hooks are reflected routine calls, not string-bound callables

The claims payload is stringly typed end to end, and the string is not merely the Java carrier: it is also how the payload reaches the database, so a consumer whose connect routine takes a user-defined type has no supported way to call it. `GraphitronFacadeGenerator` hardcodes the owned factory's leading parameter as `ClassName.get(String.class)` (`GraphitronFacadeGenerator.java:115`), the instrumentation reads it back as `String` from the `graphQLContext` under `CLAIMS_KEY` (`GraphitronConnectionInstrumentationGenerator.java:172`), the emitted `SessionHook.connect` signature is `(Connection, String claims)`, and the function-hook implementation binds it with `cs.setString(1, claims)` into a hand-assembled `{ call <fn>(?) }` (`ConnectionRuntimeClassGenerator.java:1951`-`:1960`). Nothing casts, so the parameter arrives typed `varchar` and a routine declared `connect(app.claims)` does not resolve against it; whether it works at all depends on the pgjdbc `stringtype` setting deciding to send the parameter as unspecified and letting Postgres infer the composite from its text representation. That is a fragile accident, not a contract, and it inverts the project's own posture everywhere else on this boundary: the tenant key's Java type is read off the catalog so a mis-typed map is a compile error, and contextArguments are typed from the consumer's declared parameter type so a wrong value is a compile error at the factory call site, while the one payload that carries identity, the security-load-bearing value, is an untyped blob that fails (if at all) inside the database at a cast.

## The signature is already a catalog fact; nothing extra needs naming

The consumer has *already* named the routine. `<connect><call>Pk_Ras.Connect</call></connect>` is a pointer into the database, and everything about the call shape is a property of what it points at, so requiring further `<sessionState>` elements to describe the payload type or the handle would make the author restate facts the catalog holds, and admit restating them wrongly. This item resolves the named routines against the catalog and reads their signatures: parameter names, IN/OUT direction, Java types, return type. That matches how the rest of the generator treats the database (`@routine`'s own reference says "the routine's shape (table-valued) is read off its jOOQ kind, not declared"; the tenant key's Java type is read off the column), and it is the difference between typed code the author configures and typed code the author merely *gets*.

The resolution seam already half-exists, and today throws the answer away. `JooqCatalog.findNonTableValuedRoutine` (`JooqCatalog.java:207`-`:231`) locates the generated per-routine class for exactly the population a session hook draws from, a procedure or scalar function that is not table-valued, instantiates it, and verifies `org.jooq.Routine.getName()` against the SQL name so a naming-strategy mismatch degrades to a miss rather than a false positive. It then discards the resolved routine and returns `RoutineResolution.NonTableValuedRoutine(detail)`, a prose string used only to give `@routine` a better rejection message. The work is to let that resolution carry the routine itself, from which `getParameters()`, `getInParameters()`, `getOutParameters()` and `getReturnParameter()` yield the full signature.

Binding then follows for free, and this is the part worth noticing: a UDT-typed parameter on a generated jOOQ routine class is already typed as the generated `UDTRecord`, and jOOQ already knows how to bind it. Calling the routine *through its generated class* rather than through an assembled callable string is what makes UDT support fall out, instead of needing `PGobject`/`setObject` plumbing and a `Schema.getUDTs()` lookup of our own. The consumer's factory parameter becomes the generated record type, with typed field setters and compile-time checking. R234 (UDT records as input backings) stops being a prerequisite, though the two should agree on how a UDT surfaces in the model.

## Scope: redesign, not extend

There are no known users of the function-hook form, and the tree confirms it has never been exercised end to end: `graphitron-sakila-example` configures the `<variables>` sugar in both plugin executions, `SessionHookExecutionTest` drives that sugar's emitted hook, and no fixture routine for a connect/disconnect pair exists anywhere in `graphitron-sakila-db`. The form is unit-tier only (`SessionStateConfigTest`, `SessionHookImplGeneratorTest`, `SessionStateWarningsTest`). So this item is free to change the config surface and the emitted shape rather than layering a second form beside the first, and should take that freedom:

* **There is no privileged "claims" concept.** A one-`text`-parameter connect routine is not a preserved legacy shape, it is the degenerate case of a reflected signature. The generator should carry "the connect routine's arguments" and let the string payload be what it always was, a `text` parameter. The raw-JWS cryptographic fence and the `<variables>` sugar's JSON document both remain first-class *because their signatures say so*, not because a `String` special case is held open for them.
* **N parameters is the primary shape, not a follow-on.** Reflected signatures make arity a catalog fact, so a one-argument assumption would be a self-inflicted constraint. The factory grows one typed parameter per IN parameter in declaration order, ahead of the alphabetical contextArgument slots.
* **Delete `<handle>`.** Whether connect produces an OUT value, and of what type, is a signature fact; today it is a hand-declared boolean cross-checked against a second hand-declared boolean on `<disconnect>`, with `SessionStateConfig.from` rejecting the mismatch. Reflecting *both* routines replaces boolean agreement with a genuine type check: connect's OUT (or return) type must satisfy disconnect's handle parameter. That is a stronger invariant than the one being deleted, which is the test for whether this trade is worth making.
* **Restructure `SessionStateConfig` around what is no longer declared.** With the handle derived and pairing checked across two signatures, `Unmount.PairedDisconnect(call, handle, survivesTransactions)` loses its middle field and the "declared on both or neither" rule loses its subject. `<stateSurvivesTransactions>` stays declared: it is a claim about what the routine body does to state across a commit, which no signature reveals. The unmount-free opt-out stays too, for the same reason.
* **Redesign the `graphQLContext` carrier.** `CLAIMS_KEY` publishes one `String` under `no.sikt.graphitron.request.claims`; the reflected shape needs a typed carrier for an argument tuple. The `PinnedConnection` field holding the handle for the settle re-fire becomes typed the same way.
* **Oracle package routines are in scope, not an open question.** The shipped canonical example is `Pk_Ras.Connect`, and the Oracle worked example is the load-bearing one for Sikt's kernel API, so covering only Postgres top-level routines would miss the primary case. The existing probe looks solely at `<schema>.routines.<PascalName>`, which is not where jOOQ puts package routines; teaching it the package form is part of this item.
* **Address overloads rather than tolerating first-hit.** jOOQ suffixes generated classes for same-named routines with different signatures, so a bare `<call>` naming an overloaded routine has no unique signature to reflect. With the config surface open, `<call>` can carry an explicit argument-type list (`Pk_Ras.Connect(app.claims)`) so overloads are addressable; absent that, an ambiguous name must be a typed rejection naming the candidates, never a silent pick.
* **A resolution miss cannot be silent.** For `@routine` a probe miss degrades to a rejection message, which is fine. Here, quietly falling back to a string bind would mean identity plumbing reverting to the weaker form, a security-relevant regression rather than a convenience. A miss fails the build naming what was probed. The same reasoning wants a construction-time precondition that jOOQ generated routines at all (`<routines>true</routines>`, the default but not guaranteed), in the spirit of `JooqCatalog.verifyTablesClassPresent`.
* **The hook stops being raw JDBC.** The emitted hook deliberately owns a bare `Connection` with no jOOQ involvement; executing a generated routine means building a `Configuration` over that connection inside the hook. The state contract must survive unchanged: both halves run outside any transaction, with the connection normalized to autocommit at acquisition, and the per-settle re-fire keeps working.
* **Reuse the routine carrier family instead of growing a parallel one.** `RoutineRef` already models "resolved routine class + ordered params + per-param `ParamSource`", and `ParamSource` already distinguishes argument, context, and column sources. Session hooks should ride that family, with `JooqCatalog`'s routine resolution as the single seam both `@routine` and `<sessionState>` read, rather than a session-specific carrier that re-derives the same facts.
* **Ship execution-tier proof and the fixture it needs.** The function-hook form has none. This item lands a Postgres fixture: a composite type, a connect routine taking it, a disconnect routine bound to a typed handle, RLS policies reading what connect mounted, and execution coverage over the real emitted hook, in the shape `SessionHookExecutionTest` already establishes for the sugar. That fixture is also what the Oracle-side execution coverage item can mirror.
* **Update the surfaces that describe the string payload.** The `<sessionState>` section of `docs/manual/reference/mojo-configuration.adoc`, the "Producing the claims payload" and integrity-gradient sections of `docs/architecture/reference/runtime-extension-points.adoc`, `docs/security.adoc`, and the tenant-scoping how-to all present an opaque string as the boundary. The integrity-gradient prose gets *better* under reflection rather than merely being corrected: the cryptographic fence is a routine taking `text` it verifies in-database, the enforced fence is a routine taking a composite behind a definer-rights package, and the gradient becomes readable off the signature.
* **The dev-goal and MCP surfaces assume one string payload.** `<devDatabase><claims>` (inline or `@file`), `GRAPHITRON_DEV_CLAIMS`, and the `<allowClaimsOverride>` per-call argument on the `execute` tool all need a shape for N typed arguments. This is the surface most likely to want to stay string-ish for ergonomics (an agent typing a composite literal is worse than typing JSON), so decide it deliberately rather than by inheritance.
