# A cursor issued by Graphitron 9 is rejected, so a client that stores cursors loses its place at the upgrade


## Goal

A cursor that Graphitron 9 issued keeps working as `after:` or `before:` after the consumer upgrades to Graphitron 10, on a connection that pages on the same columns in both versions: the declared order is unchanged and already identifies a row, so Graphitron 10 appends no key to it (see "An order Graphitron 10 completes" below). Today the generated decoder rejects it with "cursor is not valid", so a client that stores its last cursor as a checkpoint either replays the feed from the start or loses its place. After this item Graphitron 10 has one cursor format, the one Graphitron 9 used: URL-safe Base64 without padding of a JSON array of the order columns' values. A 9 cursor needs no translation, and the manual's "Cursor encoding is part of the public contract" section holds across the major version.

On the sakila example, where `filmsConnection` orders on `film_id`, the cursor Graphitron 9 issued for film 2 is `WzJd`, the encoding of `[2]`:

```graphql
{ filmsConnection(first: 2, after: "WzJd") { nodes { title } } }
```

Today this fails with `cursor is not valid (was: "WzJd")`. After this item it returns films 3 and 4, and the `endCursor` of that page is `WyI0Il0`, the encoding of `["4"]`. Graphitron 10 writes each value as a JSON string and reads any JSON scalar, so both cursors decode under either version's rules.

## Why a restart is not acceptable

Reported by sis. Its event feeds (`studenthendelser`, `personProfilhendelser` in the stable contract; `emnehendelser`, `studieprogramhendelser`, `evukurshendelser` in beta) are paged by consumers that poll with `after: <last cursor>` and persist that cursor between runs, often for days. sis had accepted the format change on the assumption that clients restart pagination. That holds for a UI paging through a list, but not for a feed checkpoint. `studenthendelser` orders on `INSTITUSJONSNR_EIER, ROW_SCN, ID`, all numeric, and the declared column list is the same in both versions. Graphitron 10 also pages on exactly that list provided the order covers one of the table's identifying keys (its primary key, its `@node` key, or a unique key whose columns are all `NOT NULL`), which an event table keyed on `ID` or on `(INSTITUSJONSNR_EIER, ID)` does. This is an assumption about sis's tables the spec cannot check from this repository; sis confirms it per feed before relying on this item.

## The two formats today

A *cursor* is the opaque string a connection hands out per edge and in `pageInfo`, naming the position of a row in the connection's order; the client passes it back as `after:` or `before:` and the generated fetcher turns it into a keyset seek, a `WHERE (order columns) > (cursor values)` predicate.

- **Graphitron 9** (`graphitron-common` `QueryHelper.getOrderByToken` / `getOrderByValues` at tag `v9.3.0`): `jsonArray(<order columns>)` built in SQL, so each value arrives in the database's JSON rendering, then URL-safe Base64 without padding. Decoding parsed the array with `org.json`, loaded it into a record of the order fields (`ctx.newRecord(fields).fromArray(...)`) and bound each value with the field's `DataType`. The multi-table interface variant (`getOrderByTokenForMultitableInterface`) wrapped the token in a JSON object with `typeName` and `fields`.
- **Graphitron 10** (`ConnectionHelperClassGenerator`, the emitted `ConnectionHelper.encodeCursor` / `decodeCursor`): each value's `toString()`, joined by U+0000 with U+0001 for SQL `NULL`, then standard Base64 with padding. Each token is converted with `DataType.convert`.

The difference is a by-product of the rewrite (the cursor is now built in Java from the fetched record, with no JSON dependency), not a deliberate wire change. The 10 format also carries four defects of its own that the 9 format does not have: a text value containing U+0000 splits into two tokens (PostgreSQL forbids NUL in text, Oracle, which sis runs, does not); a text value that is exactly U+0001 decodes as `NULL`; a single text order column holding `''` encodes to the empty cursor, which `pageRequest` reads as no cursor (the pitfall `connections.adoc` documents); and on an order column with a jOOQ `Converter` (a forced type mapping a column to a user type of the consumer's choosing), the cursor carries the user value's text, which the converted `DataType.convert` parses as the *database* type. Measured against jOOQ 3.20.11 with the sakila fixture's `UtcLocalDateTimeConverter` (`timestamptz` mapped to `LocalDateTime`, standing in for the Oracle `DATE` a consumer maps to `LocalDateTime`): `convert("2007-08-22T02:24")` returns `null`, so a connection ordered on such a column fails "cursor token not coercible" on its second page. The node-id encoder hit the same defect on the same converter (`ConverterTemporalKeyExecutionTest` pins its fix). Graphitron 10 has not been released, so this is the cheapest point there will be to change what it emits.

## Design

`ConnectionHelper` gets one codec, shaped like 9's on the wire and like 10's in how it binds values.

**Encode.** `encodeCursor` writes a JSON array with one element per order column, in order: SQL `NULL` as `null`, every other value as a JSON string of the column's *database value*'s `toString()`. The database value is `record.get(column)` passed through the column's converter, `column.getDataType().getConverter().to(value)`, inside a small generic helper so the wildcard captures type-check in Java 17. For a column without a converter jOOQ's converter is the identity, so the text is exactly what 10 writes today; for a converter-backed column it is the database type's text, which is what 9 carried (its `jsonArray` rendered the column before any converter ran). The string is escaped per RFC 8259: `"`, `\` and every character below U+0020 (`\n`, `\t` and the others as `\u00XX`), so U+0000 and U+0001 become ordinary escaped characters. The array's UTF-8 bytes are encoded with `Base64.getUrlEncoder().withoutPadding()`.

Every non-null value is a string on purpose. The decoder converts each element with the column's `DataType`, so a JSON number or boolean tag would carry nothing the column does not already know, and choosing it by the value's Java class would be a second type system beside the `DataType` (and would emit invalid JSON for a `Double` NaN or infinity). The cursor stays column-driven, as it is today.

**Decode.** `decodeCursor` keeps its signature, its `null` handling (`DSL.noField` per column) and its single client error. Its body becomes: `Base64.getUrlDecoder()` (which accepts padded and unpadded input), UTF-8, then an emitted reader that parses one JSON array of scalars into a `List<Object>`: a string becomes its unescaped text, a number its literal text, `true`/`false` a `Boolean`, `null` a null. Arity is strict, as today. A `null` element binds `DSL.val((Object) null, col.getDataType())`; any other element is turned into the column's value by `ColumnValues.fromDatabase(col.getDataType(), element)`, a new entry point on the emitted `ColumnValues` class (below), and bound with `DSL.val(value, col.getDataType())`. A null result is rejected as "cursor token not coercible", as today.

**`ColumnValues.fromDatabase`.** `ColumnValues` is the emitted class that already owns "is this value a value of that column, and if so which one" for every decode-side caller (`exact` for node-id slots, `coerce` for authored tenant and federation `@key` values), by running the value on the *column trip*: user value, `converter.to`, `converter.from`, with a failed step answering `null`. The cursor decode is a decode-side caller of the same question, so it joins that class rather than standing its own conversion beside it. The new entry point differs from `coerce` only in its first step: it parses the input as the column's database type, `type.getSQLDataType().convert(input)`, then takes `converter.from(database)` as the canonical value, and refuses a number that does not fit the column's declared precision with the existing `fitsPrecision` check. Like its siblings it returns `null` for a value that names nothing and lets any other exception from the consumer's converter propagate.

Parsing as the database type, rather than calling the converted `type.convert`, is required by two measured behaviours of jOOQ 3.20.11's converted data type. It returns `null` for user-type text the database type does not parse (the `LocalDateTime` case above). And when the input is already an instance of the user type it hands it back untouched: on a `bigint` column converted to `String`, `convert("186")` returns `"186"` as the *user* value even when the converter maps 186 to some other text, so a database-text cursor would bind the wrong value. `getSQLDataType()` on a converted type returns the unconverted database type (`OffsetDateTime` for the `timestamptz` fixture, `Long` for `org_code`), and on an unconverted type returns the type itself with the identity converter, so for an ordinary column `fromDatabase` binds what `convert` binds today.

The reader rejects anything else as malformed: a nested array or object (so the 9 multi-table object form is rejected, see below), trailing content after the array, an unterminated string, a bad escape. **Every reader failure is thrown as `IllegalArgumentException`**, including an overrun past the end of the input, so it lands in the existing `IllegalArgumentException | DataTypeException` catch and surfaces as `cursor is not valid (was: "…")`. An `IndexOutOfBoundsException` or `NumberFormatException` escaping the reader would be a redacted server error for what is a client's malformed input. The reader parses a number by its JSON grammar and keeps the literal text, so the column's database type does the numeric conversion and a 19-digit `ROW_SCN` loses no precision.

The reader and writer are private static helpers of the emitted `ConnectionHelper` (`writeJsonString`, `readJsonArray` or similar), written in statement form with explicit types and Java 17 syntax, as the rest of the class is. They add no dependency: the generated code still needs only jOOQ, graphql-java and the JDK.

**What a 9 value looks like to the database type's `convert`.** Checked against jOOQ 3.20.11: the database JSON renderings convert to the column's type, `"2024-01-01T00:00:00"` (Oracle `DATE`, PostgreSQL `timestamp`) to `LocalDateTime`, `LocalDate` and `Timestamp`; fractional seconds and offsets (`"2024-01-01T10:11:12.000000+02:00"`) to `LocalDateTime` / `OffsetDateTime`; a number's text to `Long`, `Integer` or `BigDecimal`; a UUID string to `UUID`. No 9-specific conversion is needed, so there is no 9-specific code path at all: a 9 cursor and a 10 cursor go through the same reader and the same conversion, differing only in whether a number element was written bare.

**A converter-backed order column.** Both versions' cursors now carry the database value's text, so one decode path serves both, and it is the one that works: measured on `UtcLocalDateTimeConverter`, PostgreSQL's JSON rendering `"2007-08-22T02:24:00+00:00"` (what 9 wrote), `OffsetDateTime.toString()`'s `"2007-08-22T02:24Z"` (what 10 will write), an offset other than UTC and fractional seconds all parse as `OffsetDateTime` and come back from the converter as the `LocalDateTime` 02:24 row's key. This is a deliberate difference from node ids, which carry the user value's text and parse it as the user type with a parse class the generator supplies per slot (`SlotParse`): the cursor codec is runtime-generic over `List<Field<?>>` with no per-column generator input, and 9 compatibility fixes the representation as the database one anyway.

The multi-table connection's cursor goes through the same codec (`MultiTablePolymorphicEmitter` builds its `extraFields` from the order slots, typed by the column's own `DataType` passed through the per-class `withoutGenerator` helper, which drops a client-side generator and keeps the converter, then the `__pk` key columns and `__typename`, which are untyped synthetic fields with the identity converter), so it gains the same fix; its 9 compatibility stays out of scope, below.

**Sort-key fields.** A connection ordered by a `path:` or `method:` sort key carries that key in the cursor as a `__sk_<n>` field among `extraFields`. The codec is driven by each field's `DataType` and never by its origin, so these go through the same encode and decode with no case of their own: a `path:` key's correlated subselect has the related column's `DataType`, converter included, and a `method:` key has whatever `DataType` the author's `Field<X>` carries. `getSQLDataType()` is non-null on every shape such a field can take; measured against jOOQ 3.20.11, a converted type, a converted `OTHER`, an untyped `DSL.field(String)` and a scalar subselect each return their database type. Graphitron 9 had no sort keys, so no 9 cursor reaches them.

**`NULL` order values.** A `NULL` element binds `DSL.val(null, type)` exactly as the U+0001 sentinel binds it today, and the null-aware seek that a nullable order column's `NULLS LAST` placement renders handles it unchanged. A 9 cursor that carries a `NULL` (PostgreSQL's `json_build_array` keeps it) decodes and seeks under 10's placement, `NULL` last in both directions, which on a descending nullable column is not where 9 put them; the migration guide's "Where `NULL` sorts" entry already tells the consumer so. Feed keys are `NOT NULL`, so the reported case never meets it.

**An order Graphitron 10 completes.** Graphitron 10 appends the table's row key to a single-table connection's order when the declared columns cover none of the table's identifying keys, and the appended columns are part of the cursor. Graphitron 9 appended nothing. On such a connection a 9 cursor has fewer elements than the order 10 pages on, and strict arity rejects it as `cursor is not valid`, which is what the R1106 changelog entry already promises for every cursor issued before the upgrade on a completed field. This item keeps that: the promise it makes covers connections where the declared order already identifies a row, so 9 and 10 page on the same columns. Accepting the shorter cursor was considered and rejected (see "Other solutions we've considered"). The connection whose order does identify a row is the feed shape: a feed that paged on a non-identifying order under 9 was skipping tied rows at page boundaries, the defect the appended key fixes.

**Out of scope, and why.**

- *The 9 multi-table interface cursor* (`{"typeName": …, "fields": …}`). 10's multi-table connection orders the union on the participants' key columns and then the type name, a different seek from 9's per-type token, so a 9 cursor cannot be translated position for position. sis's event types are single-table interfaces with a discriminator, which page as plain single-table connections. The object form fails decode with the ordinary client error. A consumer who needs it files its own item.
- *A 9 cursor on an order Graphitron 10 completes with the row key.* Rejected as `cursor is not valid`, as above; the client restarts from the first page. sis confirms its feeds are not of this shape (see "Why a restart is not acceptable"); one that is files its own item for prefix acceptance, whose cost "Other solutions we've considered" sets out.
- *A 9 cursor with a `NULL` order value issued on Oracle.* jOOQ renders `jsonArray` without an `ON NULL` clause (checked on its open-source dialects), and Oracle's `JSON_ARRAY` defaults to `ABSENT ON NULL`, so such a cursor has fewer elements than the order has columns. 9 bound it positionally, shifting the values; 10's strict arity rejects it. Feed keys are `NOT NULL`, so this does not reach the reported case, and rejecting a cursor 9 itself mis-decoded is the correct outcome.
- *Cursors issued by a Graphitron 10 snapshot.* They use the format this item retires and stop decoding. Graphitron 10 is unreleased; a consumer running a snapshot in production with persisted cursors is not known. If the reviewer knows of one, the fallback is cheap and unambiguous enough to add: a decoded text that does not start with `[` is read as the NUL tuple.
- *`graphitron-mcp`'s own page cursors* (`McpWire.encodeKeysetCursor`, a NUL-joined keyset cursor for the MCP tool surface). They are hand-written server code, not emitted into consumers, and no client stores them across a Graphitron 9 upgrade. They stay as they are, and the retirement sweep below excludes them.

## User documentation (first-client check)

The `connections.adoc` section as it reads after this item; the two unchanged bullets are elided.

```asciidoc
== Cursor encoding is part of the public contract

A cursor names one row's position in the active order: the values of the order's columns for that row, written as a JSON array with one element per column in order, then encoded as URL-safe Base64 without padding. SQL `NULL` is `null`; every other value is a JSON string of the column's database value, so a column with a jOOQ converter contributes its database type's text, not the converted value's. Clients should still treat a cursor as opaque. The format is stated here because it is a compatibility promise, not an interface to build on.

This is the format Graphitron 9 issued. A cursor a client stored under Graphitron 9 keeps working after the upgrade while the connection pages on the same columns: the order is unchanged and already identifies a row (Graphitron 9 wrote some values as bare JSON numbers; both forms are read). Two kinds of connection are the exception, and a client drops a cursor it stored from one and restarts from the first page:

* A connection whose order does not identify a row. Graphitron now appends the table's primary key to it (see xref:sort-results.adoc#stable-cursors-and-tie-breakers[How-to: Sort results]), so a Graphitron 9 cursor has too few values and is rejected.
* A connection over a multi-table interface or union. Graphitron 9 wrapped its cursors in an object naming the type, which Graphitron 10 rejects.

Three consequences worth restating here (the sort recipe covers the full set):

* *The cursor's columns are the order's columns.* (unchanged, including its sentence on the appended primary key)
* *Decoding rejects shape mismatches.* (unchanged)
* *An empty cursor is no cursor.* `after: ""` and `before: ""` (or a whitespace-only value) read as if the argument were omitted, so an operation that declares `$after: String!` can fetch the first page by sending the empty string.
```

## Tests

All execution tier, in `graphitron-sakila-example` `GraphQLQueryTest` (or `MultiTableOrderingExecutionTest` where the fixture lives there), asserting returned rows and the client error, never generated text or SQL.

- **A Graphitron 9 cursor pages correctly.** Build the cursor the way 9 did, in SQL: select `jsonArray(<order columns>)` for a seeded row through the test's `DSLContext`, encode it URL-safe without padding, and pass it as `after:`; assert the returned rows are the ones after that row. Cover `filmsConnection` (one numeric column, the `WzJd` example above) and `filmsOrderedConnection` with `order: [{field: TITLE}, {field: FILM_ID}]` (a text and a numeric column; the sequence covers the primary key, so graphitron appends nothing and the 9 cursor is `jsonArray(TITLE, FILM_ID)`). Repeat one of them as `before:` with `last:`.
- **The completion boundary.** A 9 cursor over `filmsByRateDescTitleAsc`, built in SQL as `jsonArray(RENTAL_RATE, TITLE)` for a seeded row, is rejected with `cursor is not valid (was: "…")`: rate and title do not identify a film, so 10 pages on `rental_rate DESC, title ASC, film_id ASC` and the two-element cursor fails arity. This pins the scope the Goal states, so a later change that starts accepting such a cursor does it on purpose.
- **The reported shape: a numeric composite key.** A 9 cursor over a multi-column numeric order, `filmActorsFaceted` (ordered on `film_actor`'s primary key `(actor_id, film_id)`), pages to the expected rows.
- **A 9 timestamp in Oracle's rendering.** Call the emitted `ConnectionHelper.decodeCursor` directly with a hand-built `["2024-01-01T00:00:00"]` cursor (bare JSON string, as Oracle renders `DATE`) against a timestamp column such as `FILM.LAST_UPDATE`, and assert the bound value; repeat with fractional seconds.
- **A converter-backed column, through `converterIdChangesConnection`.** A 10 cursor: `first: 1`, then `after:` that page's `endCursor` returns the 02:24 row, and `last: 1, before:` the 02:24 row's cursor returns the midnight row. Both fail today with `cursor is not valid`, so this is the fixture that pins the converter defect fixed in passing. A 9 cursor: built in SQL as above (`jsonArray(CONVERTER_ID_CHANGE.PERSON_ID, CONVERTER_ID_CHANGE.CHANGED_AT)` for the midnight row, which PostgreSQL renders with its offset), passed as `after:`, returns the 02:24 row.
- **`ColumnValues.fromDatabase` directly**, in `graphitron-sakila-example`'s unit-tier `ColumnValuesTest`, beside `exact` / `coerce` / `folded`: on `ORG_CODE` (`bigint` to `String`) the text `"186"` gives `"186"`; on a test-local `bigint` to `String` converter whose user text differs from the database text, the database text gives the *converted* user value, not the input handed back (the short-circuit the design avoids); on `timestamptz` through `UtcLocalDateTimeConverter` an offset rendering gives the UTC `LocalDateTime`, while the user type's own text `"2007-08-22T02:24"` gives `null`; and a number wider than a `NUMERIC(4)` gives `null`. The multi-table converter path keeps its existing coverage: `MultiTableOrderingExecutionTest`'s forward and backward `converterPlacesConnection` paging runs on the new format unchanged.
- **10 round-trips.** Every existing forward/backward paging test keeps passing on the new format unchanged, which is the round-trip coverage. Three families carry an element shape the others do not: `ConnectionTiebreakerExecutionTest` (an appended row key), `NullSortKeyPagingExecutionTest` (a cursor taken inside the `NULL` run, so a `null` element) and `SortKeyOrderExecutionTest` (`path:` and `method:` sort-key fields, forward and backward). Add one assertion that a page's `endCursor` decodes (URL-safe Base64, no padding) to the JSON array of strings the design names, so the emitted format is pinned and not merely self-consistent.
- **Escapes.** `decodeCursor` called directly with an element carrying `\"`, `\\`, `\u0000` and a non-BMP character escaped as a surrogate pair binds the unescaped text. No sakila row holds such text, which is why this one goes through the helper directly.
- **Malformed input stays a client error.** The three rebuilt tests above, plus: a JSON object (the 9 multi-table form), a nested array element, trailing content after the array, an unterminated string, and input truncated mid-escape. Each asserts `cursor is not valid (was: "…")` and that the message is not the redacted `An error occurred. Reference:` form, which is what proves every reader failure reaches the catch.

## Retired vocabulary

The NUL-joined cursor format of `ConnectionHelper`: "NUL-separated tuple", "NUL-joined" and U+0000 as a cursor separator, U+0001 (SOH) as the cursor's `NULL` sentinel, "PostgreSQL strings cannot contain NUL" as a cursor premise, and the claim that graphitron emits an empty cursor for a `''` text value. Sweep the generator, the emitted-code comments, `GraphQLQueryTest`, and `docs/manual/`. `graphitron-mcp`'s `McpWire` keyset cursor is a different cursor and keeps its NUL joiner.

## Roadmap entries

R1085 (`manual-v9-cursor-and-error-path-claims`) fixes the same `migrating-from-legacy.adoc` cursor sentence, with the opposite advice ("clients must drop stored cursors"), which this item makes untrue. This item owns that sentence: the reviewer session that moves this item to Ready removes R1085's error 1 from R1085's body in the same commit, leaving it the error-path fix alone. If R1085 lands first, this item's docs edit replaces its wording.

R1106 (Done) appended the row key to single-table connection orders after this spec was first drafted; "An order Graphitron 10 completes" is how the two compose. Its changelog entry ("a cursor such a field issued before the upgrade ... is rejected") stays true after this item and needs no amendment.

## Other solutions we've considered

- **Keep 10's format and add a legacy decoder beside it**, recognising a 9 cursor by its encoding (URL-safe alphabet, missing padding) and content (no U+0000, a JSON array of the order's arity). Two codecs, plus a runtime guess at which one an opaque string is in, with a residual ambiguity that cannot be removed: a one-column text order whose 10 value is itself a one-element JSON array reads either way. It also raises a lifetime question (permanent, or opt-in behind a plugin setting with a removal date nothing enforces), and a setting is one more configuration axis to test in both positions. Switching 10 to URL-safe output on top of it, which the Backlog sketch considered for URL friendliness, removes the encoding signal and leaves content as the only discriminator. Adopting 9's shape removes the guess, the ambiguity, the setting and the lifetime question together, and fixes 10's NUL, SOH and empty-cursor defects in passing.
- **Write numbers and booleans bare**, matching 9's bytes more closely. Rejected above: the tag carries nothing the column's `DataType` does not, and choosing it by Java class is a parallel type system. Byte-for-byte equality with 9 is not reachable anyway, since 9 used each database's JSON rendering.
- **`Record.formatJSON` in array format** for the writer. It renders values by their Java type (bare numbers) and through jOOQ's JSON formatting rules rather than the cursor's, so it brings back the type tag and couples the wire format to a formatting API; the writer needed is a dozen lines of string escaping.
- **Keep writing the user value's text and decode it as the user type**, as node ids do. A 9 cursor carries the database rendering, so decode would need both parses and a rule for which one wins, and the user-type parse needs a per-column parse class the generator supplies (`SlotParse`), which the runtime-generic codec does not have. Writing the database value gives both versions one representation and one parse.
- **Accept a 9 cursor on an order 10 completes**, reading a cursor one key short as the declared prefix and seeking strictly after it, which is the position 9's own seek used. jOOQ's `seek` takes one value per sort field, so this needs a hand-built row predicate over the prefix beside jOOQ's, and that predicate would have to reproduce the null-aware rendering jOOQ already does for `NULLS LAST` columns. It also gives up strict arity on exactly the connections whose order changed, so a cursor from a different, shorter order would decode instead of failing. And it carries forward a position 9 mis-handled: the page after it starts beyond every row tying with it, which is the skip the appended key exists to stop. No reported consumer needs it; a feed that does gets its own item.
- **A JSON library on the consumer classpath** (as 9 depended on `org.json`). The generated code is a consumer artifact with no runtime dependency on graphitron beyond jOOQ and graphql-java; a scalar-array reader does not justify one.
