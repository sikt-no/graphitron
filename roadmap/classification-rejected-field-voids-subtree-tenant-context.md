# A field rejected at classification voids its subtree tenant context

## Goal

In a database-per-tenant build, a field that classification rejects outright reports its own error, and the tenant-scoped fields below it are not also reported as having "no ancestor established a tenant context" when the field returns tenant-scoped table rows, directly, through an interface or union, or through a connection. Today such a field hands its subtree nothing, so one rejected root can bury its own error under hundreds of consequential ones: sis hit this on 2026-10-14 with one rejected root returning `Node`, which voided the context of every node type and produced about 680 follow-on errors. Removing the directive cleared all of them. Where the field's return type leads to no tenant-scoped table, its subtree keeps being judged as having no tenant, because that is what any fix will leave it. Where the field returns any other type (a service result type, a nesting type, a mutation payload), its subtree is judged as today: some consequential errors stay below such a field, a bounded under-count this item accepts rather than risk hiding real ones. A build that passes is unchanged, since it contains no classification-rejected field.

A minimal pair over the sakila fixture with `film_id` as the tenant column, where `@notGenerated` stands in for any classification rejection (it is retired, so classification rejects every use):

```graphql
type Film @table(name: "film") {
    title: String
    inventories: [Inventory!]! @splitQuery
}
type Inventory @table(name: "inventory") { inventoryId: Int }
type Query {
    films: [Film!]! @notGenerated        # leads to tenant-scoped 'film'
}
```

Today: the `@notGenerated` rejection on `Query.films`, plus `Film.inventories` ("no ancestor established a tenant context"), plus one per tenant-scoped field below `Inventory`. After: the `@notGenerated` rejection alone. Swap the root for `languages: [Language!]! @notGenerated` over the global `language` table, with `Language.films: [Film!]!` below it, and `Language.films` keeps its "no ancestor established" error, since fixing the root leaves a global read that hands down no tenant.

Terms used below. The *tenant fold* (`TenantBindingIndex.Fold`) decides, before any field gets its verdict, which types have a tenant on every path from a root (*context*): a tenant-scoped field on such a type inherits that tenant. It walks *edges*, one per SDL field returning an object, interface or union type, and asks of each edge whether it establishes a context (hands its subtree a tenant) or only passes on its parent's. A *site* is one classified instance of a field, the per-field input the fold reads. A *classification-rejected field* is one whose coordinate holds a `GraphitronField.UnclassifiedField`: classification could not make anything of it, and the validator reports it.

## Why it happens

`Fold.sitesOf` records sites for `OutputField`s only, and `UnclassifiedField` is not one, so a classification-rejected field has an edge (`buildEdges` reads the SDL) and no site. `edgeEstablishesContext` answers false for an edge with no sites, so the edge passes on its parent's context. At a root, or below a global parent, the parent has none, and the closure from the unbound seeds (`foldAncestorContexts`) carries "no context" through the edge into everything it reaches.

Two facts bound the fix:

- **Site-less edges are not all rejections.** An SDL-declared connection type's fields (`FilmConnection.edges`, `FilmConnection.nodes`, `FilmEdge.node`, `pageInfo`) are never classified (`GraphitronSchemaBuilder.classifyFieldsOfObject` returns early for `ConnectionType` and `EdgeType`), so they are site-less edges in passing builds, correctly passing on the context the connection-returning field established. The rule below therefore keys on the coordinate holding an `UnclassifiedField`, never on an edge having no sites.
- **No passing build has an `UnclassifiedField`.** `GraphitronSchemaValidator.validateUnclassifiedField` reports every one as a `ValidationError`, which has no severity and stops emission; only fields of reached types are classified, so none sits outside the walk's domain. A rejection nested inside a nesting type lands at the embedding field's coordinate (`FieldBuilder` turns the whole `NestingField` into an `UnclassifiedField` there), so it is covered by the same rule. Whatever the fold does with these edges changes only the error list of a failing build.

## The rule

R1027 judges a rejected site's subtree as every fix its rejection offers leaves it. A classification-rejected field has no site, so no reach, reading or offered fix to argue from; its rejection may be any of dozens of classification errors, and its fix may produce any field shape. The SDL still says what the field returns, and that is enough to answer the one question the fold needs: once fixed, will this field's own statement need a tenant?

A classification-rejected edge is *counted* when:

1. The field does not carry `@globalData`. A marked field takes its verdict from the marker's ladder once it classifies, and a field that runs on the default source hands nothing down; its subtree's errors are then real. (`@tenantFanOut` needs no condition: `edgeEstablishesContext` already answers true for a fan-marked edge ahead of reading sites, and `belowFannedEdge` already seeds from it, so a fan-marked rejected field is already judged as fanning.)
2. Its *SDL reach* holds a tenant-scoped table. The SDL reach is the set of tables the field's own statement would select from, read off the SDL: starting at the edge's targets (`edgeTargets`, which already expand interfaces and unions to their members), a type whose `types` entry is a `GraphitronType.TableBackedType` contributes its `table()`; a `GraphitronType.ConnectionType` or `GraphitronType.EdgeType` is walked through along its own outgoing edges; every other type contributes nothing and stops the walk. So `Query.films: FilmConnection` reaches `film` exactly as `Query.films: [Film!]!` does.

The pass-through set is exactly the connection and edge wrappers because those are the only types whose fields are part of the returning field's own statement: `GraphitronSchemaBuilder.classifyFieldsOfObject` never classifies their fields, so their edges are the returning field's statement seen through the wrapper. Every other non-table type's fields are sites of their own once the build passes, and decide their own subtrees; in the failing build they have no site yet, so the rule cannot judge them one by one and stops instead.

Stopping is an under-count, and it is chosen over walking through. Once the build passes, a nesting type's or result type's children split two ways. A child that needs a tenant (`Nest.films: [Film!]!` on a nesting type under the global `Language`, `Report.films` on a service result type) gets a site, routes by its parent row or rejects for want of a context, and either way R1027's `handsDownAsIfFixed` counts it, so everything below it has a context: `Film.inventories` inherits and the one error sits at the child. A child that reads a global table hands nothing down, and whatever is tenant-scoped below it keeps a real "no ancestor established" error. In the failing build neither child has a site (classification never reached it; a probe on trunk shows `Nest` and `Report` absent from `types` too), so their own errors cannot be reported yet. Stopping at the type leaves the first kind's subtree reporting consequential errors, which is today's behaviour. Walking through would count the rejected field whenever any child reaches a tenant-scoped table, give the type a context, and pass it down the second kind of child as well, hiding errors that are real in the fixed build. The rule takes the under-count: it leaves the failing build no worse than today, while the over-count would trade consequential errors for hidden real ones on a shape as ordinary as a nesting type with a global and a tenant-scoped child. Mutation payloads stop the walk for the same reason; a rejected DML mutation returning a payload keeps today's behaviour, which is the right answer when the fix is a payload-returning service and over-reports when it is a DML write.

A counted edge establishes a context (`edgeEstablishesContext`) and divines a tenant (`edgeDivinesTenant`). Both folds read one set of counted edges, computed once in `run` beside R1027's `countedSites`, before `foldAncestorContexts`.

Why "divines" too: R1027 keeps the invariant that every type with a context sits below a divining edge, a fanned edge, or a routed dispatch entry, and its argument that `siteDivinesTenant` needs no restriction rests on it. A counted edge that established without divining would break that invariant in failing builds. Divining also gives the right answer for a `@tenantFanOut` field below the rejected field: once the field is fixed it binds a tenant, so the marker below it will reject "sits under a tenant-bound ancestor"; saying so now is the same error one build earlier.

Why SDL reach is the right proxy. A fixed field hands its subtree nothing only when its own statement needs no tenant, which is when it reaches no tenant-scoped table (a global read, a plain value), or when it carries `@globalData`, which condition 1 excludes and whose ladder refuses a tenant-scoped table return anyway. A field that does reach a tenant-scoped table, once it classifies, either hands a tenant down (a binding, the parent row, node dispatch, a fan-out) or is itself a tenant rejection, which R1027 judges as fixed. So in both branches the subtree's "no ancestor established" errors are consequential until the field resolves, which is what the rule reports.

What it can get wrong, and what that costs, in both directions. *Over-counting*: a counted field whose fix classifies it as needing no tenant even though its SDL return type leads straight (or through a connection) to a tenant-scoped table. Then a tenant-scoped child's real "no ancestor established" error is hidden, and, because a counted edge also divines, a `@tenantFanOut` child below it is rejected "sits under a tenant-bound ancestor" where the fixed build would accept it. Both surface correctly in the build after the field classifies, against a field that then has a site and the ordinary rules; the build is already failing on the field's own error, which is always reported. R1027 refused that trade for `@globalData` because its rejection text *offers* `@globalData`, which makes the masking fix a likely path; with the walk confined to table-backed types and connection wrappers, the untenanted fix of a field returning tenant-scoped rows is neither offered nor natural. *Under-counting*: a field the walk stops on (a payload, a result type, a nesting type) whose fix, or whose type's tenant-needing children once they classify, hand a tenant down. Its subtree's consequential errors stay reported, which is today's behaviour, unchanged; the paragraph above says why this direction is the one taken.

The cross-scope condition of R1027 has no counterpart. It excludes a site whose one statement touches tenant-scoped and global tables, which no binding can route. An SDL return type whose closure holds both, the motivating `Node` among them, says nothing about one statement: node dispatch routes each type on its own, and `siteEstablishesContext` already counts routable node dispatch as establishing for every type in `Node`'s closure, global ones included. Counting the rejected `Node` root is the same answer.

## Implementation

All in `graphitron/src/main/java/no/sikt/graphitron/rewrite/TenantBindingIndex.java`.

1. `Fold` keeps the classification-rejected coordinates as a `Set<FieldCoordinates>`, collected in the same pass over `fields` that `sitesOf` makes, so "rejected" and "has a site" come from one read (flat only; a nested rejection already sits at the embedding coordinate).
2. A private `sdlReachesTenantTable(FieldCoordinates edge)` implementing condition 2 as `closeForward(edgeTargets.get(edge), e -> passesThrough(e.getTypeName()))`, then testing the closed set for a `TableBackedType` whose `table()` is `tenantScoped`. `passesThrough` reads the parent's `types` entry: true for `ConnectionType` and `EdgeType`, false for every other `GraphitronType` and for an absent entry. The absent case is real in failing builds: a non-table type reached only through a rejected field is never classified (`Report` and `Nest` in the probes behind the Tests below), while `ConnectionType`, `EdgeType`, `PageInfoType` and every `@table` type are classified even under a rejected root. An absent entry stops the walk and contributes no table, the same answer as any other non-wrapper, non-table type. Reusing `closeForward` keeps one traversal (and its domain filtering) in the fold rather than a second hand-written loop. It reads only the SDL edges and the classified types, never ancestor context, so it can run before the folds.
3. The counted set: every classification-rejected coordinate that is an in-domain edge, not `globalMarked`, and `sdlReachesTenantTable`. Computed once in `run`, in the loop that fills `countedSites`, so both are ready before `foldAncestorContexts`.
4. `edgeEstablishesContext`: after the `fanMarked` rung, a counted edge answers true. `edgeDivinesTenant`: a counted edge answers true. The site-based answers are untouched, so every edge that has sites, and every site-less connection-wrapper edge, behaves exactly as today.
5. Javadoc: on the counted set (what is counted, the SDL-reach proxy and its pass-through set, why only failing builds see it, and the bounded cost both ways). Say there too that the arms children get below a counted edge are counterfactual and reach no consumer: the main-source readers of `TenantBindingIndex` are the validator, which reads `rejections()`, `EntityFetcherDispatchClassGenerator`, which reads `byEntityType`, and the per-field seam `GraphitronSchema.tenantBindingOf`, read by `LauncherCommands`, `RoutineWriteCommands` and `TenantDslEmitter`. All but the validator are emit-side, and `GraphQLRewriteGenerator` produces the `EmitPlan` only when the error list is empty, so none of them runs on these arms in a failing build. A future diagnostics consumer that shows arms must revisit this. Add a sentence each on `edgeEstablishesContext`, `edgeDivinesTenant` and `foldAncestorContexts` naming the classification-rejected case. No change to `armOf`, `checkedArmOf`, the sites, any `TenantBinding` arm, the emitters, `graphitron-model` or the validator.

This builds on R1027 (Done), which reshaped the same predicates: `countedSites`, the `DispatchFact` seeds, and the routed-entry seed of `belowBoundEdge`. The edge-level answer is a sibling of R1027's site-level one, not a change to it.

## Tests

All in `TenantBindingClassificationTest` (unit tier, classification only). Each fixture uses `@notGenerated` as the classification rejection and asserts the field is an `UnclassifiedField`. "Alone" means `tenantBindings().rejections()` is empty, the field's own rejection being the validator's.

- **The sis shape:** a tenant-scoped node type `Film` (its key, `film_id`, carries the tenant) with `Film.inventories: [Inventory!]! @splitQuery`, reached through an ordinary `Query.node` and through `Query.legacyNode(id: ID!): Node @notGenerated`; `Film.inventories` inherits, alone. Today the rejected root's edge voids `Film`'s context despite `Query.node`, and `Film.inventories` rejects "no ancestor established".
- **A list root:** the Goal's `Query.films: [Film!]! @notGenerated`; `Film.inventories` inherits, alone.
- **Through a declared connection:** `Query.films: FilmConnection @notGenerated` over an SDL-declared `FilmConnection`/`FilmEdge`; `Film.inventories` inherits, alone. Witnesses that the walk passes through both wrapper kinds, and (beside the passing connection tests that already exist) that site-less wrapper edges keep passing context on.
- **A result type stops the walk (a known under-count):** a rejected root `@service` (a service class that does not resolve, or `@notGenerated`) returning a non-table `Report { films: [Film!]! }`, with `Film.inventories @splitQuery`; `Film.inventories` keeps its "no ancestor established" error. The test pins the stop, not the fixed build's answer: its name and a comment say the error is consequential (once the root classifies, `Report.films` is counted and `Film.inventories` inherits) and kept because the rule does not walk through result types.
- **Global reach stays void:** the Goal's `Query.languages: [Language!]! @notGenerated` with `Language.films: [Film!]! @reference(path: [{key: "film_language_id_fkey"}])`; `Language.films` still rejects "no ancestor established a tenant context".
- **`@globalData` excluded:** `Query.films: [Film!]! @notGenerated @globalData`; `Film.inventories` still rejects "no ancestor established", beside the marker sweep's rejection of the unreached marker.
- **Fan-out below:** `Query.films: [Film!]! @notGenerated` with `Film.inventories @tenantFanOut`; the marker rejects "sits under a tenant-bound ancestor".
- **A nesting type stops the walk (a known under-count):** `Language @table(name: "language") { nest: Nest }` under `Query.languages`, with `Nest { bad: String @notGenerated  films: [Film!]! @reference(path: [{key: "film_language_id_fkey"}]) }` and `Film.inventories @splitQuery`. The `@notGenerated` child makes `Language.nest` the `UnclassifiedField`, and `Nest.films` then has no site, so only a field below `Film` can discriminate; a tenant-scoped field directly on `Nest` reports nothing either way. `Film.inventories` keeps its "no ancestor established" error. As with the result type, the test is named and commented as a pin of the stop: with `bad` removed the build classifies `Language.nest` as a `NestingField`, `Nest.films` rejects on its own and `Film.inventories` inherits.

No pipeline, compilation or execution test changes: they run passing builds, which have no classification-rejected field. A change in one contradicts the "no passing build has an `UnclassifiedField`" premise and is a finding, not an edit to make. Other unit tests whose failing fixtures carry a classification-rejected field and assert tenant rejections may drop consequential errors; each such edit is that drop and nothing else.

## Other solutions we've considered

- **Count every classification-rejected edge.** Simpler, and a single predicate. Rejected because a rejected field over a global table is fixed into a global read that hands nothing down, so its subtree's "no ancestor established" errors are real and would be hidden for a round with nothing gained.
- **Count every site-less edge.** Would read the SDL-declared connection wrapper edges, which are site-less in passing builds, as establishing, and so change passing builds' classification (a wrapper edge below a context-less parent would hand down a tenant no one supplied). Keying on `UnclassifiedField` makes "failing builds only" structural.
- **Use the return type's structural closure alone, without walking through connections.** Misses the commonest root shape, a connection, whose own type is not a `@table` type.
- **Walk through every non-table type.** Removes the under-count below a nesting or result type whose tenant-needing children would be counted once they classify, but over-counts the type's other children: the rejected field is counted, the type gets a context, and a child reading a global table passes it on, hiding a "no ancestor established" error below that child which is real in the fixed build. The Rule explains why the under-count is the direction taken. Payloads would need an argument of their own; none is offered here, and they keep today's behaviour.
- **Judge the stopped-at type's children one by one.** Match the fixed build on both kinds of child: below a rejected field's non-table target, treat each site-less child edge as counted when its own SDL reach holds a tenant-scoped table, the way R1027 would count it once it classifies. That removes the under-count without the over-count, but it needs a failing-build-only marker for those shadow edges, or it changes passing builds (site-less wrapper and facet edges must keep passing context on). The probes show the shadow types absent from `types`, which may be that marker; nobody has shown that every in-domain type outside the wrapper and facet kinds is classified in a passing build, and this item does not take that on. A follow-up can, if the under-count proves to matter in practice.
- **Suppress consequential errors after the fact** (drop every "no ancestor established" error traced to a classification-rejected edge). Needs a provenance trail the fold does not have, and leaves the `@tenantFanOut` ladder judged against a context that will not exist; R1027 rejected the same alternative for the same reason.
- **Leave it.** sis cleared its instance by removing the directive. But any classification error on a root returning `Node` or a widely reached type reproduces the cascade, and the field's own error is the one buried.

## Reviewer findings

### Round 1 (2026-10-14, Spec -> Ready, reviewer session 01QRuom5NmUKS34NNdXeVPrB)

Verdict: withhold. One blocking finding on question one, which reaches question two through two of the tests; one smaller precision finding on question two. The goal reads cleanly from the Goal section alone, the mechanism is the right shape (an edge-level sibling of `countedSites`, keyed on `UnclassifiedField`, reusing `closeForward`), and every symbol the spec names exists as named. Every "today" claim reproduces on trunk: each Goal fixture, the sis `Node` shape, the declared connection, the result type, the global root and the nesting type gives an `UnclassifiedField` at the rejected coordinate and the cascade below it, and `FilmConnection.nodes` / `FilmEdge.node` are site-less as stated.

**Finding 1 (question one: a checkable claim the scope boundary rests on is false). Below a result type or a nesting type, the fixed build does not leave the subtree without a tenant, so the spec's own result-type and nesting-type tests would pin consequential errors as real.**

The Rule argues that the walk stops at non-table, non-wrapper types because their fields "are sites of their own once the build passes, and decide their own subtrees", and concludes that the errors below them are real. The first half is true; the conclusion misses how they decide. In the fixed build, a tenant-needing child of the nesting or result type (`Nest.films`, `Report.films`) gets a site, rejects for want of a context, and R1027's `handsDownAsIfFixed` counts it, so it establishes a context for everything below it. Checked on trunk with a probe over the sakila fixture (`film_id` tenant column):

- Passing build `Language @table(name: "language") { nest: Nest }`, `Nest { films: [Film!]! @reference(...) }`, `Film.inventories @splitQuery`: `Language.nest` is a `NestingField` (`GlobalRead`), `Nest.films` rejects "no ancestor established", and `Film.inventories` classifies `Inherited`. One tenant error, at `Nest.films`.
- The same shape with a `@notGenerated` sibling on `Nest`: `Language.nest` is the `UnclassifiedField`, `Nest.films` has no site (no classified field, and `Nest` is absent from `types`), and `Film.inventories` rejects "no ancestor established". Under the spec's rule this stays, yet it is exactly the consequential error the item exists to remove: the fixed build does not report it.
- The `Report` result type behaves the same way: `Report.films` has no site and `Report` is absent from `types` in the failing build, so the real error the spec names ("a tenant-scoped child below it has a real error to report") is not reportable at all; what is reported is `Film.inventories`, which inherits once the root is fixed.

So the "result type stops the walk" and "nesting type stops the walk" tests, as worded, pin under-counts while asserting they match the fixed build, and the nesting test's "as it would once the nesting field classifies" is contradicted by the passing probe. The nesting test's fixture is also ambiguous: a tenant-scoped field directly on the nesting type has no site in the failing build and reports nothing, before or after this change, so only a field below a table type reached through the nesting type discriminates. The "Walk through every non-table type" dismissal rests on the same premise ("pins a wrong answer outright"). Walking through has a real cost, but a different one: it would hand a context to a global sibling's subtree (a `Nest.language: Language` child would pass the context on, hiding a `Language.films` error that is real in the fixed build).

What would satisfy it: the author decides the boundary with the fixed-build outcome in view. Either keep the stop and argue it honestly as an under-count, as the spec already does for payloads (reword the two tests as pins of a known under-count, fix their fixtures so they discriminate, and replace the "Other solutions" premise with the actual over-count walking through would cause); or choose a rule that matches the fixed build on both kinds of child. One observation that may help, not a recommendation: in the failing build the stopped-at types were absent from `types` in every probe, which is a failing-build-only marker the same way `UnclassifiedField` is.

*Author response:* kept the stop and re-argued it as an under-count. The Goal names the under-count; the Rule's pass-through paragraph now states the fixed-build outcome for both kinds of child and why the under-count beats the over-count walking through causes (the global-sibling case). Both tests are renamed as pins of the stop, with the nesting fixture made discriminating (`Language.nest` → `Nest.films` → `Film.inventories`, the probe's shape). The walk-through dismissal now gives its real cost, and the per-child rule is recorded as a considered alternative whose open question is the failing-build-only marker.

Whatever Finding 1 settles, the absent case needs a stated answer.
