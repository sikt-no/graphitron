# Producer domain types are placeholders, so a shared class-backed type read as a record component can never pass the multi-producer conflict check

A shared value type that one field produces through a batched `@service` and another field reads as a component of a record-backed parent is rejected at build time, even though both producers put the very same Java object at `env.getSource()`. The rejection is `Rejection.AuthorError.MultiProducerDomainTypeDisagreement`, and it is spurious: the two producers do not report what they hand down, they report placeholders, and the placeholders can never be equal. There is no schema-side workaround, so the shape simply cannot be authored. Reported from a consumer subgraph where the type's shape is fixed by federation (another subgraph declares the field `@shareable`), which is what makes it a blocker rather than a naming inconvenience.

## The shape that fails

```graphql
type Kvotetype @table(name: "kvotetype") {
    navn: OversatteTekster @service(service: {className: "...", method: "navnByKvotetype"})
}
type OversatteTekster { nn: String  nb: String  se: String  en: String }
type SvarKvotepoeng {          # record-backed: the parent's backing class holds a navn() accessor
    navn: OversatteTekster
    poenggrense: BigDecimal
}
```

Here `navnByKvotetype` is a batch function with the signature `Map<KvotetypeRecord, OversatteTekster> navnByKvotetype(Set<KvotetypeRecord>)`, and `SvarKvotepoeng`'s backing class is a Java record whose `navn()` component returns an `OversatteTekster`. The build fails with:

```
type 'OversatteTekster' is produced with disagreeing env.getSource() Java domain types:
  - Kvotetype.navn → Plain(java.util.Map)
  - SvarKvotepoeng.navn → Plain(java.lang.Object)
```

## Why the check exists, and what it is really comparing

Any field returning an SDL object type is a *producer* for that type: at run time it puts a Java value at `env.getSource()`, and graphql-java hands that value to the datafetchers generated for the type's child fields. Graphitron generates each child fetcher once per coordinate and does not branch on the runtime source class, so two producers that hand down structurally different values would feed one of them into a fetcher compiled against the other's shape. `GraphitronSchemaBuilder.collectDomainReturnTypeConflicts` catches that by grouping the classified field registry by SDL return type and comparing each producer's `OutputField.domainReturnType()` by sealed-arm equality.

The `DomainReturnType` arms keep a sparse jOOQ `Record` projection, a typed jOOQ `TableRecord` and a plain domain object apart on purpose, because "same class" would paper over a projection difference. Inside the `Plain` arm, however, equality is exact `TypeName` equality, and that is where placeholder values become fatal.

## Root cause: neither participant reports its real source type

Two sites answer with something other than the class they hand down. Both participants in the reported shape are one of them.

`ChildField.ServiceRecordField.domainReturnType()` answers `Plain(OutputField.peelToClassName(method.returnType()))`. `peelToClassName` unwraps `Optional`, `CompletableFuture`, `List`, `Set`, `Collection` and `org.jooq.Result`, but not `Map`, and otherwise falls through to the raw type. A batch function's `Map<K, V>` therefore collapses to `java.util.Map`, which is a type that never reaches `env.getSource()` at all: the DataLoader resolves the map to one `V` per key, and `V` is what graphql-java sees. The correct answer already exists one method above, as `ServiceRecordField.elementType()` (via `RowsMethodShape.strictPerKeyType`, which returns the leaf's backing class for a `ReturnTypeRef.ResultReturnType`).

`ChildField.RecordReadField.domainReturnType()` answers `Plain(Object)` for its `ValueLocator.JavaAccessor`, `ValueLocator.ByName` and `ValueLocator.DefaultRead` arms; only `ValueLocator.TypedColumn` reports a real type. For the accessor arm the true type is available and unused: the locator carries the resolved accessor, whose declared return type is the class the read produces.

The consequence is that three producers of one Java class report three different values, so any two of them collide:

| producer | reported arm |
|---|---|
| root `@service` returning the class directly | `Plain(...OversatteTekster)` |
| batched child `@service` returning `Map<K, OversatteTekster>` | `Plain(java.util.Map)` |
| record component read through the `navn()` accessor | `Plain(java.lang.Object)` |

### The same defect one arm over: the mutation root producer

A further site misreports, and it is worth fixing here because it is the same defect in a different register: not a placeholder value, but a mislabeled arm. `QueryField.QueryServiceRecordField` and `MutationField.MutationServiceRecordField` are structural twins: both are root `@service` producers over a payload result type, and both derive their answer from the same reflected `serviceMethodCall.javaReturnType()` through the same `peelToClassName`. They disagree on the arm. The query twin answers `Plain`, the mutation twin answers `TableRecord` unconditionally, including for the plain-POJO payloads its own javadoc describes ("the service method returns the SDL payload class (or scalar / pojo) directly"). One Java class, two arms, so the two producers of one payload type can never agree.

`MutationServiceRecordField`'s javadoc asserts the gap away: "Non-carrier service shapes also answer `TableRecord` ... other arrangements either agree or are filtered by upstream classifier rejections." Against the query twin they do not agree. The assertion holds only for the population the leaf was reasoned about on, the carrier shape whose conflict against the DML `Record(table)` arm is the case anyone had exercised.

The mutation twin's `TableRecord` answer is right for some of its populations and wrong for the rest. Where the SDL return type resolved a jOOQ table (the unbacked carrier shape, whose reflected return element is the payload's single `@table`-typed data field's record class; and the reflected `JooqTableRecordType`, whose backing class the catalog knows) a typed `XRecord` really does reach `env.getSource()`. Where it did not, a class-backed payload puts the payload object there, or nothing names what arrives at all. The populations are already separated by a fact the model holds, so the fix costs a fork rather than a redesign.

## Evidence that the conflict is false

The generator's own reflection-based binding fold disagrees with the conflict check on the same schema. `RecordBindingResolver.peelReturnElement` peels `Map<K, V>` to `V` correctly, so both producers ground the *same* `Class`, the per-type fold agrees, and no `RecordBindingMultiProducer` rejection fires. The type then classifies as a single `JavaRecordType` whose children are ordinary `RecordReadField` reads. One binding, one emitted fetcher shape, one Java class at `env.getSource()`: the two producers agree in every sense the check claims to be protecting.

Measured against trunk at filing time with an inline-SDL pipeline fixture. The batched table-parent producer alone classifies cleanly with no diagnostics, and the record-component producer alone classifies cleanly; only the combination is rejected. A root producer paired with a record component read fires the same rejection with no batching involved, so this is not specific to `@service` batching. It follows that any class-backed type read as a record component anywhere and produced anywhere else is unauthorable today, which is precisely the shared-value-type pattern federation pushes consumers toward.

## Plan

Make every producer report what it actually hands down, give "cannot say" a structural home in the vocabulary, and let the grouping site compare only real claims. Emit is untouched; what changes is the metadata the conflict reduction compares, plus the admission of schema shapes the placeholders used to reject by accident.

### Vocabulary: split the sealed root into Claim and NoClaim

Restructure `DomainReturnType` as `sealed interface DomainReturnType permits Claim, NoClaim`, with `sealed interface Claim extends DomainReturnType permits Record, TableRecord, Plain` and `record NoClaim()` meaning "this producer cannot state what it puts at `env.getSource()`". The grouping and participant-comparison helpers in `collectDomainReturnTypeConflicts` are declared over `Claim`, so the invariant "a no-claim never participates in an agreement comparison" is enforced by the type system, not by a filter someone must remember. The three existing arms and their equality semantics are untouched; no exhaustive switch over `DomainReturnType` exists anywhere in the reactor (`TenantBindingIndex` uses `instanceof Record`, the builder groups by equality, `Rejection` renders `toString`, and `graphitron-lsp`'s `RejectionSeverityCoverageTest` constructs two arms directly), so the split is additive at every consumer.

`Optional<DomainReturnType>` at the `OutputField.domainReturnType()` signature was considered and rejected: it touches all ~35 leaf implementations and every consumer, and it removes the value from the diagnostic rendering, where a no-claim should still read as a statement ("makes no source-type claim").

### One mint for backing-class claims

Three spellings of "the backing class as a `TypeName`" exist today, and two of them disagree on nested classes: `ClassName.bestGuess` (used by `ChildField.RecordCompositeField.domainReturnType()`) keeps the binary `Outer$Nested` as one simple name, while `RowsMethodShape.fromBinaryName` splits it into `Outer.Nested`; the two `TypeName`s are unequal, which is a fresh instance of the exact bug this item retires. Introduce a single factory (`DomainReturnType.claimForBacking(ReturnTypeRef)` or similar, routing through the `fromBinaryName` splitting) and answer every class-backed producer through it: the sharpened `RecordReadField` and `ServiceRecordField` below, plus `RecordCompositeField` (migrating it off `bestGuess`) and the root-`@service` twins `QueryField.QueryServiceRecordField` and `MutationField.MutationServiceRecordField` (migrating their `ResultReturnType` case off reflected `peelToClassName`). `peelToClassName` survives on the twins' `ScalarReturnType` arm only, where the reflected peel is honest because a root `@service` returns its payload directly rather than through a container; note that arm is not co-extensive with "SDL scalar", per the section below.

The factory returns `DomainReturnType`, not `Claim`: the arms it is asked about include ones with no backing class to name, and `NoClaim` is the honest answer there rather than a caller-side null check that reintroduces the placeholder by another route. `fromBinaryName` is `private` on `RowsMethodShape` today; widen it to package-private (`DomainReturnType` is in the same package) rather than adding a fourth spelling of the `$`-splitting.

Bound the factory's parameter to the arms it serves rather than to `ReturnTypeRef` as a whole. A `TableBoundReturnType` does have a backing class on offer (`strictPerKeyType` answers the table's record class), but the consumer-level claim for a table-bound return is `Record(table)`, not `Plain(XRecord)`; a factory that answered the latter because no caller happens to pass that arm today would be a fresh instance of the bug this item retires. Make the restriction structural, at the signature, not a comment.

### The `ResultReturnType` rule, stated once

Three leaves ask the same question of a `ReturnTypeRef.ResultReturnType`, so the rule lives here once instead of three times with drift. The question is *not* whether `fqClassName()` is null. `fqClassName` says only "the schema grounded a backing class for this SDL type, or it did not", and that is orthogonal to the arm a producer should claim: `GraphitronType.JooqTableRecordType` has two populations, one carrying a reflected class name and one carrying the stand-in null, and both put a typed jOOQ table record at `env.getSource()`. Keying on the null would answer those two identical facts with two different arms.

The fact that decides the arm is the *resolved table*. `JooqTableRecordType` carries it on both populations: the carrier mint (`TypeBuilder.carrierVerdict` on a `CarrierBinding.TableBacked` binding) supplies `tb.table()` directly, and the reflected mint (`TypeBuilder.buildResultTypeFromClass`'s `JOOQ_TABLE_RECORD` arm) resolves it through `ServiceCatalog.resolveTableByRecordClass`. Three sub-populations, answered by fact rather than by leaf:

* **A resolved table is present.** The producer's element really is that table's typed record, and the typed record is what reaches `env.getSource()`. Claim: `TableRecord` over the table's record class. This covers both the unbacked table-backed carrier (`SingleRecordTableFieldServiceProducerPipelineTest`'s `FilmListPayload`) and the reflected jOOQ table record (`R96RecordBindingPipelineTest.singleServiceReturn_bindsToJooqTableRecord`'s `FilmDetails`, which today splits `Plain(FilmRecord)` on the query twin against `TableRecord(FilmRecord)` on the mutation twin and is therefore part of the twin-symmetry defect, not a separate concern).
* **No table, but a grounded backing class.** An ordinary class-backed result type (`JavaRecordType`, `PojoResultType.Backed`, a non-table `JooqRecordType`, or a `JooqTableRecordType` whose record class the loaded catalog does not know). Claim: the factory's backing-class claim, `Plain` over the grounded class.
* **Neither.** Result-axis grounding found nothing and no carrier binding fired. Neither the model nor the reflected return names what arrives; on a batched child leaf `peelToClassName(method.returnType())` answers `java.util.Map`, the placeholder this item retires. Claim: `NoClaim`.

Ordering matters and is not an implementation detail: the table question is asked *first*, so a `ResultReturnType` that carries both a table and a class never mints `Plain(XRecord)`. That is the same restriction the factory's bounded parameter enforces one arm over, applied inside the arm the factory does accept. `DomainReturnType.Plain`'s own javadoc defines it as "an explicit Java type with no jOOQ surface"; a `Plain(FilmRecord)` claim would falsify it, and `TableRecord`'s javadoc describes exactly this producer.

Carry the table as a fact rather than re-deriving it at each leaf. `GraphitronType.JooqTableRecordType` already holds the resolved `table` and `BuildContext.resolveReturnType` drops it when it builds the `ResultReturnType`; thread it through instead. One production construction site (`BuildContext.resolveReturnType`) and eight hand-built test fixtures move with it, so this is a small change rather than a redesign.

The alternative, deciding the sub-population at the leaf from the reflected return, cannot be made to work uniformly and should not be attempted: a root twin's reflected return peels to the typed record but a batched child's peels to `java.util.Map`, and asking "is this `ClassName` a jOOQ table record" inside the accessor would need a classload that `DomainReturnType.TableRecord`'s javadoc rules out at group-by time. Splitting `JooqTableRecordType` into reflected and class-less permits, which is the fuller version of the same fix and which that record's own javadoc asks for, is deliberately out of scope: this item needs the fact, not the permit split.

### Which SDL returns are actually compared

`collectDomainReturnTypeConflicts` groups on `sdlReturnTypeName`, which answers only when the field's unwrapped SDL return is a `GraphQLObjectType`; interfaces, unions and scalars drop out before grouping. That filter decides whether a leaf's answer is behaviour-bearing or rendering-only, and it does not line up with `ReturnTypeRef`'s arm names.

`ReturnTypeRef.ScalarReturnType` in particular is not a synonym for "SDL scalar". `BuildContext.resolveReturnType` falls through to it for a `NestingType`, a `ConnectionType`, and any carrier whose verdict is none of the other three arms, all of which are `GraphQLObjectType`s and so are grouped. The arm reaches the leaves under review by two routes: `ServiceDirectiveResolver.projectReturnType` forks straight on the arm, so a `@service` returning such a type arrives as `Resolved.Scalar` and mints a `ServiceRecordField` or `QueryServiceRecordField` carrying a `ScalarReturnType` that names an object type; and `FieldBuilder`'s object-return branch on a record-backed parent passes the same arm to `recordReadFieldOrUnclassified`.

Consequence for this plan: no `ScalarReturnType` fork may be justified as behaviour-neutral on the grounds that scalars are filtered out of the grouping. Each fork below names the sub-population it lands on, and the ungrounded-object-type sub-population is the one that needs the argument.

### Producer answers

* `ChildField.ServiceRecordField.domainReturnType()` answers the per-key element, the same `V` the emitted `DataLoader<K, V>` is typed with, derived from `returnType()` rather than from the reflected outer. `Map` never reaches `env.getSource()`; `V` does. `FieldBuilder` mints this leaf from two classify arms (`ServiceDirectiveResolver.Resolved.Result` and `Resolved.Scalar`), so the fork is spelled out per arm the same way the record-read leaf's is:
  * `ResultReturnType`: the shared rule above, in its three sub-populations. On the grounded-class sub-population the factory's backing-class claim is exactly `RowsMethodShape.strictPerKeyType`'s answer for this arm, so the claim and the loader's `V` agree by construction. The no-table, no-class sub-population matters more than a completeness note: it is grouped (the SDL return is an Object type), it is live (`ServiceRecordField.elementType()`'s "other null-perKey returns (a backing-less `ResultReturnType`)" branch is exactly that sub-population), and `strictPerKeyType` answers `null` there. An implementer who fills that null by falling back to reflected `peelToClassName` re-mints the placeholder this item retires, on a population the check actually compares.
  * `ScalarReturnType`: the per-key element, derived the way `elementType()` derives it, so the claim and the emitted `DataLoader<K, V>` cannot disagree about what `V` is. `strictPerKeyType` grounds the five built-in scalars; where it answers null (an enum, a custom scalar, or an ungrounded object type) `RowsMethodShape.perKeyFromOuter` peels `V` off the reflected outer, and `NoClaim` only when neither grounds it. Do not fall back to `peelToClassName(method.returnType())`, which answers `Plain(java.util.Map)` on every batched leaf; that is today's answer and it is the same false statement as the object case. The built-in-scalar and enum / custom-scalar sub-populations are never grouped, so for them this is rendering-only. The ungrounded-object-type sub-population *is* grouped, which is why the fork derives a real element instead of answering `NoClaim` wholesale.
  * `TableBoundReturnType` routes to `ServiceTableField` and `PolymorphicReturnType` is deferred at classify, so neither reaches this leaf.
* `ChildField.RecordReadField.domainReturnType()` forks on `returnType()`, spelled out per arm:
  * `ResultReturnType`: the shared rule above, regardless of locator arm. On the grounded-class sub-population that is the factory's backing-class claim, following the consumer-level identity precedent set by `ServiceTableField.domainReturnType()` (which answers `Record(table)` although the method returns the typed record). Deliberately derived from the leaf's `ReturnTypeRef`, not the reflected accessor handle, so a covariant accessor declaration or a raw generic return cannot mint a new false conflict. Safe to derive that way because the two are already held equal upstream for a single-valued component: `FieldBuilder.resolveRecordAccessor` passes the SDL type's bound class as `ClassAccessorResolver`'s expected return, and a component whose accessor does not yield it never reaches this leaf. See the accessor row in the loosening ledger below for what that enforcement does and does not cover. In practice a record component read off a class-backed parent lands on the no-table, no-class sub-population and answers `NoClaim`; routing it through the shared rule rather than hard-coding `NoClaim` is what keeps the three leaves from drifting apart again if a table-carrying type ever becomes readable this way.
  * `ScalarReturnType` under a `ValueLocator.TypedColumn` locator: the column type, as today, on both sub-populations. Under the other locator arms: `NoClaim`. For a genuine SDL scalar or enum that is rendering-only. For the ungrounded-object-type sub-population it is grouped and it is a real loosening, and it does not get a ledger row because no enforcer covers it: no backing class was grounded anywhere, so there is nothing to claim and nothing to check a claim against, and `FieldBuilder.mapGraphQLTypeToReflectType` already hands `ClassAccessorResolver` a bare `Object.class` expected return for such a type, leaving the accessor check vacuous there too. It joins the honest gap below.
  * `TableBoundReturnType` / `PolymorphicReturnType` do not reach this leaf.
* `QueryField.QueryServiceRecordField.domainReturnType()` forks on `returnType()` the same three ways its mutation twin does. The fork is written out rather than left to the factory's default, so the twins are symmetric by construction instead of by coincidence:
  * `ResultReturnType`: the shared rule, so a table-carrying result type reached from `Query` answers `TableRecord` exactly as the same shape reached from `Mutation` does. This population is reachable from both roots and the plan must not assume otherwise: `TypeBuilder.carrierBinding` / `carrierVerdict` key on the payload type name rather than on the operation root, `BuildContext.isServiceProducedPayload` checks `getQueryType()` alongside `getMutationType()`, and `RecordBindingResolver`'s service fold walks every object type rather than the two roots. Leaving the query twin on the factory's default would answer `NoClaim` on the unbacked carrier and drop a producer that really does put a typed record at `env.getSource()` out of the comparison, silently accepting a query-carrier producer paired with a DML producer of the same payload.
  * `ScalarReturnType`: `Plain` over the reflected peel, unchanged. A root `@service` returns its payload directly rather than through a `Map`, so `peelToClassName` is an honest answer here, and leaving it alone keeps today's teeth on the ungrounded-object-type sub-population named above.
* `MutationField.MutationServiceRecordField.domainReturnType()` answers exactly what its query twin answers, on all three forks. The unconditional `TableRecord` is what breaks the symmetry today; confining it to the carrier sub-population through the shared rule is what restores it:
  * `ResultReturnType`: the shared rule, so `TableRecord` wherever a table resolved, the factory's backing-class claim on a class-backed payload (the payload object itself reaches `env.getSource()`), and `NoClaim` on the ungrounded remainder. Same shape, same answer as the query twin, which is the point. The table-carrying sub-population is the one `SingleRecordTableFieldServiceProducerPipelineTest` pins against the DML `Record(film)` producer (its `FilmListPayload` is an unbacked carrier), and confining `TableRecord` to types that actually resolved a table keeps that pinning intact rather than incidentally true.
  * `ScalarReturnType`: `Plain` over the reflected peel, as the query twin, so the mislabeled `TableRecord` arm does not survive on a population that is not a table record. Rendering-only for a genuine scalar or enum; behaviour-bearing for the ungrounded-object-type sub-population, where it preserves today's answer rather than loosening.
* Migrate the remaining placeholder `Plain(Object)` answers to `NoClaim`: `ErrorsField` (in its single-`@error`-type flavour, `[SomeError]`, the SDL return *is* an object type and the field does enter the grouping; the `[SomeUnion]` / `[SomeInterface]` flavours are filtered out by `sdlReturnTypeName` like the rest of the polymorphic answerers. It genuinely hands down a heterogeneous list of developer exception classes; this is the one migration in the sweep that changes behaviour, and it carries its own row in the loosening ledger below), plus the never-grouped polymorphic and pivot answerers (`QueryNodeField`, `QueryNodesField`, `QueryInterfaceField`, `QueryUnionField`, `QueryServicePolymorphicField`, `QueryServiceTableInterfaceField`, their mutation analogues, `ChildField.InterfaceField` / `UnionField` / `BatchedInterfaceField` / `BatchedUnionField`, `PivotSlotField`). The never-grouped migrations are behaviour-neutral by construction (their SDL returns are interfaces, unions or scalars, which `sdlReturnTypeName` filters out); the only surface their answers reach is the rejection rendering, where `NoClaim` is honest and `Plain(java.lang.Object)` was a false statement. After this sweep, `Plain(Object)` as a placeholder is retired; `OutputField.OBJECT_CLASS` survives only as `peelToClassName`'s structural fallback.

### Grouping site

`collectDomainReturnTypeConflicts` compares claims only: group each SDL Object type's producers by their `Claim` values, no-claims excluded from the comparison. A group with fewer than two distinct claims is not a conflict. No-claim producers stay in the rejection's `Participant` list when a real conflict fires; the author's first question is "who else produces this type", and the placeholder value was the bug, not the participant row. `NoClaim.toString()` renders as a statement to that end.

### What the check still enforces, stated honestly

After this change, every producer in a group derives its claim from the same type-grain facts copied onto each leaf's `ReturnTypeRef` (`GraphitronType.ResultType.fqClassName()` for the `Plain` claim, the resolved table for the `TableRecord` claim), so the same-arm comparison over one SDL type agrees by construction. Class identity for class-backed SDL types is enforced upstream, by `RecordBindingResolver`'s per-type binding fold (`RecordBindingMultiProducer`); the reduction's remaining teeth are cross-arm (`Record` vs `TableRecord` vs `Plain`), which is exactly the projection-vs-typed-record-vs-domain-object axis the arms were built to separate. Those teeth get sharper here, not blunter: confining the mutation twin's `TableRecord` to types that resolved a table means a table-carrying `@service` mutation reached alongside a class-backed producer of the same payload still reads as the cross-arm disagreement it genuinely is (an `XRecord` and a payload object really do arrive at `env.getSource()` from the two), where before the fork every non-carrier mutation payload wore the same arm and the distinction was unavailable. The reduction's javadoc must say so and carry a `{@link}` to `RecordBindingResolver`, so the reference gate pins the linkage instead of two sites asserting the same invariant with one real enforcer.

The change is monotone on the accept side, which is worth checking rather than assuming, because it is what makes the ledger below a complete account. No producer pair that agrees today disagrees after. Walking the changed answers: `ServiceRecordField`'s `Plain(java.util.Map)` and `RecordReadField`'s `Plain(Object)` become either a real backing-class claim or `NoClaim`, and a `NoClaim` is excluded from the comparison, so a pair can only move from disagreeing to agreeing; two record-component reads of one SDL type derive from the same type-grain fact and so still agree; `RecordCompositeField`'s re-spelling only removes a disagreement; the mutation twin's `Plain` on a class-backed payload agrees with everything its old `TableRecord` disagreed with, and its `TableRecord` survives unchanged wherever a table resolved. One changed answer is a *tightening* of arm rather than a loosening and so needs checking separately: on a reflected `JooqTableRecordType` the query twin moves from `Plain(XRecord)` to `TableRecord(XRecord)`. That cannot mint a new rejection, because a new one needs a partner that agreed with the old `Plain(XRecord)`, and no producer answers that value: every leaf the plan routes over such a type carries a `ResultReturnType` and answers the same `TableRecord` through the shared rule, while the `Plain` answers that survive outside the factory cannot reach it. The twins' `ScalarReturnType` arm and the record-read leaf's `TypedColumn` answer cannot carry a `ResultReturnType` by their forks, and `ComputedField`, the one `Plain` answerer that *can* (`ExternalFieldDirectiveResolver.resolve` hands the leaf `BuildContext.resolveReturnType`'s answer verbatim, and `FieldBuilder`'s `@externalField` branch sits above its scalar/enum gate), answers `Plain(org.jooq.Field)` on every population: `ServiceCatalog.reflectExternalField` forces the reflected return to a parameterised `Field<X>`, which `peelToClassName` does not unwrap, so its answer never equalled `Plain(XRecord)` either. A DML producer's `Record(table)` disagreed with the old `Plain(XRecord)` exactly as it disagrees with the new `TableRecord(XRecord)`. So every behaviour delta is an acceptance or an arm change with no pair-level effect, and enumerating the acceptances enumerates the whole delta.

Each newly-accepted population maps to the enforcer that still covers its genuinely-broken variant. Today `Plain(Object)` never equals a real class, so any placeholder-answering producer conflicted with any real claimant:

| class-backed type also reached as a nesting projection | the unsupported jOOQ-record-carrier + nesting combination | the validator's shape-set rule over `MixedSourceReachIndex` (already exempted via `isSupportedMixedSourceReach`) |
| `@error` type reached both as an `ErrorsField` element and by another producer | a declared field on the `@error` type that no handler's source class exposes | `HandlerAccessorCheck` (`ErrorChannelWalkerError.HandlerSourceAccessorMissing`), which requires every SDL field except `path` / `message` to resolve to a `PropertyDataFetcher`-visible accessor on *every* handler's source class |

The accessor row holds at SDL wrapper depth 0 only, which bounds it more narrowly than the row alone reads. `FieldBuilder.mapGraphQLTypeToReflectType` erases any list-shaped SDL return to raw `java.util.List` before handing it to the resolver, so a component declared `[T]` is checked to be a list and its element class is not checked at all, while `RecordReadField`'s fork above claims the bound class from the leaf's `ReturnTypeRef` at every wrapper. A list-shaped record-component read of a class-backed type is therefore newly accepted with nothing vetting its element class, and it belongs in the honest gap below rather than on the row.

The `ErrorsField` row is the one migration in the sweep that is not behaviour-neutral, so it earns its own line rather than riding the never-grouped list: an `@error` type's SDL return is an Object type, so the field really does enter the grouping, and dropping its `Plain(Object)` answer really does stop it conflicting with a second producer of the same type. What that costs is bounded by the check above. The heterogeneity the errors list hands down is the safe part, because `HandlerAccessorCheck` holds every handler source class to the same field reads; a second producer is the unbounded part, and it lands in the gap below.

What remains an honest gap: a `DefaultRead`-produced object type is statically unverifiable end to end. This covers both a field on an `@error` parent returning a class-backed type and the `ErrorsField` row's second-producer half, which are the same gap under two names: an `@error` type's parent is not a `GraphitronType.ResultType` at all, so its children read through `DefaultRead` against whatever object arrives, mediated by `GraphitronType.ErrorType.accessorBaseFor`. We accept it on the same trust as every other `DefaultRead`, and a wrong developer class surfaces at run time.

The list-shaped `JavaAccessor` component named above is the second population in that gap, on the same terms: the claim is the SDL type's bound class, the wrapper erasure means nothing checks the accessor's element class, and a wrong element class surfaces at run time.

The ungrounded-object-type sub-population of `ScalarReturnType` is the third, and it is the only one where the loosening is on the reader side with no claim at all. An SDL Object type that classified as a `NestingType`, a `ConnectionType`, or a carrier the other three `ReturnTypeRef` arms do not cover has no backing class anywhere in the model, which is precisely why it fell through to that arm. Read as a record component through a non-`TypedColumn` locator it now answers `NoClaim` where it answered `Plain(Object)`, so it stops conflicting with a producer of the same type. Nothing can enforce this one: there is no class fact for a claim to be checked against, and `FieldBuilder.mapGraphQLTypeToReflectType` resolves such a type to a bare `Object.class` expected return, so the accessor check passes vacuously. The producing side is deliberately kept off this gap: both root twins and the batched child leaf keep deriving a real element on that sub-population, so it is one reader going quiet rather than the whole population dropping out of the comparison.

All three populations share the shape of the trade: the unverified fact is a single reader's, not a disagreement between two producers, so rejecting it was never something the check was measuring. Unverifiable is not disagreeing, and the placeholder's accidental rejection of any of them was not an invariant.

## Tests

Unit tier (`DomainReturnTypeCoverageTest`): `NoClaim` structural equality and `toString`; the sealed-graph walk keeps covering every leaf; the `Claim`/`NoClaim` split's permits are pinned. The two producer-answer assertions do *not* live here: hand-built leaves would bypass the derivation under test.

Mechanical fallout: threading the carrier's `TableRef` onto `ReturnTypeRef.ResultReturnType` moves its one production construction site and the eight hand-built `new ReturnTypeRef.ResultReturnType(...)` fixtures in the test tree (`DomainReturnTypeCoverageTest`, `MappingsConstantNameDedupTest`, `ErrorMappingsClassGeneratorTest`, `TypeFetcherGeneratorTest` (two), `ServiceFieldValidationTest`, `QueryServiceRecordFieldValidationTest`, `MutationServiceRecordFieldValidationTest`). Compiler-driven, but worth knowing the count up front rather than discovering it mid-change.

Pipeline tier: the reported shape, asserted positively (the coordinate classifies to the expected leaf and the shared type lands as `JavaRecordType`; absence-of-diagnostic alone can hold vacuously on a differently-broken fixture):

* `@table` parent with a batched child `@service` (`Map<XRecord, Pojo>` via a new batch method on `TestFilmService` / `TestServiceStub`) plus a class-backed parent reading the same `Pojo` as a record component: both producers classify, no `MultiProducerDomainTypeDisagreement`, and the producers' `domainReturnType()` values are the identical backing-class claim.
* Root `@service` producer plus record-component read: same assertions, pinning that the fix is not batching-specific.
* A nested backing class produced through both `RecordCompositeField` and a record-component read: pins the single-mint factory (the `bestGuess`-vs-`fromBinaryName` divergence).
* A *list-shaped* record-component read (`[Pojo]` off a `List<Pojo>` accessor) beside a producer of the same `Pojo`: pins that the claim is the element backing class at every wrapper, not the wrapper's own class. This is the population the honest-gap section admits nothing vets, so the assertion is that the claim is the element class and the pair agrees, which is what makes the gap a known one rather than an untested one.
* The root-`@service` twins over one class-backed payload: a `@service` query and a `@service` mutation both returning the same payload class classify, agree, and produce no `MultiProducerDomainTypeDisagreement`. This is the arm-level half of the same defect and fails today; assert both `domainReturnType()` values are the identical backing-class claim, not merely that no diagnostic fired.
* The root-`@service` twins over one *unbacked carrier* payload: a `@service` query and a `@service` mutation both returning the same table-backed carrier classify and both answer the identical `TableRecord` claim. This is the half of the twin symmetry that the shared rule exists for, and it is the case a factory-default `NoClaim` on the query side would have silently broken; assert the values, not the absence of a diagnostic. Pair it with the same query-carrier producer beside a DML producer of that payload and assert the `MultiProducerDomainTypeDisagreement` still fires, so the tooth this fork preserves is pinned rather than argued.
* The root-`@service` twins over one *reflected* `JooqTableRecordType`: the shape `R96RecordBindingPipelineTest.singleServiceReturn_bindsToJooqTableRecord` already classifies (a directiveless SDL object whose `@service` producer returns `FilmRecord`), reached from both roots. Assert both twins answer the identical `TableRecord(FilmRecord)`, not `Plain(FilmRecord)`. This is the sub-population that separates the table-resolved rule from an `fqClassName`-keyed one: keyed on the null, this type takes the backing-class branch and both twins mint `Plain(FilmRecord)`, which agrees but falsifies `DomainReturnType.Plain`'s "no jOOQ surface" contract and silently demotes the mutation twin's arm. Nothing else in the suite would catch that, which is why the case is listed rather than left to the carrier case's coverage.
* Existing cross-arm conflict tests (`SingleRecordTableFieldServiceProducerPipelineTest`'s DML `Record(film)` vs service `TableRecord(FilmRecord)` pair, whose `FilmListPayload` is an unbacked carrier payload and so resolves a table) keep passing unchanged: the check keeps its cross-arm teeth. Add the rule's other side as a new case in the same class: a *class-backed, table-less* payload produced by a `@service` mutation answers the `Plain` backing-class claim rather than `TableRecord`, so the rule is pinned from both directions and a future collapse back to an unconditional arm fails a test.
* An ungrounded object type (one that falls through to `ScalarReturnType`) returned by a `@service`: assert the producer still answers a real claim rather than `NoClaim`. This is the sub-population the "Which SDL returns are actually compared" section identifies as grouped despite the arm's name, and an implementer who reads `ScalarReturnType` as "SDL scalar, never grouped" would regress it to `NoClaim` with nothing failing. If a fixture for this shape proves not to be constructible at the pipeline tier, say so in the item rather than dropping the case silently: the fork's behaviour-neutrality argument is then unpinned and belongs in the honest gap.

Compile backstop: this flips a build-rejecting shape into a build-emitting one, so the newly-admitted schema reaches the emitters for the first time. Add the shared-type shape (batched `@service` producer + record-component read of one class-backed type) to the `graphitron-sakila-example` fixture surface so the emitted fetchers must compile at Java 17. No execution tier: both producers already put the same object at `env.getSource()` at run time, so runtime behaviour is not what changed.

Masked-conflict sweep: full `mvn install -Plocal-db`; any fixture newly firing the rejection was a real conflict the placeholders masked. Triage each, never suppress.

## Docs

`docs/architecture/explanation/typed-rejection.adoc` names `MultiProducerDomainTypeDisagreement` in the taxonomy tree and, in the chapter prose, enumerates the arms as "`Record(table)` vs `TableRecord(class)` vs `Plain(class)`" while describing the comparison as spanning every producer of the type. Both halves of that sentence go stale: the arm set gains `NoClaim` and the comparison is claims-only. Rewrite it. Nothing gates this (`SealedHierarchyDocCoverageTest` walks `Rejection`'s permits, not `DomainReturnType`'s), so it is a discipline check rather than a build failure. The same sentence opens by attributing the check to a roadmap item id; drop that while rewriting, since it is a transient citation of exactly the kind the reference conventions rule out.

`DomainReturnType`'s javadoc gains the `Claim`/`NoClaim` split description, and the `Plain` arm's own javadoc drops "polymorphic returns" from its enumerated populations, since the sweep moves those to `NoClaim`. `OutputField.peelToClassName`'s javadoc says it is "used by `@service`-backed permits to derive their `DomainReturnType.Plain` payload"; that stops being true of `ServiceRecordField`, so narrow it to the permits that still route through it. `QueryField.QueryServiceTableInterfaceField`'s javadoc sentence describing its answer as "`Plain` over `Object`" is rewritten with the migration; its mutation twin carries no such sentence today (its javadoc stops at "the payload is a raw `Record` / `List<Record>`"), so either leave it alone or give it the matching sentence, but do not go looking for prose that isn't there.

`OutputField.OBJECT_CLASS`'s own javadoc calls it the "Anchor for 'this permit has no concrete Java class on offer'", which is the meaning `NoClaim` takes over; after the sweep the constant survives only as `peelToClassName`'s structural fallback, so narrow the sentence to that. Leaving it is how the retired vocabulary grows back.

`MutationServiceRecordField`'s javadoc paragraph claiming non-carrier shapes "either agree or are filtered by upstream classifier rejections" is replaced by the shared `ResultReturnType` rule it now implements, with a `{@link}` to the query twin so the reference gate pins the symmetry the two leaves are supposed to hold. Give the query twin the reciprocal `{@link}` and the same fork description: the symmetry is the invariant, and a link from one side only lets the other drift.

## Retired vocabulary

* `Plain(Object)` / `Plain(java.lang.Object)` as a placeholder domain-return answer (the value survives only where it is a genuine `peelToClassName` structural fallback, never as "this producer doesn't know").
* `MutationServiceRecordField`'s unconditional `TableRecord` answer, and the javadoc claim that non-carrier `@service` mutation shapes "either agree or are filtered by upstream classifier rejections". The arm survives exactly where the leaf's `ReturnTypeRef` carries a resolved table, which is where the producer really does hand down a typed record; it is retired on every other shape.
* `ReturnTypeRef.ResultReturnType.fqClassName()`'s nullity as a proxy for "the producer hands down a typed jOOQ record". It is a statement about result-axis grounding only; the resolved table is the fact, and it is now carried.

## Adjacent, not in scope

A batched child `@service` whose leaf is an object type, sitting on a record-backed parent, drops both the parent type and the leaf type out of the model even when the leaf is independently bound and the parent can produce a valid batch key, and the only diagnostic is the generic "did not classify" on the field that returns the parent. A scalar leaf in the same position classifies fine. That is a separate defect on the classify path, not a diagnostics one, and it deserves its own item.
