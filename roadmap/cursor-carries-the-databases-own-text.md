# A connection pages wrong, or not at all, on an order column whose value Java does not carry exactly

## Goal

A connection pages through every row exactly once, forward and backward, whatever the type of the columns it is ordered on. Today that holds only for a column whose value Java carries exactly. GitHub issue #578 reports the case that broke a consumer: a table keyed on a Postgres `tstzrange` whose current rows end in `infinity`, paged in descending order, returns the same row on every `after:` request and never ends. Measured against Postgres 16, the same fault reaches further than that one type: a `bytea` key skips rows without an error, an array or composite column makes every second page a client error, and `inet`, `cidr`, `macaddr`, multiranges and any other type jOOQ reads without a binding fail every `after:` page in the database. When this lands, the cursor a page hands out names the row it was taken from to the database itself, so the next page starts after that row for all of those types.

No schema changes. The reported shape, from fs-plattform's tilgangsstyring subgraph, is a connection whose order ends in a primary key that holds the range:

```graphql
type FeideApplikasjon @table(name: "feide_applikasjon") {
  brukerdelegeringer(orderBy: BrukerdelegeringerOrderByInput): [Brukerdelegering!]!
    @asConnection
}
```

The primary key of `brukerdelegering` includes `gyldig_periode tstzrange`, and graphitron appends the primary key to every connection's order, so the fault needs no `orderBy` argument naming the range.

## What happens today

A connection cursor is a JSON array with one element per order column: the columns the page is sorted on, ending with the primary key graphitron appends so the order identifies a row. Both halves of the cursor run in Java. The emitted `ConnectionHelper.encodeCursor` reads the column out of the fetched record and writes it with `ColumnValues.toText`; `ConnectionHelper.readJsonCursor` parses the element with `ColumnValues.fromDatabase` and binds the result into jOOQ's `.seek(...)`, which renders the keyset predicate. The next page is right only when the value that comes back out of that trip is, to the database, equal to the value the row holds.

For the issue's column it is not. The row holds `["2021-01-01 00:00:00+01",infinity)`. jOOQ's `OffsetDateTimeRange` has no way to say `infinity`, so `AbstractRangeConverter` reads the bound as absent and the cursor carries `[2021-01-01T00:00+01:00,)`. Postgres orders a range ending in `infinity` before one with no upper bound, so on a descending page the predicate `(…) < (cursor…)` is true for the cursor's own row. Ascending pages on the same data happen to come out right; with `-infinity` as a lower bound the ascending direction repeats the row instead.

The measurement behind the wider claim: a scratch database with one table per column type (55 types, each with edge values), jOOQ 3.20.11 codegen over it, and the emitted `ConnectionHelper` and `ColumnValues`. For every row, in both directions: write the cursor, read it back, run the seek, and compare with the rows that should follow. With codegen's default typing 25 of the 55 types page correctly; with the `jooq-postgres-extensions` bindings applied, 31. The failures fall in four groups:

- **The next page is silently wrong.** Java's reading loses part of the value. `tstzrange` and `tsrange` with an `infinity` bound, through the extension bindings (the issue). `bytea`: the element is the array's identity text, `[B@1c32386d`, read back as the bytes of those characters, and rows are skipped. `time` with fractional seconds: jOOQ reads the `LocalTime` without the fraction. `citext` read without its binding: the seek compares case-sensitively.
- **The cursor is refused on the way back**, a client error on every second page. Every array column (`[Ljava.lang.Integer;@4aa83f4f`) and every composite column (the element is jOOQ's rendering of the record, `cast(row(1, 'a') as "probe"."pair")`).
- **The seek fails in the database**, a server error on every `after:` page. Every type jOOQ reads as `Object` when no binding is configured: `inet`, `cidr`, `macaddr`, the range and multirange types, `ltree`, `tsvector`, `pg_lsn`. The element is bound as a string and Postgres answers `operator does not exist: inet > character varying`.
- **Page one itself fails inside jOOQ or pgjdbc**, before any cursor exists: `numeric` holding `NaN`, `timestamptz` holding `infinity`, `daterange` and `numrange` with an infinite bound through the extension bindings. The cursor is not at fault here, but the order column is read only for the cursor's sake when the client did not select it.

The same oracle with the database writing the element and reading it back (`cast(column as varchar)` selected beside the row, and the seek bound as `cast(? as <the column's type>)`) pages 52 of the 55 types correctly, all four groups included. The three left over are not cursor faults: Postgres has no `<` for `hstore`, and jOOQ codegen types `bit` and `varbit` as `CHAR` and `VARCHAR`, so the cast names the wrong type and the comparison fails as it does today. Every one of the 55 types satisfies `(v::text)::<type> IS NOT DISTINCT FROM v` in Postgres, which is why the database's own text is a value the cursor can carry.

## The rule

A cursor element is the database's value, and the party that writes it is the party that reads it back.

- **Java writes and reads a column when its reading of the value is exact.** Two sets, both closed. The forms the manual promises byte for byte, because Graphitron 9 issued them: numeric, boolean, date, timestamp and timestamp with time zone. And the types whose Java value is the database's value and whose text is the database's text: character, uuid and enum columns. Nothing changes for any of these, on the wire or in the SQL.
- **The database writes and reads every other column.** The page selects `cast(column as varchar)` beside the row and the element is that text; the seek binds `cast(? as <the column's type>)`. Java never holds the value, so nothing Java cannot say (an `infinity` bound, a fraction of a second, an array, a type with no Java class) is lost on the way.

The default is the database, so a type nobody listed is carried correctly rather than approximately. This is "The database is your ally" (`docs/graphitron-principles.adoc`) applied to the one place the cursor code did the database's job for it. The first set is fixed by "Existing schemas keep working" in the same file: a cursor a client stored keeps its meaning.

## Implementation

**One predicate, in the emitted `ColumnValues`** (`ColumnValuesClassGenerator`). A public static method answering whether a column's cursor element is written by the database: `false` when `type.getSQLDataType()` is non-null and that type is numeric, boolean, character, date, timestamp, timestamp with time zone, uuid or enum; `true` otherwise, which includes every column with no SQL type. Test `isDate()`, `isTimestamp()` and `isTimestampWithTimeZone()` rather than `isDateTime()`, which also answers for `time`. It is the only place the question is asked ("Decide once, at capture", `docs/architecture/principles/development-principles.adoc`): `cursorTexts`, `encodeCursor` and `readJsonCursor` all read it, so the three cannot disagree about a column, and no emitted code outside the helpers tests it again. It stays a runtime read of the column's `DataType` rather than a fact carried from generation time, which is what "Model metadata over parallel type systems" names the cursor as its example of, and it is what lets a `method:` sort key, an arbitrary jOOQ expression the generator never classified, be handled like a column.

With the predicate in place a column with no SQL type no longer reaches `toText` or `fromDatabase`. Remove the branches the previous fix added for it (the `sql == null` arms of both, and `fromDatabase`'s `fromType().isInstance` check) together with their javadoc, unless a caller other than the cursor turns up; `readJsonCursor` is the only caller of `fromDatabase` in the generator today.

**`ConnectionHelperClassGenerator`: one projection method, and the emitted `pageRequest`.** A public static `cursorTexts(List<Field<?>> orderColumns, List<? extends Field<?>> sources)` answers the projections a page selects for its cursor: for each position `i` whose order column the predicate gives to the database, `DSL.cast(sources.get(i), SQLDataType.VARCHAR).as("__cursor_<i>")`, and nothing for a Java-written position. The predicate is asked of `orderColumns.get(i)`, the column the seek binds against; `sources.get(i)` is the expression the text is cast from, which is the order column itself everywhere except on a multi-table connection's stage 2 (see "The select lists"). The alias is positional because two order columns can share a name: a `path:` entry sorts on a related table's column. The alias text comes from one private method both `cursorTexts` and `encodeCursor` call. `pageRequest` adds `cursorTexts(extraFields, extraFields)` to `selectFields`, and does not add a database-written order column itself for the cursor's sake (it stays when the selection already holds it).

Not selecting the column is what lets a connection page on a column jOOQ cannot read at all, the fourth group above, as long as the client does not select it either. A multi-table connection is the exception (see "Not covered").

**The emitted `encodeCursor`.** For a database-written column, the element is `record.get(<alias>, String.class)` as a JSON string through `writeJsonString`, or `null` when the text is `NULL`. A record that lacks the alias is an emitter fault and should fail loudly, not fall back to the Java reading. Java-written columns go through `databaseValue` and `ColumnValues.toText` as today.

**The emitted `readJsonCursor`.** For a database-written column, a `null` element stays a typed `NULL` (`DSL.val((Object) null, col.getDataType())`), a string element (which is also how `readJsonArray` hands over a JSON number) becomes `DSL.cast(DSL.val(text, SQLDataType.VARCHAR), col.getDataType())`, and a JSON `true` or `false` is refused as `cursor token not coercible`. Checked on jOOQ 3.20.11 against Postgres: the cast renders the type's own name for everything in the probe, `cast(? as "pg_catalog"."tstzrange")`, `cast(? as int[])`, `cast(? as bytea)`, `cast(? as "probe"."pair")`, `cast(? as time(6))`, including a type carrying a binding, and `.seek(...)` accepts the cast field beside ordinary bind values.

**`readReleaseCandidateCursor` is unchanged.** A release-candidate token is the user value's `toString()`, read on the column's converted type as those releases read it. A token they could not page from (`[B@…` for a `bytea`) stays a client error, as the manual says it is; sending it to the database would turn that into a server fault.

**The select lists.** Every `pageRequest(` call site has to select the projections. `RootLauncherRenderer` (two sites) and `BatchedRowsFragments.pageRequestLocals` build their select from `page.selectFields()`, so the projections ride along; in the batched path they pass through the `ranked` derived table and the outer `select()` by name, which the nested-connection test below pins. `MultiTablePolymorphicEmitter` has two sites, the root fetcher (`buildRootConnectionFetcher`, whose stage 1 is `buildStage1ConnectionBlock`) and `buildBatchedConnectionRowsMethod`. Both pass an empty selection, and in neither are the rows a connection is built from stage 1's. Stage 1 pages the `pages` union and keeps only `__typename` and the key; the edges are the typed records stage 2 fetches per participant (`buildPerTypenameSelect`, a VALUES join on the participant's primary key), which already re-project each key column as `__pk<i>__` and each order slot as `__ord<n>__` so that `encodeCursor` reads the order values off the edge by the names the seek uses. The cursor text rides on the edge the same way, which keeps an edge's cursor a function of the element and the ordering alone:

- In connection mode the per-typename method takes the page's `extraFields` as a parameter and adds `ConnectionHelper.cursorTexts(extraFields, sources)` to its `fields`.
- `sources` holds, for each order column, the participant's own column that stage 2 already projects under that order column's name: its key column for `__pk<i>__`, its slot column for `__ord<n>__`, the `__typename` literal for the tie (character, so never cast). The emitter writes that name-to-column map per participant; the list is built from it at runtime by each order column's name, because on the root the ordering helper (`buildOrderingHelper`) chooses the order columns per request, so their positions are not known when stage 2 is generated. A name the map does not hold is an emitter fault and fails loudly.
- Stage 2 does not ask the predicate itself; it reads the answer through `cursorTexts`.
- Stage 1 is unchanged. The seek binds `cast(? as <type>)` against the `pages` column, typed by the first participant's column. The text comes from the participant's column, and the classifier's agreement rules, which are what make one column's type right for every branch, make the two one type. That agreement is the whole guarantee: the text need not come from the expression the seek compared (Filip, 2026-11-16, recorded under "Cursor encode/decode" in `docs/architecture/reference/emitter-conventions.adoc`).

**Wire bytes.** Unchanged for every Java-written column. For a database-written column the element was the Java value's `toString()` and becomes the database's text. Those are the same bytes wherever Java's text was the database's (the discrete ranges, `inet` and `ltree` through their bindings, `jsonb`), and differ for `interval`, `time with time zone` and the timestamp ranges. An outstanding JSON cursor in the old text is still read: Postgres parses `[2021-01-01T00:00+01:00,)`, `13:14:15.123456-08:00` and `+1-02 +3 04:05:06.789000000` through the cast; `CursorDatabaseTextExecutionTest` pages from one in the range's earlier text. An old element that never named a value (`[B@1c32386d`, `[Ljava.lang.Integer;@4aa83f4f`) pages as badly as it did, once, and the cursor on that page is a good one.

**Blame for a forged element narrows, on purpose.** An element Java reads is checked when the cursor is decoded, and one that is no value of its column is the client error `cursor is not valid`. An element the database reads is checked when the page query runs, so a forged or mangled one is refused there (SQLSTATE class 22) and surfaces as an unmatched exception: redacted, with a correlation id. That moves a failure below the boundary "Boundaries decode and encode; the interior is typed" wants it classified at, and it narrows what `docs/manual/how-to/error-channel.adoc` says about an invalid cursor, so it was put as a decision rather than left as residue, and ruled (Filip, 2026-11-16, recorded under "Cursor encode/decode" in `docs/architecture/reference/emitter-conventions.adoc`). The reason to accept it: only the database can tell whether the text is a value of the type, and the two ways to ask it first are both worse (see "Other solutions"). A cursor is opaque, so the client this reaches is one that edited the bytes. Base64, JSON shape, arity and every Java-read element keep the client error.

**Javadoc and conventions.** Restate the contract where it is written down: the class javadoc of `ColumnValuesClassGenerator` and `ConnectionHelperClassGenerator`, the comments above the emitted `encodeCursor`, `databaseValue` and `readJsonCursor`, and `docs/architecture/reference/emitter-conventions.adoc`. In the last, "Cursor encode/decode" gains the database-written half beside its encode and decode bullets, and "Column value binding" gets one sentence saying the cursor's database-read element is the deliberate exception to "No SQL `CAST` is rendered", since that section is about binding GraphQL input.

## User documentation (first-client check)

In `docs/manual/how-to/connections.adoc`, "Cursor encoding is part of the public contract", the last bullet of the list is replaced by two, and a paragraph follows the list:

> * A character, uuid or enum column: a JSON string of its value, an enum as its database literal.
> * Any other column: a JSON string holding the database's own text for the value, what `cast(column as varchar)` returns. The database reads it back when the next page is fetched, so the cursor names exactly the value the row holds: a range ending in `infinity` stays distinct from one with no upper bound, and an array, a `bytea` or a network address pages like any other column.
>
> Graphitron checks a cursor when it decodes it, and answers a malformed one with `cursor is not valid`. The exception is the text of a column in the last group, which only the database can read: a cursor edited so that this text is no value of the column's type fails when the page is fetched, as an unmatched exception with a correlation id.

In `docs/manual/how-to/error-channel.adoc`, both places that list "an invalid cursor" among the client errors get the same qualification in half a sentence, pointing at the paragraph above.

The section's existing sentence about a column with a jOOQ converter ("contributes its database type's value, not the converted one") stays true and needs no edit: for a database-written column the converter is simply not involved.

## Tests

The previous cursor fix argued that no execution test was needed because the cursor is column-driven and free of the dialect. Issue #578 is the counterexample: the cursor read back to the Java value it was written from, and the page was still wrong, because only the database knows whether the value it is handed equals the one it stores. This item's evidence is therefore at the execution tier, on Postgres.

**Fixtures.** In `graphitron-sakila-db`'s `init.sql`, tables whose order columns cover the four groups, each with a handful of rows chosen so that neighbouring rows differ only in what Java loses. `jooq-postgres-extensions` is already on this module's codegen classpath (it is why `region.valid_period` generates as `LocalDateRange`), and jOOQ's code generator then binds by name every type the extensions know: the range types, `inet`, `cidr`, `ltree`, `hstore`, `citext`. A fixture column is therefore typed as a consumer's with the extensions is, with no forced type and nothing written for the fixture:

- a table keyed on `(subject_id, valid_period tstzrange)` with periods ending in `infinity`, starting at `-infinity`, unbounded on each side, bounded, and `empty`. The range generates as `OffsetDateTimeRange` through the extensions' `AbstractRangeConverter`, the issue's own reading (the first group);
- two tables keyed on `bytea`, one also exposed as a multi-table participant with the other (the first group);
- a table with an `integer[]` column and a `time(6)` column carrying fractions, both exposed as sort columns (the second group and the first);
- a table with a `macaddr` column exposed as a sort column. The extensions do not bind `macaddr`, so codegen types it `Object` and the seek today binds a string (the third group);
- on that same table, a `daterange` column exposed as a sort column, with one row holding an `infinity` bound, which jOOQ fails to read through the extensions' `LocalDateRangeBinding` (the fourth group).

**The walk** (execution tier, `graphitron-sakila-example`, beside `NullSortKeyPagingExecutionTest`). For each fixture connection and each direction of its order: page with `first: 1` following `endCursor` until `hasNextPage` is false, then with `last: 1` following `startCursor`, and assert the ids seen are exactly the ids of the unpaged, ordered query, each once and in order. Connections to cover: a root connection on each fixture table; the range-keyed table as a nested connection under a list of parents, which is the batched path; and a multi-table connection over the two `bytea`-keyed tables, both at the root and nested under a list of parents. The nested multi-table form orders on the participants' first key column alone, which is why its participants are keyed on `bytea` rather than on the range. One case selects no field of the order column, and one selects it, so both select-list shapes run. On the `daterange` column the case that selects no field of it is the one expected to page; selecting it fails page one as it does today.

**The cursor's bytes** (`CursorEncodingTest`, unit tier). Every existing pin for a Java-written column passes untouched, which is the evidence that those bytes did not move; add `uuid` and an enum beside them. The "column with no SQL type" section is rewritten for the new half: the element is the record's projected text, and a JSON boolean for such a column is `cursor is not valid`. The release-candidate section passes untouched.

**The narrowed blame**, pinned so it cannot drift further: an execution test sends a cursor whose range element is `garbage` and asserts the response is the redacted, correlated error and not a page; and a cursor with bad Base64 or the wrong arity on the same connection is still `cursor is not valid`.

**`ColumnValuesTest`**: the predicate's answer for one type of each family on both sides, and the removal of the `fromDatabase` cases for a column with no SQL type. Pin as well the answer for a `citext` column's `DataType` as the extensions' `CitextBinding` produces it, since codegen binds `citext` whenever the extensions are present and the first group's `citext` case is the unbound one.

The Done gate's evidence is the walk over the range-keyed table in descending order: it is the issue's failure, it loops today, and it passes only when the row holding `infinity` is left behind.

## Where the implementation departs from the plan

- **The walk is in `graphitron`, not `graphitron-sakila-example`.** `CursorDatabaseTextExecutionTest` walks the fact scenario `cursor-database-text.graphqls` through its generated facade, every connection and case the Tests section names. `principles-architect`, consulted at take-up, pointed at `docs/architecture/how-to/testing.adoc`: generated code is tested where it is generated, and sakila-example keeps what needs the plugin path or the Java 17 compile, which the walk does not. It fails on the previous helpers in ten of its twelve cases, one in every group; the descending range walk is among them.
- **The array is the selected case.** "One case selects it" needs a GraphQL field over an order column, and of the fixture columns only `integer[]` maps to one (`[Int!]!`), so the selected walk is on that column.
- **`<deprecationOnUnknownTypes>false</deprecationOnUnknownTypes>`** in `graphitron-sakila-db`'s codegen. jOOQ marks a column of a type it has no binding for (`cursor_sort_text.mac`) `@Deprecated`, which the `-Werror` compile of the scenario's generated code rejects. The column stays typed `Object`, which is the third group.
- **A generation-time guard in `buildPerTypenameSelect`.** Order slots reaching a stage-2 select outside connection mode throw as a generator bug. No call site produces that shape; the guard keeps the slot re-projection inside the branch that owns the name-to-column map.
- **One map in stage 2, one select-side asker** (also from `principles-architect`): the per-participant name-to-column map drives both the `__pk<i>__`/`__ord<n>__` re-projection and the cursor sources, so the two cannot drift; and `pageRequest`'s merge and `cursorTexts` both read one private per-position `cursorText`, so the select side asks the predicate in one place.

## Not covered

- **`infinity` in a plain `date`, `timestamp` or `timestamptz` column, and timestamps before the common era.** They are in the promised forms, whose bytes this item does not change. Filed as R1181 (`infinity-in-a-date-or-timestamp-order-column.md`).
- **An order column the database cannot compare the way the seek needs.** Postgres has no `<` for `hstore`; jOOQ codegen types `bit` and `varbit` as `CHAR` and `VARCHAR`, so both the bind today and the cast after this item name the wrong type. Both fail on the first `after:` page as they do now, and a forced type is the consumer's remedy for the second. Refusing such an order column at build time would be its own item.
- **Oracle.** The build has no Oracle and the open-source jOOQ has no Oracle dialect, so the database-written half is verified on Postgres only. On Oracle the Java-written set covers what a key is ordinarily made of (numbers, character data, dates, timestamps); the types that move are `RAW`, the interval types and `ROWID`, and `RAW` is today's `[B@…` element there as well. jOOQ renders both casts for the dialect; a consumer on Oracle with such an order column is the first real test.
- **A multi-table connection keyed on a column jOOQ cannot read.** Stage 2 finds each participant's rows by the key values stage 1 read into Java, so a multi-table connection still reads its key columns, and its order slots as stage 2 projects them today. The database's text fixes how such a connection pages; it does not let one page on a column jOOQ cannot read, which a single-table connection gains by not selecting the column.
- **A session whose `DateStyle` or `IntervalStyle` differs between the request that wrote a cursor and the one that reads it.** The database's text for a range of timestamps or an interval is read back under the reading session's settings. With the defaults, and with any setting that is the same across the pool, text written is text read.

## Other solutions we've considered

- **Fix the range type's reading of `infinity`.** A converter that keeps `infinity` apart from an absent bound would cure the reported column, and the issue says as much. It is the binding's to fix, not graphitron's, and it leaves every other group as it is: the fault is that the cursor trusts a Java reading at all, not that this one reading is lossy.
- **The database's text for every column.** Simplest rule, and on Postgres the probe passes it. It changes the bytes of the promised forms (`2017-08-15`, not `2017-08-15T00:00:00`; `1.50`, not `1.5`), which breaks cursors clients hold and the Graphitron 9 compatibility the manual states, and on Oracle the text of a `DATE` depends on the session's NLS settings.
- **The database's text only for the types found broken.** A list of broken types is open-ended: the next binding, extension type or dialect is wrong until someone adds it. Listing the exact types and defaulting to the database fails the other way, toward a redundant cast.
- **Decide per column at generation time and emit the cast statically.** The predicate reads only the column's `DataType`, which the emitted helper already holds; a classified fact would restate it, and would not exist for a `method:` sort key.
- **On a multi-table connection, encode the edge's cursor from its stage-1 row.** That row holds the union column the seek compared, so one cast in stage 1's outer select would serve, and stage 2's `__pk<i>__` and `__ord<n>__` re-projections could go. It needs the connection class to take a cursor function that maps an edge to its stage-1 row by position, which goes against the existing rule that a cursor is computed from the element and the ordering, never from the element's place in the page, and it widens the store-rendered `Connections` class for an emitter that the classified model's retirement removes.
- **On a multi-table connection, carry stage 1's text through the VALUES join.** Stage 1 casts the union column, the VALUES rows carry the text beside the key, and stage 2 passes it through under `__cursor_<i>`. The element stays self-sufficient and the text is literally of the compared value, but it changes the typed VALUES row shape `ValuesJoinRowBuilder` builds, a larger edit than projecting from the participant's own column, which the agreement rules already make equivalent.
- **Send the element as an untyped parameter and let Postgres infer the type.** It would not need the type's name, so `bit` would work. It is a pgjdbc behaviour (`Types.OTHER`) with no jOOQ rendering and no Oracle counterpart, and it needs a custom binding in emitted code.
- **Keep the client error for a forged database-read element.** Either validate the element with a query of its own when the cursor is decoded, which costs a round trip per request and needs a connection `pageRequest` deliberately does not take, or classify a class 22 SQL error from a page query as the client's, which would also reclassify a data fault in a `@condition` or a filter argument. Neither is worth it for a cursor someone edited by hand.

## Reviewer findings

### Round 1: Spec → Ready, revisions requested (session_01FY5UvvuxCd1nhiRi5GxDaX, 2026-11-16)

Question 1 passes on the goal: read on its own it says what changes for a consumer (a connection pages every row once in both directions whatever its order columns' types; the cursor's element for a column outside the promised forms becomes the database's own text; a hand-edited element of that kind fails as a redacted server error instead of `cursor is not valid`), and the rule extends `ColumnValues` and `ConnectionHelper` on the column's `DataType` rather than standing a mechanism beside them. Every class, method, test, principle and doc section the body names exists as named. Two findings stop the plan short of something I would hand to an implementer as-is.

1. **On a multi-table connection the cursor is not encoded from the select the spec puts the projection in (question 2).** In `MultiTablePolymorphicEmitter` the rows handed to `ConnectionConstruction.build`, and so to `cursorOf(page.extraFields())`, are not the stage-1 rows of `buildStage1ConnectionBlock`'s outer select. They are the typed stage-2 records the per-typename helpers fetch by a VALUES join on each participant's own table, which project the key columns as `__pk<i>__` and the order slots under their slot aliases precisely so that `encodeCursor` finds the order values on the edge record by name. Adding the page's `__cursor_<i>` projections to the stage-1 outer select, with "nothing in the branches", leaves the alias absent on every edge record, and with the plan's own "a record that lacks the alias ... should fail loudly", every page of a multi-table connection with a database-written order column becomes a server error. The batched form (`buildBatchedConnectionRowsMethod`) has the same split, and its `ranked` derived table selects an explicit list, so a projection added only to the outer `select()` would not exist there either. The seek half is right as written: the cast compares against the `pages` column. Separately, the class has two `pageRequest(` sites (the root fetcher and `buildBatchedConnectionRowsMethod`), not three. Satisfied when the Select lists paragraph says where the text of a database-written column comes from for a multi-table edge (for instance cast in each participant's stage-2 select under the positional alias, or carried from stage 1 through the per-typename bindings) and how a participant's key or slot column maps to its position in `extraFields`, for both the root and the batched form.

   *Response (2026-11-16, at the user's direction, by the reviewing session):* Select lists revised. Both multi-table sites cast the participant's own column in stage 2 through a new shared `ConnectionHelper.cursorTexts(orderColumns, sources)`, which `pageRequest` also uses, so the predicate is still asked in one place. Positions are matched to participant columns by alias at runtime, because the root's order columns are chosen per request. Stage 1 is unchanged and the site count is corrected.
