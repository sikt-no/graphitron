# Session identity is a Java method resolved at build time, not generated SQL

`<sessionState>` names database routines as strings, and graphitron generates the call: `ConnectionRuntimeClassGenerator.functionHookImpl` assembles `{ call <fn>(?) }` and binds the payload with `cs.setString(1, claims)`, behind a generated `SessionHook` interface whose two methods are hardcoded `connect(Connection, String claims)` returning `String` and `disconnect(Connection, String handle)`.

Every problem this item was filed for is downstream of that one choice. A consumer whose routine takes a user-defined type has no way to call it, because nothing casts and the parameter arrives typed `varchar`. A consumer whose routine takes two arguments has nowhere to put the second. A consumer whose routine resolves identity in the database cannot see the result in Java, because the OUT value is captured as an opaque `String` on a private field. `<handle>true</handle>` exists as an author-declared boolean, cross-checked against a second author-declared boolean, to describe what the routine's own signature already states.

Fixing that in place means teaching graphitron to *type* a database call it generates: resolve the routine name against the jOOQ catalog, reflect parameters and directions, distinguish the value setter from the `Field` overload, distinguish an OUT parameter's generated getter from a `RETURNS` function's inherited `getReturnValue()`, handle Oracle's package-qualified naming, reject overloads it cannot disambiguate, and fail closed when jOOQ codegen emitted no routines. That is a catalog-resolution subsystem built to reconstruct type information **jOOQ codegen already generated for the consumer**, in their own module, as a typed routine class with typed setters.

So do not generate the call. Name the consumer's method in config, resolve it at build time with the reflection graphitron already does for `@service`, and emit a direct call.

## Design

The SPI is a signature contract, not a class to implement. Graphitron names a static method in config, reflects it at build time, and emits a direct call; whether jOOQ generated the method or the consumer wrote it is invisible to the resolver, because the contract is signature-shaped:

* **Public static.**
* **Exactly one seam parameter**, typed `org.jooq.Configuration` or `java.sql.Connection`, anywhere in the parameter list. The seam rule is also the overload selector: among same-named methods on the named class, exactly one must carry a seam parameter; zero or several is a build-time rejection naming the candidates.
* **Mount:** the remaining parameters, in declaration order, are the payload; the return type is the handle, `void` meaning handle-less.
* **Unmount:** the remaining parameters are either exactly the handle type or empty. Empty is legal even when mount returns a handle (a disconnect routine that clears session state takes no argument; the handle is still retained for `$session` consumers); a single parameter of any other type is the handle-mismatch rejection, naming both signatures. The return type is unconstrained and discarded, so pointing unmount at a routine that happens to return a status value is not a rejection.
* **Checked exceptions:** any declared checked exception is a rejection. `MethodRef.declaredExceptions()` already carries the fact; the rejection site is this item's to add, because the existing enforcer (`FieldBuilder.checkDeclaredCheckedExceptions`) is field-scoped, matching against a field's `@error` channels, and a session hook has neither a field coordinate nor an error channel. Unchecked propagates into the fail-closed eviction.

The contract is written to fit what jOOQ codegen already emits, because that output is not ours to change. For every routine, jOOQ generates into the consumer's `Routines` class a static executing method of exactly this shape (verified against `graphitron-sakila-db`'s generated output):

```java
// jOOQ-generated, in the consumer's own module
public static SessionHandleRecord connect(Configuration configuration, ClaimsRecord pClaims) { ... }
```

So the common case is zero hand-written Java:

```xml
<sessionState>
  <mount>com.example.db.Routines#connect</mount>
  <unmount>com.example.db.Routines#disconnect</unmount>
</sessionState>
```

The same-named `Field`-expression overloads jOOQ generates beside the executing method carry no seam parameter, so the seam rule resolves `Routines` names without a grammar for picking an overload.

When the call needs massaging (a procedure with several OUT parameters, a mount combining two calls, a payload reshaped before binding), the consumer writes a facade satisfying the same contract, and the resolver cannot tell the difference:

```java
public final class KernelIdentity {
    public static SessionHandleRecord mount(Configuration cfg, ClaimsRecord claims) {
        var call = new Connect();          // jOOQ-generated routine class
        call.setPClaims(claims);           // typed setter, jOOQ binds the composite
        call.execute(cfg);
        return call.getPHandle();
    }
    public static void unmount(Configuration cfg, SessionHandleRecord handle) { /* symmetric */ }
}
```

Graphitron reflects the named methods at build time and emits a direct call into the generated hook body. `ServiceCatalog` is already "the mirror of `JooqCatalog` for the service layer: it wraps the catalog and adds the Java-reflection logic needed to introspect service classes at build time", and `MethodRef` is already "a resolved reference to a user-provided Java method" carrying `className`, `methodName`, a javapoet `TypeName` return type off `getGenericReturnType()`, and params in declaration order. A session hook is a user-provided Java method, so this is that carrier's population, not a new one. (This is the opposite conclusion from reusing `RoutineRef`, which is a catalog handle whose params bind from GraphQL arguments and source columns; the distinction is what the thing *is*.)

Everything the item was reaching for is then a reflected fact rather than built machinery:

* **Typed payload.** The mount method's payload parameter type is whatever the consumer declared: a jOOQ `UDTRecord` for a composite, a `String` for a raw JWS, a record of their own. jOOQ does the binding, because it is jOOQ's own generated setter doing it.
* **Typed handle.** The reflected return type. Because `unmount`'s parameter is reflected too, "connect's output type matches disconnect's input type" is checked against two real signatures at build time, and the mismatch message names both. `<handle>` is deleted: its content is the return type being `void` or not.
* **Multiple arguments.** A Java signature fact. `MethodRef.params()` is already an ordered list; each reflected payload parameter becomes a contextArgument (see below), so the factory's arity grows by name-keyed slot, not by a bespoke arity mechanism.
* **Build time, not runtime.** The consumer's class is named in config and resolved during generation, so nothing is registered, nothing is dispatched polymorphically, and the emitted call site is a direct static invocation. A misnamed *routine* additionally stops needing any check from graphitron: the consumer's module does not compile. The enforcer is javac, in the module that owns the claim.
* **The facade stays static and typed.** Because the payload type is known at generation time, `Graphitron.newOwnedExecutionInput(ClaimsRecord claims, ...)` keeps its current static shape with a better type. No generics on the runtime, no move to an instance method.
* **The handle stops being opaque.** A mount that resolves identity in-database (the institution, the entitlement set, the resolved principal) returns a value service code can consume, because the value has a reflected type. The consuming surface is the `$session` argMapping sigil below; this absorbs the former companion item R640, whose contextArgument-publication premise the sigil obsoletes.

**Payload parameters are contextArguments.** Every mount payload parameter becomes a `ParamSource.Context`-sourced `MethodRef.Param`, feeding `ContextArgumentClassifier`'s existing name-keyed population as an additional root alongside every classified field's `@service`/`@condition` sites (`ContextArgumentClassifier.collectFromMethodRef` already accepts a bare `MethodRef`, independent of how the caller reached it). This is a reversal of an earlier draft of this item, which kept payload slots and contextArguments as disjoint namespaces and accepted, as residue, that a fact needed both by mount and by a `@service` method would be passed twice at the factory call site with nothing checking agreement; see "Payload/contextArgument unification reopens a closed decision" below for why that reasoning did not hold up. Under this design there is no residue: mount's payload and a same-named `@service` contextArgument are the same fact, checked once by the classifier's existing `TypeConflict` rejection (type disagreement) and otherwise unified into the one factory slot both consumers read.

There is no bundled carrier. `Graphitron.newOwnedExecutionInput` gains one ordinary contextArgument parameter per reflected payload parameter (name-keyed, alphabetical, the same population `userId`-style contextArguments already occupy). `GraphitronConnectionInstrumentationGenerator`'s generated code, exactly where it reads `CLAIMS_KEY` off `graphQLContext` today before calling `acquire`, instead reads each payload contextArgument individually, the same per-request extraction `@service` call sites already use, and passes them to `acquire`, which threads them into `sessionHook.connect(...)` in mount's own declaration order, since `Routines` renders the *database routine's* parameter order and that ordering is the generator's positional fact, never the consumer's. A mount whose only parameter is the seam contributes no contextArgument and grows the factory by nothing.

Reflection already refuses a nameless Arg- or Context-bindable parameter (`ReflectionError.ParameterNamesMissing`, thrown in `ServiceCatalog.reflectServiceMethod`/`reflectTableMethod` today whenever `Parameter.isNamePresent()` is false for a non-structural parameter), so a mount payload parameter compiled without `-parameters` fails the build through that existing gate rather than falling back to a synthesized name: a synthesized name would otherwise become the literal public factory-parameter identity, which is exactly the kind of throwaway identifier consumer-facing generated code must not carry.

**Graphitron hands over a `Configuration`, and that is load-bearing.** The `DSLContext` a carrier entry hands to fetchers carries `GraphitronTransactionProvider` on its live configuration, the transaction-demarcation seam; if a hook ran through that, "both halves run outside any transaction" would stop being structural. Because graphitron constructs what it passes, it passes a provider-free `DSL.using(connection, dialect).configuration()`, and the invariant stays structural rather than becoming a documented request. Accept a declared `Connection` parameter too, for a consumer who wants raw JDBC.

**The generated `SessionHook` interface stays, and becomes sealed.** It is generated code between generated classes, so it is not a runtime dependency; it gives `GraphitronRuntime` a field to hold and `PinnedConnection` something to call. Sealing it to permit only the generated implementation and a generated no-op makes "this is not a consumer extension point" structural, exactly as `GraphitronContext` is sealed to permit only `GraphitronContextImpl`. Its two methods take one typed parameter per reflected payload parameter (no bundled carrier) and the handle type.

## What this deletes

The whole string-named-routine path, and everything the catalog-reflection design would have needed:

* `<connect>` / `<disconnect>` / `<handle>`; `SessionStateBinding.HookBinding`, `AbstractRewriteMojo.toRawHook`.
* `SessionStateConfig.FunctionHooks`, `Unmount.PairedDisconnect`'s handle component, `SessionStateConfig.RawHook`, and the handle-agreement rules in `SessionStateConfig.from`.
* `ConnectionRuntimeClassGenerator.functionHookImpl` and `functionDisconnect`'s callable-string assembly.
* The whole settle re-fire, per the section below: `<stateSurvivesTransactions>` and its validation, `PinnedConnection`'s `remountAfterSettle` field and `afterSettle` method, and the transaction provider's settle-completion `Runnable` parameter with the `afterSettle.run()` call in its `settle`. Losing that parameter collapses the provider's two constructors into one, since the convenience constructor exists only to pass `() -> { }` for it. The provider's `priorAutoCommit` field goes too: `begin()` stops capturing it and `settle` asserts autocommit unconditionally. Also the eager single-tenant acquisition in `GraphitronConnectionInstrumentationGenerator.beginExecuteOperation` and the `graphQLContext.put(DSLContext.class, dsl)` publication it exists to feed. Release stays where it is, at operation completion.
* With the re-fire gone, so does a documented limitation: `GraphitronTransactionProviderGenerator`'s "Stated fidelity limitation of the deferred topology" says that under `ROLLBACK_ONLY` nothing settles mid-operation, so dev execution never exercises a consumer's re-fire pair. There is no longer a behavior for dev execution to be unfaithful about. That javadoc section, and the `CommitPolicy` enum javadoc's repetition of the same limit, go with the mechanism.
* Never built: routine-name resolution off the catalog, the Oracle package-qualified probe, the `Pk_Ras.Connect` schema-versus-package ambiguity, overload disambiguation grammar, the value-setter versus `Field`-overload pick, the OUT-getter versus inherited-`getReturnValue()` fork, the `<routines>true</routines>` precondition, and the `sql_routine` fact-relation question.

`SessionStateConfig` keeps three arms (`None`, `Variables`, and the method-hook arm replacing `FunctionHooks`). `<stateSurvivesTransactions>` is deleted outright rather than carried over, because the connection lifecycle below removes the question it answered. `MethodRef` already carries `declaredExceptions()` as the fact; the hook-side rejection consuming it is new (see the contract above), since `FieldBuilder.checkDeclaredCheckedExceptions` enforces a field-scoped rule this item cannot reuse.

## Unmount is optional

The shipped design rejects `<connect>` without `<disconnect>` on the grounds that "identity that mounts must unmount", and offers an empty `<disconnect/>` as an explicit opt-out whose javadoc calls it an exposure. That is too strong, and it charges every request a round trip for it.

Mount-only is sound whenever mount establishes identity *wholesale* rather than merging into whatever the connection already had, because then the mount at the start of operation N+1 overwrites everything the mount at operation N wrote. Since the same mount method runs every time, the set of state it writes is constant, so the overwrite is total by construction. Nothing can observe stale identity, because nothing reads scoped data on a pooled connection before a mount has run on it. The condition on that argument is the part worth stating rather than assuming: it holds while every reader of scoped data mounts first, which in practice means the pool is graphitron's. A consumer sharing that pool with their own DAO code, a migration tool, or an admin script has a reader that does not mount, and for them unmount is what keeps the previous caller's identity from being read. That is a property of the deployment, not of the schema, so it is the consumer's call and not something graphitron can infer.

So: `<unmount>` is simply optional. Omitting it means mount-only, with no opt-out ceremony and no rejection. This collapses `SessionStateConfig.Unmount` (and both its arms) into an optional method reference on the method-hook arm, and it removes the pairing-validation family from `SessionStateConfig.from` along with the handle rules.

Latency is the payoff: unmount costs a round trip at every release, once per pinned connection per operation. It no longer also costs at every mutation-field boundary, because the section below deletes the re-fire outright rather than halving it, so mount-only and the re-fire's removal are two independent savings rather than one compounding the other. The mount at the next acquisition is the wholesale overwrite the mount-only argument rests on.

**Correcting the record while deleting it.** `Unmount.UnmountFree`'s javadoc states that "the generation-time warning in `SessionStateWarnings` names this exposure". No such warning exists: `SessionStateWarnings.forConfig`'s `FunctionHooks` arm returns `List.of()`, and the only two warnings are `no-session-state` and `session-state-convention-fence`. The exposure was asserted in prose with nothing enforcing it, which is the shape the project's own principles call out, and it is evidence that the mount-must-unmount rule was never load-bearing in code. The stale sentence goes with the type. Separately, the `session-state-convention-fence` message text points readers at "the function-hook `<connect>`/`<disconnect>` form" and needs updating to the new element names.

**The `<variables>` sugar is untouched.** It is the one place graphitron genuinely should generate SQL, because there is no consumer method to call. Its generated implementation keeps its current shape, and every current sugar consumer, including `graphitron-sakila-example` and `SessionHookExecutionTest`, changes nothing.

## Graphitron asserts the connection's transaction mode, which is what makes the re-fire unnecessary

The shipped runtime keeps mounted identity alive across a mutation field's commit with real machinery. `ConnectionRuntimeClassGenerator`'s javadoc states why: graphitron cannot verify whether a consumer's mounted state survives a commit or rollback ("identity parked in an `ON COMMIT DELETE ROWS` temp table would not"), so the consumer declares survival with `<stateSurvivesTransactions>true</stateSurvivesTransactions>`, and undeclared, the runtime bakes `remountAfterSettle=true` and re-fires the hook pair through `PinnedConnection.afterSettle`, wired as the transaction provider's settle-completion callback.

Read against transaction semantics, the guard is redundant with a guarantee acquisition already makes. `acquire` calls `connection.setAutoCommit(true)` *before* `connect`, so the mount is always its own implicitly-committed transaction. A later `rollback()` reverts what happened inside the transaction it closes, and the mount did not happen inside it, so the mount's effect is not a candidate for reversion. A later `commit()` clears nothing. That is why the `<variables>` sugar can opt in structurally: it mounts with `set_config(name, value, false)`, session-scoped rather than transaction-local, in autocommit, and the code already documents that as surviving settles.

That line deserves naming as an invariant rather than passing as hygiene, because with the guard gone it carries the whole guarantee. The frame is ownership, not defence. Graphitron checks the connection out of the pool, holds it for the operation, and hands it back, so its transaction mode is something graphitron *asserts*, never something it inherits or preserves, and autocommit-on is the resting state every phase requires: the mount must be its own committed transaction, queries want no transaction at all rather than an idle-in-transaction snapshot pinning `xmin` for the length of a GraphQL operation, and the unmount at release must take effect immediately. Only a mutation field's own transaction wants autocommit off, for exactly its duration. What makes the assertion load-bearing rather than tidy is that session-scoped GUCs are transactional in Postgres: `set_config(name, value, false)` is `SET SESSION`, which survives a `COMMIT` but is reverted when the transaction that issued it rolls back, and `SET ROLE` behaves the same way. A mount running with autocommit off would emit its `BEGIN` lazily at the mount statement, sit in a transaction nobody commits, and be rolled back by the first failing mutation field, leaving the rest of the operation running unmounted, which under RLS is a wrong answer rather than an error. Asserting the mode at acquire excludes that before any SQL runs, where the re-fire repaired it afterwards, once per mutation, on the rollback path only. The same fact read from the other end is why `release` rolls back *before* switching the mode: JDBC commits an open transaction when autocommit is turned on, so that order is load-bearing too.

Reading the mode as asserted rather than inherited deletes a field. `GraphitronTransactionProvider.begin()` captures `priorAutoCommit = connection.getAutoCommit()` at depth 0 and `settle` restores it, as though the provider were a guest returning a connection to a mode it found. It is not, so the field is deleted and `settle` asserts autocommit unconditionally. The ground for the deletion is ownership rather than the field's current value: autocommit-on is the resting state graphitron asserts on a connection it holds, so it is what `settle` should assert after closing a top-level transaction, whatever preceded it. An earlier draft of this paragraph argued instead that the field is provably always `true` when read. That is false, and the way it fails is worth keeping, because it is the next paragraph's whole subject: the value is written by whichever provider instance opened the outermost transaction, and today one connection has several.

**One provider per pinned connection, which the carrier unification gives for free.** `dslFor` and `dslDefault` construct a fresh `GraphitronTransactionProvider` on every call (`ConnectionRuntimeClassGenerator.java:1052` and `:1070`), so a key's connection has as many providers as the operation has context resolutions, each with its own `depth` counter and savepoint stack. Two of them over one connection do not compose. Under `COMMIT`, a second provider's `begin()` sees its own `depth == 0`, captures `priorAutoCommit = false` from the transaction the first one opened, turns autocommit off again to no effect, and then its `commit()` takes the depth-0 branch and calls `connection.commit()`, committing the enclosing transaction's writes at what should have been an inner boundary. The unified per-key carrier introduced below closes that by construction: one cached `DSLContext` per key is one provider per pinned connection, `depth` is then the only nesting counter on that connection, and an inner boundary is a savepoint because that is what `depth > 0` emits. So the unification has a second justification independent of the `$session` handle it was introduced for. It imposes no new concurrency requirement, since `depth` becomes shared per key but the `Connection` beneath it was already shared per key, so the provider inherits exactly the contract the connection already carries. It also makes two provider javadoc claims true that are false in the tree today, the canonical constructor's "One instance per operation" and the class javadoc's "over the single pinned connection", both of which are repointed to one instance per pinned connection in the same change.

With the field gone, nothing reads the connection's mode as an input to preserve. Two reads survive and are a different kind of thing: `begin()`'s `ROLLBACK_ONLY` branch tests `getAutoCommit()` so that reopening at depth 0 across a deferred field boundary does not re-issue `setAutoCommit(false)`, and `release` tests it to detect a transaction the operation left open. Both interrogate state graphitron itself asserted, not a mode the pool chose. That is what makes the deletion stronger than restoring: the pool's configuration stops being an input to identity survival by construction, rather than being an input graphitron defends against.

The interesting question is whether a *consumer* mechanism can behave differently, and the item's answer is that every one that can is already broken at mount rather than at the settle. The javadoc's own example makes the point: rows in an `ON COMMIT DELETE ROWS` temp table are deleted at the end of every committing transaction, and in autocommit the mount's own `INSERT` is such a transaction, so those rows are gone before the first fetch runs, with or without a re-fire. `ON COMMIT DROP` drops the table at the end of the creating transaction, likewise immediately. `set_config(..., true)` and `SET LOCAL` revert at the end of the current transaction, which in autocommit is the statement itself. The mechanisms that do survive the mount (session GUCs, `SET ROLE`, Oracle session and global application contexts, session-level advisory locks) all survive an unrelated later transaction's outcome for the same reason the sugar does.

So `<stateSurvivesTransactions>` asks a question whose answer is "yes" for every mechanism that works at all, and the re-fire protects a failure mode that `setAutoCommit(true)` before the mount already excludes. The flag and the re-fire are deleted, and the load-bearing guarantee stays exactly where it already is, in the autocommit acquisition asserts before the mount. What replaces the declaration is not a different declaration but a documented precondition on the hook contract: mount session-scoped state, in the database's own session vocabulary. A consumer who parks identity in transaction-scoped storage has a hook that never worked, and the honest response is a contract statement, not a per-request round trip that half-hides it.

**The release point does not move, and cannot.** An earlier draft of this section had the connection returning to the pool at each transaction end, with a later fetcher re-acquiring. That is unsafe. `DSL.using(connection, dialect)` wraps the connection in jOOQ's single-connection provider whose release is a no-op, so jOOQ never gives the connection back and every fetcher holds a `DSLContext` bound to that exact `Connection` for as long as it holds the reference. Returning the connection mid-operation would leave live `DSLContext` references wrapping a connection another request had borrowed, and a fetcher issuing two queries never re-asks for a context in between, so there is no seam at which a fresh one could be handed over. Release stays at operation completion, on every path (success, error, cancellation), as today.

Two changes this item does make to acquisition, both safe because nothing holds a context before one exists:

* **Acquisition is lazy on every path.** Single-tenant stops pinning eagerly in `beginExecuteOperation` and publishing one `DSLContext` under `graphQLContext.put(DSLContext.class, dsl)`; `getDslContext(env)` pins on first demand instead, which is what `TenantConnections.dslFor` already does for the tenant-routed path. The accessor's signature does not change, so the emitters that resolve a `DSLContext` (`TenantDslEmitter.dslExpression`, `HandleMethodBody`, `ConnectionHelperClassGenerator`) keep their call sites. An operation that touches no database never pins and never mounts.
* **Per-tenant state is one carrier entry per key, not a global object beside a map of connections.** A key's entry holds that key's connection, its `DSLContext` and its handle together, minted on acquisition and discarded at release, with single-tenant as the one-key case. `ConcurrentHashMap.computeIfAbsent` already carries the one-pin-per-key contract on the tenant path (its field javadoc states it as a contract rather than an accident of the callers), and that is the pattern the unified carrier uses. This is what gives the `$session` handle a `Configuration` that exists per key, which the current per-`dslFor`-call minting does not, and it is what reduces a connection to one transaction provider, per the argument above.

The payload is retained once, by the carrier that acquires. Lazy acquisition means any fetcher may trigger the mount for a key, so that carrier holds the payload contextArguments for the life of the request, exactly as `TenantConnections` holds `claims` today; `PinnedConnection` still carries no payload field, receiving the payload as `acquire` arguments and forwarding it into `mount`.

One precondition worth stating because the model depends on it and cannot check it: identity is session-scoped state on a connection graphitron holds, so a transaction-pooling proxy in front of the database (pgbouncer's transaction mode, which resets session state between transactions) voids the model outright rather than merely complicating it, since successive transactions reach different backends. A re-fire would not have rescued that deployment either; it would have mounted identity on whichever backend the re-fire's own statement reached. Session-level pooling is the requirement, and the docs say so rather than a runtime guessing.

## The handle reaches service calls as the `$session` argMapping sigil

This absorbs the former R640, which was filed against the duplicated derivation the opaque handle forces: a connect routine that resolves identity in the database returns facts service code cannot see, contextArguments are exclusively caller-supplied, so a service wanting the same facts re-derives them from the raw claims in Java with nothing binding the two derivations. R640's shape was "publish the handle as a contextArgument", which required a second provenance in the classifier and carried four design forks. Binding the handle at the consuming site dissolves all four, so the capability ships here as part of the SPI design rather than as a follow-on.

A service binds a parameter to the handle in `argMapping`, in the grammar it already uses for "the names don't line up, bind explicitly":

```graphql
someField: [Film] @service(
  service: { className: "com.example.FilmService", method: "films" },
  argMapping: "identity: $session")
```

The sigil joins the established `$source`/`$errors` family: recognized by prefix test, stored as written, an unknown sigil rejected at parse time naming the allowed set, admission per site (`@service` `argMapping` in v1; other argMapping sites reject it naming the admitted site, the `$source` precedent exactly). GraphQL names cannot start with `$`, so the sigil is lexically disjoint from argument names by construction, and the contextArgument namespace is never involved: no factory slot, no classifier provenance, no publication name to choose. Publication-as-asked-for is satisfied by each use being the ask.

The bound parameter becomes a structural `ParamSource` variant, the pattern `DslContext`/`Sources`/`Table` already set: supplied by the generator, filtered out of `callParams()`, its emit-time extraction reading `dsl.configuration().data(KEY)` off the same `DSLContext` local the call site already resolves (forcing that local to be declared when it otherwise wouldn't be). That read placement is what dissolves R640's forks:

* **Ordering.** Mount runs on a connection as part of acquiring it, before any SQL on that connection, so a service call holding a key's `DSLContext` always reads a mounted handle. Lazy acquisition does not weaken this: the `DSLContext` cannot exist before the mount that produced its entry. No "not yet mounted" runtime state.
* **Staleness.** The handle lives in the per-key carrier entry beside the connection that produced it, and that entry's `Configuration` exposes it on jOOQ's per-`Configuration` `.data()` map. Because the entry is minted at mount and discarded at release, the handle and the connection it describes are created and destroyed together, so a handle cannot outlive its connection and never has to be overwritten in place. With the re-fire deleted there is exactly one mount per entry, so the handle is written once and read many times. Nothing is written into request scope and left to rot.
* **Fan-out is semantics, not a rejection, because the read is per-key-carrier.** R640's load-bearing scope call was that N tenant connections mean N handles and one request-scoped contextArgument slot cannot represent them; its answer was to reject fan-out plus publication. The generated call site resolves its `DSLContext` through `TenantDslEmitter.dslExpression`, which under the unified carrier resolves a key's entry on both paths (single-tenant being the one-key case), and reads the handle off that entry's `Configuration`. A fetch running under a tenant reads *that tenant's* handle because it is reading that tenant's carrier, not because of any implicit locality claim. Per-tenant identity is not an edge case; it is the read location doing the scoping. This is the half the earlier draft got wrong: it pointed the read at a `Configuration` that the tenant path minted fresh on every `dslFor` call, so there was no per-tenant object to have written a handle onto. Caching the `DSLContext` in the key's carrier is what makes the claim true by construction.
* **Type agreement** is the reflection family again: the bound parameter's declared type against mount's reflected return type, rejection naming both. `$session` against a `HandleLess` mount is a located rejection: the mount returns `void`, there is no session handle to bind.

The accepted cost is a new kind of cross-artifact edge: SDL that uses `$session` builds only against a `<sessionState>` whose mount returns a handle, so the schema is less self-contained than one that smuggles identity through re-derivation. That coupling is real (the service genuinely consumes deployment-produced identity), and the sigil makes it visible and located; the rejection message when the config side is absent has to carry the whole story, naming the field coordinate, the sigil, and the missing config.

## Implementation

* **Config.** Replace `<connect>`/`<disconnect>` with `<mount>`/`<unmount>` taking `fqcn#method`, `<unmount>` optional. Delete `<stateSurvivesTransactions>` and every rule that reads it, since the per-acquisition mount removes the question it answered. Drop the handle rules and the pairing rules, and collapse `Unmount` into an optional method reference. An `<unmount>` with no `<mount>` stays a rejection: unmounting what nothing mounted is a defect in either direction of reading it. The authored facts reduce to the two `fqcn#method` strings; the general "no method-hook configured at all" guard is unrelated and stays. How the reflected signatures relate to the fact store is an open question this item has to answer, not assume; see the review finding below on the census.
* **Resolution.** Reflect both methods through `ServiceCatalog`'s existing Java-reflection path into `MethodRef.StaticOnly` (already the variant for "static-by-construction method references"). `ServiceCatalog` stays the only holder of raw `java.lang.reflect` and of the seam-type test, per the capture-boundary containment invariant; no session-package reflector. Overload selection extends the one existing resolution point (`ServiceCatalog.pickMethod`) with the seam filter as an explicit input, so `ReflectionError.AmbiguousMethod` stays the single ambiguity vocabulary and "zero or several seam-carrying candidates" is a variant in the same family, naming the candidates; a second session-hook-local resolver is exactly the two-answers drift the principles warn about. The resolved carrier is the new method-hook arm itself (the one replacing the deleted `FunctionHooks`), the record that takes over `FunctionHooks`' structural position one level above the doomed `Unmount` hierarchy. With `<stateSurvivesTransactions>` deleted there is no orthogonal flag left to house, so the arm *is* the handle-axis fork rather than a record wrapping one: a `Handled` arm (mount, handle `TypeName`, optional unmount) and a `HandleLess` arm (mount, optional unmount). "Handle-less implies unmount takes nothing, implies the pinned carrier has no handle field, implies the `SessionHook` unmount method takes only the connection" stays structural on that fork, and every emit site switches once on the arm instead of re-testing the return type for `void`. This is the same property `SessionStateConfig.Unmount`'s sealing carries today ("a handle produced by connect that no disconnect binds" is unrepresentable), moved from declaration to reflection along with the fact itself. Rejections are the existing reflection family (`ReflectionError`, unresolvable class or method, non-static, no seam parameter or more than one candidate, seam-overload ambiguity naming the candidates, handle-type mismatch between the two signatures, `ParameterNamesMissing` on a nameless payload parameter, declared checked exception); a payload parameter's name colliding with an existing contextArgument is not a rejection of its own, it is `ContextArgumentClassifier`'s existing `TypeConflict` when the types disagree and a unified slot when they agree.
* **Emission.** `functionHookImpl` becomes a direct-call emitter, `SessionHook.connect`'s own generated body: it takes its already-typed payload parameters (supplied by its caller, see `PinnedConnection` retyping below) and forwards them into mount's call in mount's own declaration order: `return com.example.db.Routines.connect(cfg, claims);`. It never reads `graphQLContext` itself, the same shape the current hardcoded `connect(Connection, String claims)` already has. The generated hook builds its own provider-free `Configuration` from the connection and the runtime's dialect, or passes the raw `Connection` when that is what the method declares.
* **Interface.** `ConnectionRuntimeClassGenerator.sessionHook` emits a sealed `SessionHook` typed by one parameter per reflected payload parameter (no bundled carrier) and the handle type, permitting the generated implementation and a generated no-op replacing the current anonymous `NONE`.
* **The pinned carrier retypes, and the per-key carrier becomes the one acquisition seam.** `PinnedConnection` carries no payload field: `acquire` takes the reflected payload parameters directly (typed, one per parameter) and passes them straight into `sessionHook.connect(...)`, retaining only the handle field, which takes the reflected handle type. It keeps asserting autocommit before mount and failing closed by evicting on a throwing mount, and it loses `remountAfterSettle` and `afterSettle` entirely. That assertion is not optional cleanup once the re-fire is gone: it is the invariant the deletion rests on, so it stays, and `release` keeps rolling back before switching the mode. What does change is how the code says it. "Normalize" and "restore the prior autocommit" are retired here, and the phrasing is not confined to one comment: it runs to roughly eleven surviving sites across `ConnectionRuntimeClassGenerator` (class javadoc, the `acquire` and `release` comments) and `GraphitronTransactionProviderGenerator` (class javadoc, `begin`'s deferred-rollback comment, `rollback`'s top-level comment, `settle`'s javadoc), five of them javadoc *emitted into generated output* on `SessionHook`'s two methods and on `acquire` itself, so a consumer reading the generated source reads the retired framing. All of it is rewritten to the assertion: graphitron asserts autocommit on a connection it owns, and the comment states what that excludes. The sites that merely describe the re-fire seam (the `afterSettle` field javadoc, the canonical constructor's, the callback comment in `settle`) die with the mechanism instead. The payload is held for the request by the per-key carrier that performs lazy acquisition, the role `TenantConnections` fills today (holding `claims` for exactly this reason), now unified across both paths with single-tenant as the one-key case: an entry is `(connection, dsl, handle)` minted together on acquisition and cleared together on release, so `acquire` is called from one place and every mount, first or subsequent, runs on the path that already holds the payload. Mount's return value is written to the entry's two readers, never one derived from the other: the pinned carrier's handle field, which release reads to call `unmount`, and the entry's `Configuration` `.data()` slot the `$session` sigil reads. `CLAIMS_KEY` is deleted outright rather than replaced: `claims` is now an ordinary contextArgument with its own name-keyed entry, read where the instrumentation used to read `CLAIMS_KEY` and handed to the carrier at construction.
* **Facade.** `newOwnedExecutionInput` gains one ordinary contextArgument parameter per reflected payload parameter, in the same alphabetical, name-keyed population every other contextArgument already occupies; there is no separate leading block and no collision rejection to add, since a same-named collision is `ContextArgumentClassifier`'s existing `TypeConflict` check. Javadoc is emitted from the same resolved facts.
* **Sigil.** `$session` cannot tokenize through the shared `GraphQLSelectionParser.parseEntries` (`Lexer.readVariable` yields `TokenKind.VARIABLE` for any `$`-prefixed text, and `parseEntries` hard-rejects a value token that is not `TokenKind.NAME`), and `parseEntries` is shared with `GraphitronFactCapture`'s eight argMapping/columnMapping call sites (`GraphitronFactCapture.java:349,383,424,461,591,602,660,697`, all through its `pairs` helper), so the fix cannot live there. Instead `ArgBindingMap.parseArgMapping` peeks each entry's raw RHS text for a `$`-prefix before delegating to `parseEntries`, the same raw-string-seam shape `FieldSourceSigil` already uses for `$source`/`$errors`; this is local to the one caller and changes nothing `parseEntries` or its other callers rely on. A recognized `$session` is admitted at the `@service` site only and lowered to a new structural `ParamSource` variant. Its call-site extraction reads `dsl.configuration().data(KEY)` off the `DSLContext` local the call site resolves via `TenantDslEmitter.dslExpression` (forcing that local to be declared when a field's argMapping uses `$session`, even if nothing else on the call needed one), never off `graphQLContext`. Rejections, all located: unknown sigil naming the allowed set (existing pattern), `$session` at a non-admitted argMapping site naming the admitted one, `$session` against a `HandleLess` mount, `$session` with no method-hook `<sessionState>` configured (the message names the field coordinate, the sigil, and the missing config), and bound-parameter type not satisfied by the reflected handle type, naming both. Scope for this item: `$session` is wired into the classifier and the diagnostics it raises; whether it also becomes an argMapping completion suggestion (`FieldSourceSigil`'s completions arm) is a small, non-gating follow-up, since it is one more entry in an existing admitted-sigil list rather than a new mechanism.
* **Census.** A `<mount>`/`<unmount>` reference is reflection-only, outside the classpath census: `ClasspathScanner.readIfCandidate` deliberately drops the consumer's jOOQ output package, and admitting the routine surface would grow the `jvm_` fact relations for no present consumer. The scanner's javadoc enumerates why jOOQ classes are excluded ("referenced through `@table`/`@reference`, not `@service`"); this item adds a third referencing mode, so that enumeration is repointed in the same change rather than left standing as a narrower truth.
* **Two declaration-forcing meta-tests need their registries edited.** `RejectionResidueDrainageTest` spells `ReflectionError`'s leaves individually, and `RejectionSeverityCoverageTest` walks `Rejection`'s permits for an LSP severity mapping; the new seam-related `ReflectionError` variants (no/several seam candidates, seam-overload ambiguity) fail both until their hardcoded declarations are updated. Both fail loudly at build time, so this costs a round trip, not correctness, but it belongs in the implementer's checklist rather than a surprise.
* **Two prose corrections that ship with the code, not before it.** `Unmount.UnmountFree`'s javadoc claims `SessionStateWarnings` warns about an unmount-free configuration; it does not, and which way that resolves depends on this item's unmount decision (delete the claim if unmount becomes optional, add the warning if it does not), so the edit belongs here rather than as a standalone comment fix. And `SessionStateWarnings`' `session-state-convention-fence` message directs readers to "the function-hook `<connect>`/`<disconnect>` form with a SECURITY DEFINER connect"; that text is accurate against today's elements and becomes wrong the moment they are renamed, so it is repointed in the same change that renames them.
* **Fixture and execution coverage.** The form has never run end to end: `graphitron-sakila-example` configures the `<variables>` sugar at the plugin level; four of the five `rewrite-generate*` executions inherit it, and `rewrite-generate` itself repeats an identical block rather than inheriting (redundant, not a divergence, but worth trimming when this item is in the file), so all five generate the same sugar implementation today. `SessionHookExecutionTest` drives the sugar, and no mount/unmount routine exists in `graphitron-sakila-db`. Add a composite payload type, a composite handle type, and the two routines to `init.sql`, plus a fixture class whose static methods call them through their generated routine classes. Prove the round trip against real PostgreSQL with RLS, in the shape `SessionHookExecutionTest` establishes: RLS-scoped reads see only permitted rows, a mutation's post-commit read-back still does (now because the read-back's connection was acquired and mounted, not because a re-fire kept the old one alive), identity is absent after unmount, and a throwing mount fails closed.

## Trade-offs to accept explicitly

* **The contract is a convention to learn, but the common case is zero hand-written Java.** `<mount>Routines#connect</mount>` names jOOQ's own generated method; the consumer writes a facade only when the call needs massaging, and the facade is those ~6 lines of their own generated jOOQ API, typed and reviewable in their own module. What replaces the deleted resolution subsystem is a signature convention (one seam parameter, the rest is payload, return is handle), and it is the convention `@service` already teaches. The zero-code path for the common Postgres case, the `<variables>` sugar, also still exists.
* **Factory arity grows with the payload, but a shared fact enters once.** Mount payload parameters are ordinary contextArguments (see Design), so a per-request fact the mount needs and a `@service` method also wants is one factory slot, not two, with type disagreement caught by the classifier's existing `TypeConflict` rejection. Arity still grows with the payload's parameter count; a consumer drowning in slots can always bundle, since `mount(Configuration cfg, MyRequestIdentity bundle)` is one slot by the same contract. A growth-proof named surface over the factory (a staged builder) would apply to contextArguments generally, predates this item's additions, and belongs to a separate Backlog item rather than being absorbed here.
* **A connection goes back to the pool in autocommit-on, whatever mode it was handed out in.** That is the price of asserting the mode instead of restoring it, and it is worth stating rather than discovering: with `priorAutoCommit` deleted, both `release` and `settle` leave autocommit on, so a pool configured `autoCommit=false` gets its connection back in a mode it did not lend. Every pool graphitron is plausibly deployed behind already resets the flag against its own configuration when a connection is returned or re-checked-out (HikariCP tracks the dirty flag and resets on `close()`; DBCP and Tomcat JDBC reset against `defaultAutoCommit`), so the observable cost is nil. What is bought is that no code path in the runtime has to know what the pool wanted, which is what makes identity survival independent of pool configuration by construction rather than by defence.
* **The dev goal and MCP `execute` tool need a payload.** `<devDatabase><claims>` supplies one string, which works unchanged for the sugar and for any `String`-payload method. A custom payload type cannot be built from a string by graphitron. Recommendation: support string payloads and the sugar, and degrade with a message naming the limitation, rather than requiring consumers to write a parse method for a dev tool's benefit. Whether a payload is string-constructible is resolved onto the reflected `MethodRef` facts at build time and read by the dev goal, not re-derived at the dev-goal site.

## Design decisions closed at Spec → Ready review

* **Config grammar.** Keeps `<mount>com.example.KernelIdentity#mount</mount>`, not a `<class>`/`<method>` pair. `ExternalCodeReference` (the SDL-level convention for naming a Java class and method, used by `@service`/`@condition`/`@externalField`/`@enum`) splits them into separate `className`/`method` fields, but `<sessionState>` is Mojo XML config, not an SDL input type, and its immediate local precedent, the `<call>Pk_Ras.Connect</call>` single-string form it replaces, is compact. The `#` form the spec already uses throughout Design, Implementation, and the user-doc draft is consistent with that local precedent and needs no rewrite.
* **Whether the methods must be static.** Static-only (`MethodRef.StaticOnly`) for v1, as the Design and Implementation sections already commit to throughout. A session hook holds no state worth injecting, so there is no case pulling toward `MethodRef.Service.callShape()` yet; add instance support via a fresh Backlog item if a real consumer needs it.
* **Where the payload parameter sits relative to the connection.** Detect the seam parameter by type, not position: exactly one declared parameter typed `Configuration` or `Connection`, anywhere in the parameter list; zero or more than one match is a reflection rejection naming the method. This avoids a positional convention a consumer has to remember, and it costs nothing extra to implement since the reflection walk already has to inspect every parameter's type to build `MethodRef.params()`.

## Design decisions closed at the SPI revision

A design pass on the SPI shape, prompted by the observation that this is a mapping problem over methods the consumer already has, closed these:

* **The SPI is a signature contract, not a facade class.** jOOQ's generated `Routines` executing methods satisfy the contract as-is, so the primary documented path is naming them directly, and the hand-written facade demotes to the escape hatch. The contract is written to fit jOOQ's fixed output, not the other way around; the resolver never learns whether a method was generated or hand-written, which is what makes the two paths one path.
* **Overload selection is the seam rule.** jOOQ emits same-named `Field`-expression overloads beside every executing method, so overloading is the normal case, not a corner. Exactly one same-named method may carry a seam parameter; ambiguity is a rejection naming the candidates, raised through `ServiceCatalog.pickMethod`'s single ambiguity vocabulary. No grammar for naming a specific overload.
* **Declaration order survives only inside the emitted call into mount.** Payload parameters are name-keyed contextArguments and sort alphabetically like every other contextArgument slot, so regenerating `Routines` after a database-side parameter reorder cannot silently reorder factory slots under a still-compiling caller; the generator preserves mount's own declaration order only at the one call site that has to invoke mount positionally.
* **A `<mount>` reference is reflection-only, outside the classpath census.** `ClasspathScanner` deliberately drops the jOOQ output package, so the census, the store's `jvm_` relations, and the LSP will not see a routine-class method that reflection resolves fine. Admitting the routine surface would grow the census for no present consumer; instead the exclusion stands, and the scanner's javadoc enumeration of referencing modes is repointed in the same change so it does not remain as a narrower truth.
* **The former R640 is absorbed, redesigned from contextArgument publication to the `$session` sigil.** Publication needed a second classifier provenance and four open forks (availability ordering, mid-operation staleness, fan-out scope, opt-in surface); binding the handle at the consuming site dissolves all four, with fan-out inverting from a build-time rejection into per-connection semantics. `$session` stays lexically disjoint from argument and contextArgument names by construction (GraphQL names cannot start with `$`), independent of whether the payload side is unified with contextArguments or not.

## Gaps closed following the Spec → Ready rework

Three gaps were found between the plan and the tree at the last Spec → Ready pass, each checked against the code rather than reasoned from the plan. All three are resolved below, and folded into Design/Implementation/Tests above rather than left standing here as a separate account.

1. **`$session` cannot reach a prefix test at the argMapping seam.** `Lexer.readVariable` always yields `TokenKind.VARIABLE` for `$`-prefixed text, and the shared `GraphQLSelectionParser.parseEntries` hard-rejects any value token that is not `TokenKind.NAME`, so `argMapping: "identity: $session"` fails inside `ArgBindingMap.parseArgMapping` before any sigil logic runs. `parseEntries` is shared with `GraphitronFactCapture`'s eight argMapping/columnMapping call sites (`GraphitronFactCapture.java:349,383,424,461,591,602,660,697`, all through its `pairs` helper), so teaching the parser itself to accept `VARIABLE` values is not local. Resolved in favor of the narrow fix: `parseArgMapping` receives the raw string before tokenization, so it peeks each entry's RHS for a `$`-prefix and short-circuits into sigil handling before delegating to `parseEntries`, the same raw-string-seam shape `FieldSourceSigil` already uses for `$source`/`$errors`. Reflected in the Implementation § Sigil bullet and a `parseEntries`-non-regression row in Tests.

2. **The `$session` read route was unnamed, and the fan-out claim as stated was false.** The request-scoped slot published today, `graphQLContext.put(DSLContext.class, dsl)`, is a single slot per request; reading a handle from it would silently reintroduce the one-slot shape the absorbed companion item's fan-out fork was rejected for. Resolved: the handle is stashed on the resolved `Configuration`'s own `.data()` map (jOOQ's per-`Configuration` key-value store) at mount/re-mount time, and `$session` extraction reads that same key off the `DSLContext` local the generated call site already resolves via `TenantDslEmitter.dslExpression`, the identical expression the fan-out scatter path uses to mint its per-tenant contexts. That read is genuinely per-connection, so the per-tenant claim holds by construction. Reflected in Design (the `$session` bullets) and Implementation § Sigil, with an Execution-tier test proving two tenants read two distinct handles in one operation. **Superseded:** the resolution was wrong about the tenant path, which mints a fresh `Configuration` per `dslFor` call, so there was no per-tenant object to write onto. The read now resolves a per-key carrier entry that owns its `DSLContext`; see the per-key carrier bullet under "Graphitron asserts the connection's transaction mode".

3. **Superseded: `<stateSurvivesTransactions>` lost its home when `Unmount` collapses.** The flag is deleted outright, so the question of where it lives is moot; the account below is kept only because the acceptance-case flip it describes is now a deletion instead. Original text: The flag lives today on `Unmount.PairedDisconnect`, which this item deletes; it is orthogonal to the new `Handled`/`HandleLess` handle-axis fork, so it cannot move into either arm without duplicating it or forcing a meaningless default on the other. Resolved: the flag sits on the new method-hook arm itself (the record replacing the deleted `FunctionHooks`, one level above the handle-axis fork). `SessionStateConfig.from`'s rejection requiring a paired disconnect before the flag can be declared is deleted along with it, since a mount-only hook now re-fires as a single re-mount and can legitimately opt in to survival; `SessionStateConfigTest.stateSurvivesTransactions_withUnmountFreeOptOut_rejected` flips from a rejection pin to an acceptance case. Reflected in Implementation §§ Config and Resolution, and in Tests.

Smaller, non-gating notes from the same pass, also folded in above: `RejectionResidueDrainageTest` and `RejectionSeverityCoverageTest` need their hardcoded leaf declarations updated for the new `ReflectionError` seam variants (Implementation § Census, Tests); `$session` participates in the classifier and diagnostics for v1, with argMapping completions for it scoped as a small non-gating follow-up (Implementation § Sigil); and the fixture note about `graphitron-sakila-example`'s five executions is corrected to "four inherit the plugin-level sugar block, one repeats it identically" (Implementation § Fixture and execution coverage).

## Payload/contextArgument unification reopens a closed decision

The SPI revision's "Name binding to contextArguments was considered and folded" decision (an earlier draft of this section) is reversed: mount payload parameters are ordinary contextArguments, not a disjoint namespace, per Design above. The folding reasoning does not survive scrutiny against the codebase's own precedent: its strongest ground was that "an unrelated SDL edit adding a contextArgument could re-route an identity-mount input by name coincidence, on the wrong side of the integrity gradient", but this is exactly how contextArguments already work between arbitrary `@service`/`@condition` sites today, `ContextArgumentClassifier` unifies same-named entries from unrelated directive sites all the time, guarded by the same `TypeConflict` rejection this design now reuses for the payload side. Treating that coupling as intolerable specifically for mount-to-contextArgument binding while accepting it everywhere else in the same classifier was inconsistent, not a genuine risk the fold avoided.

Mechanically the reversal is a small extension, not a restructuring: `ContextArgumentClassifier.collectFromMethodRef` already accepts a bare `MethodRef` and does its dedup/type-agreement reduction independent of how entries arrived, and `GraphitronSchema`'s constructor, which already calls `ContextArgumentClassifier.classify` over classified fields, has the resolved `SessionStateConfig` (and its mount `MethodRef`) in scope at the same call site. `GraphitronFacadeGenerator` consumes the population as an opaque `List<ResolvedContextArg>`, so the merge is transparent downstream of the classifier.

The reversal also deletes machinery this item had drafted and never needed to build: the bundled carrier record (Design, Implementation §§ Emission/Carrier record/Facade in earlier drafts), the dedicated "payload slot" factory block and its ordering discipline separate from contextArguments, and the payload-name-collides-with-contextArgument rejection, replaced by the classifier's existing `TypeConflict`. It also resolves the "fact can enter twice" trade-off this item had accepted as residue: a payload fact a `@service` method also wants is now one slot, supplied once, not two.

**`-parameters` is not new machinery either.** `ReflectionError.ParameterNamesMissing` already exists and already fails the build today for any Arg- or Context-bindable parameter reflected without a real name (`ServiceCatalog.reflectServiceMethod`/`reflectTableMethod`, gated on `Parameter.isNamePresent()`); a mount payload parameter, now Context-sourced, inherits this gate automatically. What the earlier carrier-record draft would have needed, a synthesized-name fallback for a missing `-parameters` flag, is precisely what this reversal makes unnecessary and wrong: a synthesized name would have become the literal public factory-parameter identity, not just an internal record field name, which is worse under unification than it would have been under the disjoint design.

## Gaps found at the second Spec → Ready pass

Held in Spec at a second independent review. Every claim below was checked against the tree, not reasoned from the plan. None of them is an ownership question: every generated class named here is graphitron's own, with no consumer contract, so its shape is free to change. What is not free is when a given piece of generated code runs, and which object a read lands on.

Two of the findings were about the settle re-fire and the `$session` read route, and both are resolved above by deletion rather than by routing. For the record, since the resolution replaced the mechanism instead of fixing it:

* The re-fire's route contradicted itself. `afterSettle` is reached only through the transaction provider's callback slot (`ConnectionRuntimeClassGenerator.java:1052` and `:1070`, `pinned::afterSettle`), fired from inside jOOQ's settle, while the instrumentation's generated code ran once at `beginExecuteOperation`, so nothing was executing at settle time to "re-read the values off `graphQLContext`"; and `acquire` opens a connection from the `DataSource` (`:406`), so "calls `acquire` again" would have pinned a second connection rather than re-mounting. Moot now that there is one mount per acquisition and no callback.
* Under fan-out there was no per-tenant `Configuration` to stash a handle on. `dslFor` cached the `PinnedConnection` but minted a fresh `DSLContext`, hence a fresh `Configuration`, on every call (`:1051-1052`), as did `dslDefault` (`:1069-1070`), so a key had as many `Configuration`s as it had calls, mount held none of them, and the settle callback could not reach the ones already handed out. The per-key carrier entry owning its `DSLContext` is what makes the per-tenant claim true by construction.

A third correction belongs here because it was the reviewer's own, not a gap in the item. An earlier version of this section deleted the re-fire by moving the release point to each transaction end, so that a later fetcher would re-acquire and re-mount. That is unsafe and the rewritten section says why: fetchers hold a `DSLContext` bound to one `Connection` that jOOQ never releases, so returning it mid-operation dangles live references, and a fetcher issuing two queries never re-asks for a context in between. The re-fire's deletion rests on transaction semantics at the mount instead, which needs no lifecycle change at all.

The findings below are open, and none of them is affected by any of this.

1. **§ Census forecloses § Config's derived views, and the unification lands on the drained walk without saying so.** Two connected problems, both about where the reflected facts live.

   § Config used to answer the fact-family boundary in store vocabulary, saying the reflected signatures, payload and handle types "are derived views, never stored back". That sentence is now marked as an open question rather than an answer, because the answer it gave cannot hold. A derived view needs base rows, which would be `jvm_method` and `jvm_method_parameter`. But `jvm_class`'s own comment states its filter as "public, non-synthetic, top-level ... and outside the generated jOOQ package", and § Census deliberately keeps that exclusion, on the grounds that admitting the routine surface "would grow the `jvm_` fact relations for no present consumer". The headline path is `Routines#connect`, inside the excluded package, so there are no base rows and the derived view cannot exist. The two bullets have to be reconciled. `jvm_method_parameter`'s comment points at one way: "which `ParamSource` a parameter binds to is decided per directive application, not per method, so it is a derived relation keyed by the application coordinate and lands with its first consumer." A mount payload parameter is a candidate first consumer for exactly that relation, which would mean the census admits the named mount and unmount classes rather than excluding them, the first-reader principle working as designed. The other way is to drop the derived-view framing and state that reflection stays a Mojo-side step for now, with the debt named. Either resolves it; leaving both bullets standing does not.

   Second, the payload/contextArgument unification is an extension of the transitional walk, and the item presents it as a virtue rather than as debt. `ContextArgumentClassifier` runs from `GraphitronSchema`'s constructor over the leaf model (`GraphitronSchema.java:245`), so adding mount as "an additional root" extends a walk-side registry, which `docs/architecture/explanation/pipeline-overview.adoc` calls "a surface being drained, not a place to extend", with new facts landing only in the store. During the window the emitters still source from the walk, so a capability that has to reach `GraphitronFacadeGenerator` has nowhere else to land today, and the extension may well be the right call; what is missing is that "Mechanically the reversal is a small extension, not a restructuring" reads as if the walk were the destination. Say which surface the population is expected to end up on, and name the debt if it lands on the walk first.

   Where the reflection step itself runs is still unstated, and the three facts as named do not compose. `GraphitronSchema` never references `SessionStateConfig`. The config is built at the Maven seam (`AbstractRewriteMojo.java:497`) and arrives as a `RewriteContext` component (`RewriteContext.java:101`), an input to the builder, so it exists before any reflector does: `ServiceCatalog` is package-private in `no.sikt.graphitron.rewrite` (`ServiceCatalog.java:45`) and is constructed only inside `GraphitronSchemaBuilder`, from a `BuildContext` needing the assembled `GraphQLSchema` and a `JooqCatalog` (`GraphitronSchemaBuilder.java:171-173`). So "the resolved carrier is the new method-hook arm itself", built at the Mojo seam and carrying `MethodRef`s reflected through `ServiceCatalog`, cannot hold as stated, and the containment invariant the item cites rules out widening `ServiceCatalog` to make it hold. Which stage resolves follows from how the first two questions are answered, so it is the same decision, not a third one.

   Adjacent, and the author's call whether it is an edge or a note: R612 is at `Ready` and now carries the whole Maven-config family, "every parameter the build supplies is transcribed as provenance", so the authored `<mount>`/`<unmount>` strings are its rows, and this item renames the elements it will transcribe. `depends-on:` is empty.

2. **A `$session` argMapping quarantines in fact capture, losing that field's mapping facts.** Implementation § Sigil says the `parseArgMapping`-local pre-scan "changes nothing `parseEntries` or its other callers rely on". `GraphitronFactCapture.pairs` (`GraphitronFactCapture.java:866`) is a caller that relies on `parseEntries` accepting valid SDL: it catches the parse failure, writes a `graphitron_undecoded_argument` row (`GraphitronFactCapture.java:984`), and returns `List.of()`, so a `@service` field using `$session` loses *every* pair of its argMapping from `graphitron_service_arg_mapping_pair` and gains a row in the relation whose own comment calls it "the tolerant-decode overflow ... the malformed-literal detection has its row" (`graphitron-model.sql:1969`). The `$source`/`$errors` precedent does not cover this: those sigils live in `@field(name:)`, read as a free-form string through `BuildContext.argString`, and never reach `pairs`. Either the capture side learns the sigil in the same change, or the fact-store cost is accepted explicitly as a named trade-off.

3. **Sealing the generated `SessionHook` needs a shape decision this item does not make.** `SessionHook` and `GraphitronSessionHook` are two separate top-level generated types in the same package (`ConnectionRuntimeClassGenerator.java:143-145`, both `ClassName.get(schemaPackage, ...)`; both files present under `graphitron-sakila-example/target/generated-sources/`). `graphitron-javapoet` cannot emit a `permits` clause, and the cited `GraphitronContext` precedent gets away without one only because its implementation is *nested* in the interface: that generator's javadoc says so outright, "a final class inside a sealed interface is in the same compilation unit, so Java's sealed-type rules implicitly permit it without an explicit permits clause (and javapoet does not emit one)" (`GraphitronContextInterfaceGenerator.java:107-109`). So sealing means either nesting both implementations, which renames the generated impl and touches the emit plan's committed units and `ConnectionRuntimeClassGeneratorTest`, or teaching javapoet `permits`. ## User documentation (first-client check)

Draft replacement for the function-hook subsection of `docs/manual/reference/mojo-configuration.adoc` § Session identity. If this does not read more simply than what it replaces, the design is wrong.

> **Mounting identity from your own code.** When identity lives behind a database routine, you usually already have the method: jOOQ generates an executing method for every routine into your `Routines` class. Name it. `mount` runs on each connection graphitron takes, before any SQL on it; `unmount` runs when that connection goes back to the pool:
>
> ```xml
> <sessionState>
>   <mount>com.example.db.Routines#connect</mount>
>   <unmount>com.example.db.Routines#disconnect</unmount>
> </sessionState>
> ```
>
> Graphitron reads the signatures at build time: everything but the `Configuration` parameter is the payload, and the return type is the handle later passed to `unmount`. Each payload parameter becomes an ordinary contextArgument on the generated factory, so passing the wrong shape is a compile error rather than a cast failure inside the database. If a service method also needs the same value, declare it as a `contextArgument` with the same name and type; it is the same fact, supplied once, not two separately-maintained copies:
>
> ```java
> var input = Graphitron.newOwnedExecutionInput(claims, userId).query(query).build();
> ```
>
> When the call needs massaging, a procedure with several OUT parameters, a mount that combines two calls, a payload reshaped before binding, write a static method of the same shape and name that instead:
>
> ```java
> public final class KernelIdentity {
>     public static SessionHandleRecord mount(Configuration cfg, ClaimsRecord claims) {
>         var call = new Connect();
>         call.setPClaims(claims);
>         call.execute(cfg);
>         return call.getPHandle();
>     }
>     public static void unmount(Configuration cfg, SessionHandleRecord handle) { ... }
> }
> ```
>
> Your services can consume the identity your `mount` resolved. Bind a parameter to `mount`'s return value with the `$session` sigil, and the parameter receives the handle from the connection the call runs on:
>
> ```graphql
> access: [Entitlement] @service(
>   service: { className: "com.example.AccessService", method: "entitlements" },
>   argMapping: "identity: $session")
> ```
>
> Under tenant fan-out each call sees its own tenant's handle. The parameter's type must match your `mount`'s return type; both are your declarations, checked at build time.
>
> The `Configuration` you are handed is bound to the connection your `mount` is mounting, and carries no transaction provider, because both methods run outside any transaction, on a connection graphitron holds in autocommit. Declare a `Connection` parameter instead if you want raw JDBC. A throwing `mount` evicts the connection rather than returning it to the pool, and fails the request before any of your query's SQL runs.
>
> **When your methods run, and what your `mount` must mount.** Graphitron takes a connection when a field first needs one, mounts identity on it, holds it for the rest of the request, and unmounts before returning it to the pool. `mount` runs with autocommit on and no transaction open, so what it sets is committed session state: a mutation field's transaction committing or rolling back later cannot revert it, and graphitron does not re-run your methods around those boundaries. What this asks of you is that identity be *session*-scoped in your database's own vocabulary, session GUCs on Postgres, a session or global application context on Oracle. Transaction-scoped storage will not work, and will not work from the first query rather than failing later: `set_config(..., true)` and `SET LOCAL` revert at the end of the statement that set them, and rows in an `ON COMMIT DELETE ROWS` temp table are deleted by the mount's own implicit commit. One deployment requirement follows: put graphitron in front of a pool that hands out sessions, not a transaction-pooling proxy such as pgbouncer in transaction mode, which resets session state between transactions and would leave your identity on a backend nobody reads.
>
> **`<unmount>` is optional.** If your `mount` establishes identity wholesale rather than adding to whatever the connection already carried, the next request's mount overwrites the last one's, nothing can read stale identity, and unmount only costs you a round trip per request. Omit it. Keep an unmount when something other than graphitron reads scoped data on the same pool, your own DAO code, a migration tool, an admin script, because those readers never mount and would inherit the previous caller's identity.
>
> For the common Postgres case you need none of this: the `<variables>` sugar generates both halves from a list of session variables.

Also rewrite: the "Producing the claims payload" and integrity-gradient sections of `docs/architecture/reference/runtime-extension-points.adoc`, `docs/security.adoc`, and the owned-path paragraph of `docs/manual/how-to/tenant-scoping.adoc`. The integrity gradient reads better against a method than against a config block, with one care: on the headline path there is no consumer Java, so the rewrite must tell the gradient against the routine's own definition and the Mojo line that names it (the cryptographic fence is a routine verifying a raw token in-database, the enforced fence is a definer-rights package), and only on the facade path does "visible in the consumer's own code" hold literally.

## Retired vocabulary

* `<sessionState>`'s `<connect>`, `<disconnect>` and `<handle>` elements; "connect callable", "disconnect callable", "the callables", and "function-hook form".
* `SessionStateConfig.FunctionHooks`, `SessionStateConfig.RawHook`, `SessionStateBinding.HookBinding`, and the whole `SessionStateConfig.Unmount` hierarchy (`Unmount`, `Unmount.PairedDisconnect`, `Unmount.UnmountFree`), replaced by an optional method reference.
* "identity that mounts must unmount", "unmount-free opt-out", and the claim that `SessionStateWarnings` warns about an unmount-free configuration (it never did).
* `CLAIMS_KEY` and its `no.sikt.graphitron.request.claims` value.
* "opaque claims payload" / "the opaque claims" as the description of the mount parameter. The word `claims` itself is not retired: the `<variables>` sugar's `<claim>` mapping and the dev-goal `<claims>` config both name a genuine claims document.
* "publish the session-hook return value as a contextArgument", "runtime-mounted contextArgument", and "second provenance" as descriptions of how the handle reaches service code; the handle is bound at the consuming site by the `$session` sigil, and contextArguments remain exclusively caller-supplied.
* `<stateSurvivesTransactions>`, and with it "the declared survival opt-in", "unconfirmed function hooks", "confirmed / unconfirmed" as a property of a hook pair, and the question "does the mounted state survive a commit" as something a consumer is asked to answer.
* "settle" as a name for anything session-identity-related: "the settle re-fire", "mutation-field settle", "settle-completion callback", "re-fire the pair", "remount after settle", along with `remountAfterSettle` and `PinnedConnection.afterSettle` themselves. The transaction provider keeps a private `settle` for closing its own top-level transaction, which is honest about what it does and carries no identity meaning; the `Runnable` parameter and the `afterSettle.run()` call go.
* `priorAutoCommit`, and with it "restore the prior autocommit" / "normalize autocommit" as descriptions of what the runtime does to an owned connection's transaction mode. There is no prior mode to restore and nothing to normalize against: graphitron asserts autocommit at acquisition and after every top-level transaction. The mode is still *read* in two places, to detect a transaction graphitron itself left open, but never read as a value to preserve.
* "the request `DSLContext`" as a single eagerly-published per-request object, and `graphQLContext.put(DSLContext.class, dsl)` as the way a fetcher reaches one. The `DSLContext` is a per-key carrier entry, pinned on first demand. "One connection per operation" is not retired: it is still the invariant, since release stays at operation completion.
