# Session identity is a Java method resolved at build time, not generated SQL

`<sessionState>` names database routines as strings, and graphitron generates the call: `ConnectionRuntimeClassGenerator.functionHookImpl` assembles `{ call <fn>(?) }` and binds the payload with `cs.setString(1, claims)`, behind a generated `SessionHook` interface whose two methods are hardcoded `connect(Connection, String claims)` returning `String` and `disconnect(Connection, String handle)`.

Every problem this item was filed for is downstream of that one choice. A consumer whose routine takes a user-defined type has no way to call it, because nothing casts and the parameter arrives typed `varchar`. A consumer whose routine takes two arguments has nowhere to put the second. A consumer whose routine resolves identity in the database cannot see the result in Java, because the OUT value is captured as an opaque `String` on a private field. `<handle>true</handle>` exists as an author-declared boolean, cross-checked against a second author-declared boolean, to describe what the routine's own signature already states.

Fixing that in place means teaching graphitron to *type* a database call it generates: resolve the routine name against the jOOQ catalog, reflect parameters and directions, distinguish the value setter from the `Field` overload, distinguish an OUT parameter's generated getter from a `RETURNS` function's inherited `getReturnValue()`, handle Oracle's package-qualified naming, reject overloads it cannot disambiguate, and fail closed when jOOQ codegen emitted no routines. That is a catalog-resolution subsystem built to reconstruct type information **jOOQ codegen already generated for the consumer**, in their own module, as a typed routine class with typed setters.

So do not generate the call. Name the consumer's method in config, resolve it at build time with the reflection graphitron already does for `@service`, and emit a direct call.

## Design

The SPI is a signature contract, not a class to implement. Graphitron names a static method in config, reflects it at build time, and emits a direct call; whether jOOQ generated the method or the consumer wrote it is invisible to the resolver, because the contract is signature-shaped:

* **Public static.**
* **Exactly one seam parameter**, typed `org.jooq.Configuration` or `java.sql.Connection`, anywhere in the parameter list. The seam rule is also the overload selector: among same-named methods on the named class, exactly one must carry a seam parameter; zero or several is a build-time rejection naming the candidates.
* **Mount:** the remaining parameters, in declaration order, are the payload; the return type is the handle, `void` meaning handle-less.
* **Unmount:** the remaining parameters are either exactly the handle type or empty. Empty is legal even when mount returns a handle (a disconnect routine that clears session state takes no argument; the handle is still retained for `$session` consumers); a single parameter of any other type is the handle-mismatch rejection, naming both signatures. The return type is unconstrained and discarded, so pointing unmount at a routine that happens to return a status value is not a rejection.
* **Checked exceptions:** any declared checked exception is a rejection. `MethodRef.declaredExceptions()` already carries the fact; the rejection site is this item's to add, because the existing enforcer (`FieldBuilder.checkDeclaredCheckedExceptions`) is field-scoped, matching against a field's `@error` channels, and a session hook has neither a field coordinate nor an error channel. Unchecked propagates into the fail-closed eviction.

The contract is written to fit what jOOQ codegen already emits, because that output is not ours to change. For every routine, jOOQ generates into the consumer's `Routines` class a static executing method of exactly this shape (verified against `graphitron-sakila-db`'s generated output):

```java
// jOOQ-generated, in the consumer's own module
public static SessionHandleRecord connect(Configuration configuration, ClaimsRecord pClaims) { ... }
```

So the common case is zero hand-written Java:

```xml
<sessionState>
  <mount>com.example.db.Routines#connect</mount>
  <unmount>com.example.db.Routines#disconnect</unmount>
</sessionState>
```

The same-named `Field`-expression overloads jOOQ generates beside the executing method carry no seam parameter, so the seam rule resolves `Routines` names without a grammar for picking an overload.

When the call needs massaging (a procedure with several OUT parameters, a mount combining two calls, a payload reshaped before binding), the consumer writes a facade satisfying the same contract, and the resolver cannot tell the difference:

```java
public final class KernelIdentity {
    public static SessionHandleRecord mount(Configuration cfg, ClaimsRecord claims) {
        var call = new Connect();          // jOOQ-generated routine class
        call.setPClaims(claims);           // typed setter, jOOQ binds the composite
        call.execute(cfg);
        return call.getPHandle();
    }
    public static void unmount(Configuration cfg, SessionHandleRecord handle) { /* symmetric */ }
}
```

One consequence of the direct path worth naming: jOOQ's executing method for a multi-OUT procedure returns the generated routine object itself rather than a scalar, so naming one in `<mount>` satisfies the contract and silently makes that object the handle type. That is legal, and it is usually not what the author wants; the facade above is where multi-OUT is routed, and the manual says so beside the facade example.

Graphitron reflects the named methods at build time and emits a direct call into the generated hook body. `ServiceCatalog` is already "the mirror of `JooqCatalog` for the service layer: it wraps the catalog and adds the Java-reflection logic needed to introspect service classes at build time", and `MethodRef` is already "a resolved reference to a user-provided Java method" carrying `className`, `methodName`, a javapoet `TypeName` return type off `getGenericReturnType()`, and params in declaration order. A session hook is a user-provided Java method, so this is that carrier's population, not a new one. (This is the opposite conclusion from reusing `RoutineRef`, which is a catalog handle whose params bind from GraphQL arguments and source columns; the distinction is what the thing *is*.)

Everything the item was reaching for is then a reflected fact rather than built machinery:

* **Typed payload.** The mount method's payload parameter type is whatever the consumer declared: a jOOQ `UDTRecord` for a composite, a `String` for a raw JWS, a record of their own. jOOQ does the binding, because it is jOOQ's own generated setter doing it.
* **Typed handle.** The reflected return type. Because `unmount`'s parameter is reflected too, "connect's output type matches disconnect's input type" is checked against two real signatures at build time, and the mismatch message names both. `<handle>` is deleted: its content is the return type being `void` or not.
* **Multiple arguments.** A Java signature fact. `MethodRef.params()` is already an ordered list; each reflected payload parameter becomes a contextArgument (see below), so the factory's arity grows by name-keyed slot, not by a bespoke arity mechanism.
* **Build time, not runtime.** The consumer's class is named in config and resolved during generation, so nothing is registered, nothing is dispatched polymorphically, and the emitted call site is a direct static invocation. A misnamed *routine* additionally stops needing any check from graphitron: the consumer's module does not compile. The enforcer is javac, in the module that owns the claim.
* **The facade stays static and typed.** Because the payload type is known at generation time, `Graphitron.newOwnedExecutionInput(ClaimsRecord claims, ...)` keeps its current static shape with a better type. No generics on the runtime, no move to an instance method.
* **The handle stops being opaque.** A mount that resolves identity in-database (the institution, the entitlement set, the resolved principal) returns a value service code can consume, because the value has a reflected type. The consuming surface is the `$session` argMapping sigil below; this absorbs the former companion item R640, whose contextArgument-publication premise the sigil obsoletes.

**Payload parameters are contextArguments.** Every mount payload parameter becomes a `ParamSource.Context`-sourced `MethodRef.Param`, feeding `ContextArgumentClassifier`'s existing name-keyed population as an additional root alongside every classified field's `@service`/`@condition` sites (`ContextArgumentClassifier.collectFromMethodRef` already accepts a bare `MethodRef`, independent of how the caller reached it). This is a reversal of an earlier draft of this item, which kept payload slots and contextArguments as disjoint namespaces and accepted, as residue, that a fact needed both by mount and by a `@service` method would be passed twice at the factory call site with nothing checking agreement; see "Payload/contextArgument unification reopens a closed decision" below for why that reasoning did not hold up. Under this design there is no residue: mount's payload and a same-named `@service` contextArgument are the same fact, checked once by the classifier's existing `TypeConflict` rejection (type disagreement) and otherwise unified into the one factory slot both consumers read.

There is no bundled carrier. `Graphitron.newOwnedExecutionInput` gains one ordinary contextArgument parameter per reflected payload parameter (name-keyed, alphabetical, the same population `userId`-style contextArguments already occupy). `GraphitronConnectionInstrumentationGenerator`'s generated code, exactly where it reads `CLAIMS_KEY` off `graphQLContext` today before calling `acquire`, instead reads each payload contextArgument individually, the same per-request extraction `@service` call sites already use, and passes them to `acquire`, which threads them into `sessionHook.connect(...)` in mount's own declaration order, since `Routines` renders the *database routine's* parameter order and that ordering is the generator's positional fact, never the consumer's. A mount whose only parameter is the seam contributes no contextArgument and grows the factory by nothing.

Reflection already refuses a nameless Arg- or Context-bindable parameter (`ReflectionError.ParameterNamesMissing`, thrown in `ServiceCatalog.reflectServiceMethod`/`reflectTableMethod` today whenever `Parameter.isNamePresent()` is false for a non-structural parameter), so a mount payload parameter compiled without `-parameters` fails the build through that existing gate rather than falling back to a synthesized name: a synthesized name would otherwise become the literal public factory-parameter identity, which is exactly the kind of throwaway identifier consumer-facing generated code must not carry.

**Graphitron hands over a `Configuration`, and that is load-bearing.** The `DSLContext` a carrier entry hands to fetchers carries `GraphitronTransactionProvider` on its live configuration, the transaction-demarcation seam; if a hook ran through that, "both halves run outside any transaction" would stop being structural. Because graphitron constructs what it passes, it passes a provider-free `DSL.using(connection, dialect, settings).configuration()`, built from the resolved source's own dialect and jOOQ `Settings` (see the injection-surface section), and the invariant stays structural rather than becoming a documented request. Settings matter here specifically rather than incidentally: mount calls the consumer's own generated routine method through this `Configuration`, so a schema mapping the consumer configured has to be in it. Accept a declared `Connection` parameter too, for a consumer who wants raw JDBC.

**The generated `SessionHook` interface goes.** An earlier pass kept it and sealed it, so that "this is not a consumer extension point" would be structural in the way `GraphitronContext`'s sealing is. It exists to give `GraphitronRuntime` a field to hold and `PinnedConnection` something to call, which is polymorphism over a choice already made at generation time; sealing an interface with one real implementation and a no-op is defending a variation point that should not exist. What replaces it is one generated final class with static `mount` and `unmount` methods, called directly, and no emission at all under the `None` arm. Its methods take one typed parameter per reflected payload parameter (no bundled carrier) and the handle type. The reasoning is in the sugar section below, where the fact that forces it shows up.

## What this deletes

The whole string-named-routine path, and everything the catalog-reflection design would have needed:

* `<connect>` / `<disconnect>` / `<handle>`; `SessionStateBinding.HookBinding`, `AbstractRewriteMojo.toRawHook`.
* `SessionStateConfig.FunctionHooks`, `Unmount.PairedDisconnect`'s handle component, `SessionStateConfig.RawHook`, and the handle-agreement rules in `SessionStateConfig.from`.
* `ConnectionRuntimeClassGenerator.functionHookImpl` and `functionDisconnect`'s callable-string assembly.
* The whole settle re-fire, per the section below: `<stateSurvivesTransactions>` and its validation, `PinnedConnection`'s `remountAfterSettle` field and `afterSettle` method, and the transaction provider's settle-completion `Runnable` parameter with the `afterSettle.run()` call in its `settle`. Losing that parameter collapses the provider's two constructors into one, since the convenience constructor exists only to pass `() -> { }` for it. The provider's `priorAutoCommit` field goes too: `begin()` stops capturing it and `settle` asserts autocommit unconditionally. Also the eager single-tenant acquisition in `GraphitronConnectionInstrumentationGenerator.beginExecuteOperation` and the `graphQLContext.put(DSLContext.class, dsl)` publication it exists to feed. Release stays where it is, at operation completion.
* With the re-fire gone, so does a documented limitation: `GraphitronTransactionProviderGenerator`'s "Stated fidelity limitation of the deferred topology" says that under `ROLLBACK_ONLY` nothing settles mid-operation, so dev execution never exercises a consumer's re-fire pair. There is no longer a behavior for dev execution to be unfaithful about. That javadoc section, and the `CommitPolicy` enum javadoc's repetition of the same limit, go with the mechanism.
* Never built: routine-name resolution off the catalog, the Oracle package-qualified probe, the `Pk_Ras.Connect` schema-versus-package ambiguity, overload disambiguation grammar, the value-setter versus `Field`-overload pick, the OUT-getter versus inherited-`getReturnValue()` fork, the `<routines>true</routines>` precondition, and the `sql_routine` fact-relation question.

`SessionStateConfig` keeps two arms (`None` and the method-hook arm replacing `FunctionHooks`), since `Variables` goes with the sugar per the section below. `<stateSurvivesTransactions>` is deleted outright rather than carried over, because the connection lifecycle below removes the question it answered. `MethodRef` already carries `declaredExceptions()` as the fact; the hook-side rejection consuming it is new (see the contract above), since `FieldBuilder.checkDeclaredCheckedExceptions` enforces a field-scoped rule this item cannot reuse.

## Unmount is optional

The shipped design rejects `<connect>` without `<disconnect>` on the grounds that "identity that mounts must unmount", and offers an empty `<disconnect/>` as an explicit opt-out whose javadoc calls it an exposure. That is too strong, and it charges every request a round trip for it.

Mount-only is sound whenever mount establishes identity *wholesale* rather than merging into whatever the connection already had, because then the mount at the start of operation N+1 overwrites everything the mount at operation N wrote. Since the same mount method runs every time, the set of state it writes is constant, so the overwrite is total by construction. Nothing can observe stale identity, because nothing reads scoped data on a pooled connection before a mount has run on it. The condition on that argument is the part worth stating rather than assuming: it holds while every reader of scoped data mounts first, which in practice means the pool is graphitron's. A consumer sharing that pool with their own DAO code, a migration tool, or an admin script has a reader that does not mount, and for them unmount is what keeps the previous caller's identity from being read. That is a property of the deployment, not of the schema, so it is the consumer's call and not something graphitron can infer.

So: `<unmount>` is simply optional. Omitting it means mount-only, with no opt-out ceremony and no rejection. This collapses `SessionStateConfig.Unmount` (and both its arms) into an optional method reference on the method-hook arm, and it removes the pairing-validation family from `SessionStateConfig.from` along with the handle rules.

Latency is the payoff: unmount costs a round trip at every release, once per pinned connection per operation. It no longer also costs at every mutation-field boundary, because the section below deletes the re-fire outright rather than halving it, so mount-only and the re-fire's removal are two independent savings rather than one compounding the other. The mount at the next acquisition is the wholesale overwrite the mount-only argument rests on.

**Correcting the record while deleting it.** `Unmount.UnmountFree`'s javadoc states that "the generation-time warning in `SessionStateWarnings` names this exposure". No such warning exists: `SessionStateWarnings.forConfig`'s `FunctionHooks` arm returns `List.of()`, and the only two warnings are `no-session-state` and `session-state-convention-fence`. The exposure was asserted in prose with nothing enforcing it, which is the shape the project's own principles call out, and it is evidence that the mount-must-unmount rule was never load-bearing in code. The stale sentence goes with the type. The other warning, `session-state-convention-fence`, needs no repointing because it is deleted outright with the sugar it describes; see the section below.

## The `<variables>` sugar goes too

An earlier pass of this item kept the sugar, on the grounds that it is "the one place graphitron genuinely should generate SQL, because there is no consumer method to call". That is reversed: `<variables>` is deleted, and a registered method pair is the only way to mount identity. The reasons are not economy, they are that keeping it costs the item its own guarantees.

**It requires the payload to be JSON text, which is what this item stops it being.** The sugar's generated mount issues one `set_config(name, value, false)` per variable "reading the claim from the payload JSON", so it needs the payload to be a JSON document as a `String` in order to extract `<claim>sub</claim>` from it in SQL. This item's whole payload design is the opposite: the payload is whatever the consumer's method declares, a jOOQ `UDTRecord`, a record of their own, a raw token. Keeping both means the payload type forks by arm, one fixed `String` for the sugar and a reflected list for the method form, and `SessionHook`'s emitted shape forks with it. The bifurcation is carryable, and the earlier draft was carrying it without naming it, but it is the last thing keeping "the payload is a reflected fact" from being unconditionally true.

**Its own warning already tells consumers to stop using it.** `SessionStateWarnings` raises `session-state-convention-fence` whenever the sugar is configured and the schema has any `@service` field, because the GUCs it sets are a convention fence that any SQL on the pinned connection can overwrite, and `@service` runs consumer code on exactly that connection. The message's remedy is to switch to the hook form with a definer-rights routine, or a signed token verified in-database. So graphitron already directs sugar users off the sugar as soon as they use the other main feature of the generator.

**It is the only reason the runtime needs a dialect guard.** The sugar bakes Postgres `set_config` at build time, which is why the runtime constructor fails closed on a non-Postgres dialect. Deleting it deletes that guard, and with it the per-entry version of it that the source SPI above would otherwise need: nothing about identity is baked dialect-specifically any more, so a mixed-dialect per-tenant deployment stops being a special case to check and becomes simply representable.

**What it costs, stated plainly.** The zero-Java path disappears for the deployment that has no database routine at all: one GUC set from one claim. That consumer goes from a `<variables>` block to a `<mount>` naming a method they write, which is three lines:

```java
public static void mount(Configuration cfg, String tenantId) {
    cfg.dsl().execute("select set_config('app.tenant', ?, false)", tenantId);
}
```

That is not a worse security position than the sugar, and it is not a better one either. This is the honest form of the argument: hand-writing `set_config` sits at exactly the same point on the integrity gradient as generating it, and the tamper-resistance the fence warning asks for comes from a definer-rights routine or an in-database token check, never from who typed the `set_config`. What the consumer gains is that the SQL mounting their identity is visible and reviewable in their own module, and what graphitron gains is one mount mechanism instead of two.

**`session-state-convention-fence` is deleted with it, and that is a real loss.** Graphitron can warn precisely today only because it generated the GUC set and therefore knew the fence level. Against a reflected `MethodRef` it cannot tell a definer-rights routine call from a plain `set_config`, so the same warning would either fire for every `@service` consumer including the correctly configured ones, unsilenceable by anything graphitron can observe, or assert an exposure it cannot ground, which is the exact shape this item already criticizes in the `UnmountFree` javadoc. The integrity gradient moves entirely to `docs/security.adoc`, where it can be explained rather than asserted at build time. `LintRule.SESSION_STATE_CONVENTION_FENCE` and its `LintRuleRegistryCoverageTest` row go with it.

**The projection collapses to one fact, and that fact is the interface.** `RuntimeHookProjection` carries three: `hookInitializer`, `requiresPostgres`, `remountAfterSettle`, and its javadoc justifies the record by them being decided together in one exhaustive switch. This item deletes the re-fire, so `remountAfterSettle` goes; deleting the sugar takes `requiresPostgres`. What is left is a single `CodeBlock` choosing between `SessionHook.NONE` and `new SessionHookImpl()`, so the record and its rationale go too, and the choice it encodes is the last thing the generated `SessionHook` interface exists to express at runtime.

That makes deleting the interface the better answer than sealing it, and it is this item's own claim that says so: "nothing is registered, nothing is dispatched polymorphically, and the emitted call site is a direct static invocation" is asserted in Design while a `SessionHook`-typed field on `GraphitronRuntime` is dispatched through on every acquisition. One of the two has to give, and the config is known at generation time, so the choice between a mount and no mount is a choice about *what to emit*, not a value to hold. So: `SessionHook` and its generated no-op are deleted, the runtime's `sessionHook` field with them, and the emitted unit becomes one final class with static `mount` and `unmount` methods that `PinnedConnection` calls directly. Under the `None` arm nothing is emitted and `acquire` carries no mount call at all, which is stronger than holding a no-op that does nothing.

This resolves the sealing question the review left open, by deletion rather than by decision: there is no `permits` clause to emit and no implementation to nest, so neither `graphitron-javapoet`'s missing `permits` support nor a rename of the generated impl is on this item's path. The class keeps its role as the place the provider-free `Configuration` is built and the payload is spread into mount's declaration order, so `PinnedConnection` stays free of both, and the test plan's `SessionHookImplGeneratorTest` rows survive unchanged in substance.

**`no-session-state` is what stays, and it is already the warning we want.** It fires on `SessionStateConfig.None`, saying the owned-connection runtime mounts no identity so the database cannot enforce per-caller row access, and it is silenceable by rule id for a deployment that is intentionally unsecured. Nothing new is needed to warn a consumer who registered nothing; the message is repointed to the new element names, and it becomes the one build-time signal about identity, which is appropriate since registering a hook is the only thing graphitron can actually observe. Being the only signal is a reason to make it teach rather than merely fire: with the fence warning gone it is the single place a build says anything about identity, so its message names the three mount shapes a consumer chooses between (a definer-rights routine, a token verified in-database, a session variable set by convention) and points at the security guide, instead of only saying to configure something.

**Knowledge that was ours becomes the consumer's, and has to move rather than be deleted.** The sugar's deletion moves real Postgres knowledge across the boundary, and the tree keeps it in exactly the wrong place for that: `ConnectionRuntimeClassGenerator`'s javadoc explains why the generated clear is `set_config(name, '', false)` and not `RESET`, because a never-set custom GUC reads back `NULL` but a touched one cannot be returned to unset, so both `RESET` and a `NULL` set leave the empty string, and therefore an RLS policy has to treat `NULL` and `''` identically as "no identity". That was graphitron's problem while graphitron wrote the clear. It is the consumer's the moment they write their own unmount, and a consumer who writes `RESET app.tenant` and an RLS policy testing only `IS NOT NULL` has built a hole the generator used to close for them. So the paragraph does not go with the generated code it documented: it moves into the user manual beside the unmount example, and the security guide's gradient section absorbs the fence explanation the deleted warning used to carry. Two paragraphs of generator javadoc becoming two paragraphs of manual is the whole shape of this item's cost.

## Graphitron asserts the connection's transaction mode, which is what makes the re-fire unnecessary

The shipped runtime keeps mounted identity alive across a mutation field's commit with real machinery. `ConnectionRuntimeClassGenerator`'s javadoc states why: graphitron cannot verify whether a consumer's mounted state survives a commit or rollback ("identity parked in an `ON COMMIT DELETE ROWS` temp table would not"), so the consumer declares survival with `<stateSurvivesTransactions>true</stateSurvivesTransactions>`, and undeclared, the runtime bakes `remountAfterSettle=true` and re-fires the hook pair through `PinnedConnection.afterSettle`, wired as the transaction provider's settle-completion callback.

Read against transaction semantics, the guard is redundant with a guarantee acquisition already makes. `acquire` calls `connection.setAutoCommit(true)` *before* `connect`, so the mount is always its own implicitly-committed transaction. A later `rollback()` reverts what happened inside the transaction it closes, and the mount did not happen inside it, so the mount's effect is not a candidate for reversion. A later `commit()` clears nothing. That is why the now-deleted `<variables>` sugar could opt in structurally: it mounted with `set_config(name, value, false)`, session-scoped rather than transaction-local, in autocommit, and the code already documents that as surviving settles. A consumer mount issuing the same statement by hand inherits the same property, which is why deleting the sugar costs this argument nothing.

That line deserves naming as an invariant rather than passing as hygiene, because with the guard gone it carries the whole guarantee. The frame is ownership, not defence. Graphitron checks the connection out of the pool, holds it for the operation, and hands it back, so its transaction mode is something graphitron *asserts*, never something it inherits or preserves, and autocommit-on is the resting state every phase requires: the mount must be its own committed transaction, queries want no transaction at all rather than an idle-in-transaction snapshot pinning `xmin` for the length of a GraphQL operation, and the unmount at release must take effect immediately. Only a mutation field's own transaction wants autocommit off, for exactly its duration. What makes the assertion load-bearing rather than tidy is that session-scoped GUCs are transactional in Postgres: `set_config(name, value, false)` is `SET SESSION`, which survives a `COMMIT` but is reverted when the transaction that issued it rolls back, and `SET ROLE` behaves the same way. A mount running with autocommit off would emit its `BEGIN` lazily at the mount statement, sit in a transaction nobody commits, and be rolled back by the first failing mutation field, leaving the rest of the operation running unmounted, which under RLS is a wrong answer rather than an error. Asserting the mode at acquire excludes that before any SQL runs, where the re-fire repaired it afterwards, once per mutation, on the rollback path only. The same fact read from the other end is why `release` rolls back *before* switching the mode: JDBC commits an open transaction when autocommit is turned on, so that order is load-bearing too.

Reading the mode as asserted rather than inherited deletes a field. `GraphitronTransactionProvider.begin()` captures `priorAutoCommit = connection.getAutoCommit()` at depth 0 and `settle` restores it, as though the provider were a guest returning a connection to a mode it found. It is not, so the field is deleted and `settle` asserts autocommit unconditionally. The ground for the deletion is ownership rather than the field's current value: autocommit-on is the resting state graphitron asserts on a connection it holds, so it is what `settle` should assert after closing a top-level transaction, whatever preceded it. An earlier draft of this paragraph argued instead that the field is provably always `true` when read. That is false, and the way it fails is worth keeping, because it is the next paragraph's whole subject: the value is written by whichever provider instance opened the outermost transaction, and today one connection has several.

**One provider per pinned connection, which the carrier unification gives for free.** `dslFor` and `dslDefault` construct a fresh `GraphitronTransactionProvider` on every call (`ConnectionRuntimeClassGenerator.java:1052` and `:1070`), so a key's connection has as many providers as the operation has context resolutions, each with its own `depth` counter and savepoint stack. That is not a decision anywhere; it is a cardinality that changed underneath a copied recipe. The three lines (bind a `DSLContext` to the connection, `set` the provider on its live configuration, hand it out) were written for the single-tenant site, where they run once in `beginExecuteOperation` and the result is *published* under `graphQLContext` for every fetcher to read, so one provider per operation holds by placement rather than by care. The tenant path adopted the identical recipe, its own comment saying so ("the same recipe slice 2 uses for the single-connection path"), but put it inside an accessor called once per fetcher site. It cached the half that visibly needed caching, the connection, since pinning and the identity mount are per key; the `DSLContext` read as a cheap wrapper, and the stateful provider riding on it was invisible at that moment. Two of them over one connection do not compose. Under `COMMIT`, a second provider's `begin()` sees its own `depth == 0`, captures `priorAutoCommit = false` from the transaction the first one opened, turns autocommit off again to no effect, and then its `commit()` takes the depth-0 branch and calls `connection.commit()`, committing the enclosing transaction's writes at what should have been an inner boundary. The reach is multi-tenant-only today, and that matters for this item specifically. Single-tenant is immune by accident of the same placement: `getDslContext(env)` is a bare `graphQLContext.get(DSLContext.class)`, so every fetcher reads the one instance `beginExecuteOperation` published, and only one provider ever exists. Lazy acquisition, the change this item makes right below, is exactly what removes that immunity. A lazy accessor that merely *defers* the recipe, the naive port of `dslDefault`, would re-mint per call and spread the hazard to the single-tenant path, which is where nearly every consumer is. So caching the context in the carrier is not an improvement bundled alongside the laziness; it is a precondition of the laziness not regressing anything, and the two land together or not at all.

The unified per-key carrier introduced below closes it by construction: one cached `DSLContext` per key is one provider per pinned connection, `depth` is then the only nesting counter on that connection, and an inner boundary is a savepoint because that is what `depth > 0` emits. So the unification has a second justification independent of the `$session` handle it was introduced for. It imposes no new concurrency requirement, since `depth` becomes shared per key but the `Connection` beneath it was already shared per key, so the provider inherits exactly the contract the connection already carries. It also makes two provider javadoc claims true that are false in the tree today, the canonical constructor's "One instance per operation" and the class javadoc's "over the single pinned connection", both of which are repointed to one instance per pinned connection in the same change.

With the field gone, nothing reads the connection's mode as an input to preserve. Two reads survive and are a different kind of thing: `begin()`'s `ROLLBACK_ONLY` branch tests `getAutoCommit()` so that reopening at depth 0 across a deferred field boundary does not re-issue `setAutoCommit(false)`, and `release` tests it to detect a transaction the operation left open. Both interrogate state graphitron itself asserted, not a mode the pool chose. That is what makes the deletion stronger than restoring: the pool's configuration stops being an input to identity survival by construction, rather than being an input graphitron defends against.

The interesting question is whether a *consumer* mechanism can behave differently, and the item's answer is that every one that can is already broken at mount rather than at the settle. The javadoc's own example makes the point: rows in an `ON COMMIT DELETE ROWS` temp table are deleted at the end of every committing transaction, and in autocommit the mount's own `INSERT` is such a transaction, so those rows are gone before the first fetch runs, with or without a re-fire. `ON COMMIT DROP` drops the table at the end of the creating transaction, likewise immediately. `set_config(..., true)` and `SET LOCAL` revert at the end of the current transaction, which in autocommit is the statement itself. The mechanisms that do survive the mount (session GUCs, `SET ROLE`, Oracle session and global application contexts, session-level advisory locks) all survive an unrelated later transaction's outcome for the same reason a session GUC set in autocommit does.

So `<stateSurvivesTransactions>` asks a question whose answer is "yes" for every mechanism that works at all, and the re-fire protects a failure mode that `setAutoCommit(true)` before the mount already excludes. The flag and the re-fire are deleted, and the load-bearing guarantee stays exactly where it already is, in the autocommit acquisition asserts before the mount. What replaces the declaration is not a different declaration but a documented precondition on the hook contract: mount session-scoped state, in the database's own session vocabulary. A consumer who parks identity in transaction-scoped storage has a hook that never worked, and the honest response is a contract statement, not a per-request round trip that half-hides it.

**The release point does not move, and cannot.** An earlier draft of this section had the connection returning to the pool at each transaction end, with a later fetcher re-acquiring. That is unsafe. `DSL.using(connection, dialect)` wraps the connection in jOOQ's single-connection provider whose release is a no-op, so jOOQ never gives the connection back and every fetcher holds a `DSLContext` bound to that exact `Connection` for as long as it holds the reference. Returning the connection mid-operation would leave live `DSLContext` references wrapping a connection another request had borrowed, and a fetcher issuing two queries never re-asks for a context in between, so there is no seam at which a fresh one could be handed over. Release stays at operation completion, on every path (success, error, cancellation), as today.

Two changes this item does make to acquisition, both safe because nothing holds a context before one exists:

* **Acquisition is lazy on every path.** Single-tenant stops pinning eagerly in `beginExecuteOperation` and publishing one `DSLContext` under `graphQLContext.put(DSLContext.class, dsl)`; `getDslContext(env)` pins on first demand instead, which is what `TenantConnections.dslFor` already does for the tenant-routed path. It becomes a carrier resolution rather than a map read, so it inherits `TenantConnections.of(env)`'s located failure when the operation did not run through owned acquisition, and the typed `DSLContext.class` key becomes the escape hatch's alone; see the injection-surface section below. The accessor's signature does not change, so the emitters that resolve a `DSLContext` (`TenantDslEmitter.dslExpression`, `HandleMethodBody`, `ConnectionHelperClassGenerator`) keep their call sites. An operation that touches no database never pins and never mounts.
* **Per-tenant state is one carrier entry per key, not a global object beside a map of connections.** A key's entry holds that key's connection, its `DSLContext` and its handle together, minted on acquisition and discarded at release, with single-tenant as the one-key case. `ConcurrentHashMap.computeIfAbsent` already carries the one-pin-per-key contract on the tenant path (its field javadoc states it as a contract rather than an accident of the callers), and that is the pattern the unified carrier uses: the map's value type grows from `PinnedConnection` to the entry, and the whole entry is minted inside the one `computeIfAbsent`. This is what gives the `$session` handle a `Configuration` that exists per key, which the current per-`dslFor`-call minting does not, and it is what reduces a connection to one transaction provider, per the argument above. Nothing new is needed on the tenant path, which already has the map.

  **One map, `ConcurrentHashMap`, in both topologies, keyed by `Optional<tenantKey>`.** This is the simplification, not an addition: `computeIfAbsent` is then the only minting mechanism anywhere in the carrier, and three special cases go away with it. The single-tenant variant's plain `LinkedHashMap` goes, along with the constructor javadoc's "a single operation's fetchers run serially on the dispatch thread" that justifies it, which is an assumption about graphql-java's execution strategy rather than a structural guarantee, and which costs nothing today only because the eager pin runs before any fetcher does. Laziness is what would promote that comment into load-bearing correctness, and the concurrent map is cheaper than defending it. The `defaultPinned` field and `dslDefault`'s check-then-pin go too, becoming the map's `Optional.empty()` entry: its field javadoc rejected a *reserved key of the tenant-key type*, which `Optional.empty()` is not, and `Optional` is also what sidesteps `ConcurrentHashMap`'s no-null-keys rule that made a null-keyed default impossible in the first place. Its "needs no concurrency work" argument (scatter workers cannot reach it, the dispatch thread is blocked in the join) is specific to the fan-out topology and would not transfer to a lazily-pinning single-tenant runtime anyway. What remains topology-specific is the machinery that genuinely only exists under `<tenantColumn>`: scatter, the fan-out helpers, `timedOutTenants`, `closed`.

  One consequence to plan for rather than discover: single-tenant fetchers do not go through this carrier today. They read `getDslContext(env)`, a bare `graphQLContext.get(DSLContext.class)` fed by the eager publication, and the single-tenant carrier ships with `dslFor` and `releaseAll` and no live caller. So the unification does not only cache a context; it moves the single-tenant path onto a surface that topology has never exercised. The accessor's signature is unchanged, so no call site moves, but the tests behind it are new coverage rather than adapted coverage.

The payload is retained once, by the carrier that acquires. Lazy acquisition means any fetcher may trigger the mount for a key, so that carrier holds the payload contextArguments for the life of the request, exactly as `TenantConnections` holds `claims` today; `PinnedConnection` still carries no payload field, receiving the payload as `acquire` arguments and forwarding it into `mount`.

One precondition worth stating because the model depends on it and cannot check it: identity is session-scoped state on a connection graphitron holds, so a transaction-pooling proxy in front of the database (pgbouncer's transaction mode, which resets session state between transactions) voids the model outright rather than merely complicating it, since successive transactions reach different backends. A re-fire would not have rescued that deployment either; it would have mounted identity on whichever backend the re-fire's own statement reached. Session-level pooling is the requirement, and the docs say so rather than a runtime guessing.

## The handle reaches service calls as the `$session` argMapping sigil

This absorbs the former R640, which was filed against the duplicated derivation the opaque handle forces: a connect routine that resolves identity in the database returns facts service code cannot see, contextArguments are exclusively caller-supplied, so a service wanting the same facts re-derives them from the raw claims in Java with nothing binding the two derivations. R640's shape was "publish the handle as a contextArgument", which required a second provenance in the classifier and carried four design forks. Binding the handle at the consuming site dissolves all four, so the capability ships here as part of the SPI design rather than as a follow-on.

A service binds a parameter to the handle in `argMapping`, in the grammar it already uses for "the names don't line up, bind explicitly":

```graphql
someField: [Film] @service(
  service: { className: "com.example.FilmService", method: "films" },
  argMapping: "identity: $session")
```

The sigil joins the established `$source`/`$errors` family: recognized by prefix test, stored as written, an unknown sigil rejected at parse time naming the allowed set, admission per site (`@service` `argMapping` in v1; other argMapping sites reject it naming the admitted site, the `$source` precedent exactly). GraphQL names cannot start with `$`, so the sigil is lexically disjoint from argument names by construction, and the contextArgument namespace is never involved: no factory slot, no classifier provenance, no publication name to choose. Publication-as-asked-for is satisfied by each use being the ask.

The bound parameter becomes a structural `ParamSource` variant, the pattern `DslContext`/`Sources`/`Table` already set: supplied by the generator, filtered out of `callParams()`, its emit-time extraction reading `dsl.configuration().data(KEY)` off the same `DSLContext` local the call site already resolves (forcing that local to be declared when it otherwise wouldn't be). That read placement is what dissolves R640's forks:

* **Ordering.** Mount runs on a connection as part of acquiring it, before any SQL on that connection, so a service call holding a key's `DSLContext` always reads a mounted handle. Lazy acquisition does not weaken this: the `DSLContext` cannot exist before the mount that produced its entry. No "not yet mounted" runtime state.
* **Staleness.** The handle lives in the per-key carrier entry beside the connection that produced it, and that entry's `Configuration` exposes it on jOOQ's per-`Configuration` `.data()` map. Because the entry is minted at mount and discarded at release, the handle and the connection it describes are created and destroyed together, so a handle cannot outlive its connection and never has to be overwritten in place. With the re-fire deleted there is exactly one mount per entry, so the handle is written once and read many times. Nothing is written into request scope and left to rot.
* **Fan-out is semantics, not a rejection, because the read is per-key-carrier.** R640's load-bearing scope call was that N tenant connections mean N handles and one request-scoped contextArgument slot cannot represent them; its answer was to reject fan-out plus publication. The generated call site resolves its `DSLContext` through `TenantDslEmitter.dslExpression`, which under the unified carrier resolves a key's entry on both paths (single-tenant being the one-key case), and reads the handle off that entry's `Configuration`. A fetch running under a tenant reads *that tenant's* handle because it is reading that tenant's carrier, not because of any implicit locality claim. Per-tenant identity is not an edge case; it is the read location doing the scoping. This is the half the earlier draft got wrong: it pointed the read at a `Configuration` that the tenant path minted fresh on every `dslFor` call, so there was no per-tenant object to have written a handle onto. Caching the `DSLContext` in the key's carrier is what makes the claim true by construction.
* **Type agreement** is the reflection family again: the bound parameter's declared type against mount's reflected return type, rejection naming both. `$session` against a `HandleLess` mount is a located rejection: the mount returns `void`, there is no session handle to bind.

The accepted cost is a new kind of cross-artifact edge: SDL that uses `$session` builds only against a `<sessionState>` whose mount returns a handle, so the schema is less self-contained than one that smuggles identity through re-derivation. That coupling is real (the service genuinely consumes deployment-produced identity), and the sigil makes it visible and located; the rejection message when the config side is absent has to carry the whole story, naming the field coordinate, the sigil, and the missing config.

## The `DSLContext` injection surface, challenged

The consumer-supplied `DSLContext` is worth challenging here rather than later, because this item changes who writes the slot it travels in and adds the first consumer-visible read of a `Configuration`.

Today two factories write the same slot. `newExecutionInput(DSLContext defaultDsl, ...)` does `b.put(DSLContext.class, defaultDsl)`, and on the owned path the instrumentation does the same `put` in `beginExecuteOperation`. `getDslContext(env)` is a bare `env.getGraphQlContext().get(DSLContext.class)`, so the read cannot tell which mode produced the value, and the two mode choices (which factory, and `Graphitron.newGraphQL()` versus `runtime(...).newGraphQL(schema)`) are independent with nothing checking that they agree. Mismatch one way leaves the slot unwritten and the first fetcher throws `NullPointerException` with no mention of modes; the other way the instrumentation pins a connection, mounts identity, and overwrites the caller's `DSLContext`, discarding it after paying a pool checkout and a round trip. The distinct factory names are documented as preventing a caller from "silently opting out of the owned-path guarantees by passing a `DSLContext`", and they do prevent exactly that, but the failure that actually happens is the mismatched pair, which they do not address.

The tree already contains the fix, applied once. `TenantConnections.of(env)` resolves the carrier and throws a located `IllegalStateException` when it is absent, naming the two entry points the operation should have used. The tenant path therefore diagnoses the mismatch precisely; the single-tenant path shares a slot and yields a null. That asymmetry exists only because single-tenant had a published `DSLContext` to read and the tenant path did not.

Lazy acquisition removes the asymmetry as a side effect, and this item should take the consequence rather than leave it: with `graphQLContext.put(DSLContext.class, dsl)` deleted, the owned path stops writing the typed key altogether, so `getDslContext(env)` becomes a carrier resolution with `of(env)`'s loud failure on both paths, and the typed key reverts to meaning exactly one thing, a caller-supplied context from the escape hatch. Two writers with one meaning become one writer per meaning, and the accessor distinguishes the modes structurally instead of reading whichever wrote last: carrier present is owned, key present is the escape hatch, both present is the mismatched pair and can now be named as such. The accessor's signature still does not change.

`$session` inherits that treatment instead of needing its own. On the escape-hatch path the sigil's read lands on a `Configuration` graphitron never mounted, so it would hand a service parameter a null; and a caller-supplied context is usually `DSL.using(dataSource)`, whose pooled `ConnectionProvider` hands out a different connection per query, which makes identity not merely unmounted but unmountable. The build cannot see the mode, so the located throw is the honest answer, in `of(env)`'s shape and naming the field coordinate, the sigil, and the factory the operation should have used.

**The runtime's source SPI takes a `DataSource`, a dialect and jOOQ `Settings`, one triple or one per tenant.** The gap it closes: no `DSLContext` graphitron produces carries the consumer's jOOQ configuration. All three minting sites build a bare `DSL.using(connection, runtime.dialect())`, so consumer `Settings` (schema and render mapping above all) are absent from every context on the owned path. That is a *configuration* need currently served by surrendering the whole connection lifecycle, which is the strongest real reason to reach for the escape hatch at all, and this item is what makes the omission consumer-visible: mount receives a `Configuration` and calls the consumer's own generated `Routines.connect(Configuration, ...)` through it, so a consumer using jOOQ schema mapping to retarget environments would get their routine rendered against the unmapped schema.

Nothing is invented, because the shape mirrors jOOQ's own: `DSL.using(Connection, SQLDialect, Settings)` is an existing overload, and `Settings` is exactly the part of a `Configuration` that is safe to accept, since what graphitron must own (the connection provider, the transaction provider) is not in it. A generated source record carries the triple, null settings defaulting to `new Settings()`, and the runtime's canonical constructor takes a default source plus `Map<? extends K, Source>`, which generalizes the `Map<K, DataSource>` it already holds for database-per-tenant routing rather than adding a parallel structure. The existing `(DataSource, SQLDialect)` and `(DataSource, Map, SQLDialect)` constructor forms stay as delegating conveniences that wrap default settings, so the change is additive and no consumer call site breaks. Both `dialect()` reads in the carrier become the resolved entry's own source, which is where they were heading anyway: this item already reduces those three minting sites to one.

Two consequences worth taking deliberately. First, the dialect stops being one runtime-wide field, so a database-per-tenant deployment can name a different dialect per tenant. Deleting the `<variables>` sugar is what makes that free: the sugar's baked `set_config` was the only dialect-specific SQL graphitron committed to at build time, and the runtime constructor's fail-closed `dialect.family() != POSTGRES` test existed for it alone. With the sugar gone that guard goes, and nothing has to be re-checked per entry, because identity is now entirely the consumer's SQL rendered through their own source's dialect. Second, `Settings` covers rendering and mapping but not `ExecuteListenerProvider`, `RecordMapperProvider` or `ConverterProvider`, which are `Configuration`-level rather than `Settings`-level. Those stay unavailable on the owned path; it is the plausible next ask, and a separate one.

The escape hatch then survives narrowed to the case it should always have been: the caller already owns an open transaction and wants the operation to run inside it. Its name stays frozen by additive-by-construction, and the two paths converge on settings instead of diverging on them.

One forward-compatibility note on the map, because a second axis is already contemplated elsewhere: the read-only-enforcement work considers an optional read pool beside the write pool, routed by operation type. That is a *role* axis, orthogonal to the tenant axis. So the source record stays the unit of "a pool graphitron can check a connection out of" and a role, if it arrives, becomes part of the map's key rather than a second field on the record. Shaped that way it lands without rewriting the value type twice.

## The seam is general, and identity is its first participant

Read back what this item ends up building: acquisition and release are two ordered points inside a window graphitron owns, and the generated hook class is a participant at those points, a `mount(seam, payload...)` returning a handle and an `unmount(seam, handle)` consuming it. Nothing in that shape is about identity. With the sugar deleted the identity meaning lives entirely in the names, since graphitron no longer generates any identity SQL of its own. A general connection-lifecycle hook therefore needs no new mechanism, and that is worth stating outright so the next person who wants one extends this seam instead of building a parallel path beside it.

What it is not is runtime registration. This item's own ground is that a session hook is resolved at build time, so nothing is registered and nothing is dispatched polymorphically; a `Consumer<Connection>` handed to the runtime at wiring time would restore precisely the untyped `Connection`-and-`String` contract the item exists to delete, giving up the typed payload, the arity checked against a real signature, and the compile error at the factory call site. A second participant is therefore the same thing the first one is: a config-named method, reflected through `ServiceCatalog`, emitted as a direct call.

Raw checkout and release are also already the consumer's, which narrows what is worth exposing. They own pool creation, so decorating the `DataSource` gives them a checkout hook and decorating `Connection.close()` gives them a release hook, with no graphitron surface involved; pools also offer this natively, and the read-only-enforcement item's zero-per-request-cost realization is exactly that, a pool opened with `connectionInitSql = SET SESSION CHARACTERISTICS AS TRANSACTION READ ONLY`. The points `DataSource` decoration cannot reach are the ones inside the owned window: after the mount, before the unmount, between a transaction settling and the unmount. Those are the only ones a graphitron-level participant buys, and they are exactly where ordering against the mount matters. Observability, the other thing people reach for at checkout, has a better jOOQ-native home in an `ExecuteListenerProvider`, which is the `Configuration`-level surface named above as the plausible next ask; it does not want this seam at all.

So this item adds no participant registry, and the shape a second participant would take is stated rather than built. Deleting the sugar settles what that shape is: `<sessionState>` used to be identity-specific because it housed the `<variables>` sugar, and with the sugar gone its entire content is a pair of methods graphitron runs at the connection boundary, which is the seam itself. A second participant is therefore another entry in this block rather than a sibling element beside it, and the block's name is the only identity-flavored thing left about it. That name is worth keeping anyway: `<mount>` says what the consumer's method does, where an `<onCheckout>` would say only when graphitron calls it, and `no-session-state` and `$session` both read as identity vocabulary. Participants would run in declaration order with identity first, because anything that wants to read scoped data has to run after the mount. The trigger for filing that work is a named consumer need at the seam that is not identity *and* that pool-level configuration cannot serve; the read-only case does not qualify, because its own cheapest realization is the pool.

One consequence for a decision the review left open: the seam being general is not a reason to keep an interface at it. Participants are generated from config, never written by a consumer, so a second one is a second generated static call in declaration order, not a second implementation of a type. The sugar section below deletes the `SessionHook` interface for that reason, and generality is an argument for the deletion rather than against it. This is the inference most likely to be got backwards later ("extension point, so give it a type"), so it is recorded rather than left to be re-derived.

## Implementation

* **Config.** Replace `<connect>`/`<disconnect>` with `<mount>`/`<unmount>` taking `fqcn#method`, `<unmount>` optional. Delete `<stateSurvivesTransactions>` and every rule that reads it, since the per-acquisition mount removes the question it answered. Drop the handle rules and the pairing rules, and collapse `Unmount` into an optional method reference. An `<unmount>` with no `<mount>` stays a rejection: unmounting what nothing mounted is a defect in either direction of reading it. The authored facts reduce to the two `fqcn#method` strings, and strings are all the fact store ever sees of them: `GraphQLRewriteGenerator.subjectConfig` hands the config object to fact capture's `SubjectConfig`, and that provenance family stores only what the author wrote, so the method-hook arm must stay strings-only rather than carry a resolved `MethodRef` (the reflected signatures live on the model instead; see Resolution). The provenance relations collapse with the alternation: with `<variables>` deleted, `store_graph_session_state`'s `arm` discriminator has nothing left to discriminate, and `store_graph_session_disconnect`'s row-presence comment carries the declared-opt-out distinction this item deletes, so those two go with `store_graph_session_variable`, and what lands is a `graph_name`-keyed mount relation and unmount relation whose row presence is the fact, per the family's own absence-is-structural rule. `FactCaptureAgreementTest.everyRelationIsRegistered` and `FactSchemaGateTest.commentCoverageIsTotal` gate that swap, so it sits on the implementer's checklist beside the rejection gates. The general "no method-hook configured at all" guard is unrelated and stays.
* **Resolution.** Resolution runs in `GraphitronSchemaBuilder`, the stage that already owns `ServiceCatalog`: the authored strings arrive on `RewriteContext`, which is already a `BuildContext` input, and the builder reflects both methods through `ServiceCatalog`'s existing Java-reflection path into `MethodRef.StaticOnly` (already the variant for "static-by-construction method references"). The Mojo seam does no reflection. `ServiceCatalog` stays the only holder of raw `java.lang.reflect` and of the seam-type test, per the capture-boundary containment invariant; no session-package reflector, and no widening of the catalog's visibility. Overload selection extends the one existing resolution point (`ServiceCatalog.pickMethod`) with the seam filter as an explicit input, so `ReflectionError.AmbiguousMethod` stays the single ambiguity vocabulary and "zero or several seam-carrying candidates" is a variant in the same family, naming the candidates; a second session-hook-local resolver is exactly the two-answers drift the principles warn about. `MethodPick` is today a two-nullable-field bag every caller null-tests; adding a third outcome class into that shape is the moment to lift it to a sealed ok-or-rejected form, so the seam arms arrive as variants rather than as another null combination (the three existing call sites convert mechanically). The resolved carrier is a builder-minted model component, total over the outcome: `NotConfigured`, `HandleLess` (mount, optional unmount) and `Handled` (mount, handle `TypeName`, optional unmount), hung on `GraphitronSchema` upstream of the contextArgument classification in the constructor chain, defaulting to `NotConfigured` in the convenience constructors the way `tenantScopes` already defaults, so the classifier population is a function of the model's own components rather than of which constructor a caller used. Totality is what preserves `SessionStateConfig.emitsHookImplementation()`'s single-membership-fact property instead of retiring it: all three emit-side readers (`EmitPlan.produce`, `ConnectionRuntimeClassGenerator.generate`, `GraphitronDevExecutorGenerator.generate`) switch on the resolved carrier, and the authored `SessionStateConfig` keeps exactly two readers, `SessionStateWarnings.forConfig` and fact capture's verbatim transcription, so the plan and the renderer cannot fork on different answers to "is a hook configured". "Handle-less implies unmount takes nothing, implies the pinned carrier has no handle field, implies the generated unmount method takes only the connection" stays structural on that fork, and every emit site switches once on the arm instead of re-testing the return type for `void`. This is the same property `SessionStateConfig.Unmount`'s sealing carries today ("a handle produced by connect that no disconnect binds" is unrepresentable), moved from declaration to reflection along with the fact itself. Rejections are the existing reflection family (`ReflectionError`, unresolvable class or method, non-static, no seam parameter or more than one candidate, seam-overload ambiguity naming the candidates, handle-type mismatch between the two signatures, `ParameterNamesMissing` on a nameless payload parameter, declared checked exception); a payload parameter's name colliding with an existing contextArgument is not a rejection of its own, it is `ContextArgumentClassifier`'s existing `TypeConflict` when the types disagree and a unified slot when they agree. The route that makes a reflection failure fail the build is named rather than assumed, because a session hook has no field coordinate for the `UnclassifiedField` drainage `@service` uses: the lift's result is sealed, resolved or rejected-with-`ReflectionError`, and a rejection drains as a schema-wide, coordinate-less `ValidationError` in the builder's stream, which `rejection_validation_error` already admits by design (its `ordinal` comment covers coordinate-less rows). Two rejection channels, deliberately: config-shape defects (a malformed `fqcn#method`, `<unmount>` without `<mount>`) stay the Mojo seam's `IllegalArgumentException`, a `pom.xml` concern with no SDL coordinate, while the reflection failures are typed rejections carrying `typed-rejection.adoc` paragraphs; the `$session` rejections are SDL-located and stay in the field-coordinate taxonomy. The seam parameter also gets its own structural home: a `ParamSource.SessionSeam` variant carrying a sealed two-arm kind (jOOQ `Configuration` or JDBC `Connection`), decided once in `ServiceCatalog`, so no emitter re-derives the fork from a type-name string and reusing `DslContext` (a lie the `needsDsl()` family would read) is off the table; `MethodRef.callParams()` already filters to Arg/Context, so the seam drops out of call-parameter arity for free, and the emit-side switches break at compile until the new arm is covered. `ConflictSite.Site` gains a `SessionMount` arm so a mount-versus-`@service` `TypeConflict` names `<mount>` rather than only the routine class, and the dev goal's string-constructible-payload predicate reads off the resolved carrier rather than re-deriving it.
* **Source SPI.** Emit the source record (`DataSource`, `SQLDialect`, `Settings`, null settings defaulting to `new Settings()`) and take a default source plus `Map<? extends K, Source>` on the runtime's canonical constructor, keeping the existing `DataSource`-and-dialect forms as delegating conveniences. The `requiresPostgres` wiring-time guard is deleted rather than made per-entry, because the sugar it protected is deleted. The carrier's one remaining minting site becomes `DSL.using(connection, source.dialect(), source.settings())`, and the hook's provider-free `Configuration` comes from the same call, so a consumer's schema mapping reaches both the fetchers' SQL and their own mount method. `dialect()` stays as the default source's accessor rather than being deleted, since it is a public generated surface.
* **Emission.** `functionHookImpl` becomes a direct-call emitter, the generated hook class's static `mount` body: it takes its already-typed payload parameters (supplied by its caller, see `PinnedConnection` retyping below) and forwards them into mount's call in mount's own declaration order: `return com.example.db.Routines.connect(cfg, claims);`. It never reads `graphQLContext` itself, the same shape the current hardcoded `connect(Connection, String claims)` already has. The generated hook builds its own provider-free `Configuration` from the connection and the resolved source's dialect and settings, per the source-SPI bullet above, or passes the raw `Connection` when the resolved `SessionSeam` kind says so (the fork from Resolution, decided once in `ServiceCatalog`, never a type-name test at the emitter).
* **No interface.** `ConnectionRuntimeClassGenerator.sessionHook` stops emitting a unit: the `SessionHook` interface, its anonymous `NONE`, and `GraphitronRuntime`'s `sessionHook` field are deleted, and `acquire`/`release` call the generated hook class's static methods directly. `RuntimeHookProjection` goes with them, since the re-fire took one of its three facts and the sugar takes another, leaving a single hook-initializer `CodeBlock` that no longer needs to exist once the choice is "emit the call or do not". The emit plan loses one committed unit and `ConnectionRuntimeClassGeneratorTest` loses its interface assertions.
* **The pinned carrier retypes, and the per-key carrier becomes the one acquisition seam.** `PinnedConnection` carries no payload field: `acquire` takes the reflected payload parameters directly (typed, one per parameter) and passes them straight into the generated hook class's static `mount`, retaining only the handle field, which takes the reflected handle type. It keeps asserting autocommit before mount and failing closed by evicting on a throwing mount, and it loses `remountAfterSettle` and `afterSettle` entirely. That assertion is not optional cleanup once the re-fire is gone: it is the invariant the deletion rests on, so it stays, and `release` keeps rolling back before switching the mode. What does change is how the code says it. "Normalize" and "restore the prior autocommit" are retired here, and the phrasing is not confined to one comment: it runs to roughly eleven surviving sites across `ConnectionRuntimeClassGenerator` (class javadoc, the `acquire` and `release` comments) and `GraphitronTransactionProviderGenerator` (class javadoc, `begin`'s deferred-rollback comment, `rollback`'s top-level comment, `settle`'s javadoc), five of them javadoc *emitted into generated output* on `SessionHook`'s two methods and on `acquire` itself, so a consumer reading the generated source reads the retired framing. All of it is rewritten to the assertion: graphitron asserts autocommit on a connection it owns, and the comment states what that excludes. The sites that merely describe the re-fire seam (the `afterSettle` field javadoc, the canonical constructor's, the callback comment in `settle`) die with the mechanism instead. The payload is held for the request by the per-key carrier that performs lazy acquisition, the role `TenantConnections` fills today (holding `claims` for exactly this reason), now unified across both paths with single-tenant as the one-key case: an entry is `(connection, dsl, handle)` minted together on acquisition and cleared together on release, so `acquire` is called from one place and every mount, first or subsequent, runs on the path that already holds the payload. Mount's return value is written to the entry's two readers, never one derived from the other: the pinned carrier's handle field, which release reads to call `unmount`, and the entry's `Configuration` `.data()` slot the `$session` sigil reads. `CLAIMS_KEY` is deleted outright rather than replaced: `claims` is now an ordinary contextArgument with its own name-keyed entry, read where the instrumentation used to read `CLAIMS_KEY` and handed to the carrier at construction.
* **Facade.** `newOwnedExecutionInput` gains one ordinary contextArgument parameter per reflected payload parameter, in the same alphabetical, name-keyed population every other contextArgument already occupies; there is no separate leading block and no collision rejection to add, since a same-named collision is `ContextArgumentClassifier`'s existing `TypeConflict` check. Javadoc is emitted from the same resolved facts.
* **Sigil.** `$session` cannot tokenize through the shared `GraphQLSelectionParser.parseEntries` (`Lexer.readVariable` yields `TokenKind.VARIABLE` for any `$`-prefixed text, and `parseEntries` hard-rejects a value token that is not `TokenKind.NAME`), and `parseEntries` is shared with `GraphitronFactCapture`'s eight argMapping/columnMapping call sites (`GraphitronFactCapture.java:349,383,424,461,591,602,660,697`, all through its `pairs` helper), so the fix cannot live there. Instead the sigil vocabulary gets one owner in the `FieldSourceSigil` shape (the literal set, the parse fork, the admitted-site predicate, the canonical messages, unit-pinnable the way `parseRawValue` is): `ArgBindingMap.parseArgMapping` routes each entry's raw RHS through it before delegating to `parseEntries`, and `GraphitronFactCapture`'s argMapping call sites route through the same owner, so the build side and the capture side cannot drift on what a sigil is; the columnMapping call sites do not, no sigil is admitted there, and a `$` there still quarantines. `parseEntries` itself is untouched. On the capture side a recognized sigil is a decode decision carried as a fact, not a string left for readers to re-peek: the row lands in a sibling sigil relation on the pair relation's key rather than in `argument_path`, whose column comment is a closed two-alternative statement and whose rows feed dangling-author-reference detection that a generator-supplied sigil must not trip. A `$session` argMapping therefore keeps its full pair set and writes no `graphitron_undecoded_argument` row, which would otherwise be a valid literal sitting in the malformed-overflow relation. A recognized `$session` is admitted at the `@service` site only and lowered to a new structural `ParamSource` variant. Its call-site extraction reads `dsl.configuration().data(KEY)` off the `DSLContext` local the call site resolves via `TenantDslEmitter.dslExpression` (forcing that local to be declared when a field's argMapping uses `$session`, even if nothing else on the call needed one), never off `graphQLContext`. Rejections, all located: unknown sigil naming the allowed set (existing pattern), `$session` at a non-admitted argMapping site naming the admitted one, `$session` against a `HandleLess` mount, `$session` with no method-hook `<sessionState>` configured (the message names the field coordinate, the sigil, and the missing config), and bound-parameter type not satisfied by the reflected handle type, naming both. One failure is runtime rather than build-time, because the build cannot see which factory the caller used: a `$session` read on an escape-hatch operation throws in `TenantConnections.of(env)`'s shape, naming the field coordinate, the sigil, and the owned entry points, instead of binding null. Scope for this item: `$session` is wired into the classifier and the diagnostics it raises; whether it also becomes an argMapping completion suggestion (`FieldSourceSigil`'s completions arm) is a small, non-gating follow-up, since it is one more entry in an existing admitted-sigil list rather than a new mechanism.
* **Census.** A `<mount>`/`<unmount>` reference is reflection-only, outside the classpath census: `ClasspathScanner.readIfCandidate` deliberately drops the consumer's jOOQ output package, and admitting the routine surface would grow the `jvm_` fact relations for no present consumer. ## Trade-offs to accept explicitly

* **The contract is a convention to learn, but the common case is zero hand-written Java.** `<mount>Routines#connect</mount>` names jOOQ's own generated method; the consumer writes a facade only when the call needs massaging, and the facade is those ~6 lines of their own generated jOOQ API, typed and reviewable in their own module. What replaces the deleted resolution subsystem is a signature convention (one seam parameter, the rest is payload, return is handle), and it is the convention `@service` already teaches. The one case that gets strictly more work is the deployment with no routine at all, which loses the `<variables>` sugar and writes a three-line method instead; that is accepted deliberately, for the reasons in its own section.
* **Factory arity grows with the payload, but a shared fact enters once.** Mount payload parameters are ordinary contextArguments (see Design), so a per-request fact the mount needs and a `@service` method also wants is one factory slot, not two, with type disagreement caught by the classifier's existing `TypeConflict` rejection. Arity still grows with the payload's parameter count; a consumer drowning in slots can always bundle, since `mount(Configuration cfg, MyRequestIdentity bundle)` is one slot by the same contract. A growth-proof named surface over the factory (a staged builder) would apply to contextArguments generally, predates this item's additions, and belongs to a separate Backlog item rather than being absorbed here.
* **A connection goes back to the pool in autocommit-on, whatever mode it was handed out in.** That is the price of asserting the mode instead of restoring it, and it is worth stating rather than discovering: with `priorAutoCommit` deleted, both `release` and `settle` leave autocommit on, so a pool configured `autoCommit=false` gets its connection back in a mode it did not lend. Every pool graphitron is plausibly deployed behind already resets the flag against its own configuration when a connection is returned or re-checked-out (HikariCP tracks the dirty flag and resets on `close()`; DBCP and Tomcat JDBC reset against `defaultAutoCommit`), so the observable cost is nil. What is bought is that no code path in the runtime has to know what the pool wanted, which is what makes identity survival independent of pool configuration by construction rather than by defence.
* **The headline path's names are jOOQ's names.** On the direct `Routines#connect` path the reflected payload parameter names are jOOQ's own (`pClaims`-style), and under the contextArgument unification they become the public factory-slot identities and the names a same-fact `@service` contextArgument must match; the path also requires the consumer's jOOQ-output module compiled with `-parameters`, enforced loudly by the existing `ParameterNamesMissing` gate (`graphitron-sakila-db` already compiles that way, so the execution fixture is unaffected). The facade path avoids both, because the consumer picks the names. The manual's headline paragraph says so rather than letting the first build failure teach it.
* **The dev goal and MCP `execute` tool need a payload.** `<devDatabase><claims>` supplies one string, which works for any `String`-payload method; with the sugar deleted that is the only shape it covers. A custom payload type cannot be built from a string by graphitron. Recommendation: support string payloads, and degrade with a message naming the limitation, rather than requiring consumers to write a parse method for a dev tool's benefit. Whether a payload is string-constructible is resolved onto the reflected `MethodRef` facts at build time and read by the dev goal, not re-derived at the dev-goal site.

## Design decisions closed at Spec → Ready review

* **Config grammar.** Keeps `<mount>com.example.KernelIdentity#mount</mount>`, not a `<class>`/`<method>` pair. `ExternalCodeReference` (the SDL-level convention for naming a Java class and method, used by `@service`/`@condition`/`@externalField`/`@enum`) splits them into separate `className`/`method` fields, but `<sessionState>` is Mojo XML config, not an SDL input type, and its immediate local precedent, the `<call>Pk_Ras.Connect</call>` single-string form it replaces, is compact. The `#` form the spec already uses throughout Design, Implementation, and the user-doc draft is consistent with that local precedent and needs no rewrite.
* **Whether the methods must be static.** Static-only (`MethodRef.StaticOnly`) for v1, as the Design and Implementation sections already commit to throughout. A session hook holds no state worth injecting, so there is no case pulling toward `MethodRef.Service.callShape()` yet; add instance support via a fresh Backlog item if a real consumer needs it.
* **Where the payload parameter sits relative to the connection.** Detect the seam parameter by type, not position: exactly one declared parameter typed `Configuration` or `Connection`, anywhere in the parameter list; zero or more than one match is a reflection rejection naming the method. This avoids a positional convention a consumer has to remember, and it costs nothing extra to implement since the reflection walk already has to inspect every parameter's type to build `MethodRef.params()`.

## Design decisions closed at the SPI revision

A design pass on the SPI shape, prompted by the observation that this is a mapping problem over methods the consumer already has, closed these:

* **The SPI is a signature contract, not a facade class.** jOOQ's generated `Routines` executing methods satisfy the contract as-is, so the primary documented path is naming them directly, and the hand-written facade demotes to the escape hatch. The contract is written to fit jOOQ's fixed output, not the other way around; the resolver never learns whether a method was generated or hand-written, which is what makes the two paths one path.
* **Overload selection is the seam rule.** jOOQ emits same-named `Field`-expression overloads beside every executing method, so overloading is the normal case, not a corner. Exactly one same-named method may carry a seam parameter; ambiguity is a rejection naming the candidates, raised through `ServiceCatalog.pickMethod`'s single ambiguity vocabulary. No grammar for naming a specific overload.
* **Declaration order survives only inside the emitted call into mount.** Payload parameters are name-keyed contextArguments and sort alphabetically like every other contextArgument slot, so regenerating `Routines` after a database-side parameter reorder cannot silently reorder factory slots under a still-compiling caller; the generator preserves mount's own declaration order only at the one call site that has to invoke mount positionally.
* **A `<mount>` reference is reflection-only, outside the classpath census.** `ClasspathScanner` deliberately drops the jOOQ output package, so the census, the store's `jvm_` relations, and the LSP will not see a routine-class method that reflection resolves fine. Admitting the routine surface would grow the census for no present consumer; instead the exclusion stands, and the scanner's javadoc enumeration of referencing modes is repointed in the same change so it does not remain as a narrower truth.
* **The former R640 is absorbed, redesigned from contextArgument publication to the `$session` sigil.** Publication needed a second classifier provenance and four open forks (availability ordering, mid-operation staleness, fan-out scope, opt-in surface); binding the handle at the consuming site dissolves all four, with fan-out inverting from a build-time rejection into per-connection semantics. `$session` stays lexically disjoint from argument and contextArgument names by construction (GraphQL names cannot start with `$`), independent of whether the payload side is unified with contextArguments or not.

## Payload/contextArgument unification reopens a closed decision

The SPI revision's "Name binding to contextArguments was considered and folded" decision (an earlier draft of this section) is reversed: mount payload parameters are ordinary contextArguments, not a disjoint namespace, per Design above. The folding reasoning does not survive scrutiny against the codebase's own precedent: its strongest ground was that "an unrelated SDL edit adding a contextArgument could re-route an identity-mount input by name coincidence, on the wrong side of the integrity gradient", but this is exactly how contextArguments already work between arbitrary `@service`/`@condition` sites today, `ContextArgumentClassifier` unifies same-named entries from unrelated directive sites all the time, guarded by the same `TypeConflict` rejection this design now reuses for the payload side. Treating that coupling as intolerable specifically for mount-to-contextArgument binding while accepting it everywhere else in the same classifier was inconsistent, not a genuine risk the fold avoided.

Mechanically the reversal is a small extension, not a restructuring: `ContextArgumentClassifier.collectFromMethodRef` already accepts a bare `MethodRef` and does its dedup/type-agreement reduction independent of how entries arrived, and the resolved session-hook carrier is a `GraphitronSchema` component placed upstream of the classification in the constructor chain (see Implementation § Resolution), so the classifier takes mount's payload as an additional root as a function of the model's own components, not of which convenience constructor a caller used. `GraphitronFacadeGenerator` consumes the population as an opaque `List<ResolvedContextArg>`, so the merge is transparent downstream of the classifier. One thing to say plainly rather than imply: the population is walk-side, and the walk is a surface being drained, not a place to extend; during the window the facade generator has nowhere else to source from, so the extension is transitional debt riding the classifier's own drain, with the store as its destination when that surface migrates. It is named here as debt, not presented as the destination.

The reversal also deletes machinery this item had drafted and never needed to build: the bundled carrier record (Design, Implementation §§ Emission/Carrier record/Facade in earlier drafts), the dedicated "payload slot" factory block and its ordering discipline separate from contextArguments, and the payload-name-collides-with-contextArgument rejection, replaced by the classifier's existing `TypeConflict`. It also resolves the "fact can enter twice" trade-off this item had accepted as residue: a payload fact a `@service` method also wants is now one slot, supplied once, not two.

**`-parameters` is not new machinery either.** `ReflectionError.ParameterNamesMissing` already exists and already fails the build today for any Arg- or Context-bindable parameter reflected without a real name (`ServiceCatalog.reflectServiceMethod`/`reflectTableMethod`, gated on `Parameter.isNamePresent()`); a mount payload parameter, now Context-sourced, inherits this gate automatically. What the earlier carrier-record draft would have needed, a synthesized-name fallback for a missing `-parameters` flag, is precisely what this reversal makes unnecessary and wrong: a synthesized name would have become the literal public factory-parameter identity, not just an internal record field name, which is worse under unification than it would have been under the disjoint design.

## Gaps found at the second Spec → Ready pass

None of them is an ownership question: every generated class named here is graphitron's own, with no consumer contract, so its shape is free to change. Two of the findings were about the settle re-fire and the `$session` read route, and both are resolved above by deletion rather than by routing. For the record, since the resolution replaced the mechanism instead of fixing it:

## User documentation (first-client check)

Draft replacement for the function-hook subsection of `docs/manual/reference/mojo-configuration.adoc` § Session identity. If this does not read more simply than what it replaces, the design is wrong.

> **Mounting identity from your own code.** When identity lives behind a database routine, you usually already have the method: jOOQ generates an executing method for every routine into your `Routines` class. Name it. `mount` runs on each connection graphitron takes, before any SQL on it; `unmount` runs when that connection goes back to the pool:
>
> ```xml
> <sessionState>
>   <mount>com.example.db.Routines#connect</mount>
>   <unmount>com.example.db.Routines#disconnect</unmount>
> </sessionState>
> ```
>
> Graphitron reads the signatures at build time: everything but the `Configuration` parameter is the payload, and the return type is the handle later passed to `unmount`. Each payload parameter becomes an ordinary contextArgument on the generated factory, so passing the wrong shape is a compile error rather than a cast failure inside the database. Compile the module that owns the named class with `-parameters` so the parameter names are real (graphitron fails the build naming the method if they are missing); the factory parameter names are the method's own, jOOQ's `pClaims`-style names on a generated routine method, yours on a facade. If a service method also needs the same value, declare it as a `contextArgument` with the same name and type; it is the same fact, supplied once, not two separately-maintained copies:
>
> ```java
> var input = Graphitron.newOwnedExecutionInput(claims, userId).query(query).build();
> ```
>
> When the call needs massaging, a procedure with several OUT parameters, a mount that combines two calls, a payload reshaped before binding, write a static method of the same shape and name that instead:
>
> ```java
> public final class KernelIdentity {
>     public static SessionHandleRecord mount(Configuration cfg, ClaimsRecord claims) {
>         var call = new Connect();
>         call.setPClaims(claims);
>         call.execute(cfg);
>         return call.getPHandle();
>     }
>     public static void unmount(Configuration cfg, SessionHandleRecord handle) { ... }
> }
> ```
>
> Your services can consume the identity your `mount` resolved. Bind a parameter to `mount`'s return value with the `$session` sigil, and the parameter receives the handle from the connection the call runs on:
>
> ```graphql
> access: [Entitlement] @service(
>   service: { className: "com.example.AccessService", method: "entitlements" },
>   argMapping: "identity: $session")
> ```
>
> Under tenant fan-out each call sees its own tenant's handle. The parameter's type must match your `mount`'s return type; both are your declarations, checked at build time.
>
> The `Configuration` you are handed is bound to the connection your `mount` is mounting and carries the jOOQ `Settings` you gave the runtime, so a schema mapping you configured applies to your routine call as it does to graphitron's own SQL. It carries no transaction provider, because both methods run outside any transaction, on a connection graphitron holds in autocommit. Declare a `Connection` parameter instead if you want raw JDBC. A throwing `mount` evicts the connection rather than returning it to the pool, and fails the request before any of your query's SQL runs.
>
> **When your methods run, and what your `mount` must mount.** Graphitron takes a connection when a field first needs one, mounts identity on it, holds it for the rest of the request, and unmounts before returning it to the pool. `mount` runs with autocommit on and no transaction open, so what it sets is committed session state: a mutation field's transaction committing or rolling back later cannot revert it, and graphitron does not re-run your methods around those boundaries. What this asks of you is that identity be *session*-scoped in your database's own vocabulary, session GUCs on Postgres, a session or global application context on Oracle. Transaction-scoped storage will not work, and will not work from the first query rather than failing later: `set_config(..., true)` and `SET LOCAL` revert at the end of the statement that set them, and rows in an `ON COMMIT DELETE ROWS` temp table are deleted by the mount's own implicit commit. One deployment requirement follows: put graphitron in front of a pool that hands out sessions, not a transaction-pooling proxy such as pgbouncer in transaction mode, which resets session state between transactions and would leave your identity on a backend nobody reads.
>
> **`<unmount>` is optional.** If your `mount` establishes identity wholesale rather than adding to whatever the connection already carried, the next request's mount overwrites the last one's, nothing can read stale identity, and unmount only costs you a round trip per request. Omit it. Keep an unmount when something other than graphitron reads scoped data on the same pool, your own DAO code, a migration tool, an admin script, because those readers never mount and would inherit the previous caller's identity.
>
> **If you have no routine at all.** Setting a session variable that your RLS policies read is the same shape, written out:
>
> ```java
> public final class Identity {
>     public static void mount(Configuration cfg, String tenantId) {
>         cfg.dsl().execute("select set_config('app.tenant', ?, false)", tenantId);
>     }
>     public static void unmount(Configuration cfg) {
>         cfg.dsl().execute("select set_config('app.tenant', '', false)");
>     }
> }
> ```
>
> Be aware of what this does and does not give you. A session variable is a convention: any SQL running on that connection can overwrite it, including a `@service` method of your own. If you need identity that consumer code on the same connection cannot forge, mount it with a definer-rights routine, or pass a signed token your `mount` verifies in the database. That choice is yours to make and graphitron cannot check it for you, which is why it is explained in the security guide rather than warned about at build time.

Two paragraphs move out of generator javadoc into the manual rather than being deleted with the code they described, per the sugar section: the GUC clear semantics (why a touched placeholder GUC cannot return to unset, so an RLS policy must treat `NULL` and `''` alike) belongs beside the unmount example above, and the convention-versus-definer-versus-token gradient the deleted fence warning carried belongs in the security guide. Also rewrite: the "Producing the claims payload" and integrity-gradient sections of `docs/architecture/reference/runtime-extension-points.adoc`, `docs/security.adoc`, and the owned-path paragraph of `docs/manual/how-to/tenant-scoping.adoc`. The integrity gradient reads better against a method than against a config block, with one care: on the headline path there is no consumer Java, so the rewrite must tell the gradient against the routine's own definition and the Mojo line that names it (the cryptographic fence is a routine verifying a raw token in-database, the enforced fence is a definer-rights package), and only on the facade path does "visible in the consumer's own code" hold literally.

## Implementation notes for review (deviations and additions discovered in flight)

* **Dev executor mount preflight.** Lazy acquisition moved the mount inside fetchers, where the emitted error router redacts failures behind a correlation id; that silently broke the dev tool's shipped contract (graphitron-mcp's `DevQueryExecutorTest`/`ExecuteToolTest` pin that a rejected payload surfaces as the mount method's own error, verbatim). The generated `GraphitronDevExecutor.execute` now preflights the payload once through the emitted hook pair (mount, then unmount when configured) before building the engine, so a rejected payload propagates as the method's own exception; execution's own mount then overwrites the preflight's on the same connection. Documented in the emitted javadoc; pinned by `DevExecuteExecutionTest.rejectedClaims_surfaceTheHooksOwnError`.
* **Per-tenant fixture databases need the session objects.** The multitenant fixture package inherits the plugin-level `<sessionState>`, so every tenant acquisition mounts; the tenant execution tests create bare per-tenant databases, which now install the session UDTs, sequence, and routines via a shared `TenantSessionFixture` helper. The fan-out SQL baseline's per-tenant frame is repinned to mount, statement, unmount (the hook methods' own jOOQ routine calls, not generator-authored SQL).
* **Two-tenant distinct handles.** Proven by `TenantFanOutExecutionTest.sessionBoundServiceUnderFanOut_readsTwoDistinctHandlesInOneOperation` over a `mountedPrincipal` `$session` batched child service on the multitenant `Film` type; the tenants' handle sequences are restarted into disjoint ranges so the observed session number identifies the minting tenant.
* **`$session` forces tenant inheritance on service children.** Writing that proof surfaced a gap: a plain service return's SQL reach is empty, so `TenantBindingIndex` classified it `Untenanted` and the batch ran on the default source, reading the default connection's handle. A method call that binds `$session` reads per-connection state, so which connection serves it is semantics, not plumbing: a new classification arm makes a `$session`-binding field under a tenant context classify `Inherited` (tenant-partitioned loader, `dslFor` acquisition), while a `$session` field at an untenanted root stays `Untenanted`. Pinned in `TenantBindingClassificationTest`; service children without a `$session` binding keep their existing `Untenanted` classification.
* **The mutation-committed `$session` complement** is covered at the `PinnedConnection` tier (`identityCarriesAcrossTransactionBoundaries_withNoHookRunningInBetween`); the handle rides the carrier entry, which is untouched by settles by construction. No dedicated same-operation mutation-plus-`$session` engine row was added.
