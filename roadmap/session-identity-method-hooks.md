# Session identity is a Java method resolved at build time, not generated SQL

`<sessionState>` names database routines as strings, and graphitron generates the call: `ConnectionRuntimeClassGenerator.functionHookImpl` assembles `{ call <fn>(?) }` and binds the payload with `cs.setString(1, claims)`, behind a generated `SessionHook` interface whose two methods are hardcoded `connect(Connection, String claims)` returning `String` and `disconnect(Connection, String handle)`.

Every problem this item was filed for is downstream of that one choice. A consumer whose routine takes a user-defined type has no way to call it, because nothing casts and the parameter arrives typed `varchar`. A consumer whose routine takes two arguments has nowhere to put the second. A consumer whose routine resolves identity in the database cannot see the result in Java, because the OUT value is captured as an opaque `String` on a private field. `<handle>true</handle>` exists as an author-declared boolean, cross-checked against a second author-declared boolean, to describe what the routine's own signature already states.

Fixing that in place means teaching graphitron to *type* a database call it generates: resolve the routine name against the jOOQ catalog, reflect parameters and directions, distinguish the value setter from the `Field` overload, distinguish an OUT parameter's generated getter from a `RETURNS` function's inherited `getReturnValue()`, handle Oracle's package-qualified naming, reject overloads it cannot disambiguate, and fail closed when jOOQ codegen emitted no routines. That is a catalog-resolution subsystem built to reconstruct type information **jOOQ codegen already generated for the consumer**, in their own module, as a typed routine class with typed setters.

So do not generate the call. Name the consumer's method in config, resolve it at build time with the reflection graphitron already does for `@service`, and emit a direct call.

## Design

The SPI is a signature contract, not a class to implement. Graphitron names a static method in config, reflects it at build time, and emits a direct call; whether jOOQ generated the method or the consumer wrote it is invisible to the resolver, because the contract is signature-shaped:

* **Public static.**
* **Exactly one seam parameter**, typed `org.jooq.Configuration` or `java.sql.Connection`, anywhere in the parameter list. The seam rule is also the overload selector: among same-named methods on the named class, exactly one must carry a seam parameter; zero or several is a build-time rejection naming the candidates.
* **Mount:** the remaining parameters, in declaration order, are the payload; the return type is the handle, `void` meaning handle-less.
* **Unmount:** the remaining parameters are either exactly the handle type or empty. Empty is legal even when mount returns a handle (a disconnect routine that clears session state takes no argument; the handle is still retained for `$session` consumers); a single parameter of any other type is the handle-mismatch rejection, naming both signatures. The return type is unconstrained and discarded, so pointing unmount at a routine that happens to return a status value is not a rejection.
* **Checked exceptions:** any declared checked exception is a rejection. `MethodRef.declaredExceptions()` already carries the fact; the rejection site is this item's to add, because the existing enforcer (`FieldBuilder.checkDeclaredCheckedExceptions`) is field-scoped, matching against a field's `@error` channels, and a session hook has neither a field coordinate nor an error channel. Unchecked propagates into the fail-closed eviction.

The contract is written to fit what jOOQ codegen already emits, because that output is not ours to change. For every routine, jOOQ generates into the consumer's `Routines` class a static executing method of exactly this shape (verified against `graphitron-sakila-db`'s generated output):

```java
// jOOQ-generated, in the consumer's own module
public static SessionHandleRecord connect(Configuration configuration, ClaimsRecord pClaims) { ... }
```

So the common case is zero hand-written Java:

```xml
<sessionState>
  <mount>com.example.db.Routines#connect</mount>
  <unmount>com.example.db.Routines#disconnect</unmount>
  <stateSurvivesTransactions>true</stateSurvivesTransactions>
</sessionState>
```

The same-named `Field`-expression overloads jOOQ generates beside the executing method carry no seam parameter, so the seam rule resolves `Routines` names without a grammar for picking an overload.

When the call needs massaging (a procedure with several OUT parameters, a mount combining two calls, a payload reshaped before binding), the consumer writes a facade satisfying the same contract, and the resolver cannot tell the difference:

```java
public final class KernelIdentity {
    public static SessionHandleRecord mount(Configuration cfg, ClaimsRecord claims) {
        var call = new Connect();          // jOOQ-generated routine class
        call.setPClaims(claims);           // typed setter, jOOQ binds the composite
        call.execute(cfg);
        return call.getPHandle();
    }
    public static void unmount(Configuration cfg, SessionHandleRecord handle) { /* symmetric */ }
}
```

Graphitron reflects the named methods at build time and emits a direct call into the generated hook body. `ServiceCatalog` is already "the mirror of `JooqCatalog` for the service layer: it wraps the catalog and adds the Java-reflection logic needed to introspect service classes at build time", and `MethodRef` is already "a resolved reference to a user-provided Java method" carrying `className`, `methodName`, a javapoet `TypeName` return type off `getGenericReturnType()`, and params in declaration order. A session hook is a user-provided Java method, so this is that carrier's population, not a new one. (This is the opposite conclusion from reusing `RoutineRef`, which is a catalog handle whose params bind from GraphQL arguments and source columns; the distinction is what the thing *is*.)

Everything the item was reaching for is then a reflected fact rather than built machinery:

* **Typed payload.** The mount method's payload parameter type is whatever the consumer declared: a jOOQ `UDTRecord` for a composite, a `String` for a raw JWS, a record of their own. jOOQ does the binding, because it is jOOQ's own generated setter doing it.
* **Typed handle.** The reflected return type. Because `unmount`'s parameter is reflected too, "connect's output type matches disconnect's input type" is checked against two real signatures at build time, and the mismatch message names both. `<handle>` is deleted: its content is the return type being `void` or not.
* **Multiple arguments.** A Java signature fact. `MethodRef.params()` is already an ordered list; the factory grows one dedicated, typed leading slot per reflected payload parameter. No arity machinery.
* **Build time, not runtime.** The consumer's class is named in config and resolved during generation, so nothing is registered, nothing is dispatched polymorphically, and the emitted call site is a direct static invocation. A misnamed *routine* additionally stops needing any check from graphitron: the consumer's module does not compile. The enforcer is javac, in the module that owns the claim.
* **The facade stays static and typed.** Because the payload type is known at generation time, `Graphitron.newOwnedExecutionInput(ClaimsRecord claims, ...)` keeps its current static shape with a better type. No generics on the runtime, no move to an instance method.
* **The handle stops being opaque.** A mount that resolves identity in-database (the institution, the entitlement set, the resolved principal) returns a value service code can consume, because the value has a reflected type. The consuming surface is the `$session` argMapping sigil below; this absorbs the former companion item R640, whose contextArgument-publication premise the sigil obsoletes.

**How the payload travels: every hop is generated, so every hop is typed.** The facade constructs a generated carrier record with one component per mount payload parameter (for the example above, `record MountArguments(ClaimsRecord claims)`), and stores it in the `GraphQLContext` under one graphitron-owned key, replacing `CLAIMS_KEY`'s bare `String`. The instrumentation reads the record typed and hands it to `acquire`; the generated `SessionHook` implementation spreads the components back into the direct call; `PinnedConnection` retains the record, which is what the `afterSettle` re-mount replays, and mount's return value is stored typed beside it, so unmount's inputs are wholly runtime-internal and the consumer supplies the payload exactly once per request. The record is generated uniformly even for a single payload parameter, one code path and a stable named type under the key; a mount whose only parameter is the seam gets no record and no factory slot. The one untyped hop, the string-keyed `GraphQLContext`, has its write and read sites generated from the same reflection pass, so it is safe by construction, the same trick the instrumentation already plays with today's `String`.

**Payload slots and the contextArgument namespace stay disjoint.** Every payload parameter becomes a dedicated factory slot; none binds to a declared contextArgument. A payload parameter whose name collides with a declared contextArgument is a build-time rejection naming both declarations: the factory cannot carry two parameters of one name, a silent rename would be exactly the quiet coupling this item exists to remove, and rejecting the collision reserves the name-match case, so a binding feature added later would change the semantics of no configuration that builds today. Within the factory, payload slots lead as a block ordered alphabetically by parameter name, the same TreeMap discipline the contextArgument slots already use; declaration order stays load-bearing only inside the generated call into mount, where it is the generator's positional fact and never the consumer's. That matters on the headline path: `Routines` renders the *database routine's* parameter order, so a routine reordering two same-typed parameters would otherwise silently reorder the factory's slots under a caller whose arguments still compile. The accepted residue of keeping the namespaces disjoint is duplication: a per-request fact the mount needs and a contextArgument also carries is passed twice at the factory call site, and nothing checks the two values agree. That call site is one place, written once per application, which is where the exposure is at least visible; a consumer for whom it bites can bundle, since `mount(Configuration cfg, MyRequestIdentity bundle)` is one slot by the same contract.

**Graphitron hands over a `Configuration`, and that is load-bearing.** The published request `DSLContext` carries `GraphitronTransactionProvider` on its live configuration, the transaction-demarcation seam; if a hook ran through that, "both halves run outside any transaction" would stop being structural. Because graphitron constructs what it passes, it passes a provider-free `DSL.using(connection, dialect).configuration()`, and the invariant stays structural rather than becoming a documented request. Accept a declared `Connection` parameter too, for a consumer who wants raw JDBC.

**The generated `SessionHook` interface stays, and becomes sealed.** It is generated code between generated classes, so it is not a runtime dependency; it gives `GraphitronRuntime` a field to hold and `PinnedConnection` something to call. Sealing it to permit only the generated implementation and a generated no-op makes "this is not a consumer extension point" structural, exactly as `GraphitronContext` is sealed to permit only `GraphitronContextImpl`. Its two methods take the reflected payload and handle types.

## What this deletes

The whole string-named-routine path, and everything the catalog-reflection design would have needed:

* `<connect>` / `<disconnect>` / `<handle>`; `SessionStateBinding.HookBinding`, `AbstractRewriteMojo.toRawHook`.
* `SessionStateConfig.FunctionHooks`, `Unmount.PairedDisconnect`'s handle component, `SessionStateConfig.RawHook`, and the handle-agreement rules in `SessionStateConfig.from`.
* `ConnectionRuntimeClassGenerator.functionHookImpl` and `functionDisconnect`'s callable-string assembly.
* Never built: routine-name resolution off the catalog, the Oracle package-qualified probe, the `Pk_Ras.Connect` schema-versus-package ambiguity, overload disambiguation grammar, the value-setter versus `Field`-overload pick, the OUT-getter versus inherited-`getReturnValue()` fork, the `<routines>true</routines>` precondition, and the `sql_routine` fact-relation question.

`SessionStateConfig` keeps three arms (`None`, `Variables`, and the method-hook arm replacing `FunctionHooks`), and `<stateSurvivesTransactions>` stays a declaration, since it is not a signature fact. `MethodRef` already carries `declaredExceptions()` as the fact; the hook-side rejection consuming it is new (see the contract above), since `FieldBuilder.checkDeclaredCheckedExceptions` enforces a field-scoped rule this item cannot reuse.

## Unmount is optional

The shipped design rejects `<connect>` without `<disconnect>` on the grounds that "identity that mounts must unmount", and offers an empty `<disconnect/>` as an explicit opt-out whose javadoc calls it an exposure. That is too strong, and it charges every request a round trip for it.

Mount-only is sound whenever mount establishes identity *wholesale* rather than merging into whatever the connection already had, because then the mount at the start of operation N+1 overwrites everything the mount at operation N wrote. Since the same mount method runs every time, the set of state it writes is constant, so the overwrite is total by construction. Nothing can observe stale identity, because nothing reads scoped data on a pooled connection before a mount has run on it. The condition on that argument is the part worth stating rather than assuming: it holds while every reader of scoped data mounts first, which in practice means the pool is graphitron's. A consumer sharing that pool with their own DAO code, a migration tool, or an admin script has a reader that does not mount, and for them unmount is what keeps the previous caller's identity from being read. That is a property of the deployment, not of the schema, so it is the consumer's call and not something graphitron can infer.

So: `<unmount>` is simply optional. Omitting it means mount-only, with no opt-out ceremony and no rejection. This collapses `SessionStateConfig.Unmount` (and both its arms) into an optional method reference on the method-hook arm, and it removes the pairing-validation family from `SessionStateConfig.from` along with the handle rules.

Latency is the payoff, and it is larger than one call. Unmount costs a round trip at every release. It also costs at every mutation-field settle: without `<stateSurvivesTransactions>`, `PinnedConnection.afterSettle` re-fires the *pair*, so a mount-only hook halves the re-fire to a single re-mount. That re-mount is exactly the overwrite the mount-only argument rests on, so the two fit together rather than trading off.

**Correcting the record while deleting it.** `Unmount.UnmountFree`'s javadoc states that "the generation-time warning in `SessionStateWarnings` names this exposure". No such warning exists: `SessionStateWarnings.forConfig`'s `FunctionHooks` arm returns `List.of()`, and the only two warnings are `no-session-state` and `session-state-convention-fence`. The exposure was asserted in prose with nothing enforcing it, which is the shape the project's own principles call out, and it is evidence that the mount-must-unmount rule was never load-bearing in code. The stale sentence goes with the type. Separately, the `session-state-convention-fence` message text points readers at "the function-hook `<connect>`/`<disconnect>` form" and needs updating to the new element names.

**The `<variables>` sugar is untouched.** It is the one place graphitron genuinely should generate SQL, because there is no consumer method to call. Its generated implementation keeps its current shape, and every current sugar consumer, including `graphitron-sakila-example` and `SessionHookExecutionTest`, changes nothing.

## The handle reaches service calls as the `$session` argMapping sigil

This absorbs the former R640, which was filed against the duplicated derivation the opaque handle forces: a connect routine that resolves identity in the database returns facts service code cannot see, contextArguments are exclusively caller-supplied, so a service wanting the same facts re-derives them from the raw claims in Java with nothing binding the two derivations. R640's shape was "publish the handle as a contextArgument", which required a second provenance in the classifier and carried four design forks. Binding the handle at the consuming site dissolves all four, so the capability ships here as part of the SPI design rather than as a follow-on.

A service binds a parameter to the handle in `argMapping`, in the grammar it already uses for "the names don't line up, bind explicitly":

```graphql
someField: [Film] @service(
  service: { className: "com.example.FilmService", method: "films" },
  argMapping: "identity: $session")
```

The sigil joins the established `$source`/`$errors` family: recognized by prefix test, stored as written, an unknown sigil rejected at parse time naming the allowed set, admission per site (`@service` `argMapping` in v1; other argMapping sites reject it naming the admitted site, the `$source` precedent exactly). GraphQL names cannot start with `$`, so the sigil is lexically disjoint from argument names by construction, and the contextArgument namespace is never involved: no factory slot, no classifier provenance, no publication name to choose. Publication-as-asked-for is satisfied by each use being the ask.

The bound parameter becomes a structural `ParamSource` variant, the pattern `DslContext`/`Sources`/`Table` already set: supplied by the generator, filtered out of `callParams()`, its emit-time extraction reading `dsl.configuration().data(KEY)` off the same `DSLContext` local the call site already resolves (forcing that local to be declared when it otherwise wouldn't be). That read placement is what dissolves R640's forks:

* **Ordering.** Mount runs on a connection before any operation SQL, so a service call holding that connection's `DSLContext` always reads a mounted handle. No "not yet mounted" runtime state.
* **Staleness.** The handle is stashed on the resolved `Configuration`'s own `.data()` map (jOOQ's per-`Configuration` key-value store) at mount time and overwritten there on the settle re-fire, so a per-call read of that same key is simply what the next read sees. Nothing is written once into request scope and left to rot.
* **Fan-out inverts from rejection into semantics, because the read is per-`Configuration`, not per-request.** R640's load-bearing scope call was that N tenant connections mean N handles and one request-scoped contextArgument slot cannot represent them; its answer was to reject fan-out plus publication. The single-tenant request-scoped slot (`graphQLContext.put(DSLContext.class, dsl)`) is exactly that one-slot shape and cannot carry N handles, so `$session` does not read it. Instead the generated call site resolves its `DSLContext` the same way the fan-out scatter path already does, `TenantDslEmitter.dslExpression` (single-tenant: `graphitronContext(env).getDslContext(env)`; multi-tenant: `TenantConnections.dslFor(env, tenantKey)`), and reads the handle off that `Configuration`'s `.data()` entry. A fetch running under a tenant reads *that tenant's* handle because it is reading that tenant's `Configuration`, not because of any implicit locality claim. Per-tenant identity is not an edge case; it is the read location doing the scoping.
* **Type agreement** is the reflection family again: the bound parameter's declared type against mount's reflected return type, rejection naming both. `$session` against a `HandleLess` mount is a located rejection: the mount returns `void`, there is no session handle to bind.

The accepted cost is a new kind of cross-artifact edge: SDL that uses `$session` builds only against a `<sessionState>` whose mount returns a handle, so the schema is less self-contained than one that smuggles identity through re-derivation. That coupling is real (the service genuinely consumes deployment-produced identity), and the sigil makes it visible and located; the rejection message when the config side is absent has to carry the whole story, naming the field coordinate, the sigil, and the missing config.

## Implementation

* **Config.** Replace `<connect>`/`<disconnect>` with `<mount>`/`<unmount>` taking `fqcn#method`, `<unmount>` optional. Keep `<stateSurvivesTransactions>`; drop the handle rules and the pairing rules, and collapse `Unmount` into an optional method reference. An `<unmount>` with no `<mount>` stays a rejection: unmounting what nothing mounted is a defect in either direction of reading it. For the Maven-config fact family's boundary question: the authored facts are the two `fqcn#method` strings and the `<stateSurvivesTransactions>` boolean as configured; the reflected signatures, payload and handle types are derived views, never stored back. `SessionStateConfig.from`'s rejection requiring a paired disconnect before the flag can be declared is deleted along with it: mount-only re-fires as a single re-mount (see "Unmount is optional" above), so a mount-only hook can legitimately declare survival, and the general "no method-hook configured at all" guard is unrelated and stays.
* **Resolution.** Reflect both methods through `ServiceCatalog`'s existing Java-reflection path into `MethodRef.StaticOnly` (already the variant for "static-by-construction method references"). `ServiceCatalog` stays the only holder of raw `java.lang.reflect` and of the seam-type test, per the capture-boundary containment invariant; no session-package reflector. Overload selection extends the one existing resolution point (`ServiceCatalog.pickMethod`) with the seam filter as an explicit input, so `ReflectionError.AmbiguousMethod` stays the single ambiguity vocabulary and "zero or several seam-carrying candidates" is a variant in the same family, naming the candidates; a second session-hook-local resolver is exactly the two-answers drift the principles warn about. The resolved carrier is the new method-hook arm itself (the one replacing the deleted `FunctionHooks`), the record that takes over `FunctionHooks`' structural position one level above the doomed `Unmount` hierarchy: it carries `<stateSurvivesTransactions>` as a plain field, plus a sealed fork on the handle axis, not one type with a nullable handle, for the mount/unmount `MethodRef`s themselves, a `Handled` arm (mount, handle `TypeName`, optional unmount) and a `HandleLess` arm (mount, optional unmount). The flag sits on the outer record because it is orthogonal to that axis (a handle-less mount-only hook can survive transactions exactly as a handled one can); pushing it into either arm would duplicate the field or force a meaningless default on the other. "Handle-less implies unmount takes nothing, implies `PinnedConnection` has no handle field, implies the `SessionHook` unmount method takes only the connection" stays structural on the inner fork, and every emit site switches once on the arm instead of re-testing the return type for `void`. This is the same property `SessionStateConfig.Unmount`'s sealing carries today ("a handle produced by connect that no disconnect binds" is unrepresentable), moved from declaration to reflection along with the fact itself. Rejections are the existing reflection family (`ReflectionError`, unresolvable class or method, non-static, no seam parameter or more than one candidate, seam-overload ambiguity naming the candidates, handle-type mismatch between the two signatures, payload-parameter name colliding with a declared contextArgument, declared checked exception).
* **Emission.** `functionHookImpl` becomes a direct-call emitter that spreads the carrier record back into the mount signature's declaration order: `return com.example.db.Routines.connect(cfg, args.claims());`. The generated hook builds its own provider-free `Configuration` from the connection and the runtime's dialect, or passes the raw `Connection` when that is what the method declares.
* **Carrier record.** A nested record on the instrumentation class, so it is namespaced rather than a new top-level unit in the consumer's autocompletion, and its name is minted by the plan's naming vocabulary like every generated unit. One component per mount payload parameter, name-keyed and ordered alphabetically like the factory slots; the factory constructs it, the instrumentation reads it typed under the graphitron-owned key, `acquire` takes it. Component names come from reflection when `-parameters` is present, synthesized otherwise.
* **Interface.** `ConnectionRuntimeClassGenerator.sessionHook` emits a sealed `SessionHook` typed by the reflected payload and handle types, permitting the generated implementation and a generated no-op replacing the current anonymous `NONE`.
* **Carrier retyping.** `PinnedConnection`'s retained payload field holds the carrier record and the mutable handle field takes the reflected handle type; `acquire` keeps normalizing autocommit before mount and failing closed by evicting on a throwing mount; `afterSettle` keeps the re-fire, replaying the retained record. `CLAIMS_KEY` is replaced by the carrier record's own key, read typed in `GraphitronConnectionInstrumentationGenerator`. Mount's return value is written to two places on every mount and re-mount, never one derived from the other: `PinnedConnection`'s own handle field, which internal release/re-fire logic reads to call `unmount`, and the same `Configuration`'s `.data()` entry the `$session` sigil reads. Multi-tenant fan-out mints its own per-tenant pinned carrier (`pinnedByTenant` in `ConnectionRuntimeClassGenerator`), so this is one write pattern applied once per tenant connection, not a single-tenant special case.
* **Facade.** `newOwnedExecutionInput` gains one dedicated slot per payload parameter, a leading block ordered alphabetically by name, ahead of the fan-out slot and the schema's contextArgument slots; a name collision with a declared contextArgument is the resolution-time rejection above. Javadoc is emitted from the same resolved facts.
* **Sigil.** `$session` cannot tokenize through the shared `GraphQLSelectionParser.parseEntries` (`Lexer.readVariable` yields `TokenKind.VARIABLE` for any `$`-prefixed text, and `parseEntries` hard-rejects a value token that is not `TokenKind.NAME`), and `parseEntries` is shared with `GraphitronFactCapture`'s nine argMapping/columnMapping call sites, so the fix cannot live there. Instead `ArgBindingMap.parseArgMapping` peeks each entry's raw RHS text for a `$`-prefix before delegating to `parseEntries`, the same raw-string-seam shape `FieldSourceSigil` already uses for `$source`/`$errors`; this is local to the one caller and changes nothing `parseEntries` or its other callers rely on. A recognized `$session` is admitted at the `@service` site only and lowered to a new structural `ParamSource` variant. Its call-site extraction reads `dsl.configuration().data(KEY)` off the `DSLContext` local the call site resolves via `TenantDslEmitter.dslExpression` (forcing that local to be declared when a field's argMapping uses `$session`, even if nothing else on the call needed one), never off `graphQLContext`. Rejections, all located: unknown sigil naming the allowed set (existing pattern), `$session` at a non-admitted argMapping site naming the admitted one, `$session` against a `HandleLess` mount, `$session` with no method-hook `<sessionState>` configured (the message names the field coordinate, the sigil, and the missing config), and bound-parameter type not satisfied by the reflected handle type, naming both. Scope for this item: `$session` is wired into the classifier and the diagnostics it raises; whether it also becomes an argMapping completion suggestion (`FieldSourceSigil`'s completions arm) is a small, non-gating follow-up, since it is one more entry in an existing admitted-sigil list rather than a new mechanism.
* **Census.** A `<mount>`/`<unmount>` reference is reflection-only, outside the classpath census: `ClasspathScanner.readIfCandidate` deliberately drops the consumer's jOOQ output package, and admitting the routine surface would grow the `jvm_` fact relations for no present consumer. The scanner's javadoc enumerates why jOOQ classes are excluded ("referenced through `@table`/`@reference`, not `@service`"); this item adds a third referencing mode, so that enumeration is repointed in the same change rather than left standing as a narrower truth.
* **Two declaration-forcing meta-tests need their registries edited.** `RejectionResidueDrainageTest` spells `ReflectionError`'s leaves individually, and `RejectionSeverityCoverageTest` walks `Rejection`'s permits for an LSP severity mapping; the new seam-related `ReflectionError` variants (no/several seam candidates, seam-overload ambiguity) fail both until their hardcoded declarations are updated. Both fail loudly at build time, so this costs a round trip, not correctness, but it belongs in the implementer's checklist rather than a surprise.
* **Two prose corrections that ship with the code, not before it.** `Unmount.UnmountFree`'s javadoc claims `SessionStateWarnings` warns about an unmount-free configuration; it does not, and which way that resolves depends on this item's unmount decision (delete the claim if unmount becomes optional, add the warning if it does not), so the edit belongs here rather than as a standalone comment fix. And `SessionStateWarnings`' `session-state-convention-fence` message directs readers to "the function-hook `<connect>`/`<disconnect>` form with a SECURITY DEFINER connect"; that text is accurate against today's elements and becomes wrong the moment they are renamed, so it is repointed in the same change that renames them.
* **Fixture and execution coverage.** The form has never run end to end: `graphitron-sakila-example` configures the `<variables>` sugar at the plugin level; four of the five `rewrite-generate*` executions inherit it, and `rewrite-generate` itself repeats an identical block rather than inheriting (redundant, not a divergence, but worth trimming when this item is in the file), so all five generate the same sugar implementation today. `SessionHookExecutionTest` drives the sugar, and no mount/unmount routine exists in `graphitron-sakila-db`. Add a composite payload type, a composite handle type, and the two routines to `init.sql`, plus a fixture class whose static methods call them through their generated routine classes. Prove the round trip against real PostgreSQL with RLS, in the shape `SessionHookExecutionTest` establishes: RLS-scoped reads see only permitted rows, a mutation's post-commit read-back still does (the settle re-fire), identity is absent after unmount, and a throwing mount fails closed.

## Trade-offs to accept explicitly

* **The contract is a convention to learn, but the common case is zero hand-written Java.** `<mount>Routines#connect</mount>` names jOOQ's own generated method; the consumer writes a facade only when the call needs massaging, and the facade is those ~6 lines of their own generated jOOQ API, typed and reviewable in their own module. What replaces the deleted resolution subsystem is a signature convention (one seam parameter, the rest is payload, return is handle), and it is the convention `@service` already teaches. The zero-code path for the common Postgres case, the `<variables>` sugar, also still exists.
* **Factory arity grows with the payload, and a fact can enter twice.** Payload slots and contextArgument slots are disjoint namespaces, so a per-request fact the mount needs and a contextArgument also carries is passed twice at the factory call site, with nothing checking agreement (binding them by name was considered and folded; see the closed decisions). The factory is one call site per application, written once in the consumer's HTTP layer, so the exposure is at least concentrated and visible; a consumer drowning in payload slots can always bundle, since `mount(Configuration cfg, MyRequestIdentity bundle)` is one slot by the same contract. A growth-proof named surface over the factory (a staged builder) would apply to contextArguments generally, predates this item's additions, and belongs to a separate Backlog item rather than being absorbed here.
* **The dev goal and MCP `execute` tool need a payload.** `<devDatabase><claims>` supplies one string, which works unchanged for the sugar and for any `String`-payload method. A custom payload type cannot be built from a string by graphitron. Recommendation: support string payloads and the sugar, and degrade with a message naming the limitation, rather than requiring consumers to write a parse method for a dev tool's benefit. Whether a payload is string-constructible is resolved onto the carrier at build time and read by the dev goal, not re-derived at the dev-goal site.

## Design decisions closed at Spec → Ready review

* **Config grammar.** Keeps `<mount>com.example.KernelIdentity#mount</mount>`, not a `<class>`/`<method>` pair. `ExternalCodeReference` (the SDL-level convention for naming a Java class and method, used by `@service`/`@condition`/`@externalField`/`@enum`) splits them into separate `className`/`method` fields, but `<sessionState>` is Mojo XML config, not an SDL input type, and its immediate local precedent, the `<call>Pk_Ras.Connect</call>` single-string form it replaces, is compact. The `#` form the spec already uses throughout Design, Implementation, and the user-doc draft is consistent with that local precedent and needs no rewrite.
* **Whether the methods must be static.** Static-only (`MethodRef.StaticOnly`) for v1, as the Design and Implementation sections already commit to throughout. A session hook holds no state worth injecting, so there is no case pulling toward `MethodRef.Service.callShape()` yet; add instance support via a fresh Backlog item if a real consumer needs it.
* **Where the payload parameter sits relative to the connection.** Detect the seam parameter by type, not position: exactly one declared parameter typed `Configuration` or `Connection`, anywhere in the parameter list; zero or more than one match is a reflection rejection naming the method. This avoids a positional convention a consumer has to remember, and it costs nothing extra to implement since the reflection walk already has to inspect every parameter's type to build `MethodRef.params()`.

## Design decisions closed at the SPI revision

A design pass on the SPI shape, prompted by the observation that this is a mapping problem over methods the consumer already has, closed these:

* **The SPI is a signature contract, not a facade class.** jOOQ's generated `Routines` executing methods satisfy the contract as-is, so the primary documented path is naming them directly, and the hand-written facade demotes to the escape hatch. The contract is written to fit jOOQ's fixed output, not the other way around; the resolver never learns whether a method was generated or hand-written, which is what makes the two paths one path.
* **Overload selection is the seam rule.** jOOQ emits same-named `Field`-expression overloads beside every executing method, so overloading is the normal case, not a corner. Exactly one same-named method may carry a seam parameter; ambiguity is a rejection naming the candidates, raised through `ServiceCatalog.pickMethod`'s single ambiguity vocabulary. No grammar for naming a specific overload.
* **Name binding to contextArguments was considered and folded.** The draft rule bound a payload parameter to a declared contextArgument when their names matched, to keep one per-request fact from entering the request through two slots. Folded, on three grounds. It made parameter names load-bearing, the quiet coupling this item exists to remove. Its trigger matched against the schema-wide contextArgument population with a declaration at neither end, where the `@service` precedent it claimed is site-authored (`ServiceCatalog.reflectServiceMethod` receives the directive site's declared key set, so a parameter is context-sourced only because the author said so at that site); an unrelated SDL edit adding a contextArgument could re-route an identity-mount input by name coincidence, on the wrong side of the integrity gradient. And on the headline path it protected nothing: jOOQ mints parameter names from the database's (`pClaims`, `pCustomerId`), which never collide with schema contextArgument names, so the match fired exactly where the docs don't lead. Instead the namespaces stay disjoint and a name collision is a rejection, which also reserves the name-match case: a binding feature added later (site-authored, an explicit mapping in `<sessionState>`) changes the semantics of no configuration that builds today.
* **Payload slots are name-keyed and alphabetical; declaration order is the generator's fact.** The factory's payload block sorts by parameter name, the discipline the contextArgument slots already follow, so regenerating `Routines` after a database-side parameter reorder cannot silently reorder factory slots under a still-compiling caller. Declaration order survives only inside the emitted call into mount.
* **The carrier record is uniform and nested.** Generated even for a single payload parameter, so there is one transport path and the graphitron-owned context key always holds a stable named type; nested on the instrumentation class rather than minted as a new top-level unit, so it stays out of the consumer's top-level autocompletion and inside the plan's naming vocabulary.
* **A `<mount>` reference is reflection-only, outside the classpath census.** `ClasspathScanner` deliberately drops the jOOQ output package, so the census, the store's `jvm_` relations, and the LSP will not see a routine-class method that reflection resolves fine. Admitting the routine surface would grow the census for no present consumer; instead the exclusion stands, and the scanner's javadoc enumeration of referencing modes is repointed in the same change so it does not remain as a narrower truth.
* **The former R640 is absorbed, redesigned from contextArgument publication to the `$session` sigil.** Publication needed a second classifier provenance and four open forks (availability ordering, mid-operation staleness, fan-out scope, opt-in surface); binding the handle at the consuming site dissolves all four, with fan-out inverting from a build-time rejection into per-connection semantics. This is also the site-authored explicit binding the folded name-binding decision reserved: authored in `argMapping` at the service site, in an existing grammar with an existing sigil family, lexically disjoint from argument and contextArgument names, so the namespaces stay as disjoint as the fold left them.

## Gaps closed following the Spec → Ready rework

Three gaps were found between the plan and the tree at the last Spec → Ready pass, each checked against the code rather than reasoned from the plan. All three are resolved below, and folded into Design/Implementation/Tests above rather than left standing here as a separate account.

1. **`$session` cannot reach a prefix test at the argMapping seam.** `Lexer.readVariable` always yields `TokenKind.VARIABLE` for `$`-prefixed text, and the shared `GraphQLSelectionParser.parseEntries` hard-rejects any value token that is not `TokenKind.NAME`, so `argMapping: "identity: $session"` fails inside `ArgBindingMap.parseArgMapping` before any sigil logic runs. `parseEntries` is shared with `GraphitronFactCapture`'s nine argMapping/columnMapping call sites, so teaching the parser itself to accept `VARIABLE` values is not local. Resolved in favor of the narrow fix: `parseArgMapping` receives the raw string before tokenization, so it peeks each entry's RHS for a `$`-prefix and short-circuits into sigil handling before delegating to `parseEntries`, the same raw-string-seam shape `FieldSourceSigil` already uses for `$source`/`$errors`. Reflected in the Implementation § Sigil bullet and a `parseEntries`-non-regression row in Tests.

2. **The `$session` read route was unnamed, and the fan-out claim as stated was false.** The request-scoped slot published today, `graphQLContext.put(DSLContext.class, dsl)`, is a single slot per request; reading a handle from it would silently reintroduce the one-slot shape the absorbed companion item's fan-out fork was rejected for. Resolved: the handle is stashed on the resolved `Configuration`'s own `.data()` map (jOOQ's per-`Configuration` key-value store) at mount/re-mount time, and `$session` extraction reads that same key off the `DSLContext` local the generated call site already resolves via `TenantDslEmitter.dslExpression`, the identical expression the fan-out scatter path uses to mint its per-tenant contexts. That read is genuinely per-connection, so the per-tenant claim holds by construction. Reflected in Design (the `$session` bullets) and Implementation § Sigil, with an Execution-tier test proving two tenants read two distinct handles in one operation.

3. **`<stateSurvivesTransactions>` lost its home when `Unmount` collapses.** The flag lives today on `Unmount.PairedDisconnect`, which this item deletes; it is orthogonal to the new `Handled`/`HandleLess` handle-axis fork, so it cannot move into either arm without duplicating it or forcing a meaningless default on the other. Resolved: the flag sits on the new method-hook arm itself (the record replacing the deleted `FunctionHooks`, one level above the handle-axis fork). `SessionStateConfig.from`'s rejection requiring a paired disconnect before the flag can be declared is deleted along with it, since a mount-only hook now re-fires as a single re-mount and can legitimately opt in to survival; `SessionStateConfigTest.stateSurvivesTransactions_withUnmountFreeOptOut_rejected` flips from a rejection pin to an acceptance case. Reflected in Implementation §§ Config and Resolution, and in Tests.

Smaller, non-gating notes from the same pass, also folded in above: `RejectionResidueDrainageTest` and `RejectionSeverityCoverageTest` need their hardcoded leaf declarations updated for the new `ReflectionError` seam variants (Implementation § Census, Tests); `$session` participates in the classifier and diagnostics for v1, with argMapping completions for it scoped as a small non-gating follow-up (Implementation § Sigil); and the fixture note about `graphitron-sakila-example`'s five executions is corrected to "four inherit the plugin-level sugar block, one repeats it identically" (Implementation § Fixture and execution coverage).

## User documentation (first-client check)

Draft replacement for the function-hook subsection of `docs/manual/reference/mojo-configuration.adoc` § Session identity. If this does not read more simply than what it replaces, the design is wrong.

> **Mounting identity from your own code.** When identity lives behind a database routine, you usually already have the method: jOOQ generates an executing method for every routine into your `Routines` class. Name it. `mount` runs on the freshly pinned connection before any operation SQL; `unmount` runs at release:
>
> ```xml
> <sessionState>
>   <mount>com.example.db.Routines#connect</mount>
>   <unmount>com.example.db.Routines#disconnect</unmount>
> </sessionState>
> ```
>
> Graphitron reads the signatures at build time: everything but the `Configuration` parameter is the payload, and the return type is the handle later passed to `unmount`. The generated factory then takes your payload type, so passing the wrong shape is a compile error rather than a cast failure inside the database:
>
> ```java
> var input = Graphitron.newOwnedExecutionInput(claims, userId).query(query).build();
> ```
>
> When the call needs massaging, a procedure with several OUT parameters, a mount that combines two calls, a payload reshaped before binding, write a static method of the same shape and name that instead:
>
> ```java
> public final class KernelIdentity {
>     public static SessionHandleRecord mount(Configuration cfg, ClaimsRecord claims) {
>         var call = new Connect();
>         call.setPClaims(claims);
>         call.execute(cfg);
>         return call.getPHandle();
>     }
>     public static void unmount(Configuration cfg, SessionHandleRecord handle) { ... }
> }
> ```
>
> Your services can consume the identity your `mount` resolved. Bind a parameter to `mount`'s return value with the `$session` sigil, and the parameter receives the handle from the connection the call runs on:
>
> ```graphql
> access: [Entitlement] @service(
>   service: { className: "com.example.AccessService", method: "entitlements" },
>   argMapping: "identity: $session")
> ```
>
> Under tenant fan-out each call sees its own tenant's handle, and after a mutation settles, the re-mounted value is what later reads see. The parameter's type must match your `mount`'s return type; both are your declarations, checked at build time.
>
> The `Configuration` you are handed is bound to the pinned connection and carries no transaction provider, because both methods run outside any transaction, on a connection normalized to autocommit. Declare a `Connection` parameter instead if you want raw JDBC. A throwing `mount` evicts the connection and fails the request before any SQL runs.
>
> **`<unmount>` is optional.** If your `mount` establishes identity wholesale rather than adding to whatever the connection already carried, the next request's mount overwrites the last one's, nothing can read stale identity, and unmount only costs you a round trip per request. Omit it. Keep an unmount when something other than graphitron reads scoped data on the same pool, your own DAO code, a migration tool, an admin script, because those readers never mount and would inherit the previous caller's identity.
>
> Add `<stateSurvivesTransactions>true</stateSurvivesTransactions>` only if your mounted state genuinely survives a commit or rollback; otherwise graphitron re-mounts after each mutation-field settle (re-firing the pair, if you have an unmount).
>
> For the common Postgres case you need none of this: the `<variables>` sugar generates both halves from a list of session variables.

Also rewrite: the "Producing the claims payload" and integrity-gradient sections of `docs/architecture/reference/runtime-extension-points.adoc`, `docs/security.adoc`, and the owned-path paragraph of `docs/manual/how-to/tenant-scoping.adoc`. The integrity gradient reads better against a method than against a config block, with one care: on the headline path there is no consumer Java, so the rewrite must tell the gradient against the routine's own definition and the Mojo line that names it (the cryptographic fence is a routine verifying a raw token in-database, the enforced fence is a definer-rights package), and only on the facade path does "visible in the consumer's own code" hold literally.

## Tests

* **Unit.** `SessionStateConfigTest` for the method-hook arm with and without `<unmount>`, and for the surviving unmount-without-mount rejection; the handle and pairing rules go with the elements they validated. `stateSurvivesTransactions_withUnmountFreeOptOut_rejected` flips from a rejection pin to an acceptance case: a mount-only hook may declare `<stateSurvivesTransactions>`, and the flag lands on the outer method-hook arm rather than either handle-axis arm. Reflection rejections: unresolvable class, unresolvable method, non-static, wrong seam parameter, seam-overload ambiguity (two same-named seam-bearing methods) and its complement (jOOQ's triple-overload shape resolving to the one executing method), handle-type mismatch between the two signatures, payload-parameter name colliding with a declared contextArgument, declared checked exception on either method. Contract acceptance: handle-ignoring unmount (empty non-seam parameters against a handle-returning mount), discarded unmount return value. Carrier record: name-keyed alphabetical components matching the slot order, single-parameter uniformity, seam-only mount producing no record and no slot, synthesized component names when `-parameters` is absent (with the existing once-per-build warning). Sealed carrier: the `HandleLess` arm emits no handle field on `PinnedConnection` and an unmount taking only the connection. `SessionHookImplGeneratorTest` for the emitted direct call spreading the record in the mount signature's declaration order, the mount-only shape (release does nothing, `afterSettle` re-mounts without an unmount call), the sealed interface, the generated no-op, and the provider-free `Configuration`. Update `RejectionResidueDrainageTest` and `RejectionSeverityCoverageTest`'s hardcoded leaf declarations for the new `ReflectionError` seam variants.
* **Sigil unit rows.** `ArgBindingMap.parseArgMapping`'s local `$`-prefix pre-scan: `identity: $session` lowers to the structural variant and drops out of `callParams()`, without touching `parseEntries` or its `GraphitronFactCapture` call sites (a regression row confirming those call sites are unaffected). Rejections: unknown sigil at the argMapping seam naming the allowed set, `$session` at a non-admitted argMapping site naming the admitted one, `$session` against a `HandleLess` mount, `$session` with no method-hook `<sessionState>`, bound-parameter type mismatch naming both declarations.
* **Pipeline.** The owned factory's parameter list against a reflected multi-parameter payload, including the single-`String` case that reproduces today's signature, and the ordering fact: payload slots sort alphabetically by name regardless of the mount signature's declaration order, while the emitted call preserves declaration order. For the sigil: the emitted service call reads `dsl.configuration().data(KEY)`, not `graphQLContext`, and the factory grows no slot for it; a dedicated row pins the *not-via-`graphQLContext`* half of that assertion, since it is what distinguishes the per-connection read from the rejected one-slot-per-request design.
* **Compilation.** A consumer-shaped hook class and the generated sources compile at `<release>17</release>` in `graphitron-sakila-example`.
* **Execution.** The form's first end-to-end proof, with composite types both directions, per the fixture above. Point `<mount>` directly at the jOOQ-generated `Routines` method for one execution shape and at the hand-written facade for another, so "generated and hand-written are indistinguishable to the resolver" is proven rather than asserted. A `$session`-bound service method proves the handle round trip: it sees the identity the mount resolved, and after a mutation-field settle it sees the re-mounted value, not the original. Under multi-tenant fan-out, a `$session`-bound service call made against two different tenants in the same operation proves it reads two distinct handles, the assertion that actually distinguishes per-connection semantics from the rejected single-slot design.
* **Warnings.** `SessionStateWarningsTest` keeps `no-session-state` and `session-state-convention-fence` (a sugar-side warning, unaffected except for its message text naming the old elements). No unmount-free warning is added: mount-only is a supported configuration, and its precondition is about the consumer's pool, which graphitron cannot see.

## Retired vocabulary

* `<sessionState>`'s `<connect>`, `<disconnect>` and `<handle>` elements; "connect callable", "disconnect callable", "the callables", and "function-hook form".
* `SessionStateConfig.FunctionHooks`, `SessionStateConfig.RawHook`, `SessionStateBinding.HookBinding`, and the whole `SessionStateConfig.Unmount` hierarchy (`Unmount`, `Unmount.PairedDisconnect`, `Unmount.UnmountFree`), replaced by an optional method reference.
* "identity that mounts must unmount", "unmount-free opt-out", and the claim that `SessionStateWarnings` warns about an unmount-free configuration (it never did).
* `CLAIMS_KEY` and its `no.sikt.graphitron.request.claims` value.
* "opaque claims payload" / "the opaque claims" as the description of the mount parameter. The word `claims` itself is not retired: the `<variables>` sugar's `<claim>` mapping and the dev-goal `<claims>` config both name a genuine claims document.
* "publish the session-hook return value as a contextArgument", "runtime-mounted contextArgument", and "second provenance" as descriptions of how the handle reaches service code; the handle is bound at the consuming site by the `$session` sigil, and contextArguments remain exclusively caller-supplied.
