# An error handler that an earlier handler shadows is reported, as a warning or an error

## Goal

An author who declares an `@error` handler that can never claim an exception, because a handler tried earlier claims everything it would, is told so when the schema is built, as a warning or as an error according to a setting the consumer chooses. Dispatch itself stays as Graphitron 9 had it (R1167, `error-dispatch-matches-graphitron-9`): handlers are tried in the order the schema declares them, and graphitron does not reorder them. Today such a handler goes dead with no diagnostic unless its criteria are identical to the earlier one's.

```graphql
union FilmLookupError = FilmLookupCatchAll | FilmLookupInvalid

type FilmLookupCatchAll @error(handlers: [
    {handler: GENERIC, className: "java.lang.RuntimeException", description: "The film lookup failed."}
]) { path: [String!]! message: String! }

type FilmLookupInvalid @error(handlers: [
    {handler: GENERIC, className: "java.lang.IllegalArgumentException"}
]) { path: [String!]! message: String! }
```

Every `IllegalArgumentException` is a `RuntimeException`, and the catch-all is declared first, so `FilmLookupInvalid` is never answered. After this item the build says that the `IllegalArgumentException` handler is unreachable behind the `RuntimeException` handler of `FilmLookupCatchAll`, and the author moves the catch-all last.

The decision is Filip's of 2026-11-11: narrowest-first ordering (R1165, discarded) is dropped in favour of Graphitron 9's declared order plus this diagnostic.

## Glossary

- *Handler*: one entry of an `@error` type's `handlers:` argument; its *kind* is `GENERIC`, `DATABASE` or `VALIDATION`.
- *Errors container*: the union, interface or single `@error` type that a payload's errors field lists. A producer field (a `@service` field, or a payload-returning `@mutation` or `@routine` write) catches into it. Every `@error` type is also a container of itself, whether or not an errors field lists it alone: the order of its own handlers is a fact of the type.
- *Claims*: a handler claims a throw when dispatch offers it a link of the throw's cause chain that its predicate holds for. A `GENERIC` handler is offered every link from the outer exception down; a `DATABASE` handler is offered one, the first `SQLException` below an outer jOOQ `DataAccessException` (R1167).
- *Defect*: a row of the fact store (the per-graph database the generator fills from the SDL, the classpath and the jOOQ catalog) saying a schema breaks a declared rule. Each rule is one code in `graphitron_defect_type` with a severity; an `error` code stops `validate` and `generate` through the store's verdict (`docs/architecture/explanation/defects-as-facts.adoc`).

## Today

Two handlers with identical criteria in one container are refused (`ChannelRuleChecks.checkDuplicateMatchCriteria`, "rule 8", with a copy in `FieldBuilder` for the DML path). Nothing else is checked: a broad handler declared before a narrower one of the same kind leaves the narrower one dead, silently. The reference page tells the author to order handlers by hand ("Nothing sorts by specificity").

## The rule

R1167 fixes the order this rule judges by, and was still in Spec when this was written: at pickup, confirm it landed with the order stated here, and reopen this item if it did not. As its spec stood on 2026-11-12, dispatch walks one order: the container's `DATABASE` handlers, only when the outer exception is a jOOQ `DataAccessException`, then its `GENERIC` handlers. Within a kind the order is declared order: the container's `@error` types in member order, then each type's `handlers:` in array order.

**Handler A is shadowed in a container when a handler B of the same kind, declared before A in that container, claims every throw A claims.** That is decidable from what the author wrote and the class hierarchy:

- `GENERIC` behind `GENERIC`: A's class is B's class or a subtype of it, and B has no `matches:` or A's `matches:` text contains B's.
- `DATABASE` behind `DATABASE`: B has no `sqlState`/`code` or A carries the same one, and the same `matches:` rule holds. Every `DATABASE` handler is offered the same one link and reads the same messages above it, so nothing else tells two of them apart.
- `VALIDATION` never enters dispatch and takes no part.

Identical criteria are the case where the containment runs both ways, so this rule covers rule 8 and replaces it.

**A handler of the other kind never shadows.** The report is for a handler that is provably dead, and under R1167 no handler is dead because of the other kind. A `GENERIC` handler never precedes a `DATABASE` one in the order, so it cannot shadow one. A `DATABASE` handler precedes the `GENERIC` ones only for a throw whose outer exception is a `DataAccessException` with an `SQLException` below it, and a `GENERIC` handler is still reached by every other throw of its class: the class thrown as itself, or inside a wrapper that is not a `DataAccessException`, and, where the class is itself a `DataAccessException`, thrown with no `SQLException` below it (the ten domain exceptions of the first consumer R1167 studied are thrown exactly so). So R1165's cross-kind rows through `java.sql.SQLException`, and its "precedes" pair, are not part of this rule. This is why the item depends on R1167 and is not stated against today's single mixed order: against that order a `GENERIC` handler on `Exception` declared first does shadow every `DATABASE` handler, and the rule would report handlers that R1167 brings back to life.

**The grain is the handler in the narrowest container that orders it against its shadower.** A pair within one `@error` type is a fact of the type: the handler is dead wherever the type is a member, and it is reported once, under the type as its own container, not once per union the type is in. (In the first consumer R1167 studied, one type holding two duplicate pairs is the first member of 159 unions.) A pair across two member types is a fact of the union or interface that orders the two types: the same type can be a member of two unions, shadowed in one and live in the other, and each is reported or not on its own. For an interface the members are ordered by type name; the report says which earlier handler it judged against, so the author can see the order.

What is not reported, because it is not provable: two handlers that overlap with neither containing the other (two `matches:` texts on one class, a `sqlState` handler and a `code` handler), and a handler on an abstract class whose every current concrete subclass is claimed earlier.

## Decisions

The first three were put to `principles-architect`; its answers are under "Architect consultation". Decision 1 follows from the architecture pages. Decisions 2, 3 and 4 are Filip's of 2026-11-11: review round 1 put each to him by name with its recommendation, and he asked for the spec to be revised and sent back to review without changing any of them, so each stands as recommended. Decision 5 answers review round 2. It is this revision's, made on Filip's instruction of 2026-11-12 to revise against that round and reported to him with it; `principles-architect` was consulted on it (second consultation, below).

1. **A defect, not a lint rule.** The lint channel has the configuration seat already (`<lint><disabledRules>`), but it has no path to stop a build, and `fact-model.adoc` says nothing new is added to the family its rules are stated in. The defect family stops the build and puts the finding at the handler in the editor. So the rule is one defect code.
2. **The default is `error`, and the setting demotes it to `warning`.** The handler is provably dead, and the remedy is to move one line. A schema arriving from Graphitron 9 with such a handler built there and stops building here until the handler is moved or the code is demoted; R1167's compatibility ruling is about where a throw is routed, not about what is refused, and this decision does not extend it to refusals. Identical criteria are already a hard error today, so `error` by default changes nothing for them. The first consumer R1167 studied shows the case is real: its schemas carry two exact duplicate pairs in the type that opens 159 of its 161 unions, two tuples repeated across members, and three handlers behind a broader one of the same `code` (R1167, "First-client evidence"). Rule 8 refuses that consumer today with no way through; with this item it builds once it demotes the code. That evidence postdates the ruling, so it is recorded here for Filip and does not change the default.
3. **Demotion is a general, small mechanism, used here first.** No consumer setting moves a defect's severity today: `graphitron_defect_type.severity` is "a function of the code and nothing else". A code declares whether it may be demoted (a new boolean column, true for this code and false for every existing one, since most defects leave the generator nothing well defined to emit), the consumer names the codes to demote in the plugin configuration, and naming a code that may not be demoted fails the build. Severity becomes a function of the code and the configuration, both facts in the store, and the two places that state the old rule are restated with it (see "Demotion").
4. **JDK ancestry is captured in this item.** The goal's example compares two JDK classes and the store has no ancestry for them (see "Implementation"). R1166 was the item for that capture and was discarded with R1165; this rule cannot be delivered without it, so its content is folded in here and is not re-filed as an item of its own. The editor's `className:` completion is a second reader of the capture and stays out of this item.
5. **The build reports every warning-severity defect.** Today such a defect shows in the editor and the MCP server and nowhere in a build, so a demoted code would leave the build silent, which is the state this item exists to end. The build logs every warning-severity defect, whether its code is a warning by declaration or by demotion: severity is one fact, and the build, the editor and the MCP server read it alike. The one warning-severity code today, `NODE_METADATA_UNREADABLE`, therefore starts printing in the build log, a consumer-visible change this item owns (see "Warnings in the build log").

## Implementation

**Platform throwables (the capture R1166 described).** `code_throwable` and `code_throwable_supertype` are written by `CodeCapture.throwables` from the classpath census alone, so `java.lang.RuntimeException` appears only as some library exception's `supertype_name` and nothing says `IllegalArgumentException` is one. Capture the platform's throwables into the same two relations under a platform source: both relations key on `store_source`, and `FederationCapture` is the precedent for a source that is not a classpath entry, registered and stamped by version. Stamp this one by the runtime version, so it re-reads when the JDK changes and is swept like any other. Admit the throwables in the packages that the modules of the generator's boot layer export to everyone (`ModuleLayer.boot()`), not `java.base` and `java.sql` alone: the classifier resolves a handler's class by reflection, which loads from any of them, so a narrower capture leaves a class the build accepts and the rule cannot judge (`java.net.http.HttpTimeoutException` after `java.io.IOException`). Attach the platform source to every graph through `store_graph_source`, as `FederationCapture` attaches its library, since the capture is keyed by source and a graph reads only its own sources. The relation comments say the ancestry is that of the JDK the generator runs on, which is what the classifier's reflection reads today. `roadmap/derived-read-cost-is-a-shape-problem.md` plans a reshaping of supertypes in the `code` family; this adds rows and leaves the shape alone.

**The generated client exception.** `<outputPackage>.schema.GraphitronClientException` is emitted by the run and has no `code_throwable` row. `graphitron_runtime_class` is the precedent for a class no classpath declares: add a kind for it and a superclass column (`graphql.GraphqlErrorException`, today the constant `ExceptionClass.GeneratedClientException.SUPERCLASS`), and read its ancestry through that superclass's `code_throwable_supertype` rows. graphql-java's jar is in the captured classpath.

**Two derived relations and the rule.** Names are the implementer's; the grains are not. All three are written in the anchoring phase by a `graphitron` stage that runs after `fetchers` (it reads `graphitron_errors_field`), declared in `meta_stage`, `meta_relation` and `meta_stage_write`, with `touched_at` on every row and a sweep. The `graphitron` gatherer may already read the `code` family (`meta_gatherer_dependency`).

- *Container handler sequence*, grain "one dispatch-capable handler of an errors container, at its declared rank within its kind": keyed by container name, `@error` type name and the handler's declared index (its `position` in `graphitron_ast_error_handler_entry`, which counts every element of the list as written), carrying the kind and the rank, with the handler entry's written position as a cascading foreign key. Containers are every union or interface an errors field lists and every `@error` type as a container of itself. R1167 reads this same order through a query in `ErrorChannelRelation` and turned a stored relation down for having one reader; this rule is the second, so the relation is stored here and `ErrorChannelRelation` is repointed at it. The repointed read keeps ranking for its dispatch index. R1167's index is a handler's ordinal among its type's handlers that are not `VALIDATION`: a fact of the handler in its type and of no container, so the relation does not carry it. The rows of a type's own container are exactly that type's dispatch-capable handlers, and the read ranks them by declared index, in SQL, as R1167's read ranks today.
- *Shadowing*, grain "this handler is shadowed by that earlier handler, in the narrowest container that orders them both": one row per pair for which the rule holds, under the type's own container for a pair within one type and under a union or interface for a pair across two of its member types. A handler can have a row under its own type and another under a union, each naming a different earlier handler; both are true and both are kept, and the relation's comment says so. The rows are a statement over the sequence, the handler entries (`graphitron_ast_error_handler_entry` and its `GENERIC` and `DATABASE` subtype relations) and `code_throwable_supertype`, plus a substring test. "A's class is B's class or a subtype of it" is read as the names being equal or B's class being a `supertype_name` of A's. The equal-names arm reads no ancestry and holds whether or not the class has a `code_throwable` row, so identical criteria are always a row, as rule 8 refuses them today. For the subtype arm, a class present in two classpath entries has two `code_throwable` rows and the rule reads the union of their supertypes. That union is over the sources of the graph being judged and no others: `code_throwable` is keyed by source, so the statement reaches it through `store_graph_source`, and a class on a sibling graph's classpath neither shadows nor is shadowed here.
- *The defect*: one code in `graphitron_defect_type`, `ERROR_HANDLER_SHADOWED` with `lsp_code` `GRAPHITRON_ERROR_HANDLER_SHADOWED` as every existing row pairs the two, written into `graphitron_entry_defect` at the shadowed handler's position, with a detail relation keyed by defect, container and shadowing handler (type name and declared index), never a detail string. Where several earlier handlers shadow one in a container, the detail names the first of that container. The build's message names the earlier handler and the container from those rows, through an explanation read on `EntryDefectVerdict` beside `keyColumns`; the editor and the MCP tool show the statement at the shadowed handler, as they do for every defect whose detail is a relation. Follow "Adding a defect" in `defects-as-facts.adoc`.

**Unresolved classes.** A `GENERIC` handler naming a class with no `code_throwable` row from any source of its graph, and which is not the generated client exception, has no ancestry to read, so the subtype arm gives it no row, as shadower or as shadowed; the equal-names arm still judges it. Where the class does not load, the classifier's existing refusal of the unresolved name is what fails that build. Where it loads and still has no row, as a platform class in a package its module does not export does, the handler is accepted and judged by name alone: such a handler behind one on its superclass is not reported. The shadowing relation's comment says both.

**Rule 8 goes.** Delete `ChannelRuleChecks.checkDuplicateMatchCriteria`, its call in `ErrorChannelWalker`, and the `FieldBuilder.checkDuplicateMatchCriteria` copy with its two callers (`FieldBuilder` and `BuildContext`). Rule 7 (more than one `VALIDATION` handler) is a different rule and stays.

**Demotion.** `graphitron_defect_type` gains the "may be demoted" column. The plugin gains a list parameter naming codes to report as warnings. A consumer writes the `code`, not the `lsp_code`: it is the relation's key, it is never null, and it is what the build failure prints in brackets (`EntryDefectVerdict.error`), which is where a consumer meets the name when the build stops. The configuration gatherer writes the list to a `store_graph_` relation keyed by graph and code, as `store_graph_lint_disabled_rule` is written for `<disabledRules>` (`StoreEntries.lintDisabledRules`), and transcribes it as configured. What makes a wrong entry fail is the relation's key into the vocabulary: the row carries the "may be demoted" value pinned to true, with a foreign key on the code and that value into `graphitron_defect_type`, so a code nothing declares and a code that may not be demoted are both unwritable, as `graphitron_result_class.shape` is pinned so its foreign key holds a type to an object result. The refused write is reported as a build failure that names the entry and lists the codes that may be demoted, read from `graphitron_defect_type` once the write has failed. This is not `LintConfig.validated`'s shape, which compares against a Java enum at the Maven seam before a store is open: the defect vocabulary exists only as rows, so the check is the database's, and the gatherer decides nothing against rows outside its corpus. `graphitron_defect_type` is a stated relation (`meta_stated_relation`), its rows the DDL file's and no gatherer's output, so a key into it from a `store` gatherer's relation reads nothing that runs later; `store_graph_write_stage` keys into the stated `meta_stage` the same way. No architecture page says in words that a stated relation sits outside the gatherer order, so that reading is put to Filip with this revision. `EntryDefectVerdict` and the `diagnostic` view read a finding's severity as the code's own unless the graph demotes it. The two statements of the old rule are restated in the same change: the `graphitron_defect_type.severity` column comment ("A function of the code and nothing else"), and `docs/architecture/explanation/defects-as-facts.adoc`, whose column table, "Adding a defect" steps and closing line ("once declared with `error` severity, the code stops `validate` and `generate`") gain the demotion column, the question a new code answers about it, and the exception a demoted code makes.

**Warnings in the build log.** A warning-severity defect reaches the editor and the MCP server today through the `diagnostic` view's entry arm, and reaches a build nowhere: `EntryDefectVerdict.rows` selects `error` rows only, and the build logs `BuildWarning`s, none of which comes from a defect. The route mirrors the error side. `EntryDefectVerdict` reads both severities, each row at the severity its graph gives the code, and assembles one message for both (the statement, the detail, the explanation, the code in brackets), so a defect reads the same as an error and as a warning. The error rows stay what `GraphQLRewriteGenerator.storedRefusals` turns into build errors. The warning rows are logged by the generator wherever it logs warnings today (`logWarnings`, on every entry point, a round the store refuses included), in the same `file:line:column: warning:` form. They are not `BuildWarning`s, and they are not handed to `ReportFacts.write`. That channel is for findings with no stored row of their own: `BuildWarningFacts` stores what it is given into `lint_finding` and `build_warning_no_rule`, both arms of the `diagnostic` view, so a defect sent that way would show twice in the editor and the MCP tool, beside its own entry arm. The pass carries the stored warnings beside its warnings as it carries `walkErrors` beside `errors`, which is how a stored refusal already stays out of what is written back. `<lint>` suppression does not reach them.

The route is for every warning-severity defect (decision 5), so `NODE_METADATA_UNREADABLE` starts printing. Before landing, count what it hits on the sakila example and in the fact documents: `defects-as-facts.adoc` calls a defect raised on a valid schema a regression to fix ahead of the work it was found during, and a line in every build log is where one would now show. That page's sentence "A warning-severity defect shows in the editor and the MCP server and does not stop a build" is restated with the build log in it, in the same change as the two statements above.

## User documentation (first-client check)

`docs/manual/reference/directives/error.adoc`, Constraints, replacing the duplicate-criteria bullet and following R1167's bullet on order within a kind:

> * A handler that can never be reached is rejected: one declared after a handler of the same kind that matches everything it does. That is a subclass after its superclass, a handler with `matches:` after the same handler without, a `sqlState` or `code` handler after a `DATABASE` handler with neither, or two handlers with the same criteria. The build's message names the earlier handler; declare the narrower one first. A `GENERIC` handler and a `DATABASE` handler never hide one another, whichever is declared first.

`docs/manual/reference/mojo-configuration.adoc`, a new parameter row and a short section:

> Some of the rules graphitron rejects a schema for can be turned into warnings, where the schema still has a well-defined meaning without the fix. Name the rule's code, as shown in the build failure:
>
> [source,xml]
> ----
> <configuration>
>   <reportAsWarnings>
>     <code>ERROR_HANDLER_SHADOWED</code>
>   </reportAsWarnings>
> </configuration>
> ----
>
> A code that is misspelled, or that cannot be turned into a warning, fails the build with the list of codes that can. A rule turned into a warning is still reported: in the build log, in your editor and through the MCP diagnostics tool.

`docs/manual/how-to/error-channel.adoc`: the pitfall on handler order says the build catches it. `docs/manual/how-to/migrating-from-legacy.adoc`: a schema with a handler that was already dead on Graphitron 9 is now rejected, with the `<reportAsWarnings>` entry as the way to migrate first and fix later. `docs/manual/reference/diagnostics-glossary.adoc` gets the code's entry, giving both names: `ERROR_HANDLER_SHADOWED` as the build prints it and `<reportAsWarnings>` takes it, and `GRAPHITRON_ERROR_HANDLER_SHADOWED` as the editor shows it.

## Other solutions we've considered

- **Sort handlers narrowest first (the discarded R1165).** Ends the ordering chore, but answers differently from Graphitron 9 wherever a broad handler was declared first.
- **A lint rule escalated by configuration.** Warning by default through the existing `<lint>` block, with a new child naming rules to treat as errors. It reuses the seat, but a lint finding is assembled after the classification walk and cannot stop `validate` before it, so "error" would be a second verdict path beside the store's.
- **Two defect codes, one per severity.** The configuration would then decide which code a row carries, and a code names the rule broken, not how the consumer feels about it.
- **Check in the classifier, by reflection, beside rule 8.** Smallest, and needs no platform capture. It adds a rule to the walk the store is replacing and reads by reflection a fact the store should hold; the defects page lists the Java-judged rule families as what remains to move.
- **A third `BuildWarning` arm for a stored defect.** One list for every warning, and the sealed switch makes each consumer decide. It puts a finding that has a stored row and a code into the channel for findings that have neither, and its arm in `BuildWarningFacts` would be the one variant whose persistence is a no-op.
- **The build reads its warnings from the `diagnostic` view.** No new read, but the build would then read the editor's surface and not its own verdict: a second build reader beside `EntryDefectVerdict`.
- **Log demoted codes only.** `NODE_METADATA_UNREADABLE` stays out of the build log. Severity would then mean two things, depending on how a code came by it.
- **Check the demotion list in the configuration gatherer before writing it.** A friendlier place to build the message, but a capture phase would be deciding against rows outside its corpus, and the key refuses the same entries.
- **Report a pair within one type once per union the type is in.** One fact stated at the wrong grain: 160 detail rows saying one thing for the first consumer studied.
- **State the rule against today's mixed order, with R1165's cross-kind rows, and land before R1167.** It would report `DATABASE` handlers behind a `GENERIC` catch-all, which R1167 makes reachable: a defect on a schema that is about to be valid.
