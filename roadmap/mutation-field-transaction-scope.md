# One transaction per top-level mutation field, opened by the instrumentation, with nested scopes joining it

## Goal

On the owned-connection engine, every top-level mutation field runs as exactly one database transaction per connection it touches (one in a single-tenant build), which graphitron opens and closes around the whole field, its payload included. Inside that transaction there are no savepoints: a `transaction(...)` or `transactionResult(...)` opened inside the field, by a generated fetcher or by a `@service`, joins it, and a scope a `@service` opened that fails makes the whole field fail, even when the code that opened it caught the exception. A scope graphitron's own fetcher opened needs no such rule, since its failure already fails the field through the fetcher's exception. A field the client is told succeeded has committed; a commit that fails, a transaction the database has already aborted, or a nested failure that was caught, is reported as that field's error. The *owned-connection engine* is the execution mode where graphitron pins one connection per operation and owns its lifecycle (`runtime.newGraphQL(schema)`). A `@service` mutation becomes all-or-nothing like a generated one, and a write and the messages written beside it (an `@outbox` message, say) commit or roll back together. Tracked as GitHub issue sikt-no/graphitron#564.

Against the sakila schema, this request

```graphql
mutation AddFilms {
  a: createFilm(in: {title: "A", languageId: 1}) { id }
  b: createFilm(in: {title: "B", languageId: 999}) { id }   # foreign key violation
}
```

commits field `a`'s row, rolls back field `b`'s, and answers `b` with `null` and an error at its path. Each field is its own transaction, in document order.

A consumer hook that runs at the start of each such transaction is a separate item, split out of this one. The place it attaches is kept open (see No JDBC or consumer code under the field-scope lock).

Graphitron caters to good patterns, not all patterns. Work that must commit independently of the rest of a field belongs in a separate top-level mutation field, which commits on its own in document order, or in a job; graphitron offers no savepoint API, no per-field opt-out and no after-commit phase.

## User documentation (first-client check)

Draft for the section "Transactions on the owned-connection path" in `docs/architecture/reference/runtime-extension-points.adoc` (its Phase 1 text is on trunk; this draft replaces it) and a new section after it:

> **Transactions on the owned-connection path.** Each top-level mutation field runs in one transaction. It begins the first time the field uses a connection and ends when the field's value is complete, payload included: it commits when the field succeeded and rolls back when the field failed. A field fails when its fetcher, or anything under it, threw, whether or not an `@error` channel turned the exception into a typed payload, or when a GraphQL error lies under the field's path. Fields commit independently of each other, in document order. A field that never touches the database opens no transaction. Query operations run in autocommit.
>
> Inside the field there is one transaction and no savepoints. A `transaction(...)` or `transactionResult(...)` your `@service` opens joins the field's transaction, and graphitron logs a warning naming the field and your calling method, once per calling method: leaving it normally commits nothing, and leaving it by an exception marks the whole field to roll back. Catching that exception does not save the field: nothing the field wrote commits, before or after the nested scope, and the field is reported as failed with an error that says a nested transaction failed and the field's writes were rolled back, whatever else went wrong after it; the log under the error's reference says whether your code caught the exception. The same holds on every database. On PostgreSQL there is no carrying on after a failed SQL statement at all: the statement aborted the whole transaction, so the next one fails too. Only an exception that is not a database error leaves the transaction usable after the catch. The same rule applies to a `@service` on a Query field that opens a transaction of its own: what it nests inside that transaction joins it, and a caught nested failure makes the transaction's commit fail. Work that must commit on its own belongs in its own top-level mutation field, or in a job.
>
> A field reported as successful has committed, and a field that rolled back is never shown with a value: a field that rolled back because of an error under it (a nested read in its payload that failed, say) is `null`, like one that failed itself; only an `@error` channel's payload, which describes the failure, is kept. If the commit fails, or the database had already aborted the transaction (on PostgreSQL, any statement that failed inside it aborts it, and the driver's commit then rolls back without an error), the field is reported as failed: its value becomes `null` and the response carries an error at its path, logged under the error's reference. Later fields in the operation still run. The mutations run one field at a time; an engine configured with a mutation execution strategy other than graphql-java's serial one is refused when a mutation starts.
>
> In a multi-tenant build each connection the field touches has its own transaction; there is no transaction across connections. Before committing anything, graphitron checks every connection the field used, the PostgreSQL aborted-transaction check included; a field rolls back on every connection when any of them is not clean. Only then do they commit, in the order the field first used them, so a field is left partly committed only when a commit itself fails on a later connection (a deferred constraint, a serialization failure, a lost connection), and it is then reported as failed with the earlier connections' writes kept.
>
> Under `CommitPolicy.ROLLBACK_ONLY`, the dev-execution mode, each field is one savepoint in a single operation transaction that is discarded at the end, so later fields observe earlier ones. That is the only savepoint graphitron takes.
>


## Current behaviour

Phase 1 of this item is on trunk (`fd9e592`). Every bullet below was checked against the generators on 2026-10-30, at the trunk after the session-identity rework and the first two phases of `@outbox`; those marked *Moved* changed since the plan was last approved. The plan's own nested-scope text (Phase 2) describes code that does not exist yet.

* `GraphitronTransactionProvider` (emitted by `GraphitronTransactionProviderGenerator`) keeps a stack of open scopes, `TopLevel` or `Savepointed`. Its package-private `open()` turns autocommit off on an empty stack under `COMMIT`, and otherwise takes a savepoint (`connection.setSavepoint()`), pushing the scope only once the JDBC call succeeded; the package-private `end(Scope, boolean failed)` ends a scope the carrier holds, popping after a successful commit and before a rollback. The jOOQ path (`begin` / `commit` / `rollback`) records its scope on the `TransactionContext`. So every `transactionResult` nested inside a field today takes a savepoint, the generated DML and `@routine` fetchers' own `transactionResult` included (`TypeFetcherGenerator.renderTransactionalKeyFetch`, `RoutineWriteEmitter`): one subtransaction per nested scope. Under `ROLLBACK_ONLY` a field's own scope is a savepoint in one operation transaction.
* On PostgreSQL a savepoint that writes is a subtransaction with its own transaction id. A backend caches at most 64 subtransactions per transaction; past that it overflows, and until the transaction ends every other session's snapshot checks visibility through `pg_subtrans`, which contends across the cluster and is worse on replicas (PostgreSQL 17's `subtransaction_buffers` softens it). `RELEASE SAVEPOINT` does not free a slot. Savepoints combined with `SELECT ... FOR UPDATE` create multixacts. A savepoint also makes catch-and-continue look safe: code swallows a database failure and keeps going, the hidden-partial-state problem this item exists to remove. A known consumer pattern on the escape hatch today (opptak's `settTilbudsgarantiFraTidligopptak`) takes one savepoint per candidate in a sweep over a whole admission round, hundreds to thousands per transaction; that team will change it.
* `TenantConnections` carries the active `FieldScope` (`MutationFieldScopeEmitter`): every owned acquisition enlists, opening the field's scope on a connection's first use; `settleField(failed)` ends each scope in open order, probing a committing PostgreSQL `TopLevel` scope with `select 1`, rolling back the rest once one fails, never touching a timed-out tenant's connection, and refusing a connection left with an open nested scope. `scatter` captures the dispatching field scope for its workers. `TenantConnections.markFieldFailed(env)` is the lenient static `ErrorRouter` calls from `claim` and `surfaceClientErrorOrRedact`.
* `GraphitronConnectionInstrumentation` settles the previous top-level mutation field in `beginFieldExecution` and the last one in the operation callback, before `releaseAll`; refuses a non-serial mutation strategy; captures the field's `DataFetchingEnvironment` in `beginFieldFetching`; and in `instrumentExecutionResult` (every owned build) nulls a field that failed to settle and adds the error `ErrorRouter.settleFailure(cause, env, path)` built, which is redacted and logged through the configured `FetcherErrorLog.unmatched`. A remembered `SessionMountException` still takes precedence.
* Session identity is no longer a static method named in plugin configuration: the consumer builds an emitted `SessionState` per request and passes it to the generated factory, so a callback that takes an emitted type already has that precedent. The reflected `<mount>` and `<unmount>` methods and `SessionHooks` are gone from the tree; the methods generation still reflects (`@service`, `@condition`) are classes compiled before generation runs, in a dependency or reactor sibling, and cannot refer to a type generation emits. The consumer callbacks that do take emitted types, `FetcherErrorLog` and `FetcherErrorResponse`, are emitted interfaces the consumer implements in the module that uses the generated code and registers on the runtime (`GraphitronRuntime.withFetcherErrorLog` / `withFetcherErrorResponse`), and the runtime carries them to the operation.
* **Moved: generated scopes.** A generated fetcher opens its own `transactionResult` at more sites than the two this item named: the DML key fetch and bulk loop in `TypeFetcherGenerator`, the routine write in `RoutineWriteEmitter`, and, with `@outbox`, the `ID`-returning DML arm, which had no transaction before. Each is a nested scope inside the field, so the join rule's "graphitron's own scopes never warn" has to hold at every one of them, not at two named ones.
* **Moved: the claim decline.** `ErrorRouter.claim` already declines `isMountFailure(thrown) || isOutboxFailure(thrown)`; the transaction hook, if it is added, joins that one decision rather than adding a third arm.
* jOOQ 3.20.11: `transactionResult0` follows any exception out of the body with `provider.rollback(ctx)` after `ctx.cause(e)`, then rethrows; a `commit` that throws is followed by a rollback on the same context.
* graphql-java 25.0 facts phase 1 rests on, unchanged: `beginFieldExecution`'s context completes before the field's sub-selections; `AsyncSerialExecutionStrategy` starts field N+1 only once field N's value is complete; the strategy and operation contexts complete from sibling callbacks on one future, which `CompletableFuture` may run in either order; `GraphQL.executeAsync` composes `instrumentExecutionResult` after the operation context's callback.

## Built on the store

The emitters ask the store what they need to know about a schema, and the classified model learns nothing for this item. Most of the item is fixed runtime that every owned build emits the same way (the instrumentation, the provider, the carrier), so one schema-dependent fact remains:

* **Which fields open a scope of graphitron's own.** Derived, and already derived: `graphitron_producer.kind` says INSERT, UPDATE, DELETE and ROUTINE are generated writes and SERVICE is consumer code, and `graphql_root_operation` says which type is the mutation root. The join answers every question a test or a reader asks ("which mutation fields does graphitron open a nested scope for?"), so it is read, not stored.

**No new relation.** A relation owes an owner, a grain and a sweep, and each of those would be invented here: the only derivable fact is a join of two relations that already own their grains, and no emitter branches on it. A table holding "this coordinate opens a scope" would be a second home for what `graphitron_producer.kind` holds, to be kept in step with it. The seam is where the emitters meet the fact instead: every generated scope is rendered by one renderer, called from each write emitter (the walk-driven DML emitters now, and the store-driven routine and outbox emitters), so the mark in Phase 2 is applied by construction at every site and a site added later gets it by calling the renderer. When the DML emitters move onto store rows the seam is already the right shape. `RoadmapReferenceGuardTest` is the model for the guard that holds this: a unit-tier test over the emitters' sources that fails when any renders `transactionResult(` outside the renderer.

## Implementation

### Phase 1, shipped at `fd9e592`

One transaction per top-level mutation field, without the join rule or the hook: the carrier's field scope and lazy enlistment, the provider's package-private `open()` / `end()`, the boundaries (`beginFieldExecution`, settle then release in the operation callback), the serial-strategy check, failure marking (`markFieldFailed`, the `getErrors()` backstop), settling (the PostgreSQL probe, timed-out entries never touched, the scatter binding to the dispatching field), and the settle-failure report through `instrumentExecutionResult` and `ErrorRouter.settleFailure`. Learnings it leaves for the phases below:

* A failed-settle report reuses `ErrorRouter` with the field's own environment, captured in `beginFieldFetching`, rather than `GraphQLContext` overloads; the consumer's `FetcherErrorLog` and `FetcherErrorResponse` see a real field.
* Once one connection of a field fails to settle, the rest roll back. Phase 2 tightens this into a scan before any commit.
* The rejected-mount multi-tenant execution test was not written: no fixture has a mutation field that writes on one tenant and then reaches another. Phase 2's multi-tenant fixture (below) is the place to add it.
* A `<mutationState>` hook reflected at build time cannot work: it would take an emitted type its class, compiled before generation, cannot see. The hook item registers it on the runtime instead.

### Phase 2: nested scopes join the field transaction

* **A third scope variant.** The provider's stack gains `Joined`, a scope with no JDBC state. The carrier opens a field's scope through a new package-private `openField()`, which pushes the field's `TopLevel` (or, under `ROLLBACK_ONLY`, `Savepointed`) scope marked as the field's own. A nested `begin` on a non-empty stack pushes `Joined` and makes no JDBC call, so it cannot fail. The stack and its innermost-only rule from R1055 stay: every close still names its scope.
* **The rule applies to every nested scope, not only inside a mutation field.** On the owned path a `@service` on a Query field can open nested transactions too, through the same provider; they join the outermost scope the same way. So the only savepoint the provider ever takes is a field's own scope under `ROLLBACK_ONLY`, bounded by the number of fields in the document. (Decided with the user, on the principle that opening a transaction is fine and opening a subtransaction is not: a query's outermost `transactionResult` is still a real transaction, and only what nests inside it joins. The narrower alternative would have kept savepoints outside mutation fields.)
* **Joined exits.** A `Joined` commit pops and does nothing. A `Joined` rollback pops and marks the outermost scope on the stack rollback-only, a mark that is sticky for the scope's life. A scope is *own* when the seam rendered it (graphitron's own fetcher) and *consumer* otherwise; only a consumer scope's rollback also records the first cause it saw (jOOQ's `ctx.cause()`) on the outermost scope. The difference is what reports: a generated scope that fails throws out of the fetcher, the router already reports that and marks the field failed, and a recorded cause would add a second, misleading error to every failed generated mutation and to a typed `@error` payload that is meant to stand alone.
* **The outermost scope's end.** A rollback-only outermost scope never commits. On the jOOQ path (a top-level `transactionResult` outside any field, queries included), `commit` on a rollback-only scope throws a `DataAccessException` naming the nested failure without touching the connection, and jOOQ's follow-up rollback rolls back, so the caller sees the failure it swallowed. On the carrier path, `settleField` reads the mark.
* **Settle scans before it commits.** `settleField` first reads every enlisted connection's state: the field's failed flag, an error under its path, a timed-out key, each connection's rollback-only mark, and, on a PostgreSQL-family dialect for each `TopLevel` scope, the probe (`select 1`, which throws `25P02` on an aborted transaction, the case of a failed statement outside any nested scope that the service caught). The probe runs in the scan, not before each commit, so no connection commits before every other one is known to be clean. Only then does it commit, in open order; a commit that itself fails (a deferred constraint, a serialization failure, a lost connection) is the one residual partial case, and every later connection rolls back. Any finding in the scan rolls back every connection that is not timed out. The scan runs on the dispatch thread after the field's value is complete, and a scatter worker's marks are visible after the scatter join, the same happens-before the timed-out handling uses. Settling one connection catches every `RuntimeException`, not only `SQLException` and `IllegalStateException` as phase 1 does: an unchecked failure from a driver or pool wrapper fails that connection and the field, and the remaining connections still settle, instead of escaping from the next field's `beginFieldExecution` with the earlier field reported as successful.
* **The named error.** A field whose own result was successful but whose connection is rollback-only is reported as failed with an error that names what happened: a fixed graphitron message, "A nested transaction in this field failed; the field's writes were rolled back", followed by the error's reference. It does not say whether the exception was caught, so it holds whether or not the field also failed some other way; the log under the reference does. The swallowed exception is logged under that reference through the configured `FetcherErrorLog.unmatched`, never sent. The message is graphitron's, not the consumer's `FetcherErrorResponse.unmatchedMessage`, so it states the cause the same way in every deployment; it carries no database text. (Decided with the user: the alternative, keeping every settle message under `FetcherErrorResponse` and naming the cause only in the log and an `extensions.classification` code, would let a deployment hide the cause.) `ErrorRouter.settleFailure` takes the distinction from the cause it is handed: a new emitted `NestedScopeFailedException` for this case, the redacted answer for every other settle failure. The named error is reported whenever a connection of the field carries a recorded consumer-scope cause, even when the field also failed some other way, and is added beside the field's other errors rather than replacing them. A field whose only rollback-only mark came from an own scope gets the router's error and no named one. On PostgreSQL that is the common case, not the exception: a nested scope that failed on a SQL error aborted the transaction, so the service's next statement fails with `25P02` and reaches the router as an ordinary redacted error; without the named error beside it, the client would never learn the root cause. The swallowed nested cause and every other cause are logged under the named error's reference.
* **A rolled-back field shows no value.** Under phase 1 a field that rolled back because of an error strictly under its path (a nested read in its payload that failed) still returns its value, so `createFilm { filmId language { name } }` whose `language` read fails reports a `filmId` for a row that no longer exists. Phase 2 nulls such a field in `instrumentExecutionResult`, with null propagation, as it nulls a field that failed to settle; the errors under it stand and no error is added. The one kept value is an `@error` channel's payload: a claim leaves no error under the path, and the payload describes the failure rather than a write.
* **Service code that opens a nested scope is warned about.** A nested scope taking no savepoint is the rule, but code that opens one expects a subtransaction it no longer gets, so the provider logs a WARN when service code opens one: that the nested transaction joined the enclosing one and took no savepoint, that a failure inside it now fails the whole transaction even if caught, the mutation field's coordinate when there is one, and the calling frame. The calling frame is found with `StackWalker`, walking outward from the provider's `begin`: past the provider's own frames, past jOOQ's (`org.jooq`), and the next frame is the code that called `transaction` or `transactionResult`; no stack trace is logged, and no package rule is needed, so a consumer service placed under `<outputPackage>` is still named. It logs once per calling frame per runtime: the carrier hands the provider a reporting callback when it builds it, and the runtime keeps the set of frames already reported, so a service that wraps every call in `transactionResult` logs one line for the life of the deployment, not one per request, and a sweep that nests per item logs one. Graphitron's own nested scopes never warn: the generated fetchers' `transactionResult` joins inside every field, and the seam (see Built on the store) marks each one it renders (an entry in the derived `Configuration`'s data the provider reads in `begin`), so a `Joined` begin carrying the mark is an own scope, silent and recording no cause. Every write emitter renders its scope through the seam, the `ID`-returning DML arm and the `@outbox` emit included, so the sites that exist today and the ones added later are covered by one rule rather than a list.
* **No JDBC or consumer code under the field-scope lock.** Phase 1's `enlist` runs the open's JDBC calls inside the field scope's monitor, which `settleField` also takes, so a scatter worker whose open stalls on a hung tenant makes every other tenant's worker queue behind it, and once the join deadline passes blocks the dispatch thread in `settleField` until the hung call returns, the wait the deadline exists to bound. Phase 2 keeps the monitor to bookkeeping: under the lock `enlist` checks the scope is not settled and reserves the key with a per-key completion; outside the lock it opens the scope; under the lock again it records the opened scope against the key, and then it completes the key's completion, normally, or exceptionally when the open threw. A consumer hook, if one is added, runs between the record and the completion, outside the lock. The key is usable only once that completion is done: every other acquirer of the same key in the field waits on it before it is handed the `DSLContext`, so no statement for the field runs before autocommit is off, or concurrently with the open's JDBC calls, and a waiter whose first acquirer's open threw fails the same way. A scope is recorded as soon as it is open, so a failure after that point leaves a scope settle rolls back, never one left open on the provider's stack. Settle marks the scope settled under the lock and reads its keys after. A key still reserved but not recorded when the field settles belongs to a scatter worker that has not finished, which the join only leaves behind once its deadline passed, so the key is timed out: settle treats it like any timed-out key, the worker's late record is refused because the scope is settled, and the connection, with whatever the open left on it, is aborted at release. On the dispatch thread `enlist` is synchronous, so a reserved key there is always recorded before settle runs.
* **A settled field refuses its stragglers.** A scatter worker that resumes after its field settled and acquires a key that did not time out gets, under phase 1, a connection in autocommit, whose writes commit on their own (and phase 1's `TenantScatterSubstrateTest.mutationField_aStragglerEnlistsOnTheFieldThatDispatchedIt_neverOnALaterOne` asserts that as correct). Phase 2 refuses it: an acquisition whose captured field scope is settled throws, so the straggler writes nothing; that test changes to expect the refusal.
* **The connection key is opaque to the field scope.** Today the carrier keys a connection by the tenant (`Optional<K>`, with the mount receiving it as `mountedTenant`), and a signed-voucher handover under design adds a second dimension: a field with a voucher in context needs a different connection from one without, so the choice reads the tenant and the voucher together, and the mount has to be told both. What a graph's connection key is made of is a fact about the graph, derived from facts the store holds or will hold (the tenant column row, and the presence of a voucher marker in the schema): a tenant component only in a multi-tenant build, a voucher component only in a graph that has a marker. This item takes no part in deciding that shape and writes nothing that depends on it: the field scope, the reservation and its per-key completion, the timed-out set, the straggler refusal and the scan use the key for equality and hashing only, and say "connection key" where they mean it. Whoever adds the voucher component changes the key type and the mount's session value in one place, and this item's code follows.
* **The generated fetchers.** Their own `transactionResult` stays: inside a field it joins and commits nothing, and outside one it is the outermost scope. The one emit change is that every site renders it through the seam, which adds the mark; the sites are the DML key fetch, the bulk loop, the routine write and the `@outbox` emit's `ID`-returning arm. jOOQ's default provider on the escape hatch ignores the mark. A unit-tier guard over the emitters' sources fails when one renders `transactionResult(` outside the seam.
* **The escape hatch** keeps jOOQ's default provider and the consumer's own transactions; nothing here applies.

## Tests

The rule for this item is the one the neighbouring store-built items follow: generated code is exercised, never read as strings. A unit-tier test compiles the emitted unit it is about and calls it, against a recording `Connection` wrapper on the execution tier's PostgreSQL (no mocked `DSLContext`, no in-memory database), and asserts what the wrapper recorded and what the database holds afterwards. The pipeline tier pins only that a unit is emitted and what its signature is, from the `TypeSpec`. A GraphQL round trip is the top of the pyramid, kept to the few cases only a whole request can show (document order, null propagation).

New in this revision, ahead of the lists below:

* **Store tier.** Nothing is added to the store, so there is no capture or anchor test; one test pins the join this item relies on over the fixture schema, `graphitron_producer.kind` against `graphql_root_operation`: the mutation fields graphitron opens a scope for are exactly the INSERT, UPDATE, DELETE and ROUTINE ones, and the SERVICE one is not. The seam tests below take their list of coordinates from that join, so a write field added to the fixture is covered without the test being edited.
* **The seam, unit tier.** For every coordinate that join returns, the generated fetcher (or its companion) is called with a stub environment through a provider whose `begin` the test observes: each scope it opens is an own scope, makes no JDBC call when joined, logs no WARN and records no cause. This covers the `ID`-returning DML arm, the bulk loop, the routine write and the `@outbox` arm. A source guard over the emitters fails when one renders `transactionResult(` outside the seam.
* **An own scope that fails.** A generated mutation whose write violates a foreign key: the field is `null` with the router's one redacted error and no named error; with an `@error` channel that claims the exception, the field keeps its typed payload and `errors` is empty; with `@outbox` whose emit fails, the field fails with the redacted error and nothing is written. Each is a unit-tier call of the fetcher plus the instrumentation's settle, with the rows read back.
* **A consumer scope that fails**, for contrast: the named error appears, as the lists below pin.

Phase 1's tests are on trunk: provider field-scope cases in `GraphitronTransactionProviderGeneratorTest`, carrier cases in `TenantScatterSubstrateTest` (timed-out tenant, straggler binding, rollback of every connection, a commit failing on the second), and `MutationScopeExecutionTest` (a throwing service, a claimed exception, a caught failed statement, a failed commit as middle and last field, null propagation, the batched-payload release race, a field with no database, a non-serial strategy).

Phase 2, execution tier, no generated-body string assertions. A recording connection wrapper on the test's `DataSource` records `setAutoCommit`, `setSavepoint`, `commit`, `rollback` and `close` per connection:

* A generated `@mutation` that runs its own `transactionResult` commits once, with no savepoint and no warning.
* A `@service` mutation whose nested `transactionResult` succeeds: no savepoint, one commit at settle, one WARN naming the field and the service's method; a second request through the same service logs no second WARN.
* A `@service` mutation that writes, opens a nested scope that throws a non-database exception, catches it, writes again and returns normally: the field is `null` with the named error and its reference, nothing it wrote before or after the nested scope is visible afterwards, and the next field commits.
* The same with the nested scope failing on a SQL error: on PostgreSQL the service's next statement fails with `25P02`; the field carries the named error beside the router's redacted one, nothing is written, and the log under the named error's reference holds both causes.
* A nested scope that throws and is not caught: the field fails with the router's ordinary redacted error and the named one beside it.
* A Query `@service` that nests a transaction inside its own: no savepoint, and a caught nested failure makes its own outermost commit fail with the named cause.
* Two top-level mutation fields still commit independently, in document order.
* A field rolled back for an error under its path, `createFilm { filmId <a sub-field whose read fails> }`: the field is `null` and its row is gone; a claimed `@error` payload keeps its value.
* Settle before release, pinned directly: the wrapper records the last mutation field's `commit` on its connection before that connection's `close`. This replaces phase 1's `theLastFieldsBatchedPayload_neverLosesItsCommitToRelease`, which the round 4 review found never completed off the dispatch thread, so it did not exercise the race it is named for; the order is by construction, and the pin holds whichever thread completes the operation.
* A query operation runs in autocommit: no `setAutoCommit(false)`, no `commit`.
* `ROLLBACK_ONLY` (the dev executor's engine): one savepoint per field, nested scopes join it with none of their own, and nothing is left after the request.
* The router mark is harmless off the owned path: on the escape hatch (`newExecutionInput(dsl, ...)`), a fetcher that throws, with and without an `@error` channel claiming it, answers exactly as before; on the owned path a Query fetcher that fails before acquiring a connection does too.
* Multi-tenant, at the execution tier with rows read back after `execute` (phase 1 has these only against fake connections). A new fixture in the multi-tenant schema: a mutation field routed to tenant 1 that writes a marker row there, whose payload reads a `@tenantFanOut` field over tenants 1 and 2. With tenant 2 hanging past the fan-out deadline: the field fails and tenant 1's marker is gone. With a mount that rejects tenant 2 only (the tenant session fixture gains a principal it refuses on that tenant): `execute` throws `SessionMountException` and tenant 1's marker is gone, the case phase 1 left unwritten. A rollback-only mark on the second of two connections needs a nested scope on a fanned read, which no generated fetcher opens, so that case is pinned at the carrier tier below.

## Breaking change

Phase 1 broke, and recorded, three behaviours on the owned path: a `@service` mutation that committed in steps commits once at the end of the field; one that throws after writing rolls back; on PostgreSQL one that catches a failed statement and returns normally is reported as failed. Phase 2 tightens that: catching an exception from a nested scope no longer lets a field partly succeed, on any database, and the same join applies to a transaction a Query `@service` opens, which phase 1 told consumers was unchanged. A field that rolled back because of an error under it is now `null` rather than showing a value for writes that are gone. Two patterns stop working on the owned path: per-item failure tolerance through nested transactions (a sweep that takes one transaction per item and carries on past the ones that fail), and dry-run done by writing and then rolling back a nested scope. The phase 2 commit follows the breaking-change convention: the subject says it breaks, the message records the FS-plattform check (no subgraph is on the owned path today), and its `changelog.md` line names those two patterns and that they stop working on queries too.

## Other solutions we've considered

* **Savepoints for nested scopes** (phase 1 as shipped). Every nested `transactionResult` a subtransaction, the generated fetchers' own included, with the cluster-wide cost described under Current behaviour, and catch-and-continue made to look safe. Joining with a rollback-only mark keeps the field's all-or-nothing promise without either.
* **A savepoint API, a per-field opt-out, or an after-commit phase** for work that must commit independently. Not offered: such work belongs in a separate top-level field, which commits on its own in document order, or in a job.
* **Marking rollback-only only where PostgreSQL aborts the transaction.** The probe already catches that case; making the rule depend on the database would let the same service partly succeed on one engine and not another.
* **Settling in the `beginFieldExecution` completion**, or **when the `beginExecutionStrategy` context completes.** The first commits before the payload is read; the second races release. Phase 1 settles in `beginFieldExecution` of the next field and in the operation callback, before release.
* **Reading the driver's transaction state instead of probing.** The generated runtime would name a driver class.
* **A store relation for "this coordinate opens a scope of its own".** A second home for what `graphitron_producer.kind` already says, kept in step by hand, with no emitter branching on it; the seam makes the mark follow the emit instead.
* **Marking the generated scopes at two named sites.** What the earlier draft did. R1113 then added sites the draft did not name, so a list rots and a renderer every emitter calls does not.
* **A recorded cause for every nested rollback, own scopes included.** Every failed generated mutation, and every `@error` payload, would then carry a named error describing a nested transaction the client never knew existed.
