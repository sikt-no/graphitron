# One transaction per top-level mutation field, opened by the instrumentation, with a consumer hook at its start

## Goal

On the owned-connection engine, every top-level mutation field runs as exactly one database transaction per connection it touches (one in a single-tenant build), which graphitron opens and closes around the whole field, its payload included. A consumer-named static method runs at the start of each such transaction, inside it, knowing which mutation field and which operation it belongs to. A field the client is told succeeded has committed; a commit that fails, or a transaction the database has already aborted, is reported as that field's error. The *owned-connection engine* is the execution mode where graphitron pins one connection per operation and owns its lifecycle (`runtime.newGraphQL(schema)`). A consumer can then attach who and why to every write with one method instead of one call per service, and a `@service` mutation becomes all-or-nothing like a generated one. Tracked as GitHub issue sikt-no/graphitron#564.

The motivating consumer is FS audit logging: change data capture reads row changes from the PostgreSQL WAL, and the who and why travel in the same transaction as a transactional logical message, which the database discards with the transaction on rollback:

```xml
<mutationState>
  <begin>no.sikt.fs.audit.AuditContext#begin</begin>
</mutationState>
```

```java
public static void begin(Configuration tx, MutationScope scope, String claims) {
    tx.dsl().select(DSL.function("pg_logical_emit_message", Object.class,
        DSL.inline(true), DSL.inline("audit"),
        DSL.val(json(scope.operationName().orElse(null), scope.fieldCoordinate(), claims)))).fetch();
}
```

With that configured, a request against the sakila schema

```graphql
mutation AddFilms {
  a: createFilm(in: {title: "A", languageId: 1}) { id }
  b: createFilm(in: {title: "B", languageId: 999}) { id }   # foreign key violation
}
```

runs `begin` twice, each time inside the field's own transaction with `scope.fieldCoordinate()` equal to `Mutation.createFilm` and `scope.operationName()` equal to `Optional.of("AddFilms")` (empty for an anonymous `mutation { ... }`). Field `a` commits its row and its message together; field `b` rolls back its row and its message together.

## User documentation (first-client check)

Draft for a new section in `docs/architecture/reference/runtime-extension-points.adoc`, after the `<sessionState>` section, and a row in `docs/manual/reference/mojo-configuration.adoc`:

> **Transactions on the owned-connection path.** Each top-level mutation field runs in one transaction. It begins the first time the field uses a connection and ends when the field's value is complete, payload included: it commits when the field succeeded and rolls back when the field failed. A field fails when its fetcher, or anything under it, threw, whether or not an `@error` channel turned the exception into a typed payload, or when a GraphQL error lies under the field's path. Fields commit independently of each other, in document order. A `transactionResult` your `@service` opens inside the field is a savepoint in that transaction, not a commit. A field that never touches the database opens no transaction. Query operations are unchanged and run in autocommit.
>
> A field reported as successful has committed. If the commit fails, or the database had already aborted the transaction (on PostgreSQL, any statement that failed inside it, even one your code caught, aborts the transaction, and the driver's commit then rolls back without an error), the field is reported as failed: its value becomes `null` and the response carries a redacted error at its path, and the cause is logged under the error's reference. Later fields in the operation still run. The mutations run one field at a time; an engine configured with a mutation execution strategy other than graphql-java's serial one is rejected when the operation starts.
>
> **Running code at the start of each mutation transaction.** A `<mutationState>` block names a static method graphitron calls once per transaction it opens for a mutation field, right after the transaction begins and before any SQL for the field:
>
> ```xml
> <mutationState>
>   <begin>com.example.db.AuditContext#begin</begin>
> </mutationState>
> ```
>
> Graphitron reads the signature at build time. A `Configuration` parameter receives the transaction's configuration. A `MutationScope` parameter receives the field: `fieldCoordinate()` (`Mutation.createFilm`), `fieldName()`, `alias()` (empty when the field is not aliased), `path()` (the result path, `/a`) and `operationName()` (empty for an anonymous operation). A parameter of the `<sessionState>` mount's return type receives the session handle; at most one may, and when the mount returns a JDK type such as `String` a parameter of that type is rejected as ambiguous, so give the handle a type of its own. Every other parameter is payload and becomes a contextArgument on the generated factory; one with the same name and type as a mount payload parameter is the same value, supplied once. Field arguments are not offered, since they can carry personal data.
>
> If the method throws, the field fails and its transaction rolls back; the error is logged and redacted, and no `@error` channel can claim it. In a multi-tenant build the method runs once per tenant connection the field touches, and each connection commits or rolls back on its own: there is no transaction across connections, so a field whose first connection committed and whose second failed to commit is reported as failed with the first connection's writes kept.
>
> Typical uses: `SET LOCAL` of session variables that audit triggers read, a transactional `pg_logical_emit_message`, or `SET LOCAL lock_timeout` for writes.

## Current behaviour

Verified against trunk at `916639caf` (R1055's provider change and R1097 both on trunk):

* `GraphitronConnectionInstrumentation` (emitted by `GraphitronConnectionInstrumentationGenerator`) implements `createState` and `beginExecuteOperation`, whose returned context runs `TenantConnections.releaseAll()` when the operation completes, plus `instrumentExecutionResult` in a build with a `<sessionState>` mount, where it throws the operation's remembered `SessionMountException` in place of the result. Its class javadoc states the contract this item replaces: no outer transaction is opened, and each mutation field's shipped `dsl.transactionResult(...)` is the per-field writable boundary.
* The generated DML mutation fetchers (`TypeFetcherGenerator.renderTransactionalKeyFetch`) and `@routine` writes (`RoutineWriteEmitter`) wrap the statement in `dsl.transactionResult(...)` and read the payload back after it returns, in autocommit under `CommitPolicy.COMMIT`. `@service` mutations get no transaction (`TypeFetcherGenerator.buildServiceFetcherCommon`); `service.adoc` documents that contract.
* `GraphitronTransactionProvider` (emitted by `GraphitronTransactionProviderGenerator`) keeps a stack of open scopes, each a `TopLevel` transaction or a `Savepointed` one. Its private `open()` makes its JDBC calls first and pushes the new scope only once they succeed (autocommit off when the stack is empty, a savepoint otherwise), returning the scope; private `close(Scope, boolean failed)` dispatches on the variant, and `requireInnermost(Scope, String)` refuses a close of anything but the top of the stack. On the jOOQ path `begin` records the scope on the `TransactionContext` and `commit`/`rollback` read it back, so a rollback for a scope that never opened changes nothing; a failed `commit` leaves its scope open for jOOQ's follow-up rollback. `settle` commits or rolls back and reasserts autocommit. Under `ROLLBACK_ONLY` each field is already a savepoint inside one operation transaction, with the payload read back before the discard: the topology this item gives `COMMIT` per field.
* PostgreSQL aborts a transaction after any failed statement, and pgjdbc 42.7.13 (the pinned driver) does not report a commit on an aborted transaction: `Connection.commit()` returns normally and the server rolls back. Checked against the local database: insert a row, run `select 1/0` and catch the `22012`, commit; the commit returns and the row is gone. Today this is unreachable on the owned path, because `@service` mutations run in autocommit and the generated DML fetchers do not catch.
* The graphitron JavaPoet fork emits no records (R1055's implementation notes; the scatter `Outcome` arms in `ConnectionRuntimeClassGenerator` are final classes with record-style accessors for the same reason), and emitted sources target Java 17.
* An owned fetcher without the carrier fails loudly: `TenantConnections.of(env)` throws when the instrumentation did not publish it. A consumer who replaces the instrumentation therefore gets errors, not unattributed writes.
* graphql-java 25.0 (read from the sources jar): `ExecutionStrategy.resolveFieldWithInfo` completes the `beginFieldExecution` context when the `FieldValueInfo` future completes, which can be before `FieldValueInfo.getFieldValueFuture()`, the field's sub-selections, completes. `AsyncSerialExecutionStrategy` starts field N+1 only after field N's value future completed, and completes its `beginExecutionStrategy` context after the last one. `beginExecutionStrategy` is called by the root strategies only; nested objects use `beginExecuteObject`. `ExecutionContext.getErrors()` exposes the errors recorded so far, and `ExecutionContext.getMutationStrategy()` the strategy the engine runs mutations with. Ordering at the end of an operation (bytecode of `AsyncSerialExecutionStrategy`, `Execution` and `GraphQL`): the strategy context and the operation context complete from two `whenComplete` callbacks on the same root future, and `CompletableFuture` runs dependents registered on a not-yet-complete future in reverse registration order, so when the root future completes on another thread (a DataLoader-batched payload, say) the operation context, and with it `releaseAll`, runs before the strategy context. `Execution.executeOperation` returns the future derived from the operation context's `whenComplete`, and `GraphQL.executeAsync` composes `instrumentExecutionResult` onto that future, so `instrumentExecutionResult` runs after the operation context's callback has returned.

## Implementation

* **Field scope on the carrier.** `TenantConnections` (in `ConnectionRuntimeClassGenerator`) gains one active field scope at a time: the `MutationScope` value, a failed flag (an `AtomicBoolean`, since scatter workers may set it), and the provider scopes the field opened, one per entry, in a concurrent insertion-ordered map keyed by entry (scatter workers open on distinct keys concurrently). Every owned acquisition path (`getDslContext` / `dslFor` / `dslDefault` / `dslGlobal`) checks, after resolving the entry, whether a field scope is active and has not yet opened on that entry; if so it opens one through the entry's provider, stores the returned scope in the map, and calls the hook. The state lives on the carrier, so it exists exactly when the instrumentation ran.
* **The provider scope the carrier holds.** A field scope has no jOOQ `TransactionContext` to record its scope on, so the carrier holds the `Scope` object `open()` returned and hands it back to `close(scope, failed)` at settle. `GraphitronTransactionProvider`'s `open()`, `close(Scope, boolean)` and `requireInnermost(Scope, String)`, private since R1055, and its `Scope` type become package-private: the provider and the carrier are both emitted into `<outputPackage>.schema`, so nothing outside the generated runtime can reach them. `open()` decides the variant from the stack as it does for jOOQ: under `COMMIT` the stack is empty at a field's first acquisition, so the field scope is `TopLevel`; under `ROLLBACK_ONLY` it is `Savepointed` inside the operation transaction, as each field is today. Inside an open field scope, the fetcher's own `transactionResult` and any a `@service` opens push `Savepointed` scopes on top and close them through jOOQ, with no change to their emit.
* **Scope boundaries in the instrumentation.** `GraphitronConnectionInstrumentation` overrides `beginFieldExecution`: for a field at result-path level 1 in a `MUTATION` operation, it settles the previous field's scope, if any, and makes the new field's scope active (opened lazily per entry, as above). This point is after the previous field's value, payload included, is complete under the serial strategy, which the previous field's own `beginFieldExecution` completion is not (see Current behaviour). The last field's scope settles in the callback of the context `beginExecuteOperation` returns, which today runs `releaseAll()`: it settles the active scope first and then calls `releaseAll()`, in that order, inside one callback. One callback orders the two by construction, whatever thread completes the root future and in whatever order `CompletableFuture` runs dependents; no `beginExecutionStrategy` override is added. `releaseAll` keeps its existing open-transaction handling as the backstop for a scope that never settled (an operation that threw).
* **The mutation strategy must be serial.** `beginExecuteOperation` fails fast, as it already does for incremental support, when the operation is a `MUTATION` and `executionContext.getMutationStrategy()` is not an `AsyncSerialExecutionStrategy` (a subclass is accepted). Under a parallel strategy field N+1's `beginFieldExecution` would settle field N while it is still running.
* **Failure.** A scope settles as failed when the `ErrorRouter` handled an exception for a field under it, whether it redacted the exception or an `@error` channel claimed it into a payload; or when `ExecutionContext.getErrors()` holds an error whose path starts with the field's path; or when the hook threw; or when an entry's scatter worker timed out (Settling one entry). `ErrorRouter` is a fixed runtime class that today reaches the carrier only through the static `TenantConnections.isMountFailure`, and `TenantConnections.of(env)` throws when no carrier was published, which is every fetcher on the escape hatch and none of graphitron's business to break. So the mark goes through a new static on the carrier, `TenantConnections.markFieldFailed(DataFetchingEnvironment env)`, emitted in every build like `isMountFailure`: it reads the carrier leniently from `env.getGraphQlContext()`, and is a no-op when there is no carrier, when no field scope is active (queries, and the escape hatch), or when `env`'s result path does not start with the active field's path. It only sets the scope's `AtomicBoolean`, so it is safe from a scatter worker's thread. `ErrorRouter` calls it from `claim` when an `@error` channel claims the exception, and from `surfaceClientErrorOrRedact` on both arms, the client-error surface and the fall-through to `redact`; together those are every exception an emitted fetcher hands the router. The `getErrors()` path check stays as the backstop for errors that never pass through the router (graphql-java's own, and the fan-out failure markers).
* **A timed-out tenant's entry is never settled.** A field scope opens on every owned acquisition while it is active, reads included, so a `@tenantFanOut` read in a mutation payload opens one on each tenant entry, from the scatter worker. When a worker misses the join deadline its key enters `timedOutTenants`, and the carrier's rule is that such a connection may still be mid-statement and is touched again only through `PinnedConnection.abort()` in `releaseAll`. Settle keeps that rule: before settling, it checks every entry the field opened on against `timedOutTenants`. A timed-out entry is skipped (no probe, no `close`), its scope stays on that provider's stack, and `releaseAll`'s abort discards the transaction with the connection. Its presence marks the field failed, and a settle failure naming the timed-out tenant is recorded for the field's path, so the client is never told a write committed that the abort will roll back. Because the field is failed, every other entry closes with `close(scope, true)`. A later acquisition on the timed-out key already throws (`entryFor` refuses it), so no later field pushes a scope onto that stack. The timeout check runs on the dispatch thread after the scatter join, the same happens-before `releaseAll` relies on.
* **Settling one entry.** For each entry the field opened on that did not time out, in the order opened: a failed field closes the scope with `close(scope, true)`. A successful field first checks, on a PostgreSQL-family dialect and a `TopLevel` scope only, that the transaction is not aborted, by running one probe statement (`select 1`) on the connection; a probe that throws (SQLState `25P02` when the transaction is aborted) settles the entry as failed with the probe's exception as the cause. Otherwise it closes with `close(scope, false)`. A close that throws on commit leaves the scope open (R1055's contract), and the carrier then closes it with `close(scope, true)` and records the commit's exception as the cause. If `requireInnermost` refuses the field's scope, a scope opened under it was left open, which jOOQ's `transactionResult` cannot produce: the carrier records an `IllegalStateException` naming the field, rolls the connection back and evicts the entry the way the scatter straggler path aborts one, and a later field that routes to that key fails with a located error rather than pushing a scope onto a broken stack. A `Savepointed` scope needs no probe: releasing a savepoint inside an aborted transaction already throws. The probe is dialect-gated rather than reading the driver's transaction state, so the generated runtime names no driver class.
* **A failed settle is reported at the field.** Each entry's settle failure is recorded on the carrier as the field's result path plus the cause, and logged once under a reference through the consumer's configured `FetcherErrorLog` and `FetcherErrorResponse`, with the same reference-only wire message a fetcher failure gets. `ErrorRouter`'s `newReference` and `toConfiguredLog` read their configuration from the field environment's `GraphQLContext`; they gain overloads keyed on the operation's `GraphQLContext`, which the instrumentation state holds, since a settle has no field environment. `instrumentExecutionResult` (now emitted in every owned build, not only with a mount) rewrites the result when settle failures were recorded: the failed field's value becomes `null`, null propagation follows the spec's rules (a non-null mutation field nulls `data`), and a redacted error with the field's path is added. A remembered `SessionMountException` still takes precedence: it is thrown before any rewrite, as today. `instrumentExecutionResult` runs after the operation context's callback (see Current behaviour), so the last field's settle failure is in the record by then. In a multi-tenant field, each entry settles independently, so one connection may commit while another fails; the field is reported as failed either way, with the committed connection's writes kept.
* **The hook.** `<mutationState>` with a `<begin>` method reference: a new `MutationStateBinding` beside `SessionStateBinding` in graphitron-maven-plugin, a `@Parameter` on `AbstractRewriteMojo`, and resolution at build time into the existing `MethodRef.Param` / `ParamSource` taxonomy (`Context` for payload, `SessionHandle` for the mount's handle) plus two new sources for `Configuration` and `MutationScope`, so the same signature rules and build failures as `<sessionState>` apply. The session handle is recognised by type, as the `<unmount>` hook recognises it, but unlike the unmount the mutation hook also takes payload, so a type could mean either. The rule: a parameter whose type equals the mount's declared handle type binds the handle, and a hook may declare at most one (a second fails the build naming both parameters). When the handle type is a JDK type (a `java.*` class, a primitive or its box), a parameter of that type is rejected at build time as ambiguous between the handle and a payload contextArgument, naming the parameter and the handle type; such a consumer wraps the handle in a type of its own, which is what every known mount returns already. Nothing binds silently to the wrong value. The emitted `GraphitronMutationHook` mirrors `GraphitronSessionHook`. `MutationScope` is a new emitted final class in `<outputPackage>.schema` with record-style accessors (the JavaPoet fork emits no records): `String fieldCoordinate()`, `String fieldName()`, `Optional<String> alias()` (empty when the field is not aliased), `String path()` (the field's `ResultPath` as text, `/a`), and `Optional<String> operationName()` (empty for an anonymous operation). `beginExecuteOperation` captures the operation name from `ExecutionContext.getOperationDefinition().getName()`; `beginFieldExecution` supplies the rest from the field's `ExecutionStepInfo`. Payload contextArguments are read in `beginExecuteOperation`, as the mount's are.
* **Hook failure routing.** A throw from the hook is wrapped in a new emitted `MutationHookException`. It must never be claimed by an `@error` channel, so an infrastructure fault never becomes business data. R1097 landed the precedent: `ErrorRouter.claim` declines any chain for which `TenantConnections.isMountFailure` holds. This item extends that decline to a chain carrying `MutationHookException`, through a sibling predicate emitted on the carrier in every build, rather than adding a parallel arm. Unlike a rejected mount, a hook failure is a field failure: once `claim` declines, it reaches the ordinary `surfaceClientErrorOrRedact` path, which logs it with a correlation id and redacts it, so it needs no surface arm of its own.
* **No hook configured.** The scope and its transaction are unconditional on the owned path; only the hook call and its types are gated on `<mutationState>`.
* **Escape-hatch path out of scope.** With `newExecutionInput(dsl, ...)` the consumer owns the `DSLContext` and its transactions; graphitron opens no scope there. The documentation states how to get the same effect with a consumer `Instrumentation` and a jOOQ `TransactionListener`.

## Tests

Execution tier in graphitron-sakila-example, a new `MutationScopeExecutionTest` beside `SessionHookExecutionTest`, with a test hook that records `txid_current()`, the coordinate and the operation name in a fixture table (a real table in `init.sql`, with the schema version bumped above trunk's):

* Two `createFilm` fields, the second violating a foreign key: the first commits with its hook row in the same transaction as its film row (same `txid`), the second leaves neither.
* A `@service` mutation that writes twice in autocommit and then throws: both writes roll back. The same with an `@error` channel claiming the exception into a payload: the payload is returned and both writes still roll back.
* The payload of a DML mutation, including a batched sub-field, resolves inside the field's transaction (same `txid`).
* The release race: an operation whose last field is a DML mutation with a DataLoader-batched payload sub-field commits that field, its row visible on a fresh connection after `execute` returns. Run it enough times to cover completion on a non-dispatch thread, and pin the ordering directly: the generated operation-context callback settles before it releases (a carrier spy records the order).
* A mutation field that touches no database opens no transaction and calls no hook.
* A query operation calls no hook and runs in autocommit.
* The hook throwing: the field fails with a redacted error, an `@error` channel on the field does not claim it, nothing is written, and the next field in the operation still runs and commits.
* `ROLLBACK_ONLY`: the hook runs per field and everything is discarded at release.
* Multi-tenant: a field touching two tenant connections calls the hook once per connection, and a failed field rolls back both. A field whose second connection fails to settle (the aborted-transaction case on that tenant only) is reported as failed while the first connection's commit stands: the documented contract, not cross-connection atomicity.
* A hanging tenant under a mutation payload: a field whose payload fans out over two tenants, one of which outlives the join deadline (the existing `TenantFanOutExecutionTest` hang fixture). The field is reported as failed, the responsive tenant's writes roll back, the hanging tenant's connection is aborted at release and never settled (a carrier spy records no `close` or probe on it), and its writes are gone after `execute` returns.
* A rejected mount inside a multi-tenant mutation field: the field writes on tenant A, then acquires tenant B, whose mount rejects. `execute` throws `SessionMountException` as R1097 specifies, and tenant A's write does not stand.
* Operation name: a named operation records its name for every field; an anonymous `mutation { ... }` records empty.
* The aborted transaction: a `@service` mutation that writes, runs a failing statement, catches it and returns normally. The field is reported as failed (null, redacted error at its path, one log line under the reference), its write is gone, and the next field in the operation runs and commits. This is the case pgjdbc commits silently, so it is the test that proves the probe.
* A commit that fails: a deferred constraint (`DEFERRABLE INITIALLY DEFERRED` on a fixture table) violated by a field's write fails at commit; the field is reported as failed, nothing it wrote remains, and the next field commits. As the last field of the operation too, so the report reaches the result from the operation-context settle.
* A non-null mutation field whose settle fails nulls `data`, per null propagation.
* A mutation strategy other than the serial one (`.mutationExecutionStrategy(new AsyncExecutionStrategy())`) fails the operation before any field runs; the sibling of the replaced-instrumentation test.
* With a mount configured and rejected, a mutation still throws `SessionMountException` from `execute`, not a rewritten result.
* A consumer instrumentation that replaces graphitron's fails the mutation loudly rather than writing without a scope.
* The router mark on the escape hatch: a fetcher on the `newExecutionInput(dsl, ...)` path that throws, with and without an `@error` channel claiming it, answers exactly as today (no `IllegalStateException` from a missing carrier). The same for a query fetcher on the owned path that fails before acquiring.

Unit tier, `GraphitronTransactionProviderGeneratorTest`: the package-private `open` / `close` reached as the carrier will reach them, without a `TransactionContext`: a `TopLevel` field scope with a nested jOOQ savepoint closes cleanly; a close while a nested scope is still open is refused and leaves the stack unchanged; a failed commit followed by `close(scope, true)` leaves the stack empty and autocommit restored.

Pipeline tier: the hook class, `MutationScope` and `MutationHookException` are emitted only with `<mutationState>`; `instrumentExecutionResult` and `TenantConnections.markFieldFailed` are emitted in every owned build; a malformed `<begin>` reference fails the build naming the method; a hook with two parameters of the handle type fails naming both; with a mount returning `String`, a hook parameter of type `String` fails as ambiguous, naming the parameter and the handle type. `MojoDocCoverageTest` covers the new parameter row.

## Breaking change

Three behaviours change for owned-path consumers with no configuration: a `@service` mutation that commits in steps now commits once at the end of the field; one that throws after writing now rolls back; and on PostgreSQL, one that catches a failed statement and returns normally is now reported as failed, since the database discards the transaction anyway (today it writes in autocommit, so the statements before the failure persist). A commit failure stays visible as the field's error, as it is today when the fetcher's own `transactionResult` commits, so that is not a change. An engine configured with a non-serial mutation strategy is now rejected; graphql-java's default is serial. The implementation commit follows the breaking-change convention: the subject says it breaks, the message records the check against the known consumers, and `changelog.md` gets its line in the same commit.

* **R1055** (Done), a failed begin closes the enclosing scope: a hard dependency. * **R469** (Backlog), `@defer` on the owned path: a deferred payload fragment would complete after the scope settles. Incremental delivery stays rejected; R469 has to account for this when it lifts that.

## Other solutions we've considered

* **A hook in `GraphitronTransactionProvider.begin`, keeping the fetcher-owned transaction.** Smallest change, but the provider sees no field, `@service` mutations would still write in autocommit outside any transaction, and the payload would still be read after commit.
* **Settling in the `beginFieldExecution` completion.** Simpler, and wrong: graphql-java completes that context before the field's sub-selections are done, so the scope would commit before the payload is read and before its errors are known.
* **Settling the last field when the `beginExecutionStrategy` context completes**, with `releaseAll` as a backstop (the first draft). The two callbacks hang off the same future and `CompletableFuture` runs them in reverse registration order when it completes on another thread, so release can roll back the last field after its success is in the result. One callback that settles, then releases, orders them by construction.
* **Reading the driver's transaction state instead of probing** (pgjdbc's `BaseConnection.getTransactionState()`). No round trip, but the generated runtime would name a driver class, and the consumer's classpath decides which driver is present. The probe costs one statement per field per connection on PostgreSQL only.
* **Documenting that a commit failure after the field resolved is invisible to the client.** Smaller, but a regression against today, where the fetcher's own commit fails inside the fetcher and surfaces as the field's error, and it leaves the aborted-transaction case reporting success for writes that are gone.
* **A custom mutation `ExecutionStrategy`.** It would see the true end of each field, but `resolveSerialField` is private, and a strategy set on the builder is replaced by a later `.mutationExecutionStrategy(...)` as silently as an instrumentation is.
* **A per-field opt-out** for services that must commit in steps. Not offered: one pinned connection cannot hold an independent commit inside an open transaction, and no known consumer needs it. A successor can add it if one appears.

## Reviewer findings

### Round 1 (2026-10-26, Spec -> Ready, reviewer session 01AzNHaZ9KuhqRa3sNfSoAPn)

Verdict: withhold. One blocking finding on question one (viability), one on question two (architecture fit), and two non-blocking. The goal reads on its own: a consumer can say what changes for them (one transaction per top-level mutation field, payload included, a hook at its start) without the phase list, and the audit example makes the motivation concrete. The plan extends the shapes already in the tree (the carrier, the provider's depth and savepoint stack, `MethodRef.Param` / `ParamSource`, the `ErrorRouter` arms) rather than standing a parallel mechanism beside them. The claims under Current behaviour check out against the tree and against the graphql-java 25.0 sources, including the early completion of the `beginFieldExecution` context and the serial ordering in `AsyncSerialExecutionStrategy`.

**Finding 1 (question one: viability). The last field's settle races `releaseAll`, and on the asynchronous path `releaseAll` wins, rolling back a field the client is told succeeded.**

The plan settles the last scope when the `beginExecutionStrategy` context completes, and keeps `releaseAll` as a backstop. In graphql-java 25.0 both callbacks hang off the same future: `AsyncSerialExecutionStrategy.execute` registers `overallResult.whenComplete(executionStrategyCtx::onCompleted)`, and `Execution.executeOperation` then derives `result.thenApply(mergeExtensions...).whenComplete(executeOperationCtx::onCompleted)` from that same `overallResult`; the emitted instrumentation's `beginExecuteOperation` returns the context whose completion runs `releaseAll()`. `CompletableFuture` fires dependents of a future completed later in reverse registration order, so when `overallResult` completes asynchronously the derived chain, and with it `releaseAll`, runs first. A standalone reproduction of exactly that chain shape on JDK 25 prints `releaseAll` before the strategy settle when the future is completed from another thread; completed synchronously, the order is the other way round. `PinnedConnection.release` rolls back any open transaction before restoring autocommit. So whenever the root strategy finishes asynchronously, which is the case for a payload with a DataLoader-batched sub-field (a case the Tests section names), the last mutation field's work is rolled back while its success is already in the result. The outcome depends on scheduling, which is the worst kind of failure here.

What would satisfy it: settle the last scope at a point ordered before release by construction, not by registration order. The obvious one is the operation context itself: `beginExecuteOperation`'s completion settles any open scope and then calls `releaseAll`, in that order, in one callback. The `beginExecutionStrategy` override may then be unnecessary. The plan should state the chosen point and why it is ordered, and the Tests section should pin it with the batched-payload case as the last field of the operation.
