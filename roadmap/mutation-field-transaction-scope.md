# One transaction per top-level mutation field, opened by the instrumentation, with nested scopes joining it

## Goal

On the owned-connection engine, every top-level mutation field runs as exactly one database transaction per connection it touches (one in a single-tenant build), which graphitron opens and closes around the whole field, its payload included. Inside that transaction there are no savepoints: a `transaction(...)` or `transactionResult(...)` opened inside the field, by a generated fetcher or by a `@service`, joins it, and a scope a `@service` opened that fails makes the whole field fail, even when the code that opened it caught the exception. A scope graphitron's own fetcher opened needs no such rule, since its failure already fails the field through the fetcher's exception. A field the client is told succeeded has committed; a commit that fails, a transaction the database has already aborted, or a nested failure that was caught, is reported as that field's error. The *owned-connection engine* is the execution mode where graphitron pins one connection per operation and owns its lifecycle (`runtime.newGraphQL(schema)`). A `@service` mutation becomes all-or-nothing like a generated one, and a write and the messages written beside it (an `@outbox` message, say) commit or roll back together. Tracked as GitHub issue sikt-no/graphitron#564.

Against the sakila schema, this request

```graphql
mutation AddFilms {
  a: createFilm(in: {title: "A", languageId: 1}) { id }
  b: createFilm(in: {title: "B", languageId: 999}) { id }   # foreign key violation
}
```

commits field `a`'s row, rolls back field `b`'s, and answers `b` with `null` and an error at its path. Each field is its own transaction, in document order.

A consumer hook that runs at the start of each such transaction is a separate item, split out of this one. The place it attaches is kept open (see No JDBC or consumer code under the field-scope lock).

Graphitron caters to good patterns, not all patterns. Work that must commit independently of the rest of a field belongs in a separate top-level mutation field, which commits on its own in document order, or in a job; graphitron offers no savepoint API, no per-field opt-out and no after-commit phase.

## User documentation (first-client check)

Draft for the section "Transactions on the owned-connection path" in `docs/architecture/reference/runtime-extension-points.adoc` (its Phase 1 text is on trunk; this draft replaces it) and a new section after it:

> **Transactions on the owned-connection path.** Each top-level mutation field runs in one transaction. It begins the first time the field uses a connection and ends when the field's value is complete, payload included: it commits when the field succeeded and rolls back when the field failed. A field fails when its fetcher, or anything under it, threw, whether or not an `@error` channel turned the exception into a typed payload, or when a GraphQL error lies under the field's path. Fields commit independently of each other, in document order. A field that never touches the database opens no transaction. Query operations run in autocommit.
>
> Inside the field there is one transaction and no savepoints. A `transaction(...)` or `transactionResult(...)` your `@service` opens joins the field's transaction, and graphitron logs a warning naming the field and your calling method, once per calling method: leaving it normally commits nothing, and leaving it by an exception marks the whole field to roll back. Catching that exception does not save the field: nothing the field wrote commits, before or after the nested scope, and the field is reported as failed with an error that says a nested transaction failed and the field's writes were rolled back, whatever else went wrong after it; the log under the error's reference says whether your code caught the exception. The same holds on every database. On PostgreSQL there is no carrying on after a failed SQL statement at all: the statement aborted the whole transaction, so the next one fails too. Only an exception that is not a database error leaves the transaction usable after the catch. The same rule applies to a `@service` on a Query field that opens a transaction of its own: what it nests inside that transaction joins it, and a caught nested failure makes the transaction's commit fail. Work that must commit on its own belongs in its own top-level mutation field, or in a job.
>
> A field reported as successful has committed, and a field that rolled back is never shown with a value: a field that rolled back because of an error under it (a nested read in its payload that failed, say) is `null`, like one that failed itself; only an `@error` channel's payload, which describes the failure, is kept. If the commit fails, or the database had already aborted the transaction (on PostgreSQL, any statement that failed inside it aborts it, and the driver's commit then rolls back without an error), the field is reported as failed: its value becomes `null` and the response carries an error at its path, logged under the error's reference. Later fields in the operation still run. The mutations run one field at a time; an engine configured with a mutation execution strategy other than graphql-java's serial one is refused when a mutation starts.
>
> In a multi-tenant build each connection the field touches has its own transaction; there is no transaction across connections. Before committing anything, graphitron checks every connection the field used, the PostgreSQL aborted-transaction check included; a field rolls back on every connection when any of them is not clean. Only then do they commit, in the order the field first used them, so a field is left partly committed only when a commit itself fails on a later connection (a deferred constraint, a serialization failure, a lost connection), and it is then reported as failed with the earlier connections' writes kept.
>
> Under `CommitPolicy.ROLLBACK_ONLY`, the dev-execution mode, each field is one savepoint in a single operation transaction that is discarded at the end, so later fields observe earlier ones. That is the only savepoint graphitron takes.
>


## Current behaviour

Phase 1 of this item is on trunk (`fd9e592`). Every bullet below was checked against the generators on 2026-10-30, at the trunk after the session-identity rework and the first two phases of `@outbox`; those marked *Moved* changed since the plan was last approved. The plan's own nested-scope text (Phase 2) describes code that does not exist yet.

* `GraphitronTransactionProvider` (emitted by `GraphitronTransactionProviderGenerator`) keeps a stack of open scopes, `TopLevel` or `Savepointed`. Its package-private `open()` turns autocommit off on an empty stack under `COMMIT`, and otherwise takes a savepoint (`connection.setSavepoint()`), pushing the scope only once the JDBC call succeeded; the package-private `end(Scope, boolean failed)` ends a scope the carrier holds, popping after a successful commit and before a rollback. The jOOQ path (`begin` / `commit` / `rollback`) records its scope on the `TransactionContext`. So every `transactionResult` nested inside a field today takes a savepoint, the generated DML and `@routine` fetchers' own `transactionResult` included (`TypeFetcherGenerator.renderTransactionalKeyFetch`, `RoutineWriteEmitter`): one subtransaction per nested scope. Under `ROLLBACK_ONLY` a field's own scope is a savepoint in one operation transaction.
* On PostgreSQL a savepoint that writes is a subtransaction with its own transaction id. A backend caches at most 64 subtransactions per transaction; past that it overflows, and until the transaction ends every other session's snapshot checks visibility through `pg_subtrans`, which contends across the cluster and is worse on replicas (PostgreSQL 17's `subtransaction_buffers` softens it). `RELEASE SAVEPOINT` does not free a slot. Savepoints combined with `SELECT ... FOR UPDATE` create multixacts. A savepoint also makes catch-and-continue look safe: code swallows a database failure and keeps going, the hidden-partial-state problem this item exists to remove. A known consumer pattern on the escape hatch today (opptak's `settTilbudsgarantiFraTidligopptak`) takes one savepoint per candidate in a sweep over a whole admission round, hundreds to thousands per transaction; that team will change it.
* `TenantConnections` carries the active `FieldScope` (`MutationFieldScopeEmitter`): every owned acquisition enlists, opening the field's scope on a connection's first use; `settleField(failed)` ends each scope in open order, probing a committing PostgreSQL `TopLevel` scope with `select 1`, rolling back the rest once one fails, never touching a timed-out tenant's connection, and refusing a connection left with an open nested scope. `scatter` captures the dispatching field scope for its workers. `TenantConnections.markFieldFailed(env)` is the lenient static `ErrorRouter` calls from `claim` and `surfaceClientErrorOrRedact`.
* `GraphitronConnectionInstrumentation` settles the previous top-level mutation field in `beginFieldExecution` and the last one in the operation callback, before `releaseAll`; refuses a non-serial mutation strategy; captures the field's `DataFetchingEnvironment` in `beginFieldFetching`; and in `instrumentExecutionResult` (every owned build) nulls a field that failed to settle and adds the error `ErrorRouter.settleFailure(cause, env, path)` built, which is redacted and logged through the configured `FetcherErrorLog.unmatched`. A remembered `SessionMountException` still takes precedence.
* Session identity is no longer a static method named in plugin configuration: the consumer builds an emitted `SessionState` per request and passes it to the generated factory, so a callback that takes an emitted type already has that precedent. The reflected `<mount>` and `<unmount>` methods and `SessionHooks` are gone from the tree; the methods generation still reflects (`@service`, `@condition`) are classes compiled before generation runs, in a dependency or reactor sibling, and cannot refer to a type generation emits. The consumer callbacks that do take emitted types, `FetcherErrorLog` and `FetcherErrorResponse`, are emitted interfaces the consumer implements in the module that uses the generated code and registers on the runtime (`GraphitronRuntime.withFetcherErrorLog` / `withFetcherErrorResponse`), and the runtime carries them to the operation.
* **Moved: generated scopes.** A generated fetcher opens its own `transactionResult` at more sites than the two this item named: the DML key fetch and bulk loop in `TypeFetcherGenerator`, the routine write in `RoutineWriteEmitter`, and, with `@outbox`, the `ID`-returning DML arm, which had no transaction before. Each is a nested scope inside the field, so the join rule's "graphitron's own scopes never warn" has to hold at every one of them, not at two named ones.
* **Moved: the claim decline.** `ErrorRouter.claim` already declines `isMountFailure(thrown) || isOutboxFailure(thrown)`; the transaction hook, if it is added, joins that one decision rather than adding a third arm.
* jOOQ 3.20.11: `transactionResult0` follows any exception out of the body with `provider.rollback(ctx)` after `ctx.cause(e)`, then rethrows; a `commit` that throws is followed by a rollback on the same context.
* graphql-java 25.0 facts phase 1 rests on, unchanged: `beginFieldExecution`'s context completes before the field's sub-selections; `AsyncSerialExecutionStrategy` starts field N+1 only once field N's value is complete; the strategy and operation contexts complete from sibling callbacks on one future, which `CompletableFuture` may run in either order; `GraphQL.executeAsync` composes `instrumentExecutionResult` after the operation context's callback.

## Built on the store

The emitters ask the store what they need to know about a schema, and the classified model learns nothing for this item. Most of the item is fixed runtime that every owned build emits the same way (the instrumentation, the provider, the carrier), so one schema-dependent fact remains:

* **Which fields open a scope of graphitron's own.** Derived, and already derived: `graphitron_producer.kind` says INSERT, UPDATE, DELETE and ROUTINE are generated writes and SERVICE is consumer code, and `graphql_root_operation` says which type is the mutation root. The join answers every question a test or a reader asks ("which mutation fields does graphitron open a nested scope for?"), so it is read, not stored.

**No new relation.** A relation owes an owner, a grain and a sweep, and each of those would be invented here: the only derivable fact is a join of two relations that already own their grains, and no emitter branches on it. A table holding "this coordinate opens a scope" would be a second home for what `graphitron_producer.kind` holds, to be kept in step with it. The seam is where the emitters meet the fact instead: every generated scope is rendered by one renderer, called from each write emitter (the walk-driven DML emitters now, and the store-driven routine and outbox emitters), so the mark in Phase 2 is applied by construction at every site and a site added later gets it by calling the renderer. When the DML emitters move onto store rows the seam is already the right shape. `RoadmapReferenceGuardTest` is the model for the guard that holds this: a unit-tier test over the emitters' sources that fails when any renders `transactionResult(` outside the renderer.

## Implementation

### Phase 1, shipped at `fd9e592`

One transaction per top-level mutation field, without the join rule or the hook: the carrier's field scope and lazy enlistment, the provider's package-private `open()` / `end()`, the boundaries (`beginFieldExecution`, settle then release in the operation callback), the serial-strategy check, failure marking (`markFieldFailed`, the `getErrors()` backstop), settling (the PostgreSQL probe, timed-out entries never touched, the scatter binding to the dispatching field), and the settle-failure report through `instrumentExecutionResult` and `ErrorRouter.settleFailure`. Learnings it leaves for the phases below:

* A failed-settle report reuses `ErrorRouter` with the field's own environment, captured in `beginFieldFetching`, rather than `GraphQLContext` overloads; the consumer's `FetcherErrorLog` and `FetcherErrorResponse` see a real field.
* Once one connection of a field fails to settle, the rest roll back. Phase 2 tightens this into a scan before any commit.
* The rejected-mount multi-tenant execution test was not written: no fixture has a mutation field that writes on one tenant and then reaches another. Phase 2's multi-tenant fixture (below) is the place to add it.
* A `<mutationState>` hook reflected at build time cannot work: it would take an emitted type its class, compiled before generation, cannot see. The hook item registers it on the runtime instead.

### Phase 2, shipped at `377e41d` (the seam) and `203d56f` (the join, a breaking commit)

Nested scopes join the field transaction, and the carrier settles by scanning before it commits. As built:

* **The seam.** `OwnedScope` (in `emit`) renders every generated `transactionResult` as `<Provider>.owned(dsl).transactionResult(tx -> ...)`; the emitted provider's `owned(dsl)` marks the scopes opened on its context, and `isOwn(ctx)` reads the mark in `begin`. The DML key fetch, the bulk loop, the routine write and the `@outbox` `ID`-returning arm all go through it, and `OwnedScopeSeamGuardTest` fails when an emitter renders a transaction any other way. The provider is a frozen scaffold in the compile graph, since every write fetcher now names it.
* **The provider.** `Scope` is a sealed class with `rollbackOnly`, `consumerFailure` and `cause` on the outermost scope; `Joined` has no JDBC state. A nested `begin` joins, a joined commit does nothing, a joined rollback marks the outermost scope, and only a consumer scope records its first cause. On the jOOQ path an outermost commit on a rollback-only scope throws a `DataAccessException` naming the nested failure without touching the connection, and `end(scope, false)` on one throws. `open()` stays the carrier's entry (the plan's `openField()` is not a separate method). The provider reports the calling method of every consumer scope that joined, found with `StackWalker` past its own, jOOQ's and the JDK's frames (jOOQ runs a transaction through `ForkJoinPool.managedBlock`).
* **The carrier.** `settleField` reads every connection first (the failed flag, a rollback-only mark, a timed-out or still-opening key, and the PostgreSQL probe on each `TopLevel` scope), then ends them in open order; a commit that itself fails rolls back that connection and the rest, and every `RuntimeException` is caught per connection. The field monitor covers bookkeeping only: the first acquirer of a key reserves an `Opening`, opens outside the monitor, records under it, and completes a per-key future that every other acquirer waits on, failing the way the first did. An acquisition after the field settled, or for a timed-out key, is refused. `markFieldFailed(env, thrown)` also remembers the handled exception, so the report says whether the consumer's code caught the nested one. A consumer scope's failure returns `TenantConnections.NestedScopeFailedException`, nested in the carrier rather than a unit of its own.
* **Reporting.** `ErrorRouter.settleFailure` answers it with the fixed message and a reference. `instrumentExecutionResult` adds it beside the field's other errors, drops the field's value unless it had already failed, and now also drops the value of a field that rolled back for an error under its path, adding nothing; an `@error` payload stays. A failed generated scope adds no second error.
* **The warning.** One WARN per calling method for the life of the process (a static set in the carrier), naming the running mutation field when there is one. The plan said once per runtime; a runtime copy shares nothing, so the process is the simplest scope that gives the same result.
* **Known limits.** On the jOOQ path (a Query `@service`'s own outermost transaction) a failed statement swallowed inside a nested scope that then returns normally is not seen, as with no nested scope at all: the field-path probe is the carrier's, and the provider names no driver. The planned carrier test with a composite connection key was not built: the key type is derived from the tenant column's catalog type, so a composite one cannot be constructed until the voucher dimension exists; the scope code uses the key only as a map key. The FS-plattform check the breaking-change convention asks for: no subgraph has switched to the owned-connection path yet, confirmed by Alf after the delivery and recorded on the changelog line.

## Breaking change

Phase 1 broke, and recorded, three behaviours on the owned path: a `@service` mutation that committed in steps commits once at the end of the field; one that throws after writing rolls back; on PostgreSQL one that catches a failed statement and returns normally is reported as failed. Phase 2 tightens that: catching an exception from a nested scope no longer lets a field partly succeed, on any database, and the same join applies to a transaction a Query `@service` opens, which phase 1 told consumers was unchanged. A field that rolled back because of an error under it is now `null` rather than showing a value for writes that are gone. Two patterns stop working on the owned path: per-item failure tolerance through nested transactions (a sweep that takes one transaction per item and carries on past the ones that fail), and dry-run done by writing and then rolling back a nested scope. The phase 2 commit follows the breaking-change convention: the subject says it breaks, the message records the FS-plattform check (no subgraph is on the owned path today), and its `changelog.md` line names those two patterns and that they stop working on queries too.

## Other solutions we've considered

* **Savepoints for nested scopes** (phase 1 as shipped). Every nested `transactionResult` a subtransaction, the generated fetchers' own included, with the cluster-wide cost described under Current behaviour, and catch-and-continue made to look safe. Joining with a rollback-only mark keeps the field's all-or-nothing promise without either.
* **A savepoint API, a per-field opt-out, or an after-commit phase** for work that must commit independently. Not offered: such work belongs in a separate top-level field, which commits on its own in document order, or in a job.
* **Marking rollback-only only where PostgreSQL aborts the transaction.** The probe already catches that case; making the rule depend on the database would let the same service partly succeed on one engine and not another.
* **Settling in the `beginFieldExecution` completion**, or **when the `beginExecutionStrategy` context completes.** The first commits before the payload is read; the second races release. Phase 1 settles in `beginFieldExecution` of the next field and in the operation callback, before release.
* **Reading the driver's transaction state instead of probing.** The generated runtime would name a driver class.
* **A store relation for "this coordinate opens a scope of its own".** A second home for what `graphitron_producer.kind` already says, kept in step by hand, with no emitter branching on it; the seam makes the mark follow the emit instead.
* **Marking the generated scopes at two named sites.** What the earlier draft did. R1113 then added sites the draft did not name, so a list rots and a renderer every emitter calls does not.
* **A recorded cause for every nested rollback, own scopes included.** Every failed generated mutation, and every `@error` payload, would then carry a named error describing a nested transaction the client never knew existed.

## Reviewer findings

### Round 1 (2026-10-26, Spec -> Ready, reviewer session 01AzNHaZ9KuhqRa3sNfSoAPn)

Verdict: withhold. One blocking finding on question one (viability), one on question two (architecture fit), and two non-blocking. The goal reads on its own: a consumer can say what changes for them (one transaction per top-level mutation field, payload included, a hook at its start) without the phase list, and the audit example makes the motivation concrete. The plan extends the shapes already in the tree (the carrier, the provider's depth and savepoint stack, `MethodRef.Param` / `ParamSource`, the `ErrorRouter` arms) rather than standing a parallel mechanism beside them. The claims under Current behaviour check out against the tree and against the graphql-java 25.0 sources, including the early completion of the `beginFieldExecution` context and the serial ordering in `AsyncSerialExecutionStrategy`.

**Finding 1 (question one: viability). The last field's settle races `releaseAll`, and on the asynchronous path `releaseAll` wins, rolling back a field the client is told succeeded.**

The plan settles the last scope when the `beginExecutionStrategy` context completes, and keeps `releaseAll` as a backstop. In graphql-java 25.0 both callbacks hang off the same future: `AsyncSerialExecutionStrategy.execute` registers `overallResult.whenComplete(executionStrategyCtx::onCompleted)`, and `Execution.executeOperation` then derives `result.thenApply(mergeExtensions...).whenComplete(executeOperationCtx::onCompleted)` from that same `overallResult`; the emitted instrumentation's `beginExecuteOperation` returns the context whose completion runs `releaseAll()`. `CompletableFuture` fires dependents of a future completed later in reverse registration order, so when `overallResult` completes asynchronously the derived chain, and with it `releaseAll`, runs first. A standalone reproduction of exactly that chain shape on JDK 25 prints `releaseAll` before the strategy settle when the future is completed from another thread; completed synchronously, the order is the other way round. `PinnedConnection.release` rolls back any open transaction before restoring autocommit. So whenever the root strategy finishes asynchronously, which is the case for a payload with a DataLoader-batched sub-field (a case the Tests section names), the last mutation field's work is rolled back while its success is already in the result. The outcome depends on scheduling, which is the worst kind of failure here.

What would satisfy it: settle the last scope at a point ordered before release by construction, not by registration order. The obvious one is the operation context itself: `beginExecuteOperation`'s completion settles any open scope and then calls `releaseAll`, in that order, in one callback. The `beginExecutionStrategy` override may then be unnecessary. The plan should state the chosen point and why it is ordered, and the Tests section should pin it with the batched-payload case as the last field of the operation.

> *Author response (session 013nppeKAeTQdYmEGB6LeLv8, 2026-10-26).* Taken as suggested. The last scope settles in the callback of the context `beginExecuteOperation` returns, which settles and then calls `releaseAll()` in one callback; the `beginExecutionStrategy` override is dropped (Scope boundaries, and the first draft moved to Other solutions with the reason). Tests pin the batched-payload case as the operation's last field and the settle-before-release order directly.

**Finding 2 (question two: architecture fit). The plan does not say where a failed commit goes, and both settle points sit where the result can no longer carry it.**

Today a field's `transactionResult` commits inside its fetcher, so a commit that fails (a deferred constraint, a serialization failure, a lost connection) surfaces as that field's error. Under this plan field N commits from field N+1's `beginFieldExecution`, and the last field from a completion callback (Finding 1). By then field N's value is in the result as a success, and an exception thrown from either point would land on field N+1 or be swallowed. The multi-tenant case has the same gap at a finer grain: the field's connections share one failed flag, but the first can commit and the second fail. The plan has to state the contract: either a commit failure is reported (for example, recorded on the instrumentation state and added at the field's path in `instrumentExecutionResult`, which `GraphQL.executeAsync` composes after the operation context completes, with the field's data nulled per the spec's error handling), or the documentation says plainly that a commit failure after the field resolved is not visible to the client. The first is what today's behaviour gives; dropping it is a regression the Breaking change section does not list.

> *Author response (session 013nppeKAeTQdYmEGB6LeLv8, 2026-10-26).* Reported, not documented away. Each entry's settle failure is recorded on the carrier with the field's path and cause, logged once under a reference through the consumer's configured log and response, and applied in `instrumentExecutionResult` (now emitted in every owned build): the field becomes `null` under the spec's null propagation and gets a redacted error at its path. That runs after the operation context's callback, which `Execution` and `GraphQL` order by future composition (verified in the 25.0 bytecode), so the last field's failure is in the record. A remembered `SessionMountException`, which R1097 throws from the same method, still wins. The multi-tenant gap is stated as the contract: entries settle independently and the field is reported as failed with a committed connection's writes kept; the multi-tenant test no longer asserts cross-connection atomicity, which contradicted the user-docs draft. A failed commit is followed by `close(scope, true)`, since R1055 leaves a failed commit's scope open. Breaking change now says commit failures stay visible.
