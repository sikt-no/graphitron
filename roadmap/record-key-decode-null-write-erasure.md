# A later fromArray load erases an explicit-null write to a NOT NULL column via jOOQ from() flag reset

In a generated record-instantiation helper (`JooqRecordInstantiationEmitter`), key decodes load via `Record.fromArray`, whose `from()` null-skip semantics reset the touched flag of every null-valued column record-wide. Column bindings are emitted before key decodes, so a present identity field silently erases any explicit-null column write made earlier in the same helper: `customerUpsert(in: {identity: {...}, details: {firstName: null}})` leaves `first_name` untouched, while the same input without the identity group writes `NULL`. Whether a column write survives thus depends on an unrelated sibling field's presence, which no author would predict. Both halves are execution-pinned (`GraphQLQueryTest#customerUpsert_explicitNullNestedLeaf_collapsesToOmitted` / `#customerUpsert_explicitNullNestedLeaf_noIdentityDecode_writesNull`) and the mechanism is documented on `JooqRecordInstantiationEmitter#emitKeyDecode`, discovered by R527's truth-probe (the prior prose blamed graphql-java coercion, falsely — coercion retains nested explicit-nulls at every depth). Candidate fixes: emit key decodes before column bindings, or load decoded keys via per-column `set()` instead of `fromArray`. Either is a behavior change to pinned execution contracts (the collapse test and the service javadoc treat the erasure as the current contract), so it needs its own design pass, not a drive-by.

Correction (found while implementing R747): the reset is `Tools.resetTouchedOnNotNull`, which `from()` runs after every load, and it clears the touched flag only on null-valued columns whose `DataType` is `NOT NULL` (`customer.first_name` is; `film.description` is not, and keeps its `NULL` write beside a decoded id). It is therefore not specific to key decodes: any later `fromArray` load in the helper, a present plain value included, erases an earlier explicit null on a `NOT NULL` column. A fix has to cover both paths. `GraphQLQueryTest#countFilmRecordDrafts_nullForANotNullColumnBesideADecodedNodeId_isWrittenAndChecked` pins that R747's VALIDATION check follows the write.

Progress (R876, 2026-11-10): the record helper the store emits for a `@service` loads every value before any explicit null, so the null survives, and that test now pins the null written and checked. Alf ruled the erasure a bug, to be fixed rather than reproduced. The store now builds `customerUpsert` too, its groupings read through, so `GraphQLQueryTest#customerUpsert_explicitNullNestedLeaf_besideADecodedNodeId_writesNull` pins the null written beside the decode. What is left is the classified emitter's helper, which still builds the records the store does not yet (the polymorphic node ids of `assignOccupantRecord` and its siblings); it goes with that emitter, or with the store building those shapes.

Consumer report (sis, Graphitron 10.0.0-RC47, jOOQ 3.20.11, Oracle, 2026-11-11): the plain-value path the correction predicts, with no key decode involved in the erasure. `EndreKullInput` binds `navn: String` to `STUDIEKULLNAVN`, a `NOT NULL` column, followed by `navnEn: String` on a nullable column; `endreKull` is a `@service` mutation taking `List<KullRecord>` and running `ctx.batchUpdate(records)`. With variables `{ navn: null, navnEn: "X", ... }` the record builder runs `rec.set(KULL.STUDIEKULLNAVN, null)` and then `rec.fromArray(new Object[]{ value }, KULL.STUDIEKULLNAVN_ENGELSK)` for the next field, which clears the flag the first call raised. The fetcher's `element.touched(KULL.STUDIEKULLNAVN)` guard then skips the jakarta `@NotNull` check, and `batchUpdate` leaves the column out. The client sees the kull with `errors: null`, the old name kept and the element's other fields written: a silent partial write where the author expects a validation error and no write. The outcome depends on field order, since the explicit null survives only when no later field in the same record loads through `fromArray`. This is the sis differential-test finding M6 (2026-10-19), and the same jOOQ behaviour R1039 addressed for generated UPDATE mutations. Sis reproducer, red until a fix lands: `EndreKullMutationIT.endreKull_eksplisittNullINavn_girUgyldigInputUtenAaLagre`, which expects `UgyldigInput` and no write. The execution pins named above all use a decoded id as the later load; a fix should add one where the later load is a plain value, the shape sis hit.
