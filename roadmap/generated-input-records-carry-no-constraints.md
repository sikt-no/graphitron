# Generated input records carry no constraint annotations, so the VALIDATION handler can never fire

## Goal

An author who puts Jakarta Bean Validation constraints on what their `@service` method takes, a
record or bean bound to an SDL input or a jOOQ record, and gives the field's error channel (the set
of `@error` types its payload's `errors` field can hold) a `{handler: VALIDATION}` member, gets one
typed error per violated constraint in that `errors` list, with the service never called.
Graphitron used to validate a copy of the argument it generated itself (`<outputPackage>.inputs`),
so the only constraints that counted were ones a consumer attached to that generated class by hand.
When this lands, graphitron validates the very instance it is about to hand the service, so the
constraints that count are the ones on the class or record the service takes. For a jOOQ record
that includes what jOOQ's `<validationAnnotations>` generates from the schema (`@Size` on a
`varchar(n)` column, `@NotNull` on a `NOT NULL` one), checked for the columns the request wrote.

The sakila example has both shapes. `Mutation.countFilmDrafts` takes a list of `FilmDraftInput`,
binds each element to the consumer record `FilmDraft`, and shares the VALIDATION-handled
`FilmWriteInvalid` with the DML mutations:

```graphql
input FilmDraftInput {
    title: String!
}

type FilmWriteInvalid @error(handlers: [{handler: VALIDATION}]) {
    path: [String!]!
    message: String!
}

union FilmDraftError = FilmWriteInvalid

type FilmDraftsCountedPayload {
    count: Int
    errors: [FilmDraftError]
}

type Mutation {
    countFilmDrafts(in: [FilmDraftInput!]!): FilmDraftsCountedPayload
        @service(service: {
            className: "no.sikt.graphitron.rewrite.test.services.FilmDraftService",
            method: "count", argMapping: "drafts: in"
        })
}
```

The minimal pair for a class is one annotation:

```java
public record FilmDraft(String title) {}              // before: nothing to validate
public record FilmDraft(@NotBlank String title) {}    // after: a blank title is a client error
```

With the annotation, `countFilmDrafts(in: [{title: "DRAFT ONE"}, {title: ""}]) { count errors {
__typename ... on FilmWriteInvalid { path message } } }` answers with `count: null` and one error,
`FilmWriteInvalid`, `path: ["countFilmDrafts", "in", "1", "title"]`, `message: "must not be blank"`;
`FilmDraftService.count` is not called.

The jOOQ record shape is the one sis's `angiStudentbilder` has (`List<PersonbildeRecord>`, with
`@NotBlank` mapped onto the record and `@Size` generated by jOOQ). In sakila it is a new sibling,
`countFilmRecordDrafts(in: [FilmRecordDraftInput!]!)`, whose service takes `List<FilmRecord>`, the
input binding `title` and `description`. With `@NotBlank` and `@Size(max = 255)` on `FilmRecord`'s
`title` property, a blank title in the second element answers `count: null` and one
`FilmWriteInvalid` at `["countFilmRecordDrafts", "in", "1", "title"]`, and a 256-character title
answers `size must be between 0 and 255`, the message Graphitron 9 gave.

Constraints on scalar arguments (`filmLookupValidated(id: Int!)` wanting `@Positive`) stay out of
reach: Jakarta places those on method parameters, method validation does not apply to static
methods, and the static call shape is the common one. The manual says so and names the remedy (take
the argument as an input bound to a class or record).

## User documentation (first-client check)

Replaces the `VALIDATION` paragraphs of `docs/manual/how-to/error-channel.adoc` (anchor
`bean-validation`, as shipped) and its `Coming from Graphitron 9` line; the `@error` reference's
`handler` row and `VALIDATION` section gain "or jOOQ records" where they name what is validated.

> `VALIDATION` is special-cased. There is at most one `VALIDATION` handler per channel (`Rule 7`).
> It turns on Bean Validation for every `@service` field whose payload carries the channel: before
> the service method runs, Graphitron validates what each method parameter receives as a class you
> wrote (a Java record or a bean bound to an SDL `input`) or as a jOOQ record. A list parameter is
> validated element by element. Every violation becomes one entry in the errors list, typed as the
> `VALIDATION` member, with the constraint's own interpolated message, and the service is not
> called. The validation never enters the dispatch loop.
>
> ```java
> public record FilmDraft(@NotBlank String title) {}
> ```
>
> A class is validated whole, with the `jakarta.validation` constraints declared on it. Nested
> classes are validated only where you ask for it with `@Valid`, as Bean Validation always does.
>
> A jOOQ record is validated column by column, for the columns the request wrote: each column is
> checked against the constraints on the record's property for it. Those are the ones jOOQ
> generates when `<validationAnnotations>` is on (`@Size` on a `varchar(n)` column, `@NotNull` on a
> `NOT NULL` one) and any you map onto the record yourself. A column the request left out is not
> checked, so a record that sets two columns does not fail on the others; a column the request
> sets to null is. Key columns decoded from a node id are not checked, and neither is a constraint
> on the record class as a whole. Graphitron finds a column's property by jOOQ's default getter
> name (`get` followed by the column name in PascalCase); if your generator strategy names getters
> differently, the build warns, naming the column, and that column is not checked.
>
> A violation's `path` names the SDL input fields, not the Java members: the field's path, the
> argument, the element index for a list, then the input fields down to the violated value
> (`["countFilmDrafts", "in", "1", "title"]`). Where an input field flattens onto the class or
> record from a grouping input, the path keeps the grouping field. A class-level constraint ends the
> path at the argument (or element).
>
> Only the values a parameter receives as a class you wrote or a jOOQ record are validated. A
> scalar or enum argument, an input read field by field into scalar parameters, and an input passed
> through as a `Map` are passed through unchecked; to constrain one, take the argument as an input
> bound to a record, bean or jOOQ record. Constraints attached to Graphitron's own generated
> `<outputPackage>.inputs` classes are not read: attach them to what the service takes. Validation
> runs after Graphitron has resolved the request's tenant and decoded any node ids in the
> arguments, so a client error from either of those is reported instead of the violations. (A
> `@mutation` field's character length check is separate and described below.)

The `Coming from Graphitron 9` line becomes: the error type `<recordValidation><schemaErrorType>`
named is the one to give `{handler: VALIDATION}`. Graphitron 10 has no `<recordValidation>`
setting; the constraints jOOQ's `<validationAnnotations>` generates are checked on the jOOQ records
a `@service` method takes, so a too-long value still answers `size must be between 0 and n`.

## Shipped

Bound-class validation shipped at `704dd50`, with `d4b7346`, `b08b80e` and `829e203`. What the
remaining work builds on:

- `ValueShape.BoundClass`, a sealed interface over `RecordInput` and `JavaBeanInput`, carries the
  argument it binds (`argName()`), set by `ServiceMethodCallWalker`; `outerArgOf` is gone.
- `ServiceMethodCall.validationTargets()` derives the targets from `methodArgs`: one
  `ValidationTarget.Single` or `PerElement` per `MappingEntry.FromArg` whose shape is a
  `BoundClass` or a `ListOf` one, carrying the call-site local (`FromArg.javaName()`). The stored
  `validatedArguments`, its walker computation and the list-of-lists classification rejection
  retired.
- The pre-step sits between the argument locals and the `result` assignment, through
  `ServiceMethodCallEmitter.emitWithPreCall` (an overload: the fetcher pastes the list-returning
  `emit` one statement at a time, which a block with control flow cannot ride), called only from
  `TypeFetcherGenerator.buildServiceFetcherCommon`. A call with no targets emits no pre-step.
- `ConstraintViolations.toGraphQLError(violation, env, argPath, paths)` translates the property
  path through a `ConstraintViolations.Paths` tree (member name to SDL access path, plus a child
  tree), reading an index from whichever node carries it. The trees are
  `private static final` constants on the `*Fetchers` class, registered through
  `TypeFetcherEmissionContext.validationPathsConstant` and deduped on the translation they build.
- The manual's `bean-validation` paragraphs and the `@error` reference describe the bound-class
  half; the paragraphs above replace them.

## Implementation

The remaining work makes a jOOQ record parameter a validation target.

*Model: the validatable shapes.* A sealed `ValueShape.Validated` over `BoundClass` and
`JooqRecordInput` names the shapes the pre-step validates (`ValueShape permits Scalar, ListOf,
Validated`; `Validated permits BoundClass, JooqRecordInput`). `ValidationTarget.boundClass()`
becomes `subject()`, typed `Validated`, and `validationTargets()` matches `Validated` wherever it
matches `BoundClass` today, directly or as the element of a `ListOf`. Switches over `ValueShape`
that name both arms stay exhaustive.

*Model: the property a column is validated through.* Bean Validation names a record's values by
its getter properties, and graphitron never learns those: it reads and writes a jOOQ record
through `Tables.<T>.<COL>`, with `ColumnRef.javaName` reflected from the generated table class.
Where `InputBeanResolver` builds a `CallSiteExtraction.JooqRecord`, each plain
`CallSiteExtraction.ColumnBinding` resolves the property it is validated through: the record
class's public no-argument getter named by jOOQ's default strategy (`get` plus the SQL column name
in PascalCase: `bilde` gives `getBilde`, `film_id` gives `getFilmId`), confirmed by reflecting the
record class, its return type assignable from the column's Java type. The binding carries the
property name, or its absence where no such getter exists (a generator strategy that renames
getters). Key decodes (`JooqRecord.keyDecodes`) resolve none: graphitron decoded those values
itself, and a decode failure is already a client error.

*Classification.* Nothing new rejects. A `@service` field whose channel carries a `VALIDATION`
handler and that binds a column with no resolved property gets a build warning naming the field,
the column, the record class and the getter looked for; the field classifies as before. A warning,
not a rejection, because rejecting would stop a schema that builds today from building.

*Emission.* Per jOOQ target, with a null record (a null element, for `PerElement`) skipped as for a
bound class, and per bound column with a resolved property:

```java
if (element.changed(Tables.FILM.TITLE)) {
    for (ConstraintViolation<?> violation : validator.validateProperty(element, "title")) {
        violations.add(ConstraintViolations.toGraphQLError(violation, env, List.of("in", i),
            VALIDATION_PATHS_FILM_RECORD));
    }
}
```

The `changed` guard answers the partial-record objection that kept jOOQ records out until now:
`create<Record>` leaves an omitted column `changed=false`, jOOQ leaves it out of the statement,
and its constraints are not checked, including the `@NotNull` that `<validationAnnotations>` puts
on every `NOT NULL` column. A column the client sent, null included, is checked. `validateProperty`
runs no class-level constraint, which jOOQ does not generate. The `Paths` constant is a projection
of the column bindings, `bind(property, primaryPath, null)` per resolved binding, registered
through the shipped `validationPathsConstant`, so the translation and the wire shape are the
bound-class ones. A client writing a column through a deprecated alias sees the live field's name
in the path, the primary path being the live one. The record's violations join the same
accumulator, so a field binding a class and a record reports both.

*Fixtures and prose.* `graphitron-sakila-example` gains `countFilmRecordDrafts` (input
`FilmRecordDraftInput { title: String, description: String }` over `film`, service
`FilmRecordDraftService.count(List<FilmRecord>)`, payload and channel shared with
`countFilmDrafts`), and a Hibernate Validator `ConstraintMappingContributor` on the module's test
classpath, mapping `@NotBlank` and `@Size(max = 255)` onto `FilmRecord`'s `title` getter and
`@NotNull` onto its `description` getter. It is registered the way the example's default
`Validator` bootstraps (standard bootstrap reads `hibernate.validator.constraint_mapping_contributors`
from `META-INF/validation.xml`; the implementer confirms that holds beside the module's
`quarkus-hibernate-validator`). That is the shape sis has, and it stands in for
`<validationAnnotations>`, which the sakila catalog build does not enable. Docs: the draft above into `error-channel.adoc`, the `@error` reference's
`handler` row and `VALIDATION` section, and the javadoc of `validatorPreStep`,
`ServiceMethodCall.validationTargets()` and `ConstraintViolationsClassGenerator` to name records.

## Other solutions we've considered

- *Validating the whole record (`validator.validate(record)`).* jOOQ's `<validationAnnotations>`
  puts `@NotNull` on every `NOT NULL` column without a default, and a record bound from an input
  carries only the columns the input names, so an update naming two columns would fail on every
  other. Validating the written columns only, through `changed`, keeps the database-derived
  constraints without the false positives.
- *Keep validating the generated `.inputs` classes as well.* Restores a hand-attached mapping
  unchanged, but keeps graphitron validating an object the service never sees, which is the defect
  this item removes, and reports a violation twice where both carry the constraint.
- *Extend the `@mutation` column-length check to `@service` jOOQ records.* Catalog-derived and
  independent of how the consumer configures jOOQ, but it reports a too-long value twice wherever
  `<validationAnnotations>` is on, which is where the consumer who needs it has it. It stays open
  for consumers without the annotations.
- *Constraints declared in SDL and emitted onto the generated record.* Closes the loop with no
  consumer Java, and would reach scalar arguments. It costs a new directive and a mapping from SDL
  to the constraint vocabulary, and duplicates what the class or record the service takes can
  already say.
- *Jakarta method validation (`ExecutableValidator.validateParameters`).* Would reach scalar
  parameters (`lookup(@Positive Integer id)`), but the specification excludes static methods and
  most `@service` methods are static; it would split VALIDATION's behaviour by call shape.
- *A consumer-supplied `ValidatorFactory`.* Reopens programmatic `ConstraintMapping` against the
  generated classes; the smallest change and the one that pushes most onto the author, and it keeps
  graphitron validating an object the service never sees.
- *Resolving a column's getter through the consumer's generator strategy.* Would cover renamed
  getters, but graphitron does not run or configure the consumer's jOOQ code generation and has no
  strategy to ask; the default name confirmed by reflection, with a warning where it is absent,
  says what it can and cannot check.
- *Validating before the tenant hand-down.* Keeps violations ahead of tenant and node-id errors,
  at the cost of materialising bound classes ahead of tenant resolution, which a divining field
  reads its tenant from. Rejected; the order is stated in the manual instead.
- *Warning at build time on a VALIDATION channel whose field validates nothing.* A VALIDATION type
  shared by DML mutations and a `@service` mutation is a deliberate shape (`FilmWriteInvalid`), and
  the warning would fire on every `@service` field in that union with no way to silence it but
  splitting the union. The manual's rule carries the signal instead.
