# The VALIDATION handler validates what a @service method receives, jOOQ records included

## Goal

An author who puts Jakarta Bean Validation constraints on what their `@service` method takes, a
record or bean bound to an SDL input or a jOOQ record, and gives the field's error channel (the set
of `@error` types its payload's `errors` field can hold) a `{handler: VALIDATION}` member, gets one
typed error per violated constraint in that `errors` list, with the service never called.
Graphitron used to validate a copy of the argument it generated itself (`<outputPackage>.inputs`),
so the only constraints that counted were ones a consumer attached to that generated class by hand.
When this lands, graphitron validates the very instance it is about to hand the service, so the
constraints that count are the ones on the class or record the service takes. For a jOOQ record
that includes what jOOQ's `<validationAnnotations>` generates from the schema (`@Size` on a
`varchar(n)` column, `@NotNull` on a `NOT NULL` one), checked for the columns the record writes.

The sakila example has both shapes. `Mutation.countFilmDrafts` takes a list of `FilmDraftInput`,
binds each element to the consumer record `FilmDraft`, and shares the VALIDATION-handled
`FilmWriteInvalid` with the DML mutations:

```graphql
input FilmDraftInput {
    title: String!
}

type FilmWriteInvalid @error(handlers: [{handler: VALIDATION}]) {
    path: [String!]!
    message: String!
}

union FilmDraftError = FilmWriteInvalid

type FilmDraftsCountedPayload {
    count: Int
    errors: [FilmDraftError]
}

type Mutation {
    countFilmDrafts(in: [FilmDraftInput!]!): FilmDraftsCountedPayload
        @service(service: {
            className: "no.sikt.graphitron.rewrite.test.services.FilmDraftService",
            method: "count", argMapping: "drafts: in"
        })
}
```

The minimal pair for a class is one annotation:

```java
public record FilmDraft(String title) {}              // before: nothing to validate
public record FilmDraft(@NotBlank String title) {}    // after: a blank title is a client error
```

With the annotation, `countFilmDrafts(in: [{title: "DRAFT ONE"}, {title: ""}]) { count errors {
__typename ... on FilmWriteInvalid { path message } } }` answers with `count: null` and one error,
`FilmWriteInvalid`, `path: ["countFilmDrafts", "in", "1", "title"]`, `message: "must not be blank"`;
`FilmDraftService.count` is not called.

The jOOQ record shape is the one sis's `angiStudentbilder` has (`List<PersonbildeRecord>`, with
`@NotBlank` mapped onto the record and `@Size` generated by jOOQ). In sakila it is a new sibling,
`countFilmRecordDrafts(in: [FilmRecordDraftInput!]!)`, whose service takes `List<FilmRecord>`, the
input binding `title` and `description`. With `@NotBlank` and `@Size(max = 255)` on `FilmRecord`'s
`title` property, a blank title in the second element answers `count: null` and one
`FilmWriteInvalid` at `["countFilmRecordDrafts", "in", "1", "title"]`, and a 256-character title
answers `size must be between 0 and 255`, the message Graphitron 9 gave.

Constraints on scalar arguments (`filmLookupValidated(id: Int!)` wanting `@Positive`) stay out of
reach: Jakarta places those on method parameters, method validation does not apply to static
methods, and the static call shape is the common one. The manual says so and names the remedy (take
the argument as an input bound to a class or record).

## User documentation (first-client check)

Replaces the `VALIDATION` paragraphs of `docs/manual/how-to/error-channel.adoc` (anchor
`bean-validation`, as shipped) and its `Coming from Graphitron 9` line; the `@error` reference's
`handler` row and `VALIDATION` section gain "or jOOQ records" where they name what is validated.

> `VALIDATION` is special-cased. There is at most one `VALIDATION` handler per channel (`Rule 7`).
> It turns on Bean Validation for every `@service` field whose payload carries the channel: before
> the service method runs, Graphitron validates what each method parameter receives as a class you
> wrote (a Java record or a bean bound to an SDL `input`) or as a jOOQ record. A list parameter is
> validated element by element. Every violation becomes one entry in the errors list, typed as the
> `VALIDATION` member, with the constraint's own interpolated message, and the service is not
> called. The validation never enters the dispatch loop.
>
> ```java
> public record FilmDraft(@NotBlank String title) {}
> ```
>
> A class is validated whole, with the `jakarta.validation` constraints declared on it. Nested
> classes are validated only where you ask for it with `@Valid`, as Bean Validation always does.
>
> A jOOQ record is validated column by column, for the columns the record writes: each column is
> checked against the constraints on the record's property for it. Those are the ones jOOQ
> generates when `<validationAnnotations>` is on (`@Size` on a `varchar(n)` column, `@NotNull` on a
> `NOT NULL` one) and any you map onto the record yourself. A column the request left out is
> neither written nor checked, so a record that sets two columns does not fail on the others; a
> column the request sets to null is written as `NULL` and checked. One exception: where the same
> input also carries a node id that Graphitron decodes into the record, a null sent for another
> column is dropped from the record, so that column is neither written nor checked. Key columns
> decoded from a node id are not checked, and neither is a constraint on the record class as a
> whole. Graphitron finds a column's property through the getter jOOQ's default generator strategy
> writes: `get`, then the column's SQL name with each underscore-separated word capitalised and the
> rest of it lower-cased (`BILDE` gives `getBilde`, `film_id` gives `getFilmId`). If your generator
> strategy names getters differently, that column is not checked, and the build reports a
> `validation-column-unchecked` lint finding naming it, which you can suppress like any lint rule.
>
> A violation's `path` names the SDL input fields, not the Java members: the field's path, the
> argument, the element index for a list, then the input fields down to the violated value
> (`["countFilmDrafts", "in", "1", "title"]`). Where an input field flattens onto the class or
> record from a grouping input, the path keeps the grouping field. A class-level constraint ends the
> path at the argument (or element).
>
> Only the values a parameter receives as a class you wrote or a jOOQ record are validated. A
> scalar or enum argument, an input read field by field into scalar parameters, and an input passed
> through as a `Map` are passed through unchecked; to constrain one, take the argument as an input
> bound to a record, bean or jOOQ record. Constraints attached to Graphitron's own generated
> `<outputPackage>.inputs` classes are not read: attach them to what the service takes. Validation
> runs after Graphitron has resolved the request's tenant and decoded any node ids in the
> arguments, so a client error from either of those is reported instead of the violations. (A
> `@mutation` field's character length check is separate and described below.)

The `Coming from Graphitron 9` line becomes: the error type `<recordValidation><schemaErrorType>`
named is the one to give `{handler: VALIDATION}`. Graphitron 10 has no `<recordValidation>`
setting; the constraints jOOQ's `<validationAnnotations>` generates are checked on the jOOQ records
a `@service` method takes, so a too-long value still answers `size must be between 0 and n`.

## Shipped

Bound-class validation shipped at `704dd50`, with `d4b7346`, `b08b80e` and `829e203`. What the
remaining work builds on:

- `ValueShape.BoundClass`, a sealed interface over `RecordInput` and `JavaBeanInput`, carries the
  argument it binds (`argName()`), set by `ServiceMethodCallWalker`; `outerArgOf` is gone.
- `ServiceMethodCall.validationTargets()` derives the targets from `methodArgs`: one
  `ValidationTarget.Single` or `PerElement` per `MappingEntry.FromArg` whose shape is a
  `BoundClass` or a `ListOf` one, carrying the call-site local (`FromArg.javaName()`). The stored
  `validatedArguments`, its walker computation and the list-of-lists classification rejection
  retired.
- The pre-step sits between the argument locals and the `result` assignment, through
  `ServiceMethodCallEmitter.emitWithPreCall` (an overload: the fetcher pastes the list-returning
  `emit` one statement at a time, which a block with control flow cannot ride), called only from
  `TypeFetcherGenerator.buildServiceFetcherCommon`. A call with no targets emits no pre-step.
- `ConstraintViolations.toGraphQLError(violation, env, argPath, paths)` translates the property
  path through a `ConstraintViolations.Paths` tree (member name to SDL access path, plus a child
  tree), reading an index from whichever node carries it. The trees are
  `private static final` constants on the `*Fetchers` class, registered through
  `TypeFetcherEmissionContext.validationPathsConstant` and deduped on the translation they build.
- The manual's `bean-validation` paragraphs and the `@error` reference describe the bound-class
  half; the paragraphs above replace them.

## Implementation

The remaining work makes a jOOQ record parameter a validation target.

*Capture: the property a column is read through.* Bean Validation names a record's values by its
getter properties, and nothing in graphitron knows those: a jOOQ record is read and written through
`Tables.<T>.<COL>`, with `ColumnRef.javaName` reflected from the generated table class, and the
`code_` census skips the generated jOOQ package. It is a fact about the jOOQ corpus at the
(table, column) grain, so it is captured there, beside `sql_table_record_supertype`, whose catalog
walk already holds the record `Class`. A new relation `sql_column_record_accessor`, grain "this
table's generated record reads this column through this public no-argument getter", keyed as
`sql_column` and referencing it `ON DELETE CASCADE`, holds `getter_name` and the Bean Validation
`property_name` it names (java.beans decapitalisation). `JooqFactCapture` writes it in the same pass
as `recordSupertypes`. The getter name is the one jOOQ's `DefaultGeneratorStrategy` writes with its
defaults: `get` plus `org.jooq.tools.StringUtils.toCamelCase` of the SQL name after ` `, `-` and `.`
become `_`, which is the strategy's own path (`getJavaGetterName` through `getJavaClassName0` and
`toPascalCase`). That conversion capitalises each underscore-separated word and lower-cases the
rest of it, so `BILDE` gives `getBilde`, `film_id` gives `getFilmId` and a mixed-case `FilmId` gives
`getFilmid`; it is the rule, and "PascalCase" in a literal reading (`getBILDE`) is not. The name is
confirmed on the record class as a public no-argument method with a return type assignable from the
column's Java type, which also rejects a name jOOQ disambiguated against a `Record` method. A column
whose getter is not there (a generator strategy that renames getters, or
`javaBeansGettersAndSetters`) has no row. The relation is single-corpus (stratum one), owned by
`JooqFactCapture` in `meta_relation`, marked and swept with the `sql_` family; the
`adding-a-relation` skill governs the rest.

*Model: the validation subject.* `ValueShape` is unchanged: a bound class is a pathless composite
and a jOOQ record a path-carrying leaf, and "validatable" is the pre-step's view, not the shape's.
`ValidationTarget.boundClass()` becomes `subject()`, a sealed `ServiceMethodCall.ValidationSubject`
with two arms: `WholeObject(ValueShape.BoundClass)`, today's case, and
`WrittenColumns(ValueShape.JooqRecordInput)`. `validationTargets()` yields a `WrittenColumns`
target, `Single` or `PerElement` as for a class, for a record with at least one plain column
binding; a record whose bindings are all key decodes (`JooqRecord.keyDecodes`) yields none, since
graphitron decoded those values itself and a decode failure is already a client error. The
cardinality axis stays orthogonal to the subject.

*One read, one partition.* The accessor rows have one reader, a query class in
`no.sikt.graphitron.emit` beside `OutboxQuery` (`read(store)` to a `Rows` lookup keyed by table and
column). `GraphQLRewriteGenerator.runPipeline` reads it once from the live store, ahead of
`capturedFrom`, and hands the same `Rows` to both consumers: to `withLintFindings` (through
`capturedFrom`) for the lint below, and to `TypeFetcherGenerator.generate`, which installs it on
`TypeFetcherEmissionContext` the way `setErrorChannels` and `setOutboxes` install theirs. Which of
a record's columns are checked is decided once, by a pure function of a `WrittenColumns` subject
and those `Rows`: it returns the checks, one `ColumnCheck(column, property, primaryPath)` per plain
column binding with an accessor row, and the unchecked bindings, those with none. The pre-step
reads the first list and the lint the second, so the two cannot disagree about a column.

*Emission.* Both the loop and the `Paths` constant read a subject's checks. A target with no
checks is dropped before the "no targets, no pre-step" test, so a field whose records offer nothing
to check still emits no `Validator` lookup. Per check, with a null record (a null element, for
`PerElement`) skipped as for a class:

```java
if (element.changed(Tables.FILM.TITLE)) {
    for (ConstraintViolation<?> violation : validator.validateProperty(element, "title")) {
        violations.add(ConstraintViolations.toGraphQLError(violation, env, List.of("in", i),
            VALIDATION_PATHS_FILM_RECORD));
    }
}
```

The `changed` guard answers the partial-record objection that kept jOOQ records out until now: it
checks exactly the columns the record will write. It rests on a contract
`CallSiteExtraction.ColumnBinding` already pins: `create<Record>` leaves an omitted column (an
omitted alias group included) `changed=false`, jOOQ leaves it out of the statement, and its
constraints are not checked, including the `@NotNull` that `<validationAnnotations>` puts on every
`NOT NULL` column. A column the client sent is checked, null included, with one exception the guard
inherits rather than introduces: R534 (`record-key-decode-null-write-erasure`, Backlog). A key
decode loads through `Record.fromArray`, whose null-skip resets the changed flag of every
null-valued column record-wide, after the column bindings ran
(`JooqRecordInstantiationEmitter.emitKeyDecode` documents it). An explicit null beside a decoded
node id is therefore neither written nor checked. The check and the write agree, which is the
property this item needs; the manual draft states the exception, and when R534 changes the write
the check follows it with no change here. `validateProperty` runs no class-level constraint, which
jOOQ does not generate. The
`Paths` constant binds each check's property to its primary path (`ColumnBinding.path()`, the live
name in an alias group, so a client writing through a deprecated alias sees the live field's name)
and is registered through the shipped `validationPathsConstant`, whose signature, like
`ConstraintViolationsClassGenerator.pathsInitializer`'s, widens to take the subject. The
translation and the wire shape are the bound-class ones, and a record's violations join the same
accumulator, so a field binding a class and a record reports both.

*Lint.* A `@service` field whose channel carries a `VALIDATION` handler and that binds a plain
column with no accessor row cannot have that column checked. A new `LintRule`,
`validation-column-unchecked` of `Source.CODEGEN`, says so. It is produced at report assembly,
not during emission. `withLintFindings` is the one point where warnings enter the report, and it
runs inside `capturedFrom` before `TypeFetcherGenerator.generate`, under the suppression filter.
A projection that emits nothing (the LSP, validate) never reaches the fetcher generator at all. The
producer is a `ValidationColumnWarnings.findings(schema, accessors, excludedTypes)` in `graphitron`,
beside `SessionStateWarnings` and `DependencyVersionWarnings`, folded in at `withLintFindings` like
them. It walks the classified `ServiceField`s whose `errorChannel()` has `hasValidationHandler()`,
takes each `WrittenColumns` target from `validationTargets()`, and reads the unchecked bindings off
the shared partition. It emits one finding per (record class, column), located at the first field in
schema order that reaches it, naming the column and the getter looked for, and applies
`excludedTypes` at that field's owning type through `ExcludedTypes`, as `ReferencePathFanout` does.
This is the shape `LengthCheck` and `dml-write-length-unrouted` already have: one derived value,
read by the emitter and by the advisory. A lint finding rather than a `BuildWarning.NoRule`, because
a consumer whose strategy renames getters gets it on every build and must be able to suppress it; a
warning rather than a rejection, because rejecting would stop a schema that builds today from
building. `LintRuleCatalogueTest`'s pinned `CODEGEN` set gains the id.

*Fixtures and prose.* `graphitron-sakila-example` gains, sharing `countFilmDrafts`' payload and
channel: `countFilmRecordDrafts(in: [FilmRecordDraftInput!]!)` over
`FilmRecordDraftService.count(List<FilmRecord>)`, and `countFilmRecordDraft(draft: FilmDraftInput!,
film: FilmRecordDraftInput!)` over `FilmRecordDraftService.countOne(FilmDraft, FilmRecord)`. The
input is `FilmRecordDraftInput { id: ID @nodeId(typeName: "Film"), title: String, description:
String }` on `film`. A Hibernate Validator `ConstraintMappingContributor` on the module's test
classpath maps `@NotBlank` and `@Size(max = 255)` onto `FilmRecord`'s `title` getter, `@NotNull`
onto `description`, and `@Null` onto `filmId`, the last one there only to show a decoded key is not
checked. The generated default `GraphitronContext.getValidator` bootstraps through
`Validation.buildDefaultValidatorFactory()`, which reads
`hibernate.validator.constraint_mapping_contributors` from `META-INF/validation.xml`; that is the
registration. This is the shape sis has, and it stands in for `<validationAnnotations>`, which the
sakila catalog build does not enable. The module also runs `@QuarkusTest` tests on
`quarkus-hibernate-validator`, so the implementer confirms they still boot with the file present.
If they do not, the contributor is registered through
`HibernateValidatorConfiguration.CONSTRAINT_MAPPING_CONTRIBUTORS` as a system property set for the
plain-JUnit execution tier only, which reaches the same bootstrap. Docs: the draft above into
`error-channel.adoc`, which also carries the lint rule's paragraph and its suppression (the manual
documents each rule on its feature's page, as `asConnection.adoc` does `shared-type-tags-narrowed`),
the `@error` reference's `handler` row and `VALIDATION` section, and the javadoc of
`validatorPreStep`, `ServiceMethodCall.validationTargets()` and `ConstraintViolationsClassGenerator`
to name records.

## Implementation notes

The record half landed as planned, with these choices the plan left open or that moved:

- *The partition is the subject's own method.* `ValidationSubject.WrittenColumns.partition` takes a
  property lookup rather than the `Rows` themselves, so the model package does not reach into
  `no.sikt.graphitron.emit`; `RecordAccessorQuery.Rows.propertyOf` is the lookup both readers pass.
  `ColumnCheck` and `Partition` sit beside it in `ServiceMethodCall.ValidationSubject`.
- *The rows are keyed by record class.* A `TableRef` carries no catalog source or schema, so
  `RecordAccessorQuery` joins `sql_table` for `record_class_fqn` and keys on it and the column's SQL
  name, scoped to the graph's sources through `store_graph_source`.
- *The naming rule is one public class.* `RecordGetters` in `graphitron-model` holds `getterName`
  and `propertyName`; the capture confirms the name, and the lint uses the same rule to name the
  getter it looked for.
- *The argument path uses the outer argument name,* as the bound-class half does.
- *The hand-written catalog test is its own class,* `JooqRecordAccessorCaptureTest`, because
  `JooqFactCaptureTest`'s premise is the generated fixture catalog. The catalog lives under
  `capture/jooq/handwritten` in the model's test sources.
- *The lint's pipeline cases drop an accessor row from the captured store* to stand for a renaming
  generator strategy, the sakila catalog having every getter where the default rule looks.
- *Test plumbing:* `TestSchemaHelper.storeBackedFetchers` reads the accessor rows from the store it
  plans from, so a store-backed pipeline test emits record checks as a run does.
- *The guard reads `touched(Field)`,* jOOQ 3.20's non-deprecated name for the changed flag;
  `changed(Field)` is deprecated there and fails the example's `-Werror` compile.
- *The R534 exception is narrower and wider than the plan stated.* jOOQ's `from()` (which every
  `fromArray` load runs) calls `Tools.resetTouchedOnNotNull`, clearing the flag only on null-valued
  columns whose type is `NOT NULL`, and it does so on every value load, not only a key decode. So a
  null for a nullable column beside a decoded id is written and checked, and a null for a `NOT NULL`
  column is dropped by any later load. The check still agrees with the write, which is what the
  plan asked of it. The execution case moved to `title` (`NOT NULL`) beside a decoded id, a second
  case pins `description` (nullable) as written and checked, and the manual states the exception in
  those terms. R534's own body is corrected to match.

## Other solutions we've considered

- *Validating the whole record (`validator.validate(record)`).* jOOQ's `<validationAnnotations>`
  puts `@NotNull` on every `NOT NULL` column without a default, and a record bound from an input
  carries only the columns the input names, so an update naming two columns would fail on every
  other. Validating the written columns only, through `changed`, keeps the database-derived
  constraints without the false positives.
- *Keep validating the generated `.inputs` classes as well.* Restores a hand-attached mapping
  unchanged, but keeps graphitron validating an object the service never sees, which is the defect
  this item removes, and reports a violation twice where both carry the constraint.
- *Extend the `@mutation` column-length check to `@service` jOOQ records.* Catalog-derived and
  independent of how the consumer configures jOOQ, but it reports a too-long value twice wherever
  `<validationAnnotations>` is on, which is where the consumer who needs it has it. It stays open
  for consumers without the annotations.
- *Constraints declared in SDL and emitted onto the generated record.* Closes the loop with no
  consumer Java, and would reach scalar arguments. It costs a new directive and a mapping from SDL
  to the constraint vocabulary, and duplicates what the class or record the service takes can
  already say.
- *Jakarta method validation (`ExecutableValidator.validateParameters`).* Would reach scalar
  parameters (`lookup(@Positive Integer id)`), but the specification excludes static methods and
  most `@service` methods are static; it would split VALIDATION's behaviour by call shape.
- *A consumer-supplied `ValidatorFactory`.* Reopens programmatic `ConstraintMapping` against the
  generated classes; the smallest change and the one that pushes most onto the author, and it keeps
  graphitron validating an object the service never sees.
- *Resolving a column's getter through the consumer's generator strategy.* Would cover renamed
  getters, but graphitron does not run or configure the consumer's jOOQ code generation and has no
  strategy to ask; the default name confirmed by reflection, with a suppressible lint finding where
  it is absent, says what it can and cannot check.
- *Reflecting the getter in the classifier onto `ColumnBinding`.* The fact depends only on
  (table, column) and comes from the jOOQ corpus, so a per-use-site component would reflect it again
  at every binding, and it would change the equality `JooqRecordHelperNames` dedups `create<Record>`
  helpers on without changing the helper body. Captured into the `sql_` family instead.
- *A sealed `ValueShape.Validated` over `BoundClass` and `JooqRecordInput`.* Declares nothing the two
  arms share, so every reader still forks, and it puts the pre-step's policy into the shape
  taxonomy. The subject is the pre-step's own sealed type instead.
