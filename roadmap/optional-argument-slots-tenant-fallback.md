# A field whose tenant slots may all be absent is a build error, or fans out when they are

## Goal

In a database-per-tenant build, a field that learns its tenant only from values the client may leave out no longer compiles into a fetcher that crashes when the client does leave them out. A *tenant slot* is an argument or input field whose value names the tenant column, such as a scalar mapped to that column, a scalar marked `@tenant`, or an encoded node id whose key holds it. Today a field whose every slot sits behind a nullable argument or input field builds cleanly, and a request omitting them all fails at runtime with an internal `NoSuchElementException: The tenant binding value is absent`. When this lands the build rejects that field and names two fixes: make one slot non-null, or mark the field `@tenantFanOut`, which now accepts optional slots and means "query only the tenants the given values name, or every tenant the request may see when none is given".

A minimal pair over the sakila multi-tenant fixture (`multitenant.graphqls`, compiled with `<tenantColumn>film_id</tenantColumn>`), where `films(filmId: Int! @field(name: "film_id"))` is the existing routed root:

```graphql
type Query {
    # Rejected: every request that omits filmId names no tenant.
    filmsMaybe(filmId: Int @field(name: "film_id")): [Film!]!

    # Accepted: filmId given queries only that tenant; filmId omitted queries every
    # tenant in the request's tenant set and unions the rows.
    filmsNarrowable(filmId: Int @field(name: "film_id")): [Film] @tenantFanOut
}
```

The same holds for a slot nested in a filter input, which is the shape the provenance below hit: `studieprogrammer(filter: StudieprogramFilter)` whose `terminer` and `campuser` fields carry the tenant routes only when one is given, so it rejects unless marked.

## Design

Three changes, one in each place the tenant-binding axis already lives. The *tenant-binding axis* is `TenantBinding`, the per-field verdict on where a field's tenant comes from; `TenantBindingIndex.Fold.armOf` assigns it, reading a per-field `DirectBinding` (the slots, declines and evidence the field's own arguments carry).

**A slot's presence is a classification fact.** A bound slot is *required* when the client cannot omit it: its read path is non-null all the way down. For `SlotRead.TopLevelArg` that is the argument's type; for `SlotRead.NestedInput` it is the outer argument and every input field on the path; `SlotRead.ContextArg` counts as required, because the consumer supplies context arguments server-side and a missing one is a wiring bug, not a client choice. "All the way down" includes every list wrapper on the path: its element type must be non-null too, since `filter: [F]!` can arrive as `[null]` and `ids: [ID]!` as `[null]`, and neither names a tenant. So `[ID!]!` and `[F!]!` with a non-null slot inside are required, and `[ID]!` is not. Nullability decides alone: a non-null list slot is required even though it can arrive empty (see Out of scope). One function computes it from the coordinate's `GraphQLFieldDefinition`, the slot name and the slot's `SlotRead`; the name is what `TopLevelArg` and `ContextArg` read by, since those arms carry no name of their own. It is called from `SlotCollector.add`, which every mint site (column bindings, lookup scalars and map inputs, WHERE keys, agreement-checked SET columns, service value shapes, `@tenant`-marked scalars) already funnels through, so no mint site computes it on its own. `SlotCollector` is a static class built fresh in `Fold.directBinding`, so it takes the site's field definition (`fieldDefinition(site.coord())`) as a constructor argument. It rides `BoundSlot` as a `boolean required`, and the arm constructors enforce the rule rather than leaving it to the rung that applies it: `ArgumentBound` asserts at least one of its slots is required, and `FanOut` asserts none of its narrowing slots is.

**`DirectBinding` gets a closed reading.** Five readers consult `divines()` / `slots()` once R1018 has landed (`armOf`, `fanOutArmOf`, `globalDataArmOf`, `siteDivinesTenant`, `siteEstablishesContext`; R1018 removes `parentRowBinding`'s read), and a boolean `divines()` would make each of them decide afresh what an optional-only binding means. Replace it with a sealed reading the readers switch on: `Unbound` (no slots, no declines), `Declined(declines, slots)` (declines present, whatever slots sit beside them), `Guaranteed(slots)` (no declines, at least one required slot) and `Conditional(slots)` (no declines, slots, none required). `Declined` carries its slots because one reader below judges them. The readers decide, arm by arm:

- `armOf`: `Unbound` falls through to the rungs below the argument rung, as today. `Declined` takes today's declines branch: it rejects when the statement needs a tenant (with `unroutedServiceCall` when nothing in reach is tenant-scoped) and falls through otherwise. `Guaranteed` classifies `ArgumentBound` carrying every slot, optional ones included, as today. `Conditional` rejects when the statement needs a tenant and falls through like `Unbound` otherwise (below).
- `fanOutArmOf`: `Unbound` is today's plain fan-out. `Guaranteed` keeps today's "already binds the tenant column" rejection, since the field would never fan. `Conditional` falls through and becomes the arm's narrowing. `Declined` is judged on its slots as if the declines were absent: a required slot rejects as `Guaranteed` does, otherwise the optional slots narrow (none: plain fan-out). The declined shape stays a row filter that neither routes nor narrows. Today a fanned field with declines and no slots classifies `FanOut`, and that verdict is kept. A field with declines and slots rejects today as "already binds" and now behaves like its slots alone. Leaving a declined shape out of the narrowing is safe because narrowing never changes which rows a fanned field answers, only how many tenants it asks (see the narrowing bullets below).
- `globalDataArmOf`: `Declined`, `Guaranteed` and `Conditional` all contradict `@globalData`, as any tenant-naming argument or declined shape does today; `Unbound` goes on to today's evidence rung.
- `siteDivinesTenant` and `siteEstablishesContext`: only `Guaranteed` counts. `Unbound` and `Declined` count as they do today, which is not at all (`divines()` is false for both). A `Conditional` field never establishes a tenant of its own: unmarked, it either rejects or (below a parent that supplies a tenant, by R1018's ordering) inherits one that an upstream edge already counted; marked, it is covered by the `fanMarked` short-circuit in `edgeEstablishesContext` and by `anyFannedAncestor`. This narrows R1018's "`siteDivinesTenant` keeps counting the argument slot" to required slots, with no verdict change, since every path through such a field already crossed the edge that bound it.

**`armOf` rejects a `Conditional` binding.** The rung sits where the `divines()` rung sits today. Unlike that rung (which `Guaranteed` keeps, ungated as today), it is gated by `needsTenant` like the declines branch above it, and it picks its rejection family the same way that branch does. A `Conditional` field whose own statement needs no tenant (nothing in its reach is tenant-scoped, and it is not a connection-bound root `@service`) falls through like `Unbound`, because nothing in its own SQL can leak. Any tenant-scoped child below it then finds no context and rejects with today's `noTenantBinding`, so the gap stays loud. Where it does need a tenant:

- Where the field's reach holds a tenant-scoped table, the rejection is `Rejection.noTenantBinding`, the family that already covers "nothing names the tenant". Its `tableName` is the first tenant-scoped table in reach, as for every other `noTenantBinding` the rung ladder raises, and its detail names the optional slots and the fixes.
- Where nothing in reach is tenant-scoped, the field can only be a connection-bound root `@service`: `needsTenant` holds through `connectionService` alone, and service-call slots are root-only. A typical case is one returning a plain payload, whose reach is structurally empty, with a nullable `@tenant` input member. `noTenantBinding` would have no table to name there, so the rejection is `Rejection.unroutedServiceCall`. The optional-slot detail goes in as its one decline, and the declines branch already does this for the same reason. That variant's declines form reads "its arguments name tenant column '…' only through shapes that cannot route the call", which is true of an optional-only binding, because no single request is guaranteed a tenant.

The fan-out fix comes first in the detail, because with two optional slots "make one non-null" breaks every client that sends only the other:

> 'Query.filmsMaybe' takes its tenant only from optional values (filmId); a request that omits all of them names no tenant. Mark the field @tenantFanOut to query every tenant the request may see when none is given, or make one of them non-null.

The `@tenantFanOut` sentence appears only where the fan-out ladder would accept the marker on this field. Derive that from the ladder itself (factor `fanOutArmOf`'s rungs so they can be asked without the marker present; the ladder has no side effects, `recordMarkerVerdict` lives in `armOf`), not from a second list of its conditions: a mutation, `@asConnection`, `@service`, `@routine`, `@lookupKey` or non-list field gets the non-null fix alone. So does a field of a nesting type, which `armOf` turns away from both marker ladders before either runs (`site.nested()`); the hint check asks that guard first, so it never offers a marker the field could not carry.

This rung only ever sees fields that still classify `ArgumentBound` after R1018 moves the parent-row and inherited tenants ahead of argument slots. That is why this item depends on R1018: before it, a child field whose parent row names the tenant but whose filter has an optional slot (`StudieprogramFetchers.rowsKull`) would reject here, though R1018 makes it route correctly.

**`@tenantFanOut` with a `Conditional` binding narrows the fan-out.** `TenantBinding.FanOut` stops being a singleton and becomes `FanOut(List<BoundSlot> narrowing)`, where an empty list is today's plain fan-out; its javadoc's "nothing for the model to carry" goes. This is the "fan-out arm gains a carried argument reference" shape R517's open question 4 named, and a sibling arm would only repeat every exhaustive `FanOut` switch for a difference that lives in one runtime argument.

Narrowing is a set, not the single-tenant agreement fold `divinedTenant` / `agreeOnTenant` performs for `ArgumentBound`. A fanned field already answers from several tenants, and a filter slot such as `filter.terminer` is list-valued, so a client filtering terms in two tenants must get both tenants' rows, not a disagreement error. The generated `TenantConnections` gains a narrowing form of `fanOutDomain` taking the slot values:

- A slot contributes a set only when every value its read yields names a tenant. The read is flattened as `agreeOnTenant` flattens, through list values and through the per-element results `tenantSlot` and the decode helpers hand back for a list-shaped level. A slot whose read holds a null anywhere contributes no constraint, and so does one whose read is empty. That covers an absent or null argument, a null element, an element of a list-of-inputs filter that leaves the slot out, and an empty list. Dropping only the nulls would be wrong for a list of filter objects: an element that leaves the slot out may match rows in any tenant, so narrowing on its siblings' tenants would lose those rows.
- Values are coerced to the tenant key type as `divinedTenant` coerces them: a `String` (a decoded node-id segment, an `ID`-typed argument) parses to a numeric tenant column's type. Without this a narrowed node-id slot never matches a hosted key.
- The domain is today's domain (the request's tenant set intersected with the hosted tenant map, in configured order, with today's error for a claimed tenant the deployment does not host) intersected with every contributed set. Intersecting across slots is exact, since a row must satisfy every filter; a union would also be correct but queries tenants that cannot answer. Narrowing never changes which rows the field answers, only how many tenants it asks. A tenant's database holds only rows whose tenant column names that tenant, so a tenant outside a slot's set holds no row the slot's filter admits. That is the invariant behind both the conservative null rule above and leaving declined shapes out of the narrowing. The one exception is a slot whose predicate an authored `@condition` overrides: its binding stays in place (`Fold.directBinding` reads it from the column-binding ledger, not from the emitted predicate), so it narrows as it would route an `ArgumentBound` field. That is the posture `filmsUnderOverride` already pins for routing.
- A named tenant outside the request set is silently not queried, the same authorization pre-filter fan-out applies to hosted tenants outside the set, and the posture `node` / `nodes` / `_entities` take for an id whose tenant is outside it. An empty domain answers an empty list without taking a connection.

The zero-slot call is today's full domain, so the emitter does not branch on an empty `narrowing`. Everything downstream of the domain is the fan-out path unchanged: per-element `localContext` stamping, failure markers, `collapseFanOut`. `TenantStrategy.Fanned` carries the narrowing slot reads, rendered with the same slot-read fragments `ArgumentBound` acquisition uses.

This settles R517's open questions 1 (a requested tenant outside the request set is skipped) and 4 (the arm carries the slots) for both items; R517 keeps the remaining design, the list-valued tenant-column argument whose job is narrowing rather than filtering, and its open questions already record both answers. Two consequences to document rather than avoid: a narrowed fan-out that hits a failing tenant answers like a fan-out (a `null` element and a path-bearing error, or a nulled field under `[Film!]`), not like a routed field; and a value naming a tenant the request may not see answers no rows from it rather than an error.

## Implementation

- `TenantBindingIndex`: the presence function and its call in `SlotCollector.add`, with `SlotCollector` taking the site's field definition; `DirectBinding`'s sealed reading (`Declined` carrying its slots) and its five readers; the `needsTenant`-gated `Conditional` rejection in `armOf`, choosing `noTenantBinding` or `unroutedServiceCall` by reach as the declines branch does; the ladder factoring and the `Conditional` / `Declined` narrowing in `fanOutArmOf`.
- `TenantBinding`: `BoundSlot.required`; the `ArgumentBound` and `FanOut` constructor assertions; `FanOut(List<BoundSlot> narrowing)`, with every `FanOut.INSTANCE` site and exhaustive switch over the arm moved to the record.
- `ConnectionRuntimeClassGenerator`: the narrowing `fanOutDomain` form (the null-anywhere rule and the key-type coercion `divinedTenant` applies); `fanOutRows` / `fanOutBatchRows` take the narrowing values and pass them through.
- `TenantStrategy.Fanned` and the launcher render (`plan/LauncherCommands`, `render/`): carry and render the narrowing reads. The batched form (`fanOutBatchRows`) reads the narrowing values from the same environment its statement reads the filter's own values from, so the domain and the WHERE clause see one set of arguments.
- Docs: `docs/manual/how-to/tenant-scoping.adoc` (the "Routing is divined" paragraph and §3) and `docs/manual/reference/directives/tenantFanOut.adoc` (the rejection list's "an argument bound to the tenant column" becomes "a non-null argument bound to the tenant column", plus the narrowing paragraph drafted below).

## User documentation (first-client check)

For `tenant-scoping.adoc`, after "A tenant-scoped field that nothing routes is a build error":

> The same holds for a field whose tenant comes only from optional arguments: a request that leaves them all out names no tenant, so the build rejects the field. Mark the field `@tenantFanOut` (§3) to query every tenant the request may see when none is given, or make one of the arguments non-null.

For `tenantFanOut.adoc`, a new paragraph after the rejection list:

> A fanned field may take optional arguments that name the tenant, such as a nullable `filmId: Int @field(name: "film_id")` or a node id in a filter. When the request gives one, the field queries only the tenants its value names (several, for a list of ids); when it gives none, the field fans out as usual. Two such arguments narrow together: only tenants both name are queried. A tenant the request may not see is never queried, so a value naming one answers no rows from it, exactly as a filter on rows you cannot see would. A non-null argument naming the tenant is still rejected: the field would never fan out, so drop the directive.

## Out of scope

- An empty list in a non-null list slot. It folds to no tenant and keeps today's runtime error on an `ArgumentBound` field (under a narrowed fan-out it constrains nothing, so the field fans and the filter decides the rows). Treating `[ID!]!` as optional would reject every list-filtered routed root; the empty list deserves its own decision, likely an empty answer without a connection.
- The error type of the remaining runtime absence (`NoSuchElementException`, reported to clients as an internal error). After this item it is reachable only through the empty list above and a missing context argument.
- A list-valued argument whose purpose is choosing tenants rather than filtering rows, and its interplay with the request set, which stays R517.

## Other solutions we've considered

- **Fall back to the request's default tenant.** `RequestTenants.defaultTenant()` already exists, but its documented role is to serve global reads, and the manual promises "which tenant to name is your policy; graphitron never picks one". An omitted filter answered from one tenant's database is a subset presented as complete, the failure `fanOutDomain` already refuses for unhosted tenants.
- **Fan out implicitly, without the marker.** Fan-out is the right meaning of an omitted filter, but the manual's position is that fan-out cannot be inferred, it must be asked for: it multiplies connections and changes the field's failure shape. The rejection asks for it.
- **Reject only, with no new fan-out shape.** Leaves an author whose filter is optional by design (sis) one fix, changing the API to make a filter required.
- **A build warning instead of a rejection.** The field has no correct execution for a legal request; the axis's posture for that is a typed rejection, as with `noTenantBinding` itself.
