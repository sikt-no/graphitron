# A @splitQuery field on a nesting type routes on its tenant binding

## Goal

In a database-per-tenant build (one with `<tenantColumn>` configured, so every tenant's rows live in their own database), a field on a nesting type gets the same tenant routing it would get if it sat directly on the enclosing `@table` parent. A nesting type is an object type without `@table`, reached through a field on a `@table` parent, so it shares that parent's row. Today a `@splitQuery` field on such a type picks no tenant at all: it reads through the fixed default data source and batches its DataLoader by query path alone, so one batch can mix tenants. `graphitron:validate` reports nothing. The sis Graphitron 10 port has 15 such fields in 10 wrapper types, all over tenant tables (for example `EmneFagkoblinger.fag` under `Emne @table(name: "EMNE")`), and they block its go-live. When this item lands, those fields read from the tenant their parent row came from (a nesting type shared by several `@table` parents keeps its existing multi-parent deferral for `@splitQuery` fields, unchanged here), each DataLoader batch holds one tenant's keys, and a nested field that cannot be routed is a build error with the same message a flat field gets. A missing routing decision at any generated database access becomes a generator failure, not a silent read on the default source.

The minimal pair, on the multi-tenant sakila fixture (`graphitron-sakila-example/src/main/resources/graphql/multitenant.graphqls`, tenant column `film_id`). `Film.inventories` exists there today; `Film.stock` and `FilmStock` are the fixture addition this item makes:

```graphql
type Film implements Node @table(name: "film") @node(keyColumns: ["film_id"]) {
    id: ID! @nodeId
    # Routed today: reads from the tenant the Film row was fetched under.
    inventories: [Inventory!]! @splitQuery @reference(path: [{key: "inventory_film_id_fkey"}])
    # A nesting edge: FilmStock has no @table and shares the Film row.
    stock: FilmStock
}

type FilmStock {
    # Today: default source, path-keyed loader. After: routed exactly like Film.inventories.
    inventories: [Inventory!]! @splitQuery @reference(path: [{key: "inventory_film_id_fkey"}])
}
```

## Mechanism today

Terms used below. The *tenant binding* (`TenantBinding`) is the per-field decision of where the tenant comes from, computed once after classification by `TenantBindingIndex` (the *fold*). Its arms that matter here are `Inherited` (an ancestor already fixed the tenant, so the field reuses it) and `ParentRowBound` (a global parent row names the tenant of the child row it references, through a foreign key that lands on the tenant column). `TenantDslEmitter` turns the arm into the generated `DSLContext` acquisition (`TenantConnections.dslFor(...)` for routed arms) and into the DataLoader name (`tenantLoaderName(env)` for routed arms, so each batch holds one tenant).

There are two independent causes, and either one alone produces the wrong fetcher:

1. **The fold never sees the field.** `TenantBindingIndex.Fold.run()` assigns arms to the coordinates in `schema.fields()`. `FieldBuilder` classifies a nesting type's fields inside the enclosing parent's classification (`classifyChildFieldOnTableType`, with `parentTypeName` set to the nesting type), and they live only in `ChildField.NestingField.nestedFields()`. So the coordinate gets neither an arm nor the `noTenantBinding` rejection, which is why validation stays green. `OperationMemberRelation` deliberately mints no rows for nested coordinates either (its class javadoc states that domain boundary); nested instances keep the leaf-local `OperationMembers.membersOf(OutputField)`.
2. **The nested Fetchers class is generated without the schema.** In `TypeFetcherGenerator.generate`, the branch for a nesting-reached row (`reach.wiringFor(row.typeName())`) calls `generateTypeSpec` with a null `GraphitronSchema`, and every `TenantDslEmitter` entry point returns the single-tenant form when the schema is null, before it looks up a binding.

Underneath both, `TenantDslEmitter` also falls back to the single-tenant `getDslContext(env)` form whenever `tenantBindingOf` returns null under `TenantScopes.Configured`, in `resolve`, `resolveByName`, `dslExpression`, `handDownOnly` and `loaderNameDeclaration`. That fallback is what let both causes stay silent.

The pieces the fix reuses already handle nesting types. The fold's ancestor-context graph (`buildEdges`, `foldAncestorContexts`) is built from the SDL, so a nesting type already gets a correct `tenantContextOf` answer: the nesting edge establishes nothing and passes on its parent's context. `ColumnBindingLedger` already holds rows for nested coordinates, because `FieldBuilder` records them under the nested `parentTypeName`. And a nested fetcher's `env.getSource()` is the enclosing parent's record (the nesting fetcher passes the source through), which is what `TenantDslEmitter.parentRowRead` reads.

## Implementation

**`TenantBindingIndex.Fold`: one loop over sites.**

- *A site is one classified instance of a coordinate*: the `OutputField` plus its operation members. The constructor builds one `Map<FieldCoordinates, List<Site>>`. A flat coordinate is one site, built from `fields` and the minted `OperationMemberRelation` exactly as today. A nested coordinate gets one site per classified instance, found by a recursive descent through every `NestingField` in `fields` (nesting inside nesting included), with its members read through the leaf-local `OperationMembers.membersOf`. That is the same production the emit-side producers already use for nested instances (`ConditionCommands`, `ProjectionCommands`), so the fold's "one production" guard stays honest. A nesting type reached from several `@table` parents contributes several sites. A coordinate reached both flat and nested (the mixed-source reach `MixedSourceReachIndex` covers) gets the union. `run()` replaces its loop over `fields` with one loop over this map.
- The site is the only per-field input. `armOf`, `parentRowBinding`, `directBinding`, `collectFromServiceCall`, `globalDataArmOf` and `fanOutArmOf` take a site, so no reader looks a coordinate up in `fields` or `operationMembers` again. `armOf` returns a sealed verdict instead of null plus an appended rejection: `Arm(TenantBinding)` or `Rejected(List<ValidationError>)`. That makes combining a coordinate's sites a pure step. The marker sweeps (`sweepTenantMarkers`, `unconsumedTenantMarkerReason`) read the same map.
- **Combining sites.** If every site yields an arm and all arms are equal, that arm is recorded. If any site is rejected, the coordinate records no arm and reports each distinct rejection once, deduplicated across sites. A distinct text from a different site is kept, which is what preserves the `@splitQuery` hint that only a global-parent site produces. If the sites yield unequal arms, the fold throws a generator-bug `IllegalStateException`; it adds no user-facing text. That case is unreachable on a schema the validator admits. `tenantContextOf` is a per-type, every-path fact, so it is the same at every site of a coordinate. The one per-parent input, `parentRowTenantSlot`, applies only to a Table-sourced `BatchedTableField`. `GraphitronSchemaValidator.validateNestingParentCompat` already defers that shape when a nesting type is shared by several parents ("not yet supported across multiple parents"), and it stays the owner of multi-parent admissibility.
- **Edge predicates.** Each one states its own quantifier over a nested edge's sites. `edgeEstablishesContext` is true only when every site establishes context: it feeds the every-path "has a tenant context" fact, where the safe reading is every. `edgeDivinesTenant` is true when any site divines: it feeds the any-path `belowBoundEdge` fact on the rejection side, where the safe reading is any. With these, a nested `@splitQuery` edge that divines, or is `ParentRowBound`, establishes context for its own subtree exactly as a flat one does.
- Marker ladders stay off nested sites. `armOf` runs the `@tenantFanOut` / `@globalData` ladders only on flat sites, and that is decided from the site, not left incidental. A nested site carrying either marker gets no arm and records no marker verdict, so `sweepUnreachedMarkers` keeps rejecting it with its current text, which already names nesting-backed parents as unsupported.
- Nested fields that do not batch get verdicts too, the same ones they would get flat. A nested inline `@reference` into tenant data under a tenant-scoped parent is `Inherited`. Under a global parent it is rejected with the existing `@splitQuery` hint, because the inline child would run inside the global parent's statement. That nested hole is closed by the same change.

**`ColumnBindingLedger.requireCovers`.** It also walks the nested instances' leaf-local condition members, so the coverage invariant holds for every slot the fold now reads. The ledger's `(coordinate, table)` key merges a shared nesting type's parents, which is safe because `validateNestingParentCompat` requires their filters to agree.

**`TypeFetcherGenerator.generate`: the nested class sees the run's tenancy, through one fact.**

- The nesting-reached branch passes `schema` to `generateTypeSpec`. That covers pivot wirings too (`NestingReach` includes them), and their `PivotSlotField`s never reach `TenantDslEmitter`. `dualShapeBinding` is gated on a non-null `resultType`, which this branch never passes, and `buildTableInterfaceReprojection` serves the joined-table interface fetcher, which a nesting type never emits.
- Passing the schema also turns on `TenantDslEmitter.isMultiTenant(ctx)` for the nested class, and `buildScatterConnectionByIdxHelper` reads that predicate. The nested class's launcher relation, however, comes from `LauncherCommands.produceWithoutSchema`, which always carries `CarrierDsl.ENV_ACQUIRED`, so the rows-method call site in `BatchedRowsFragments` would leave out the `dsl` argument the helper now declares. A nested `@splitQuery` connection in a multi-tenant build would not compile. Even with the call site patched, `ENV_ACQUIRED` would run the connection's lazy `totalCount` on the default source. There are two facts answering "is this run routed", and they diverge only on this branch. The fix makes it one fact with one source: `produceWithoutSchema` takes its `CarrierDsl` from the run's own relation (`launchers.carrierDsl()`, which `LauncherCommands.produce` sets to `ROUTED` under configured scopes), and `buildScatterConnectionByIdxHelper` reads the class's relation's `carrierDsl` instead of `isMultiTenant`. The implementer audits the remaining `isMultiTenant` readers on the nested path for the same divergence.
- In a single-tenant build the run's relation is `ENV_ACQUIRED` and every `TenantDslEmitter` entry point returns the single-tenant form, so single-tenant output stays byte-identical.

**`TenantDslEmitter`: no silent fallback under configured scopes.**

- In `resolve`, `dslExpression`, `handDownOnly` and `loaderNameDeclaration`, a null binding with a non-null schema, `TenantScopes.Configured` and a non-null `parentTypeName` throws a generator-bug `IllegalStateException` naming the coordinate. This is sound because every `Rejected` verdict carries its rejection, the fold visits every site that gets emitted, and `GraphQLRewriteGenerator` fails the build on validator errors before any emission. A null binding at emission therefore means the fold missed a coordinate. The schema-null fallback stays, for unit-tier callers that build the model only.
- `resolveByName` resolves through `tenantBindingOf` rather than `schema.fields()`. `resolve` reads only the field's name off its carrier, so the binding is the whole input it needs, and one lookup serves flat and nested coordinates alike. (Nested multi-table polymorphic children do not reach this site today, since `GraphitronSchemaValidator.isNestedWireableLeaf` rejects them at nested depth; the change is for uniformity, not a live hole.)
- If the multi-tenant fixture or the corpus trips the new invariant at a site the fold does not visit, the fix is to widen the fold to that site, or to give the site an explicit arm. Never restore the silent fallback.

**User manual.** Add one sentence to `docs/manual/how-to/tenant-scoping.adoc`: fields of a type without `@table`, reached through a field on a `@table` type, route exactly as they would on that `@table` type, including the parent-row routing described in its section 2.

## Tests

- **Classification** (`TenantBindingClassificationTest`): a nesting type's `@splitQuery` field under a tenant-scoped parent classifies `Inherited`. Variants: one whose `@reference` carries a `@condition` join, one declared in an `extend type`, one two nesting levels deep, and one connection-shaped (`@asConnection`). Under a global parent, a nested `@splitQuery` child whose foreign key lands on the tenant column classifies `ParentRowBound`, and a nested child with no such key is rejected with `noTenantBinding`. A nested inline `@reference` into tenant data under a global parent is rejected with the `@splitQuery` hint. A nesting type shared by two parents, with an inline tenant-reaching child, reports each distinct rejection once. A nested child carrying `@tenantFanOut` keeps its current unreached-marker rejection.
- **Pipeline** (`TenantRoutedFetcherPipelineTest`): assert the facts, not the emitted body text. `schema.tenantBindingOf("FilmStock", "inventories")` is `Inherited`, and the nested `ParentRowBound` case's coordinate carries that arm, the same shape the file already asserts for flat coordinates. The nested Fetchers class's launcher relation carries `CarrierDsl.ROUTED` under configured scopes and `ENV_ACQUIRED` without them. Code-string assertions on generated method bodies are banned at every tier (`docs/architecture/how-to/testing.adoc`). A unit test pins the new `TenantDslEmitter` invariant: a configured schema with a coordinate missing from the index throws, naming the coordinate.
- **Compilation and execution** (sakila-example): add `Film.stock: FilmStock` to `multitenant.graphqls`, with `FilmStock.inventories` (a list `@splitQuery`), a connection-shaped `@asConnection @splitQuery` sibling, and `FilmStock.scenes` (a list `@splitQuery` over `film_scene`). Compiling the multi-tenant package proves the scatter helper and its call site agree. In `TenantDivinedRoutingExecutionTest`, mirror the existing `Film.inventories` assertions for `stock { inventories }`: a query that divines a tenant through `films(filmId:)` reads the nested inventories from that tenant's database, a request divining two different tenants never shares one loader batch between them (asserted on `stock { scenes }`, since both tenants hold scenes and a shared batch empties one film's list), and the connection's `totalCount` reads the same tenant. This is the acceptance evidence for the goal.

## Other solutions we've considered

- **Register nesting types' fields in `schema.fields()`.** That would make every per-coordinate consumer see them for free. It was rejected because the flat index, and `OperationMemberRelation` with it, deliberately leaves nested coordinates out: the same nested coordinate can be reached through more than one parent, with different members per reach, and a coordinate-keyed row would collapse those. The fold owns the one decision this item needs, so the agreement check lives there.
- **Fix only the null schema in `TypeFetcherGenerator`.** That alone emits nothing new, because the fold still holds no arm for the coordinate and the emitter falls back silently. Both causes have to go, and removing the fallback is what keeps the next coordinate the fold misses from slipping through the same way.

## Relation to other items

R557 (the `@splitQuery` marker completeness sweep) covers the marker on the nesting field itself, where it is inert. This item covers fields *of* a nesting type, where `@splitQuery` is consumed and produces a batched leaf. The two sets of coordinates are disjoint, and neither item depends on the other.

## Implementation notes

- **Unequal arms across sites record no arm rather than throwing in the fold.** The plan had the fold throw a generator-bug `IllegalStateException` when a coordinate's sites yield unequal arms. The fold runs at schema build, before `GraphitronSchemaValidator`, so a throw there would crash the build (and `graphitron:validate`, and the LSP) on exactly the schemas `validateNestingParentCompat` is about to reject: two global parents of one shared nesting type whose `@splitQuery` field mints `ParentRowBound` over each parent's own table is one. The fold instead records no arm and adds no text for that coordinate, the validator's multi-parent rejection reports it, and should a schema the validator admits ever reach the case, the new `TenantDslEmitter` invariant fails the generation naming the coordinate. Same guarantee, without the crash.
- **`isMultiTenant` audit.** The scatter helper now reads the class's launcher relation's `carrierDsl`. The remaining `isMultiTenant` readers are the three connection-shaped sites in `MultiTablePolymorphicEmitter`, which serve multi-table polymorphic children; `isNestedWireableLeaf` rejects those at nested depth, so none is on the nested path.
- **The per-tenant batch evidence reads scenes, not inventories.** The first delivery asserted the two-tenant case on `stock { inventories }`. Tenant 2 holds no inventory, so a batch shared between the tenants and run on tenant 1 gave the same answer, and a bare-path loader-name mutation left the class green. `FilmStock.scenes` is the fixture's one tenant table populated in both tenant databases (one scene for film 1, three for film 2). Under the same mutation the test now fails, with tenant 2's film answering 0 scenes instead of 3.

## Reviewer findings

**In Review → Ready, 2026-10-12, at trunk `bbfd1de`.** Question 1 holds and question 2 fails. On question 1, the delivery is the change the spec approved. The fold builds one `Site` map with the sealed `Verdict` and the stated edge quantifiers. The nested class gets the schema plus the run's `carrierDsl`, and the scatter helper reads that fact. The emitter invariant replaces the silent fallback. The coverage walk in `ColumnBindingLedger` is extended, and the manual sentence is in. The one substitution, unequal arms recording no arm instead of throwing, is recorded under Implementation notes with its reason, and the reason holds. The emitter invariant also reaches `TenantDslEmitter.parentRowBinding`, one site beyond the four the plan named. That is inside the plan's own "no silent fallback under configured scopes", so it is not a finding. `mvn install -Plocal-db` passes. The generated `FilmStockFetchers` in the multitenant package reads `TenantConnections.tenantLoaderName(env)` and `dslFor(...)` on both nested fields.

The failure is in the acceptance evidence for "each DataLoader batch holds one tenant's keys". The spec names it: in `TenantDivinedRoutingExecutionTest`, "a request divining two different tenants never shares one loader batch between them". The delivered test, `nestedInheritedChild_neverSharesOneBatchBetweenTwoTenants`, does not demonstrate this. I tested it by mutation. I made `TenantDslEmitter.loaderNameDeclaration` emit the bare-path `loaderName(env)` for `Inherited` on `FilmStock`, so both tenants' films share one batch. The generated class carried the bare name, and all 61 tests in the class still passed. The cause is the fixture: tenant 2 holds no inventory. A shared batch that runs on tenant 1's database therefore answers film 1 with two rows and film 2 with none, which is exactly what the test expects. The test also asserts no acquisition counts, and counts would not help here because a tenant's connection is taken once per request. Per `roadmap/workflow.adoc` (Revive), named acceptance evidence that does not demonstrate the goal decides the goal as undelivered. The routing half is demonstrated: `nestedInheritedChild_routesItsBatchToTheDivinedTenant` reads 2 rows where the default source would answer differently.

**What would satisfy it.** The test has to fail when the nested loader name loses its tenant segment, so both tenants' films must expect non-empty, different answers. One way needs no fixture change. Add a nested `@splitQuery` child over `film_scene` (foreign key `film_scene.film_id` to `film`) to `FilmStock`. Tenant 1 holds one scene for film 1 and tenant 2 holds three for film 2, so a batch shared on either tenant empties the other film's list. Then assert 1 and 3 through `endorsements { film { stock { scenes } } }`. Seeding a tenant 2 inventory would also work, but it disturbs the existing "tenant 2 holds no inventory" assertions. Whichever way you choose, rerun the bare-path mutation above and confirm the test now fails. The rest of the delivery can stand as is.

*Addressed:* `FilmStock.scenes` was added and the two-tenant test asserts 1 and 3 scenes. The bare-path mutation now fails that test. See Implementation notes.
