# Reset session variables at release as a backstop to the consumer's unmount

## Goal

A connection Graphitron returns to the pool carries no session variables, even when the consumer's unmount is wrong. Today release runs the consumer's unmount callback and nothing else; whether identity is actually cleared rests entirely on that callback following the hook state contract (`docs/architecture/reference/runtime-extension-points.adoc`, "The hook state contract"). An unmount written with `set_config(..., true)` or `SET LOCAL` is transaction-scoped, so in autocommit it clears nothing, raises nothing, and the connection goes back to the pool still holding the previous caller's claims. No test or runtime check can see this from Graphitron's side. When this lands, release on PostgreSQL runs a reset after the consumer's unmount (and before close), so a defective unmount degrades to fail-closed rather than to a cross-user leak.

## Context

Found in an adversarial review of the owned-connection session lifecycle. The release sequence lives in the emitted `PinnedConnection.release()` (generated by `ConnectionRuntimeClassGenerator`): roll back any open transaction, restore autocommit, call the consumer's unmount, close. A failed unmount already evicts the connection; this item covers the silent case where unmount succeeds and clears nothing.

## Open questions

- `RESET ALL` (session settings only, cheap, leaves pgjdbc's server-prepared statements intact) or `DISCARD ALL` (also drops prepared statements, temp tables, advisory locks, and resets the session authorization; pgjdbc invalidates its statement cache on the command tag, but the per-request cost is higher)? `RESET ALL` covers the GUC-based identity this item is about; check whether it also undoes a mount that used `SET ROLE`.
- Unconditional, or on by default with an opt-out for consumers who keep deliberate session state across borrows? A failing reset should evict, like a failing unmount.
- Oracle: RAS detach and VPD context clears are the consumer's routines; is there a comparable cheap backstop, or is this PostgreSQL-only with the Oracle case left to R468's execution coverage?
