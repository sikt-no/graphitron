# Reflect the connect routine's signature instead of binding claims as an opaque String

The claims payload is stringly typed end to end, and the string is not merely the Java carrier: it is also how the payload reaches the database, so a consumer whose connect routine takes a user-defined type has no supported way to call it. `GraphitronFacadeGenerator` hardcodes the owned factory's leading parameter as `ClassName.get(String.class)` (`GraphitronFacadeGenerator.java:115`), the instrumentation reads it back as `String` from the `graphQLContext` under `CLAIMS_KEY` (`GraphitronConnectionInstrumentationGenerator.java:172`), the emitted `SessionHook.connect` signature is `(Connection, String claims)`, and the function-hook implementation binds it with `cs.setString(1, claims)` into `{ call <fn>(?) }` (`ConnectionRuntimeClassGenerator.java:1951`-`:1960`). Nothing casts, so the parameter arrives typed `varchar` and a routine declared `connect(app.claims)` does not resolve against it; whether it works at all depends on the pgjdbc `stringtype` setting deciding to send the parameter as unspecified and letting Postgres infer the composite from its text representation. That is a fragile accident, not a contract, and it inverts the project's own posture everywhere else on this boundary: the tenant key's Java type is read off the catalog so a mis-typed map is a compile error, and contextArguments are typed from the consumer's declared parameter type so a wrong value is a compile error at the factory call site, while the one payload that carries identity, the security-load-bearing value, is an untyped blob that fails (if at all) inside the database at a cast. The `<variables>` sugar is not affected in the same way (it explicitly casts to `jsonb`, and a claims *document* is genuinely JSON there), so the gap is specific to the function-hook form, which is also the form the integrity gradient recommends for a privilege fence.

## The signature is already a catalog fact; nothing extra needs naming

The consumer has *already* named the routine. `<connect><call>Pk_Ras.Connect</call></connect>` is a pointer into the database, and the payload's type is a property of what it points at, so requiring a second `<sessionState>` element naming the UDT would make the author restate a fact the catalog holds, and admit the possibility of restating it wrongly. This item's approach is therefore to resolve the named routine against the catalog and read its signature: parameter names, IN/OUT direction, Java types, return type. That matches how the rest of the generator treats the database (`@routine`'s own reference says "the routine's shape (table-valued) is read off its jOOQ kind, not declared"; the tenant key's Java type is read off the column) and it is the difference between typed code the author configures and typed code the author merely *gets*.

The resolution seam already half-exists, and today throws the answer away. `JooqCatalog.findNonTableValuedRoutine` (`JooqCatalog.java:207`-`:231`) locates the generated per-routine class for exactly the population a session hook draws from, a procedure or scalar function that is not table-valued, instantiates it, and verifies `org.jooq.Routine.getName()` against the SQL name so a naming-strategy mismatch degrades to a miss rather than a false positive. It then discards the resolved routine and returns `RoutineResolution.NonTableValuedRoutine(detail)`, a prose string used only to give `@routine` a better rejection message. The work is to let that resolution carry the routine itself, from which `getParameters()`, `getInParameters()`, `getOutParameters()` and `getReturnParameter()` yield the full signature.

Binding follows for free from the same decision, and this is the part worth noticing: a UDT-typed parameter on a generated jOOQ routine class is already typed as the generated `UDTRecord`, and jOOQ already knows how to bind it. So calling the routine *through its generated class* rather than through the hand-assembled `{ call <fn>(?) }` string is what makes UDT support fall out, instead of needing `PGobject`/`setObject` plumbing and a `Schema.getUDTs()` lookup of our own. The consumer's factory parameter becomes the generated record type, with typed field setters and compile-time checking, and R234 (UDT records as input backings) stops being a prerequisite for this item, though the two will want to agree on how a UDT surfaces in the model.

Consequences beyond the payload type, which are part of why this shape is worth the work:

* **`<handle>` becomes derivable.** Whether connect produces an OUT value, and of what type, is a signature fact. Today it is a hand-declared boolean cross-checked against a second hand-declared boolean on `<disconnect>`, with `SessionStateConfig.from` rejecting the mismatch. Reflected signatures make "produced but not bound" a structural comparison of two real signatures rather than a config-consistency rule, which is the stronger form of the same invariant. Decide whether `<handle>` becomes redundant-but-verified (declared value must agree with the catalog, so existing POMs keep working and a wrong declaration fails loudly) or deprecated.
* **The hook stops being raw JDBC.** The emitted hook deliberately owns a bare `Connection` and uses `CallableStatement` with no jOOQ involvement. Executing a generated routine means building a `Configuration` over that connection inside the hook. The invariant that must survive unchanged is the state contract: both halves run outside any transaction, with the connection normalized to autocommit at acquisition.
* **A resolution miss cannot be silent.** For `@routine` a probe miss degrades to a rejection message, which is fine. Here, silently falling back to the current string bind would mean identity plumbing quietly reverting to the weaker form, which is a security-relevant regression, not a convenience. A miss must either fail the build naming what was probed, or require an explicit opt-in to the string form.

Open scoping questions the item must answer rather than assume. **Oracle packages:** the shipped canonical example is `Pk_Ras.Connect`, a package procedure, and the existing probe only looks at `<schema>.routines.<PascalName>`, which is not where jOOQ puts package routines; either the probe learns the package form or the feature covers Postgres top-level routines only, and says so. **Overloads:** jOOQ suffixes generated classes for same-named routines with different signatures, so a `<call>` naming an overloaded routine has no unique signature to reflect; this is the one place where the author may genuinely have to name something extra, and it should be a typed rejection rather than a first-hit guess. **Codegen prerequisites:** the approach assumes jOOQ generated routines at all (`<routines>true</routines>`), which is the default but not guaranteed, and warrants the same kind of construction-time precondition as `verifyTablesClassPresent`. Keeping the `String` form working is a hard constraint throughout: it is the shipped signature, the compact-JWS cryptographic-fence pattern depends on passing a raw token, and both the `<variables>` sugar and the dev-goal `<claims>` config feed strings.

## Secondary: multiple parameters

Once the signature is reflected, an N-parameter connect routine is not a special case, it is just what the signature says, so the primary work should avoid baking in a one-parameter assumption even if it only ships the single-parameter shape. What multi-parameter support additionally needs is a decision about where the extra values come from. Taking them all from the caller generalises cleanly (the factory's leading `claims` parameter becomes one typed parameter per IN parameter, in declaration order, ahead of the alphabetical contextArgument slots), but three shipped surfaces assume exactly one payload and each needs an answer: `CLAIMS_KEY` publishes a single `graphQLContext` value, the `<variables>` sugar casts a single JSON document, and the dev-goal `<devDatabase><claims>` config (plus `GRAPHITRON_DEV_CLAIMS`, and the `<allowClaimsOverride>` per-call argument) supplies one inline-or-`@file` string. Lower priority than the primary typing work.
