= Writing a rule
:description: Where a rule's text lives and who evaluates it: a view by default, a table when a grain is established or a cost was measured, and what a stored relation owes for the privilege.
:!toc:

Every fact in the store is there because somebody wrote a rule. This page is about the decision
that comes up each time one is written and tends to get made without being noticed: where the
rule's text goes, and who runs it. The strict statement of the model lives in
xref:fact-model.adoc[The fact model] and the naming half in xref:naming-the-row.adoc[Naming the
row]. This page is the decision itself, with a worked example, the obligations that follow from
it, and an honest account of how little of it a test will catch.

== Two questions wearing one coat

A rule gets discussed as though it had a kind: this one is capture, that one is a derivation,
this other one is anchoring. That framing hides a fork, and the fork is where the mistakes live.
There are two independent questions, and every rule answers both.

*Where does the rule's text live?* In a view, if a view can state it. That is the default and it
is not a close call: a view states the rule once, in the catalog, where `ViewReferences` can read
what it reads and where a gate can hold it to its owner. The alternative is a rule spelled in Java
or in hand-written jOOQ, which is invisible to every catalog parse in the tree.

*Who evaluates it, and when?* A reader, on read, is the default. The alternative is a gatherer,
once, writing rows into a table.

The two are independent. A rule whose text is in a view may be evaluated on read or copied into a
table; a rule that fills a table may have been stated in a view first or spelled directly in
jOOQ. Storing a rule's result is not a reason to stop stating the rule in SQL, and this is the
single most common way the discipline gets misread. When a rule is stored, the writer should be
`INSERT INTO target SELECT ... FROM <the rule's view>`, not a second statement of the rule.

== A word that is already spoken for

`anchor` is used four ways across this store, and three of them predate the one this page needs.
xref:fact-model.adoc[The fact model] uses it for the resolved twin of an entry, for the existence
relation a reference web keys on, and for a per-view test oracle. All three are live and none is
wrong.

The fourth sense, and the only one this page means, is structural: *an anchor is a relation whose
key no other relation is the authority for.* It is decidable rather than declared, by looking at
the declared keys and the foreign keys between them. A key that a relation's own references
already cover is _composed_; a key they do not cover is _established_. Composing a key out of
references you already hold establishes nothing, and a relation that establishes nothing has no
claim on a table.

An anchor is not a third kind of rule sitting beside capture and derivation. It cuts across both:
a relation that reads a corpus may establish a grain, and so may one derived from rows already
stored.

== Ask the prior question first

Before deciding where a rule goes, ask whether it needs to exist.

*Does a stage upstream already hold this fact and throw it away?*

If it does, the rule does not need a category. It needs an owner. The cheapest and most durable
fix to an expensive rule is not a better rule; it is a captured fact, because capture removes the
evaluation rather than relocating it. The store's lever order puts this first for that reason,
ahead of indexing, rewriting, and registering.

The shape to watch for: an unbounded descent through a tree. If a rule walks a structure that some
reader already had in its hand while reading, that reader is usually the right owner. The same
rule stated at the reading can be total where the query form has to stop at a depth. When you find
yourself arguing that no view can state something, check upstream before you accept the argument.

== The three questions that decide storage

Once the rule has to exist here, storing it has three possible reasons and no default. Asked in
order, the honest answers are usually no:

. *Does it read a corpus?* A view cannot open a file, a jar or a catalog, so a rule that reads one
outside the store is a table filled by a gatherer.
. *Does it establish a key its own references do not already cover?* If yes it is an anchor, and a
foreign key cannot reference a view, so it is a table.
. *Has a read cost been measured?* Not estimated, not feared. Measured, against the criterion that
a consumer's query gets simpler or a timed reader gets faster.

If all three answer no, the rule is a view and writing it as anything else is a defect.

Note what is not on that list. Aggregation, recursion and window functions are not triggers. They
are the constructs that make a reader _suspect_ a rule will be too slow, which is a useful
instinct and a bad rule: the store today has recursive views, dozens of windowed views and dozens
of grouped views, all correctly views. A recursive view has to terminate on the population the
store can hold rather than the one the subject would have, which is a real constraint and a
different one from "this uses `WITH RECURSIVE`". The two answers the DDL header admits are that a
view cannot express the rule, or that a view expresses it correctly and too slowly. A stored
relation always says which of the two it is.

== A worked example, and its failing sibling

`graphitron_field_column_scope` is a table. A gatherer fills it. By the questions above that
should make a reader suspicious, so look at how it is built.

The rule is a view, `graphitron_field_column_scope_rule`, and it aggregates. The writer is one
statement:

[source,text]
----
INSERT INTO <target> SELECT <the rule view's own columns> FROM <the rule view>
----

The class that does it argues for the split in its own words: the rule stays stated once, in SQL,
in the catalog where a parse can read what it reads, and what the class adds is who evaluates it
and when. It then names the payoff, which is the part worth carrying away. Because the rule is
still a view, an `EXCEPT` between the target and the rule view is runnable for as long as both
exist. The table can be checked against the rule that is supposed to have produced it. Nobody has
to believe the two agree.

Now the sibling. `graphitron_field_navigation` is also a table, and it is also filled by the same
gatherer, ten lines away. Its population is a left join and a `CASE`, at a grain that already
exists: its key is `graphitron_field`'s key, unchanged. No corpus, no established grain. It is
stored so that a reader joining on the navigated type meets an indexed column instead of a view's
projection, which is a real reason and the third of the three above.

But there is no rule view under it. The rule is stated once, in jOOQ, and there is nothing to diff
it against. If the jOOQ and the intended rule ever disagree, no `EXCEPT` will say so, and the
store has a named mechanism for exactly this case that was not used: a registration keeps the rule
in a view, moves the canonical name onto a table of the same shape, and refills it inside the
capture transaction.

Two stages of one gatherer, written ten lines apart, take opposite positions on the same question.
The first is the discipline. The second is the departure, and it is in the tree.

== What a stored relation owes

Storing is not free, and the price is not performance. A stored relation owes three things.

*An owner.* Not chosen, computed: a relation's owner is the latest, in gatherer dependency order,
of the owners of the relations it reads. Because it is a function of the schema, it can be gated,
and because it can be gated the convenient answer is not available. A rule that reads one family's
facts belongs to that family. A rule crossing families belongs to the gatherer that runs last
among them, which is not the same as inventing a gatherer to run last.

*A grain.* One sentence saying what a single row is about, and a key that is that sentence's
natural key. A relation with no grain does not get a pass; it gets a registration, which is what a
rule with no owner is given so that something somewhere refreshes it.

*A mark and a sweep.* This is the obligation that gets forgotten, and the one with the least
support. A stored relation's rows outlive the reading that wrote them unless something removes the
ones a later reading no longer derives. Each gatherer holds its own list of relations to sweep.
A relation added to a gatherer and left off that gatherer's list will accumulate every reading's
rows, forever, silently. A cascade is not a substitute: a cascade corrects a row when its parent
goes, and does nothing for a row whose parent stands and which this reading simply no longer
produces.

Anchoring, when it happens, is a gatherer's last step and not a gatherer of its own. An anchor
establishes a grain out of what the whole corpus says, so it cannot run per document; it runs
after its gatherer's own sweep, over the rows that survived.

== The calculated column

Between a view and a stored table sits the `GENERATED ALWAYS AS` column, and it is worth knowing
when it earns its place because it is easy to reach for and not a resting place.

The store's clear case is the case fold. Where an authored spelling has to meet a catalog name,
each side carries an `_upper` companion the database computes and nobody writes, and an index
leads with it. That turns a per-row `UPPER()` on both sides into an equality a seek can serve. The
column exists because a comparison needs it, at the relation that owns the spelling.

The warning case is a rule that was made into a stored column so that an index could serve it, in
a family that did not know the answer. If a computation had to become a column to be fast, ask
whether the side that knows the answer should have written it down instead. That is the prior
question again, arriving in a different disguise, and at least one such column has since been
deleted in favour of the reading that already held the fact.

== Where it pinches

It would be dishonest to present this as enforced. Most of it is not.

What does hold, and holds well, is that a *new* relation cannot arrive without an owner and a
grain. `MetaDeclarationGateTest` compares every observed relation against the declarations, the
register and a frozen roster of relations nobody has got to yet, and that roster only shrinks. Two
columns of one row, both `NOT NULL`, so owner and grain cannot come apart. If you add a relation,
this is the gate you will meet.

What does not hold is most of the rest, and the gaps are worth knowing precisely rather than
discovering:

* *Nothing enforces the sweep.* Not one gate checks that a stored relation's rows are swept. One
gatherer's clear set is re-derived from its own source text and compared; the other lists are
unchecked.
* *The ownership gate binds on declared views only*, and within those, only where both ends are
declared. A relation filled by hand-written jOOQ is outside it entirely, because what such a
producer reads is in no stored definition for a parse to find.
* *Nothing checks that a declared grain is the right grain.* The gate compares the declared key
against the actual primary key, which is two authored strings agreeing with each other. A relation
whose key and whose declaration state the same wrong grain passes cleanly. Writing the reader's
query first is what exposes a wrong key, and it is worth doing for that reason.
* *A declared relation's comment is checked against its declaration*, not against its rows.
* Roughly half the schema stands on the undeclared roster, so a claim about "every relation" is
today a claim about the declared half.

The declaration itself is a gate and not a mechanism. Nothing that runs reads `meta_relation`;
`MetaDeclarationGateTest` is its only reader. That is still worth doing, because the gate is what
makes the default impossible to take, but it is not load-bearing at run time and should not be
argued for as though it were.

The discipline is a compass. The gates cover the entrance and very little of the interior.
