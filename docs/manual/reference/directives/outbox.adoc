= @outbox
:description: Write a transactional outbox message every time a mutation field succeeds, inside the transaction that made the change.
:!toc:

Tells graphitron to write a message to your transactional outbox every time a mutation field succeeds, inside the transaction that made the change, so the message exists if and only if the write committed. A *transactional outbox* is the pattern where a service records "this happened" in its own database, in the transaction that made it happen, and a separate relay (a poller, or change data capture such as Debezium) publishes it to a message broker afterwards.

A message is a business event: what happened, named by you (`FilmCreated`, `RentalReturned`), and a body you shape for the systems that consume it. It is not a record of which rows changed, and an event may mention any number of ids in its payload. Graphitron writes the event's type and its payload; your table or routine gives it an id and a time, and your relay decides where it goes.

The directive is repeatable: each `@outbox` on a field is one message, written once per successful call, in the order the directives appear. To publish something new, add another `@outbox` beside the ones you have; the published messages do not change, so their consumers are not affected. That includes a new version of an event: add `@outbox(event: "FilmCreated.v2", ...)` beside the old one, and remove the old one when its last consumer has moved.

== SDL signature

[source,graphql]
----
directive @outbox(event: String, argMapping: String) repeatable on FIELD_DEFINITION
----

== Parameters

[cols="1,1,1,3",options="header"]
|===
| Name | Type | Default | Description
| `event` | `String` | the field's coordinate (`Mutation.createFilm`) | The message's event type, the name your downstream consumers subscribe to. Name it when the event should outlive the field's name, since renaming a field without an `event` renames the event its consumers subscribe to. Two `@outbox` in the schema with the same event, given or defaulted, fail the build, so on one field at most one `@outbox` may leave `event` out.
| `argMapping` | `String` | (none) | Builds the message's flat JSON payload, `jsonKey: source`, comma-separated, the same form `@service` and `@routine` use. The same key twice in one `argMapping`, or a key that is also in the common payload, fails the build.
|===

== Where a value comes from

[cols="1,3",options="header"]
|===
| Source | Meaning
| `title`, `in.title` | A field argument, walking into nested input fields with dots, as in every `argMapping`. An input-object argument yields an object of the fields the client sent, and a list yields an array. A field the client left out is absent from the payload; a field set to `null` is `null`.
| `$result`, `$result.id` | The field's success outcome: what the write produced. For an `@mutation` field that is the written type's node id and its own column fields, read from the rows the write wrote. A path that would need another query (a `@reference`, a `@splitQuery` field, a `@service` child) is rejected at build. A list result yields an array. After a `DELETE` there are no rows left to read, so only the node id can be named. For a `@service` field it is the value the service returned: `$result` itself where that is a scalar, a member read through the fields your path names (`$result.holder.blurb.description`), or the node id of a record a member returns (`$result.film.id`). A path through a list, or ending on an object or a record, is rejected at build.
| `$session.userId` | One member of the session handle your `<sessionState>` mount returned, read on the write's own transaction. The handle must be configured, the member named exactly as in xref:../mojo-configuration.adoc#consuming-the-handle[`@service` and `@condition`], and its type must be one a JSON payload carries: text, a number, a boolean, a character, a UUID or a `java.time` value. A member that is not, an unknown or ambiguous one, and the whole handle `$session` are rejected at build. Only the owned acquisition mounts a handle, so a field that reads one fails on a caller-supplied `DSLContext` and rolls its write back.
| `$scope.coordinate`, `$scope.operationName`, `$scope.alias` | The field and its operation. `operationName` and `alias` are absent when there is none.
|===

Values appear in your API's own representation: an `ID` as your clients see it, an enum by its GraphQL name.

Keys are flat, one JSON key per entry. An object or an array in the payload comes from its source, not from the key.

== When

Right after the field's write succeeds and before its payload is resolved, as one more statement in the field's transaction. A field that failed writes no message: its transaction rolls back, and a failure an `@error` channel turned into a typed payload is a failure. If the emit fails, the field fails and rolls back, write included; the error is logged and redacted, and no `@error` channel can claim it, since an outbox fault is not business data.

A call that wrote no rows (an `UPDATE` that matched nothing, or one whose input sets no column) writes no message.

On a `@service` field the service runs inside the same transaction as its messages: graphitron opens it and hands the service a `DSLContext` on it. What the service writes through that `DSLContext`, nested transactions included, commits with the messages or rolls back with them. A write the service makes some other way, through a connection of its own or a call to another system, is outside the transaction, and no message can be made atomic with it.

== Constraints

* Valid on Mutation fields that write a table with `@mutation` (`INSERT`, `UPDATE` or `DELETE`), and on Mutation fields a `@service` answers; every other placement is a build error naming the field.
* On a `@service` field, the field's fetcher must be one graphitron generates from its model of the schema. A service taking a jOOQ record built from its input is not yet, and its `@outbox` is a build error naming why, until it is.
* Where the messages go is configured once, in the plugin's `<outbox>` block. A schema with an `@outbox` field and no `<outbox>` block fails the build, naming the field.

== What is yours, and what is the relay's

The outbox makes a message exist exactly when its write commits. What happens after that is the relay's and the consumers', and the mistakes outboxes are known for happen there:

* *Every message is delivered at least once.* A relay that crashes after publishing and before recording it publishes again. Consumers must drop a message they have seen, by its id, which is why the build requires the table's primary key.
* *Order holds per key, never globally.* Two fields committing at once can publish in either order. Where order matters, have the relay key messages by something in the payload (`filmId`), so one film's events stay in order on one partition.
* *The table is a conduit.* Rows a relay has published can be deleted or archived; how long they stay is your relay's setting, not graphitron's.
* *A payload is a contract.* Change it by adding a new `@outbox` beside the old one (see above), and put in it what a consumer needs, no more: the common payload goes on every message, so a secret or a personal detail there goes to everyone subscribed.
