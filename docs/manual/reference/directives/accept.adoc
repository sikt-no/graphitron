= @accept
:description: Mark a table-bound entity, so this subgraph grants access to its rows on another subgraph's voucher.
:!toc:

Marks a table-bound entity in a federated subgraph that owns the data another subgraph vouches for. Graphitron gives the type a *voucher* field, `_voucher: String`, which the router fills with the voucher it fetched from the issuing subgraph's xref:issue.adoc[`@issue`] type; Graphitron verifies it and reads the vouched row on the connection your connection source leases for a key carrying the voucher's *vouched-for values*, so your database's row-level security decides what the vouched-for values unlock. The voucher is not a column and is never selected.

The entity and every field below it are read on that connection. A field its SELECT reads, reference children nested in it included, is read in the entity's own statement; a field that runs a query of its own, a split query, a routine, a polymorphic field or a `@service`, runs on the connection key the entity row hands down, and so does everything below it. A type with a connection below it, at any depth, whether the connection is an `@asConnection` field, a field returning a connection type or a `@service` returning one, is refused for now with `VOUCHER_ACCEPT_NOT_GENERATED`, since a connection's count and facets do not yet read on the vouched connection. The same field reached from outside a vouched entity's subtree runs on the request's own connection.

== SDL signature

[source,graphql]
----
directive @accept(scope: String!, key: String, vouchesFor: String!) on OBJECT
----

[cols="1,1,3"]
|===
| Parameter | Type | Meaning

| `scope`
| `String!`
| What the voucher is for. Names the scope of the issuing subgraph's `@issue(scope:)`.

| `key`
| `String`
| The field set of the authored `@key` the voucher's lookup part decodes to, as `@key(fields:)` spells it. Leave it out when the type has exactly one authored resolvable key.

| `vouchesFor`
| `String!`
| The fields of this type the voucher's vouched-for values parse into, a field set as `@key(fields:)` spells one: whose rows are vouched for. Names the same fields as the issuing subgraph's `@issue(vouchesFor:)`. A vouched-for field may be `@inaccessible`, so the owner is not published to clients.
|===

== Canonical example

[source,graphql]
----
type VgsResultat @table(name: "vgs_resultat") @key(fields: "id")
    @accept(scope: "vgs-resultater", vouchesFor: "eierId") {
  id: ID!
  eierId: String! @inaccessible
  fag: String!
  karakter: Int!
}
----

The voucher's lookup part decodes to `id`, the type's one authored key, and its vouched-for values parse into `eierId`. Name and type both exactly as the issuing subgraph's absorbed fields.

== How a voucher is read

For each `_entities` representation carrying the voucher, before any type is resolved:

. The voucher is decoded and checked: its format, its signature over the token and the representation's `__typename` against your verification keys, its expiry (with 30 seconds of tolerance for clock skew), its scope, and that its sections name exactly this type's `vouchesFor` fields and the fields of the key it decodes to. A voucher longer than `VoucherCodec.MAX_TOKEN` characters (16384), or carrying a number whose text is longer than `VoucherCodec.MAX_NUMBER_TEXT`, is malformed before it is decoded, and no value in it is read until its signature verifies, so a forged token costs work in proportion to its bounded length. A representation that carries the voucher is always read through it, never past it by plain key fields.
. Each value is coerced to its field's column, as a plain representation's key values are; a value no column takes is a failed check, not a missing row.
. The vouched-for values become the parts of the generated `ConnectionKey`, one `Optional` per vouched-for field typed by its column (`key.eierId()` in the example), and the lookup values are read through the authored key's own SELECT on the connection your source leases for that key. Vouchers carrying the same value share one connection.

Your `ConnectionSource` reads the vouched-for values off the key and returns a connection whose session sets them where your policies read them; for the key whose parts are empty it returns the request's own connection. A build that accepts vouchers has no escape hatch: `Graphitron.newExecutionInput(dsl, ...)` is not generated, since a vouched connection can only come from the request's source.

The voucher is verified with the generated `VoucherKeys`, the last argument of every `Graphitron.runtime(...)` overload: `VoucherKeys.accepting(Map.of(keyId, publicKey))` holds the issuing subgraph's Ed25519 public keys by the key id each voucher carries, so a key is rotated by adding the new id beside the old one. xref:../../how-to/voucher-handover.adoc[How-to: Voucher handover] makes the keys, wires both subgraphs and writes the connection source and policies.

A voucher that fails any check rejects the request as a whole, before any connection is taken: `GraphQL.execute` throws the generated `VoucherRejectedException` in place of a result, its message naming the check that failed and nothing from the token. A request presenting vouchers for more than one vouched-for value is rejected the same way with `VouchedValueLimitExceededException`, an error naming the limit rather than a `null` that would read as a denial. Both are arms of the generated `RequestRejectedException`, which the facade's `Graphitron.requestRejection(thrown)` answers; see xref:../../../architecture/reference/runtime-extension-points.adoc#rejected-mount[A request rejection rejects the request]. A plain representation of the type's authored key resolves on the request's own connection, under the caller's own access: a voucher only ever adds access.

Every redemption and rejection is logged at `INFO` on the logger `no.sikt.graphitron.voucher.audit`, by vouch id, scope and outcome (redeemed, or rejected with the check that failed); never the token, its values or the connection key.

== What the subgraph publishes

* `@key(fields: "_voucher")` on the accepting type, resolvable, after every key you wrote, so a router hands this subgraph the voucher it fetched from the issuing one. Your own keys are untouched, so the type still resolves by them under the caller's own access.
* The voucher field, `_voucher: String`, marked `@inaccessible` so clients never see it. You do not write it; its name is the same in every subgraph, so the issuing and accepting sides cannot disagree on it. It is nullable here, where the issuing side's is not: this subgraph receives a voucher in a representation but never computes one, so a row it reads by any other route has none to give. Federation lets a shared field differ in nullability, and the supergraph takes the nullable one. The link imports `@inaccessible` for you.

== Constraints

Each refusal below is reported at the `@accept`.

[cols="1,3"]
|===
| Code | Rule

| `VOUCHER_WITHOUT_FEDERATION_LINK`
| The schema has a federation `@link`: a voucher only makes sense where a router plans across subgraphs, and the key it is reached by needs the link.

| `VOUCHER_FIELD_NAME_TAKEN`
| The type declares no field named `_voucher`, the name Graphitron mints the voucher field under. Such a field is refused, not taken for the voucher, and no voucher field is minted beside it.

| `VOUCHER_MARKERS_BOTH`
| The type is not also marked `@issue`: a type issues or accepts one voucher. Refused at each marker.

| `VOUCHER_ACCEPT_WITH_TENANT_COLUMN`
| The build configures no `<tenantColumn>`. A vouched connection is keyed by the vouched-for values alone, and a voucher is not yet paired with the tenant of the key it decodes to.

| `VOUCHER_VOUCHES_FOR_EMPTY`
| `vouchesFor` selects at least one field.

| `VOUCHER_VOUCHED_FOR_NOT_A_FIELD`
| Each vouched-for field names a field of the type: not a name the type does not declare, not `_voucher`, not a nested selection.

| `VOUCHER_VOUCHED_FOR_REPEATED`
| No vouched-for field is named twice.

| `VOUCHER_VOUCHED_FOR_NOT_A_COLUMN`
| Each vouched-for field reads one column of the type's own table, as a key field does: not a list, not a field read some other way.

| `VOUCHER_VOUCHED_FOR_IN_KEY`
| No vouched-for field is a field of the key the voucher decodes to: the vouched-for fields and the lookup part never share a value.

| `VOUCHER_ACCEPT_WITHOUT_KEY`
| The type has an authored `@key` this subgraph resolves it by, which the voucher's lookup part decodes to.

| `VOUCHER_ACCEPT_KEY_AMBIGUOUS`
| `key` is given when the type has more than one authored resolvable key.

| `VOUCHER_ACCEPT_KEY_NESTED`
| `key` has no nested selection: the lookup part carries top-level scalar fields.

| `VOUCHER_ACCEPT_KEY_UNKNOWN`
| `key` names the fields of an authored resolvable key of the type, in any order.

| `VOUCHER_ACCEPT_VOUCHED_FOR_DIFFERS`
| Every `@accept` in the graph vouches for values of one shape, the same vouched-for field names each reading a column of the same Java type, since the graph's vouched connections are keyed by one generated `ConnectionKey`. Refused at each `@accept` whose shape differs from the first accepting type's by name.

| `VOUCHER_ACCEPT_NOT_GENERATED`
| No connection below the type, at any depth through the types its subtree reads: a connection does not yet read on the vouched connection. Read those rows as a list instead, in the entity's SELECT, a split query or a `@service`.
|===
