= @defaultOrder
:description: Set the fallback sort order for a field when no @orderBy argument is provided.
:!toc:

Specifies a static `ORDER BY` for a field. When the field also carries an xref:orderBy.adoc[`@orderBy`] argument and the client supplies a value, the dynamic order wins; otherwise `@defaultOrder` applies. Without an explicit `@defaultOrder`, paginated fields default to ascending primary-key order.

== SDL signature

[source,graphql]
----
directive @defaultOrder(
    index: String,
    fields: [FieldSort!],
    primaryKey: Boolean = false,
    direction: SortDirection = ASC
) on FIELD_DEFINITION

input FieldSort {
    name:      String
    path:      [ReferenceElement!]
    method:    ExternalCodeReference
    collate:   String
    direction: SortDirection
}

enum SortDirection { ASC, DESC }
----

== Parameters

[cols="1,1,1,3",options="header"]
|===
| Name | Type | Default | Description
| `index` | `String` | none | Name of a database index. The generator emits the index's column list as the sort specification. Requires `<includeIndexes>true</includeIndexes>` in the jOOQ generator.
| `fields` | `[FieldSort!]` | none | Explicit sort list. Each `FieldSort` sets exactly one of `name` (a column on the field's return-type table) and `method` (a static method returning the sort key), with an optional `collate` (database-specific collation) and `direction`. Beside `name`, an optional `path` resolves the column on a to-one related table instead; see xref:order.adoc#sorting-by-a-related-value[`@order`: Sorting by a related value].
| `primaryKey` | `Boolean` | `false` | When `true`, sorts by the parent table's primary key columns in declaration order. Common choice for stable keyset pagination.
| `direction` | `SortDirection` | `ASC` | Sort direction applied to every column in the spec. `ASC` or `DESC`.
|===

Exactly one of `index`, `fields`, or `primaryKey` must be set.

[#plural-routine-write]
== On a plural mutation backed by a routine

A mutation field taking a list argument and returning a list answers one item per element of that argument, in the order of the input. A field of that shape behind a `@routine` that returns a table reads the routine's result, and the rows of a table have no order of their own. On such a field, `@defaultOrder` states the order the routine's result keeps: `fields:` names columns of the routine's result, not of the table the field's type is bound to, and each `name` resolves against those columns.

[source,graphql]
----
type Mutation {
    rentFilmsInOrder(inventoryIds: [Int!]!, customerId: Int!): [Rental!]!
        @routine(
            name: "rent_films_in_order"
            argMapping: "pInventoryIds: inventoryIds, pCustomerId: customerId"
        )
        @reference(path: [{table: "rental"}])
        @defaultOrder(fields: [{name: "input_index"}])
}
----

Here `rent_films_in_order` returns `TABLE(rental_id INTEGER, input_index INTEGER)`, `input_index` being each rental's place in `inventoryIds`. The written rows are read back from `rental` in the order of `input_index`, so the answer follows the input. Which column keeps the input's order is the routine's to say; the column of the bound table, such as `rental_id`, cannot say which element a row answers.

Only arguments that are lists count toward the shape, so scalar arguments beside the list, `customerId` here, leave it a plural mutation.

* Only `fields:` applies. A routine's result has no primary key and no index, so `primaryKey: true` fails the build with `ORDER_PRIMARY_KEY_MISSING` and `index:` with `ELEMENT_UNRESOLVED`.
* A `name` that is not a column of the routine's result fails the build with `COLUMN_UNRESOLVED`, naming it.
* A `fields` element with a `method:` or a `path:` names no column of the routine's result and fails the build with `ROUTINE_WRITE_PLURAL_ORDER_NOT_A_COLUMN`.
* A field of this shape with no `@defaultOrder` fails the build with `ROUTINE_WRITE_PLURAL_UNORDERED`, naming the list argument.
* An xref:orderBy.adoc[`@orderBy`] argument is not accepted on a `@routine` mutation field (`READ_SURFACE_ON_WRITE`): a client-chosen order would break the order the schema states.

[#constraints]
== Constraints

* Exactly one of `index`, `fields`, or `primaryKey` must be set. Multiple or none fails the build.
* `fields` names at least one field. An empty list, `fields: []`, names nothing to sort by and fails the build at the application (`ORDER_FIELDS_EMPTY`), wherever the field is read; so does an `@order` value written the same way.
* `primaryKey: true` needs the target table to have one. Over a table with no primary key it fails the build, naming the table and listing the columns available, so the `fields:` spelling is one edit away. A table-valued function's result is the standing case: it declares no key, so a routine-backed field orders by naming the function's own result columns (see xref:routine.adoc[`@routine`]).
* Applies to fields only. Apply it to the connection-bearing field, not the synthesised `Connection` / `Edge` types.
* When combined with xref:orderBy.adoc[`@orderBy`] on the same field, the client's argument value (when present) takes precedence; `@defaultOrder` is the fallback.
* `direction` is global across the spec. Per-column direction requires xref:orderBy.adoc[`@orderBy`] (the enum input carries its own `SortDirection`).
* `index` requires jOOQ index generation. `fields[].name` resolves against the field's return-type table, not the parent, or against the table its `path` lands on.
* A `path` follows to-one hops only and carries no `condition:`; a `method` takes the field's table and returns a `Field<X>`. Neither counts toward a connection's row identity, and neither is available on a multi-table interface or union or over a table-valued function result. See xref:../../how-to/sort-results.adoc#sort-by-a-related-value[How-to: Sort by a value on another table].
* On a root field returning a list or connection of a multi-table interface or union, the columns resolve against each participant's own table, and every participant has to carry them at the same SQL type and bound Java type, position by position (`ORDER_POSITIONS_DISAGREE`). A child field, or a single-valued root field, over such a type rejects the directive. See xref:../../how-to/sort-results.adoc#sort-across-polymorphism[How-to: Sort across polymorphism].
* Stable keyset pagination depends on the order identifying a row. On a connection, graphitron appends the table's primary key to a field-based or index-based order that does not already contain a key, in the direction of the last listed column; see xref:../../how-to/sort-results.adoc#stable-cursors-and-tie-breakers[Stable cursors and tie-breakers].
* A list or connection over a table with no primary key, or over a table-valued function's result, has nothing to fall back to, so it needs `@defaultOrder` or an xref:orderBy.adoc[`@orderBy`] argument; one with neither fails the build (`LIST_ORDER_UNDETERMINED`) rather than return rows in whatever order the database hands them back, whether it is read inside its parent's query, by a query of its own at the root or split from its parent, or over several types' tables. A lookup answers in its keys' order and a `@service` in the order it hands back, so neither is refused. The other refusals above are `ORDER_SURFACES`, `ORDER_FIELDS_EMPTY`, `ORDER_PRIMARY_KEY_MISSING`, `ELEMENT_UNRESOLVED` for an index the table does not have, `COLUMN_UNRESOLVED` for a column it does not have, and `ORDER_FIELD_SHAPE`, and an `@orderBy` on a list read inside its parent's query is deferred (`ORDER_CHOICE_ON_INLINE_LIST`); see xref:../defects.adoc#graphitron-defects[the defects reference].
* A column that admits `NULL` sorts its `NULL` rows last whatever the `direction:`, on lists and connections alike; see xref:../../how-to/sort-results.adoc#where-null-sorts[Where `NULL` sorts].
