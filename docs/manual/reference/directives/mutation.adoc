= @mutation
:description: Flip a mutation resolver into INSERT, UPDATE, DELETE, or UPSERT; the write target is named by the field's return type or @mutation(table:).
:!toc:

Marks a mutation field as fully generated and picks the SQL shape (`INSERT`, `UPDATE`, `DELETE`, `UPSERT`). The write runs inside a transaction graphitron opens, with a primary-key-only `RETURNING`; a `@table`-typed response is then read back by a follow-up SELECT keyed on those primary keys, so the response selection set never widens the write statement itself. On the owned-connection path that transaction is the field's own and covers the read-back too: the write, the follow-up SELECT and the payload's nested reads commit or roll back together (xref:../../../architecture/reference/runtime-extension-points.adoc#owned-path-transactions[Transactions on the owned-connection path]). The delegated alternative carries no boundary of its own on the escape-hatch path: see xref:service.adoc#transaction-demarcation[`@service`].

Every `INSERT`, `UPDATE` and `UPSERT` checks the strings it writes against their columns' declared lengths before the statement runs, and rejects an over-long value without writing anything; see xref:../../how-to/error-channel.adoc#column-length-check[the column-length check].

== SDL signature

[source,graphql]
----
directive @mutation(typeName: MutationType!, multiRow: Boolean = false, table: String,
                    missingAsDeleted: Boolean = false) on FIELD_DEFINITION

enum MutationType { UPDATE, DELETE, INSERT, UPSERT }
----

== Parameters

[cols="1,1,1,3",options="header"]
|===
| Name | Type | Default | Description
| `typeName` | `MutationType!` | (required) | The SQL shape to emit. `INSERT` writes a row; `UPDATE` modifies the row identified by the input's primary-key-or-unique-key coverage; `DELETE` removes the row(s) identified the same way; `UPSERT` emits `INSERT … ON CONFLICT … DO UPDATE`.
| `multiRow` | `Boolean` | `false` | On `DELETE`, opts into a broadcast delete when the input covers no primary key or unique key (the filter may match more than one row). Rejected on `INSERT` (no `WHERE` clause), `UPDATE` (no broadcast shape; cover a key), and `UPSERT`.
| `table` | `String` | (none) | Names the SQL table to write to, on the consuming field. It gives a write that carries no table on its return side a field-relative write target: a bare `ID` / `Boolean` / count return names no table, so `@mutation(table: "film")` names it directly (the field-level analogue of xref:service.adoc[`@service(argMapping:)`]). A `DELETE` always names its table this way; on `INSERT` and `UPDATE` it is the fallback for a return that names no table, and a field whose return *does* name the table (a `@table` return, or a payload's `@table`-element data field) needs no `table:`. Wired for `DELETE`, `INSERT`, and `UPDATE`; supplying it on `UPSERT` is rejected.
| `missingAsDeleted` | `Boolean` | `false` | On a payload-returning `DELETE`, an input key that matches no row counts as already deleted: the call deletes the rows that exist, commits, and the payload echoes every input key, in input order. Requires the input to identify rows by exactly the primary key. Rejected on `INSERT`, `UPDATE`, `UPSERT`, and on a `DELETE` that returns `ID` or `[ID!]` directly. See <<when-a-key-matches-no-row>>.
|===

== Input shape

A `@mutation` field takes exactly one input argument. Its fields bind to columns of the write target's table (`@field(name:)`, or the SDL name by default). The input type carries no table directive of its own (`@table` on an input is a xref:table.adoc[deprecated location] and is ignored): for `INSERT` and `UPDATE` the write target is derived from the field's return (see <<_naming_the_insert_and_update_write_target>>), and for `DELETE` it is named on the field with `@mutation(table:)` (see <<_naming_the_delete_write_target>>).

An input field may also be a nested input object: a grouping shape whose own fields map onto columns of the *same* table. The grouping carries no DML semantics; the leaves flatten onto the outer write target as if declared at the top level, and absent-vs-null is honored independently at every nesting layer (an absent or `null` group skips its whole subtree; a present group descends per leaf). The tutorial's xref:../../tutorial/05-mutations.adoc#grouping-fields-with-nested-input-types[Grouping fields with nested input types] walks a worked example. A nested input introducing a *second* DML target is a separate compound-mutation shape and is not admitted here.

== Canonical example

The tutorial's film mutations cover the two most common shapes. Neither input carries a directive; the write target is derived from the `Film` return type (`Film` carries `@table(name: "film")`):

[source,graphql]
----
input FilmCreateInput {
    title:      String! @field(name: "title")
    languageId: Int!    @field(name: "language_id")
}

input FilmUpdateInput {
    filmId: Int!    @field(name: "film_id")
    title:  String! @field(name: "title")
}

type Mutation {
    createFilm(in: FilmCreateInput!): Film @mutation(typeName: INSERT)
    updateFilm(in: FilmUpdateInput!): Film @mutation(typeName: UPDATE)
}
----

The `INSERT` shape produces a two-step exchange. The write commits inside a transaction with a primary-key-only `RETURNING`:

[source,sql]
----
INSERT INTO film (title, language_id)
     VALUES (?, ?)
  RETURNING film.film_id
----

and the response selection set is then read back by a follow-up SELECT keyed on the returned primary key:

[source,sql]
----
SELECT film.film_id AS "filmId", film.title AS "title"
  FROM film
 WHERE film.film_id = ?
----

The follow-up SELECT narrows to the response selection set: a mutation that asks for `{ filmId title }` retrieves only those columns. On the escape-hatch path the write has already committed when the read-back runs, so an error during the response SELECT surfaces as a field error and cannot undo the write. On the owned-connection path the read-back runs inside the field's transaction, so such an error fails the field and rolls the write back.

For a bulk mutation (list input, `[Film!]!` return), the follow-up SELECT joins a `VALUES (idx, pk)` table over the returned keys and orders by `idx`. The payload list contains one entry per written row, in the order the rows were written, mirroring xref:lookupKey.adoc[`@lookupKey`]'s ordering contract ("returns a list of results in the same order").

`UPDATE` identifies the target row by which input columns cover a primary key or unique key of the write-target table (inferred from the jOOQ catalog, no directive needed): the matched key's columns become the `WHERE` clause and the remaining input fields populate the `SET` clause. `UPSERT` adds `ON CONFLICT` keyed on the matched key's columns.

Most input fields fall wholly on one side of that boundary, but a xref:nodeId.adoc[`@nodeId`] reference to another table need not: it expands into the foreign key's child columns on the write target, and those can include columns the matched key also covers. Such a field partitions *per column* rather than being rejected. Its out-of-key columns become `SET` writes; its in-key columns are the row's identity, so they contribute to the `WHERE` clause where no other field supplies them, and are otherwise only checked. Where both the reference and another field decode a value for the same column, the two are compared before any DML runs and a mismatch fails the call with an error naming both input fields, writing nothing. The foreign key forces them equal for well-formed input, so this only catches a caller who sent a reference belonging to a different row.

A reference in that shape may be nullable (`ID`). Its in-key half is row identity and is therefore never written, so an explicit `null` clears only its out-of-key half: those columns are written `NULL`, and the in-key columns stay as the rest of the input pins them. A half-null foreign key imposes no referential obligation under PostgreSQL's default `MATCH SIMPLE`, so a cleared reference is an absent one rather than a dangling one. A cleared reference supplies no value, so it takes no part in the comparison above. The build rejects the nullable spelling in one shape only: when the reference is the sole supplier of one of the matched key's columns, since an omitted or cleared value would leave nothing to find the row by. Give that column another contributor, or spell the reference `ID!`.

A field carrying the row's *own* columns is still rejected when it straddles part of the matched key, because writing only some of a row's key columns would move the row rather than update it. The exception is a node id whose key columns are the whole matched key plus more, for example a type declared `@node(keyColumns: ["inventory_id", "store_id"])` over a table whose primary key is `inventory_id`. Such an id identifies the row by the matched key alone: its other columns are neither filtered on nor written. Another field may write them; a `storeId: Int @field(name: "store_id")` beside the id moves the item to another store, and the payload's ids encode the new value. An id minted before that change still updates the row.

`DELETE` identifies rows the same way (primary-key-or-unique-key coverage), but has no `SET` clause: *every* admitted input column is a `WHERE` filter, and the deleted row's primary key is returned through `RETURNING`. Extra input columns beyond the matched key add further `AND`ed predicates (they narrow the match, they don't move to a `SET` side). A node id whose key columns are the whole matched key plus more is the exception: it filters on the matched key only, so an id whose extra columns have since changed still deletes its row. When the input covers no primary key or unique key, the DELETE is rejected at build time so a non-unique filter cannot silently broadcast; set `multiRow: true` on the `@mutation` directive to opt into a deliberate broadcast (non-key) delete that may remove more than one row.

[[_naming_the_insert_and_update_write_target]]
== Naming the INSERT and UPDATE write target

An `INSERT` or `UPDATE` usually names its write target on the *return* side: the written row's type is the natural return. Graphitron derives the write target by this precedence:

. **The return's own `@table` (preferred).** A direct `@table` return (`createFilm(...): Film`, `Film` carrying `@table`), or a carrier payload whose single data field is a `@table`-element (`createFilms(...): FilmsPayload`, `FilmsPayload { films: [Film!] }`). The input's fields resolve against the return's table.
. **`@mutation(table:)` on the field.** For the encoded-`ID` / scalar-return field whose return names no table (`createFilm(in: FilmInput!): ID @mutation(typeName: INSERT, table: "film")`).

Where the return names the table, a `@mutation(table:)` also present must name the *same* table (the `RETURNING` projection reads from the write target, so a disagreement cannot emit a coherent statement); a mismatch is rejected at build time. A field that names its table by neither rung is rejected, with the message leading with the preferred return-derived fix.

[source,graphql]
----
input FilmInput {              # no directive: the write target is derived from the return
    title: String! @field(name: "title")
}
type FilmsPayload { films: [Film!] }   # Film is @table(name: "film")

type Mutation {
    createFilms(in: [FilmInput!]!): FilmsPayload @mutation(typeName: INSERT)
}
----

[[_naming_the_delete_write_target]]
== Naming the DELETE write target

`DELETE` cannot use the return-derived rung: it commonly returns a bare `ID` (the encoded primary key of the deleted row), a `Boolean`, or a delete count, and it can never return the deleted row's `@table` type, because the row is gone after the statement runs. So a `DELETE` names its write target on the consuming field with `@mutation(table:)`:

[source,graphql]
----
input FilmDeleteInput {
    filmId: Int! @field(name: "film_id")
}

type Mutation {
    deleteFilm(in: FilmDeleteInput!): ID @mutation(typeName: DELETE, table: "film")
}
----

The input type carries no directive; its fields resolve against the table named on the field. A `DELETE` that does not name its table with `@mutation(table:)` is rejected at build time, with the message steering you to the argument. (An input type still carrying a legacy `@table` builds with a warning; the directive is ignored, so it does not name the table either. See the xref:table.adoc[deprecated location].)

== Payload-returning DELETE

`@mutation(typeName: DELETE)` supports two payload-carrier shapes. Both echo information about the rows the DML actually removed; neither projects non-primary-key columns from the deleted rows (the row is gone before the response can read it).

=== Echoing the deleted primary key (recommended)

The simplest payload returns the encoded NodeId of each deleted row:

[source,graphql]
----
type SlettRegelverksamlingPayload {
    deletedIds: [ID!]   # implicit @nodeId; encoder resolves against the write-target table's @node
}

extend type Mutation {
    slettRegelverksamling(input: [RegelverksamlingDeleteInput!]!): SlettRegelverksamlingPayload
      @mutation(typeName: DELETE)
}
----

The carrier field's element type must be `ID` (single DELETE) or `[ID!]` (bulk DELETE). The list wrapper must be list-of-non-null; `[ID]` (list-of-nullable) is rejected, because every element of a successful DELETE response is the encoded PK of an actually-deleted row, the slot cannot be null. The encoder is recognised implicitly when the mutation's write-target table backs a `@node` type. If the write-target table is not `@node`-backed, the carrier is rejected with the same diagnostic as the bare-`ID` DELETE path; register the table's SDL type as `@node` first. To pin the encoder explicitly (recommended when grep-ability matters), attach `@nodeId(typeName: "...")` to the carrier field; the directive's encoder must resolve to the same table as the mutation's write target. An `@nodeId` whose encoder resolves to a different table is rejected: you would be returning IDs of a different entity than the one the DML acted on.

The response contains exactly the IDs of rows the DML actually removed, unless the field sets `missingAsDeleted: true`. When the node type's key columns go beyond the primary key, the extra columns are read back from the deleted row, so each id encodes the row as it was stored rather than as the input id described it.

=== Projecting the deleted row's primary key onto an SDL type

The carrier may also return the `@table`-backed SDL type, but only when every non-nullable field on the type resolves to a primary-key column:

[source,graphql]
----
type Regelverksamling @table(name: "regelverksamling") @node {
    id: ID!                              # PK; admits
    navn: String                         # non-PK, nullable; admits, runtime returns null
    beskrivelse: String!                 # non-PK, non-nullable; REJECTS the carrier
}
----

The classifier inspects every field on the element type and rejects the carrier if any non-nullable field maps to a non-PK column. Nullable non-PK fields admit and always resolve to `null` at runtime; this is by design — after a DELETE there is no row left to read those columns from. If your SDL type carries non-nullable non-PK fields, prefer the `[ID!]` shape above, or define a dedicated `DeletedRegelverksamling` SDL type whose non-nullable fields are PK-only.

`@service`-resolved fields are not admitted on the element type, nullable or not. The service would receive a PK-only row at runtime and any non-PK source parameter would silently produce `null`. Use the `[ID!]` shape and resolve service-backed data on the deleted entity through a sibling lookup if needed. FK-traversing reference fields (`@reference` paths to a joined target table) are also rejected on DELETE carriers, since the join cannot run after the row is gone.

=== Single vs bulk

Both shapes work with single and bulk DELETE; cardinality follows the carrier field's wrapper (`ID`/`Foo` for single, `[ID!]`/`[Foo!]` for bulk).

[#when-a-key-matches-no-row]
=== When a key matches no row

By default a bulk `DELETE` whose input names a key that matches no row fails the whole call: nothing is deleted, and the field reports an error (a typed one if a handler in the payload's errors field matches, otherwise a redacted one). A single-row `DELETE` renders the payload `null`.

Set `missingAsDeleted: true` to treat such a key as already deleted. The rows that exist are deleted, the call commits, and the payload's id field holds every input key in input order, whether or not its row existed. A retried batch, or two clients deleting the same row, then succeed, and the response does not tell the caller which rows existed.

[source,graphql]
----
deleteFilmsIdCarrier(in: [FilmDeleteInput!]!): DeletedFilmsIdPayload
    @mutation(typeName: DELETE, table: "film", missingAsDeleted: true)
----

The input must identify rows by exactly the table's primary key, directly or through a node id. A unique key is not enough, because the response echoes the primary key and only the input can supply it for a row that is not there; an extra filter column is refused, because a key whose row survives the filter would be echoed as deleted. A node id whose key columns go beyond the primary key qualifies; a key that matches no row is echoed as the id the client sent. If the payload's ids need such columns and the input supplies only the primary key, the build fails, because there is nothing to encode a missing row's id from. Key the input by the node id instead.

=== What you can't return

* Arbitrary non-PK columns of the deleted row. The row is gone; `RETURNING` is narrowed to primary-key columns, plus the node key's other columns where the payload's ids encode them. If you need the full pre-delete state, snapshot it in your application code before issuing the mutation.
* A bare class-backed payload type. Use a NodeId echo or a `@table` projection.

[#payload-with-an-errors-field]
== Payload with an errors field

A payload may declare an errors-shaped field beside its data field, a list of xref:error.adoc[`@error`] types; the xref:../../how-to/error-channel.adoc[errors-channel how-to] covers the types themselves. When the write raises an exception one of the handlers matches, the transaction rolls back and the field renders `{ films: null, errors: [<typed error>] }` with no field error. On success the data field carries the written rows and `errors` is `null`.

[source,graphql]
----
type FilmsPayload {
    films: [Film]
    errors: [FilmWriteError]
}
----

Two rules follow from that:

* On the error path a nullable data field renders `null`. A non-null list data field renders `[]`, since nothing was written; declare `[Film!]!` when your clients should never see `null` there. Every other data field must be nullable: `Film!` beside an errors field is rejected at build time, because there is no empty value to give it and a `null` would let null propagation erase the errors list. A connection (`@asConnection`) counts as a single value here, not a list.
* A single-row write whose key matches no row renders the whole payload `null`, the same as on a payload without an errors field, unless the field sets `missingAsDeleted: true`.

Give one `@error` type in the errors field `{handler: VALIDATION}` and the column-length check's errors become entries in the errors list rather than top-level errors; see xref:../../how-to/error-channel.adoc#column-length-check[the column-length check]. Without that member a payload with an errors field skips the check.

The same rules hold in a database-per-tenant build: the payload's fields read the tenant the write ran on, and the errors travel with the payload.

[#update-key-matches-no-row]
== When an UPDATE key matches no row

A list-input `UPDATE` that returns a payload fails the whole call when any input row's key matches no row: nothing is written, and the field reports an error, a typed one if a handler in the payload's errors field matches, otherwise a redacted one. Graphitron runs every row before failing, so the error counts all of them. The exception is `<outputPackage>.schema.ZeroRowsMatchedException`, generated into your output package; it is an `IllegalStateException` whose message contains "matched zero rows", and it tells you which rows missed:

[source,java]
----
@Override
public String unmatchedMessage(Throwable thrown, String reference, DataFetchingEnvironment env) {
    if (thrown instanceof ZeroRowsMatchedException miss) {
        return miss.missCount() + " of " + miss.rowCount()
            + " rows in this write were not found, or are not writable for you.";
    }
    return FetcherErrorResponse.super.unmatchedMessage(thrown, reference, env);
}
----

`missedRowIndices()` gives the zero-based input positions, and `fieldCoordinate()` the field, as `Mutation.updateFilms`. A key that matches no row may be a row the caller is not allowed to see, so decide how much of this to show. A list-input `UPDATE` that returns the `@table` type or ids directly does not fail on a missed key: it returns the rows it wrote.

== Constraints

* `INSERT` and `UPDATE` derive their write target from the return (a `@table` return, or a payload's `@table`-element data field), falling back to `@mutation(table:)` for an encoded-`ID` / scalar return (see <<_naming_the_insert_and_update_write_target>>). `DELETE` names its write target with `@mutation(table: "…")` on the field (it cannot derive the table from its return type, since the row is gone after the statement). A field with no write-target source is rejected at build time, with the message naming the applicable fix. `@table` on the input type is a xref:table.adoc[deprecated location], ignored rather than consulted, so it is never a write-target source.
* `UPDATE` and `DELETE` require the input columns to cover a primary key or unique key of the write-target table (inferred from the catalog, no directive needed); otherwise the build fails so a non-unique filter cannot silently broadcast. `DELETE` can opt out with `multiRow: true` for a deliberate broadcast; `UPDATE` has no broadcast shape (cover a key). `@lookupKey` on a mutation input field is no longer supported (it identified rows in the pre-catalog model); remove it.
* `UPDATE` requires at least one input field outside the matched key (otherwise the `SET` clause is empty). `DELETE` has no such requirement — a key-only DELETE is the canonical single-row delete. `UPSERT` is exempt on the SET side: an upsert with no SET-clause fields is `INSERT … ON CONFLICT DO NOTHING`, which is a legitimate shape.
+
The `UPDATE` rule is about the input _type_. A _request_ may still leave every one of those fields out, or send a nested group as absent or `null`: the row is then an empty patch. Graphitron issues no `UPDATE` for it, reads the row back by its key, and returns it in the payload in the row's position, as it would an updated row; other rows in the same list input update normally. An empty patch on a key that matches no row behaves like any `UPDATE` on that key: a single-row mutation resolves `null`, and a list input with a payload raises the same "matched zero rows" error its error handlers already see (see <<update-key-matches-no-row>>).
* `@mutation` and xref:service.adoc[`@service`] are mutually exclusive on the same field. Pick one: `@mutation` for fully-generated DB operations, `@service` for handing the operation to custom Java.
* Optional input fields participate in the operation only when the client provides them. Absent optional fields are omitted from the `SET` clause (`UPDATE`/`UPSERT`) and from the column list of a single-row `INSERT` and of a bulk `INSERT` whose rows supply the same fields, so the database applies each column's default without being asked by name. A bulk `INSERT` is one statement with one column list: when its rows differ, the list covers every field some row supplies, and a row that leaves one of those out writes `DEFAULT` for it. A bulk `INSERT` of several rows that supply no field at all names every column with `DEFAULT`, since an empty column list would insert a single row. An `INSERT` that supplies no field at all renders `default values`, which jOOQ emulates with a `DEFAULT` per column on a database that lacks that clause, Oracle among them. Oracle rejects an explicit `DEFAULT` against a view (ORA-32575), so on an Oracle view these three shapes fail at the database: a bulk `INSERT` whose rows differ, one whose rows supply no field, and an `INSERT` with no field at all.
