= How-to: Map types to tables
:description: Bind GraphQL types and fields to jOOQ tables and columns, with enum-value mapping (text-column and jOOQ-enum), input-field binding, and the case-sensitivity rules.
:!toc:

xref:../reference/directives/table.adoc[`@table`] anchors a GraphQL type to a database table; xref:../reference/directives/field.adoc[`@field`] points a slot at a specific column or string. Together they carry every type-to-storage mapping in the rewrite. This recipe walks through the four directive sites of `@field` (object field, argument, input field, enum value), shows the two enum-mapping shapes (text-column and jOOQ-enum), and covers the case-sensitivity and re-binding rules that catch teams new to the directive pair.

== When to spell `@table` and when to omit it

xref:../reference/directives/table.adoc[`@table`] without `name:` looks up the jOOQ table by the GraphQL type name, case-insensitively. So `type Customer` resolves to the `customer` table without configuration. Spell `name:` explicitly when:

* The GraphQL type name and the SQL identifier diverge (renamed type, namespace prefix, plural/singular mismatch). Example: `type Person @table(name: "customer")` keeps the schema-side rename intact while binding to the existing table.
* The SQL identifier carries casing or punctuation the GraphQL type can't replicate (uppercase, underscores, or quoted identifiers in the jOOQ catalog).
* Two GraphQL types bind to the same table (e.g. `Customer` and `CustomerSummary`); both need explicit `@table(name: "customer")` because one is going to lose the case-insensitive default.

The `name:` value must match the jOOQ-generated identifier exactly (typically uppercase for PostgreSQL when jOOQ's default casing is in effect). The build fails with an unclassified-type error if the catalog has no matching `Table` class.

== Tables in non-default schemas

When the consumer's jOOQ codegen straddles two or more SQL schemas (`public`, `archive`, an external integration namespace), `@table(name:)` accepts a qualified `"schema.table"` form to scope the lookup. Unqualified names still work in the common case where the table name is unique across every schema in the catalog:

[source,graphql]
----
type Widget @table(name: "widget") {                       # unique across schemas
    id: ID! @field(name: "WIDGET_ID")
}

type ArchivedEvent @table(name: "archive.event") {         # qualified
    id: ID! @field(name: "EVENT_ID")
}

type CurrentEvent @table(name: "public.event") {           # qualified
    id: ID! @field(name: "EVENT_ID")
}
----

When the bare table name appears in two or more schemas, an *unqualified* lookup fails the build with `@table(name: 'event') is ambiguous: defined in schemas [archive, public]; qualify as 'archive.event', 'public.event'` (the catalog returns empty rather than picking whichever schema iterated first; the rejection names the colliding schemas and the qualified forms inline). The fix is to pick the right schema and qualify; the message tells you both options. Single-schema consumers see no change; only collision sites are forced to qualify, so adding a non-default schema to a previously single-schema project only forces edits where a name actually collides.

A genuinely missing name (the value isn't in any schema) takes a different path: the standard `table 'X' could not be resolved in the jOOQ catalog` rejection with a Levenshtein-ranked candidate hint pointing at near matches. The two messages distinguish "this column was renamed" from "this column lives somewhere; pick which one".

The same syntax applies on interfaces; `@table(name: "schema.table")` is valid wherever bare `@table(name:)` is. Schema and table halves of the qualified value are both case-insensitive (consistent with the unqualified form). The qualified form also works in `@mutation(table:)` on a mutation field.

== Field-to-column with `@field`

The most common shape: bind every scalar to its column.

[source,graphql]
----
type Customer @table(name: "customer") {
    customerId: Int!     @field(name: "CUSTOMER_ID")
    firstName:  String!  @field(name: "FIRST_NAME")
    lastName:   String!  @field(name: "LAST_NAME")
    email:      String   @field(name: "EMAIL")
}
----

The selection set drives projection: a query asking for `firstName lastName` produces `SELECT customer.first_name AS "firstName", customer.last_name AS "lastName"`, not `SELECT *`. Adding columns to the type only widens the projection when clients ask for them.

Four practical rules:

* *Names match case-insensitively.* When GraphQL `firstName` and column `FIRST_NAME` already match (lowercased and underscore-normalised), the directive is technically redundant. The example schema applies it explicitly anyway because mismatches creep in over time and explicit binding keeps the drift detectable in code review.
* *Mismatch fails the build.* `@field(name: "FIRST_NAMEZ")` (typo) fails resolution against the catalog, with a candidate hint pointing at `FIRST_NAME`.
* *Nested `@table` re-binds.* A nested type with its own `@table` re-anchors column lookup; an xref:../reference/directives/reference.adoc[`@reference`]-annotated field hops into the joined table for the duration of that field's subquery. Inside `Customer`, `address: Address @reference(...)` resolves `Address`'s columns against the `address` table, not `customer`.
* *Don't use `@field` on relations.* `@field` is for column-bound slots only. Relations (`address: Address`, `films: [Film!]!`) use xref:../reference/directives/reference.adoc[`@reference`] or auto-discovered FK paths instead.

== Argument-to-column: avoid silent column collisions

When a `Query` field exposes a filter argument whose name doesn't match the column, `@field` pins the binding:

[source,graphql]
----
type Query {
    customers(active: Boolean @field(name: "ACTIVEBOOL")): [Customer!]!
}
----

Without the directive, the generator would look up a column called `active` on the `customer` table. Sakila's `customer` table happens to have one (an unused integer flag), so the filter would silently bind to the wrong column. `@field(name: "ACTIVEBOOL")` makes the binding explicit and the build will fail loudly if `ACTIVEBOOL` ever disappears from the catalog.

This is the canonical case where `@field` is *not* redundant: GraphQL conventions favour short, intuitive argument names (`active`, `name`, `id`) while databases often keep longer, more specific column names (`ACTIVEBOOL`, `FIRST_NAME`, `CUSTOMER_ID`). The directive is what makes the schema readable on both sides without coupling them.

The argument can also drive a typed-enum filter (see "Enum values" below) or a xref:../reference/directives/lookupKey.adoc[`@lookupKey`] batch lookup; `@field` works the same way in either case.

== Input-field-to-column: mutations and filters

`@field` on `INPUT_FIELD_DEFINITION` plays the same role inside an `input` type used by a mutation or a filter. The input type itself carries no table directive (`@table` on an input is a deprecated location; the classifier ignores it and warns): its fields resolve against each *consuming field's* table. For a mutation that is the write-target table (derived from the field's return type, or named with xref:../reference/directives/mutation.adoc[`@mutation(table:)`]); for a query filter it is the field's return-type table.

[source,graphql]
----
input FilmCreateInput {
    title:      String! @field(name: "title")
    languageId: Int!    @field(name: "language_id")
}

type Mutation {
    createFilm(in: FilmCreateInput!): Film @mutation(typeName: INSERT)   # Film is @table(name: "film")
}
----

The `INSERT` writes `title` and `language_id`; the GraphQL camelCase never reaches SQL. The write targets `film` because the `Film` return type carries `@table(name: "film")`.

Three things that surface here and not on output types:

* *Required input scalars are write-time required.* A `title: String!` field on a mutation input means the column must be supplied on every call; nullability of the underlying column does not relax the GraphQL contract.
* *Input types don't compose like output types.* You cannot reuse `Customer` (an output type) as an input. Define `CustomerCreateInput` separately; its fields resolve against the consuming mutation's write target.
* *Filter inputs follow the same rule.* A `FilmConditionInput` consumed by `filmsByCondition(filter: FilmConditionInput): [Film!]!` resolves its fields against the `film` table (the query's return-type table) and uses `@field` on each input field to point the match at the right column. An input reused by consumers on different tables resolves per-consumer; a field that resolves on no consumer's table fails the build naming that table.

== Enum values: text-column and jOOQ-enum

GraphQL enums map to two distinct database shapes, and `@field` on `ENUM_VALUE` carries the right thing for each.

*Text-column enum.* The column is `text`, `varchar`, or another string type, and the DB stores literal values (some of which can't be GraphQL identifiers). Use `@field(name:)` on each value where the storage diverges:

[source,graphql]
----
"""Text-column enum: values map to database strings via @field(name:)."""
enum TextRating {
    G
    PG
    PG_13 @field(name: "PG-13")
    R
    NC_17 @field(name: "NC-17")
}
----

GraphQL doesn't allow `-` in enum values, but the database stores `"PG-13"` and `"NC-17"`. `@field` per value provides the GraphQL-safe identifier-to-storage mapping. The generator writes each database string into the generated enum type as the value's runtime value, so graphql-java does the translation at its own boundary: a GraphQL value becomes its DB string on the way down (filter arguments, mutation input), and a DB string becomes its GraphQL value on the way up (selection projections). Values without `@field` default to their own name, so `G`, `PG`, and `R` map to `"G"`, `"PG"`, and `"R"` without further configuration. Two values may map to the same string, as a deprecated spelling beside its replacement does; reading that string returns the first of them.

A text column can hold values the enum does not name, for example when the schema deliberately exposes only some of them. A single-valued enum field read from such a column resolves a row holding an unnamed value to `null`, and the response carries no error for it. The value is logged at `DEBUG` under the `<outputPackage>.schema.UnmappedEnumValue` category, with the field's coordinate, and never reaches the client. On a non-null field the `null` is a non-null violation, so the parent field resolves to `null` as graphql-java does for any missing non-null value. To make an unnamed value impossible, constrain the column in the database (a `CHECK` constraint, or a database enum type, the case below).

*jOOQ-typed enum.* The column is a database-native ENUM type (PostgreSQL `CREATE TYPE`) for which jOOQ generates a Java enum class. GraphQL enum values must match the Java constants exactly:

[source,graphql]
----
enum MpaaRating {
    G
    PG
    PG_13
    R
    NC_17
}
----

The generator validates every GraphQL value against the jOOQ-generated Java enum's `Enum.values()` and rejects mismatches at build time with a candidate-hint diagnostic. There is no `@field` per value on the jOOQ-enum case because the Java enum names are the contract; renaming a GraphQL value to a non-matching name fails the build.

The two cases coexist on the same database. The Sakila example schema's `Film.rating` is the jOOQ-enum form (`mpaa_rating` is a Postgres ENUM); `Film.textRating` is the text-column form on a sibling `TEXT_RATING` column that stores the same values as plain strings.

When the column is a jOOQ enum but the GraphQL side carries `@field` on values, the build fails. When the column is text but the GraphQL enum has no `@field` overrides, the values default to their own names; that's only correct if the DB happens to store the GraphQL identifiers verbatim.

== Re-binding and the table-context cascade

Column lookup resolves against a *current table context*. The cascade rules:

. The containing GraphQL type's `@table`, if it has one.
. A nested type's own `@table` re-binds inside that type.
. An xref:../reference/directives/reference.adoc[`@reference`]-annotated field hops the context into the joined table for the duration of its subquery.
. An argument or input field resolves against the *consuming field's* table, not the parent's: the return-type table on a query field, the write-target table on a `@mutation` field.

Two consequences worth highlighting:

* *Nested types don't inherit `@table` from their parent.* `Address` inside `Customer` re-binds to its own table; `@field` inside `Address` resolves against `address`, not `customer`. The xref:../reference/directives/reference.adoc[`@reference`] on `customer.address` carries the FK path so the join is correct.
* *Arguments resolve against the return type.* `customers(active: Boolean @field(name: "ACTIVEBOOL")): [Customer!]!` resolves `ACTIVEBOOL` against the `customer` table (the return type) even though the field lives on `Query`. This is why argument-side `@field` works without a `@table` on the argument itself.

== Grouping columns into a nested object

An object type without `@table`, returned by a field of a `@table` type, groups columns of the parent's row under one field. It is not a join: its fields read the parent's columns.

[source,graphql]
----
type Film @table {
    release: FilmRelease
}
type FilmRelease {
    year: Int @field(name: "RELEASE_YEAR")
    minutes: Int @field(name: "LENGTH")
}
----

A nullable field returning the nested type resolves to `null` when the object would hold nothing; see <<single-object-null,When a single object resolves to `null`>>. Declare the field non-null (`release: FilmRelease!`) to always get an object.

[#parents-own-row-as-table-type]
== Returning the parent's own row as a table type

A field whose return type is bound to the same table as its parent, with no xref:../reference/directives/reference.adoc[`@reference`], reads the parent's own row. Use it when the return type must stay `@table` because other fields return it on their own:

[source,graphql]
----
type Film @table {
    summary: FilmSummary
}
type FilmSummary @table(name: "film") {
    title: String @field(name: "TITLE")
    length: Int @field(name: "LENGTH")
}
----

`film { summary { title } }` returns each film's own title, in the same statement as the film. The field must be single-valued and take no arguments. A nullable one resolves to `null` when the object would hold nothing; see <<single-object-null,When a single object resolves to `null`>>.

With arguments, a xref:../reference/directives/condition.adoc[`@condition`] or a xref:../reference/directives/lookupKey.adoc[`@lookupKey`], the same field means something else: a read of the whole table narrowed by them, the same for every parent. `related(filter: FilmFilter): [Film!]` on `Film` returns the films matching the filter, whichever film it is selected under. A same-table field that is neither, a list or a single field with arguments that filter nothing, would read every row of the table under every parent and is rejected at build time. To reach other rows of the table related to the parent, state the self-referencing key with `@reference(path: [{key: ...}])`.

[#single-object-null]
== When a single object resolves to `null`

A nullable field of a `@table` type, or of an object nested in one, that returns one object resolves to `null` when the object would hold nothing: every column it reads is `null`, every single xref:../reference/directives/reference.adoc[`@reference`] in it finds no value, and every list in it is empty. A child with its own `@table` also resolves to `null` when no row matches. This is decided over all of the type's fields, whatever the query selects, so `address { __typename }` and `address { street }` agree on whether `address` is `null`. xref:../reference/directives/splitQuery.adoc[`@splitQuery`] does not change the answer.

[source,graphql]
----
type Customer @table {
    address: Address @splitQuery   # null when the row is missing or every column of it is null
    billing: Address!              # always an object; an error if no row matches
}
----

Declare the field non-null to always get an object. A type holding a list that takes arguments, a connection, an interface or union, an xref:../reference/directives/externalField.adoc[`@externalField`], a xref:../reference/directives/service.adoc[`@service`] field, a field reached through a database routine, or, in a multi-tenant build, a `@splitQuery` field read from another tenant's or the global database always resolves to an object, because whether it holds anything depends on the query, on code outside the table's rows, or on a database the parent's statement cannot reach. A type with a xref:../reference/directives/nodeId.adoc[`@nodeId`] field, or a field reading a column that is never `null`, never resolves to `null` while its row exists.

The rule is for fields of table types. A field of `Query`, a field returning an interface or union, and a `@service` field return what they fetch, so a row of nulls there is an object.

== Constraints and pitfalls

* `@field(name:)` is required (graphql-java rejects no-arg `@field` at parse time).
* The target identifier must resolve in the surrounding `@table`'s jOOQ catalog; mismatches fail the build with a candidate hint.
* `@field` is for column-bound slots only. Relations and nested types use xref:../reference/directives/reference.adoc[`@reference`] or auto-discovered FK paths.
* GraphQL slot name and target identifier match case-insensitively (lowercased + underscore-normalised). The directive is redundant when names match; spell it out anyway to surface drift.
* Input types carry no `@table` (the location is deprecated and ignored); their fields resolve against each consuming field's table.
* Text-column enum values default to their own name when `@field` is omitted; that is only correct when the DB stores the GraphQL identifier verbatim.
* jOOQ-enum values must match the Java enum constants 1:1; `@field` per value is rejected on the jOOQ-enum case.
* The argument-side default (column lookup against the field's *return-type* table) is what makes argument `@field` work without a `@table` on the argument itself; it also means the same argument bound to two different return types resolves against two different tables.
