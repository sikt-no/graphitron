# Lookup Field Generation

Plan for implementing the argument-to-SQL mapping for lookup fields — the `VALUES(...)` derived table construction and result partitioning.

## Context

`QueryLookupTableField` currently generates a thin fetcher + rows method that builds a condition and calls `selectMany`. This works for simple single-column scalar lookups (e.g., `filmById(film_id: [ID!]!)`). It does NOT handle:

- **Composite key lookups** — input-type arguments where multiple fields form the key (e.g., `rentalByKey(key: RentalKeyInput!)` where `RentalKeyInput` has `rentalId` + `inventoryId`)
- **Result ordering matching input order** — the Relay contract is that results come back in the same order as the input IDs. The current condition-based approach (`WHERE film_id IN (...)`) doesn't guarantee this.
- **`VALUES(...)` derived table pattern** — the correct approach: build a `VALUES(idx, col1, col2, ...)` derived table from the input arguments, JOIN against the target table, partition results back by `idx`. This preserves input ordering and handles both scalar and composite keys.

## Design

### The `VALUES(...)` pattern

For a lookup field `filmById(ids: [ID!]!)`:

```sql
SELECT f.*
FROM (VALUES (1, 42), (2, 17), (3, 99)) AS input(idx, film_id)
JOIN film f ON f.film_id = input.film_id
ORDER BY input.idx
```

For a composite key `rentalByKey(keys: [RentalKeyInput!]!)`:

```sql
SELECT r.*
FROM (VALUES (1, 42, 7), (2, 17, 3)) AS input(idx, rental_id, inventory_id)
JOIN rental r ON r.rental_id = input.rental_id AND r.inventory_id = input.inventory_id
ORDER BY input.idx
```

The `idx` column (1-based) preserves input ordering. `GRAPHITRON_INPUT_IDX` (already generated by `GraphitronValuesClassGenerator`) is the jOOQ `Field<Integer>` constant for this.

### What the generator produces

For each `QueryLookupTableField`, the rows method:

1. **Builds the derived table** from the arguments. Scalar list args become single-column VALUES; input-type args become multi-column VALUES with one column per input field.
2. **JOINs** the derived table against the target table using the column bindings from the field's arguments.
3. **Applies conditions** (from `filters()`) and ordering (from `orderBy()`).
4. **Orders by `idx`** to preserve input ordering.
5. **Returns** `Result<Record>` — the fetcher already handles wiring.

### Depends on argument taxonomy

The generator needs to know, per argument:
- Is it a scalar (`ColumnArg`) or input-type (`TableInputArg`)?
- What columns does it bind to?
- Is it a list (multiple rows in VALUES) or scalar (broadcast to all rows)?

This is exactly what `ArgumentRef` provides. Without it, the generator would have to reverse-engineer argument types from `GeneratedConditionFilter.bodyParams()`, which doesn't carry the scalar-vs-input distinction or the list flag at the right level.

## Implementation order

| Step | What | Depends on |
|---|---|---|
| 1 | Argument taxonomy (see [argument-taxonomy.md](argument-taxonomy.md)) | — |
| 2 | `VALUES(...)` derived table builder in `GeneratorUtils` — takes a list of `ColumnArg`/`TableInputArg` and produces the jOOQ `DSL.values(...)` expression | Step 1 |
| 3 | Replace the condition-based lookup in `buildQueryLookupRowsMethod` with the VALUES + JOIN pattern | Step 2 |
| 4 | Handle composite keys — `TableInputArg` with multiple bound columns | Steps 2-3 |
| 5 | Execution test — lookup with scalar key, composite key, verify result ordering matches input ordering | Steps 3-4 |

Step 1 is prerequisite. Steps 2-4 are the generator work. Step 5 validates correctness.

## Out of scope

- **Child-level lookup fields** (`LookupTableField`, `SplitLookupTableField`, `RecordLookupTableField`) — these use the same VALUES pattern but in a subquery or DataLoader context. The building block (step 2) is reusable; the integration is separate work tracked in the roadmap's G6 section.
- **Mutations** — mutations also use input-type arguments for DML, but the argument mapping is different (INSERT values, not lookup VALUES). Separate concern.
