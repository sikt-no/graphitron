# Lookup Field Generation

Plan for implementing the argument-to-SQL mapping for lookup fields — the `VALUES(...)` derived table construction and result partitioning.

## Context

`QueryLookupTableField` currently generates a thin fetcher + rows method that builds a condition and calls `selectMany`. This works for simple single-column scalar lookups (e.g., `filmById(film_id: [ID!]!)`). It does NOT handle:

- **Composite key lookups** — input-type arguments where multiple fields form the key
- **Result ordering matching input order** — the current `WHERE film_id IN (...)` approach doesn't guarantee results come back in input order
- **The `VALUES(...)` pattern** — the correct approach that preserves ordering and handles both scalar and composite keys

## The `VALUES(...)` pattern

For a scalar lookup `filmById(ids: [ID!]!)`:

```sql
SELECT f.*
FROM (VALUES (1, 42), (2, 17), (3, 99)) AS input(idx, film_id)
JOIN film f ON f.film_id = input.film_id
ORDER BY input.idx
```

For a composite key `rentalByKey(keys: [RentalKeyInput!]!)`:

```sql
SELECT r.*
FROM (VALUES (1, 42, 7), (2, 17, 3)) AS input(idx, rental_id, inventory_id)
JOIN rental r ON r.rental_id = input.rental_id AND r.inventory_id = input.inventory_id
ORDER BY input.idx
```

The `idx` column (1-based) preserves input ordering. `GRAPHITRON_INPUT_IDX` (already generated by `GraphitronValuesClassGenerator`) is the jOOQ `Field<Integer>` constant for this.

## `LookupMapping` — the generation-ready abstraction

The generator doesn't work with raw arguments. It works with `LookupMapping`, built by the builder from classified arguments (see [argument-taxonomy.md](argument-taxonomy.md)):

```java
record LookupMapping(
    List<LookupColumn> columns,
    TableRef targetTable
) {
    record LookupColumn(
        String argName,
        ColumnRef column,
        CallSiteExtraction extraction,
        boolean list
    ) {}
}
```

The generator iterates `columns` to build the `VALUES(idx, col1, col2, ...)` derived table and the JOIN condition. It uses `extraction` to emit the value extraction code. No argument classification at generation time.

This follows the same pattern as `GeneratedConditionFilter`: arguments are lifted into a generation-ready abstraction. The generator switches on pre-resolved data, not raw GraphQL types.

## Implementation order

| Step | What | Depends on |
|---|---|---|
| 1 | Argument taxonomy — `classifyArguments()` in the builder | [argument-taxonomy.md](argument-taxonomy.md) |
| 2 | Define `LookupMapping` + `LookupColumn` in the model | Nothing |
| 3 | Build `LookupMapping` from classified arguments for lookup fields | Steps 1-2 |
| 4 | `VALUES(...)` builder in `GeneratorUtils` — takes `LookupMapping`, produces jOOQ `DSL.values(...)` expression | Step 2 |
| 5 | Replace condition-based lookup in `buildQueryLookupRowsMethod` with VALUES + JOIN pattern | Steps 3-4 |
| 6 | Handle composite keys — `TableInputArg` with multiple bound columns | Steps 3-5 |
| 7 | Execution test — scalar key, composite key, verify result ordering matches input | Steps 5-6 |

## Out of scope

- **Child-level lookup fields** (`LookupTableField`, `SplitLookupTableField`, `RecordLookupTableField`) — same VALUES pattern in subquery or DataLoader context. The building block (step 4) is reusable; integration is separate work tracked in the roadmap G6 section.
- **Mutations** — input-type arguments for DML use a different mapping. Separate concern.
