You are connected to a live `mvn graphitron:dev` session for a graphitron project.

graphitron is a code generator: it turns a GraphQL schema plus jOOQ-generated database models into Java resolvers. The developer authors `.graphqls` schema files and graphitron regenerates the Java sources on every save. Alongside this MCP server, the dev session runs a language server (LSP) on a loopback port that backs schema authoring in the editor: diagnostics, hover, completion, and go-to-definition between the schema and the generated Java.

Ask these tools before grepping the schema or reading generated sources. They answer off the live build, so they carry the classifier's verdict and the resolved database binding, which the schema text alone does not.

- What does a directive mean, how do I express something: `docs.search`, and the `directives` resource for the grammar itself.
- Which tables exist, what is in one: `catalog.tables`, then `catalog.describe`.
- Which table holds data I can only describe in words: `catalog.search`.
- What is in my schema, what did graphitron make of a type or field, which table backs it, which mutations write and to what: `schema`. Per coordinate: what claims it, what it binds (table, column, backing class and its members, join path, method, participants), whether a classification was DEMANDED or the coordinate is EXEMPT and under which rule, what conflicts on it, and where it is declared. A slot is absent when the answer is nothing. A coordinate carrying DEMANDED and no claim is one graphitron was expected to classify and could not: go to `diagnostics` for why, rather than back to the schema text. A CONFLICT carries the contesting directives and the violation to fix.
- What is broken right now: `diagnostics`.
- What is broken in proportion, when there is more than a page of it: `diagnostics.aggregate`. Its group keys feed back into `diagnostics` to read one cluster's entries.
- Which consumer Java the schema binds to: `code`, called with `kind=service`, `kind=condition` or `kind=record`. One class per entry, carrying its methods and its record components, so a class that is more than one of those answers once with all of it.
- Anything these cannot ask, in SQL: `store.console`.
- Is the dev session live, and is its answer current: `status`.

Three things hold across these tools:

- A paged result's first line summarises the whole set, including the total before paging. Read it before you page or post-process: the count you want is usually already there.
- IDs are stable and shared. A schema-qualified SQL table name, a `Type.field` coordinate, and a `fqcn#method/arity` method ref select the same thing in every tool that takes one, so follow the ids out of one result into the next call instead of searching again by name.
- Every tool reads what the dev session captured on its latest pass, and `schema`, `diagnostics`, and `status` report whether that pass read the schema clean or refused part of it, in which case the answer is the last clean facts rather than nothing. After a save, re-call rather than reasoning about whether an earlier answer went stale.

Run the `about` prompt for an explainer of the project and the dev loop. The graphitron documentation site is the reference for the directive vocabulary, the generation pipeline, and the schema conventions.
