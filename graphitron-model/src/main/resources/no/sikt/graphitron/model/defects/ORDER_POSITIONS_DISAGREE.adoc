Reported at each `@defaultOrder` or `@order` whose order is read over several participant tables, the field named in the detail. A root list over a union or interface with no table of its own reads one branch per participant table and sorts the branches together, position by position: the first sort key of every participant in one column, the second in the next, and so on.

So every participant's order has to name the same number of keys, and at each position columns of one SQL type bound to one Java type. Their names may differ: an index of one name covering `event_id` on one table and `note_id` on the other, both integers, sorts together. Columns that differ in type at a position, an `integer` beside a `boolean`, have no one column to sort in, and an index covering one column on one table and two on another leaves a position with nothing on one side.

*Instead.* Name columns of one type in the same places on every participant, for example a column every participant table holds at one type, or give the indexes the order names the same shape on each table. An order by every participant's own primary key is compared by the keys instead. See xref:../how-to/sort-results.adoc#sort-across-polymorphism[How-to: Sort across polymorphism].
