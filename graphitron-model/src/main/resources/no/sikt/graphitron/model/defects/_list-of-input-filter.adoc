A filter field typed as a list of input objects matches rows equal to any one element, comparing the element's fields together as one row (`(c1, c2) IN ((..), (..))`). That reading holds only when every element field is one value bound to a column, so the build refuses an element field that is itself a list or a list of input objects, is a node id, or carries `@condition`; one that binds no column is `COLUMN_UNRESOLVED`, as anywhere else. Each defect sits at the element field, because the same input type is fine elsewhere (as a non-list nested input, or as a `@service` parameter), and one declaration read through two list filters is one defect. A `@lookupKey` list is the lookup's key rather than a filter, and none of this applies to it. Under a `@condition` written with `override: true`, on the list field or anything enclosing it, the condition owns the list and its elements are not compared as rows, so only `LIST_ELEMENT_CONDITION` still applies there.

The element fields' columns may all sit on the filtered table, or all on one table reached through the same `@reference` path, so the build also refuses, as `LIST_ELEMENT_PATHS_DIFFER`, element fields whose columns are reached through different `@reference` paths, two paths reaching one table over different keys or conditions among them, or that mix the filtered table's own columns with a path.

*Next step.* Give every element field the same `@reference` path, or move the field out of the element type. To filter on a shape the row cannot express, put `@condition(override: true)` on the list field; the method receives the whole list and owns the predicate. xref:directives/field.adoc#list-of-input-filter[`@field` on a list-of-input filter] describes the semantics.
