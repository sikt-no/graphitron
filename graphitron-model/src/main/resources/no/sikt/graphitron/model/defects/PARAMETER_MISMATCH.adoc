Reported at the directive's method reference, naming the parameter, or at a `@routine`, which names none; at the input field for a member of a class a `@service` builds, naming the member; and at the `@externalField` reference, naming the first table its parameter does not accept.

The generated call passes each parameter the value as it arrives, so it compiles only where the two agree: a list for a list and one value for one, and the class the value arrives as. An `ID` arrives as a `String`, an `Int` as an `Integer` or `int`, and an `Object` parameter takes any scalar or enum value. A `@condition` parameter taking one Java enum takes one enum value, not a list of them. An `@externalField` method's table parameter takes the table its field's values are rows of.

A parameter an `argMapping` hands a generated scalar's component, `pStart: input.sti.startType`, takes that component's class, a `String` for every component today, at a `@service` and at a root `@routine` alike: the generated call decodes the value and passes the component, never the whole value. At a `@routine` only such a binding is judged, against the type the database function declares for the parameter.
