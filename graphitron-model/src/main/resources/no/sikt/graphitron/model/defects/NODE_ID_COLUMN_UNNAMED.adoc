Reported at the xref:directives/service.adoc[`@service`] or xref:directives/condition.adoc[`@condition`] reference, or at the xref:directives/routine.adoc[`@routine`], the detail naming the parameter; a `$tenant` pair is reported where it is written.

A decoded node id is the node's whole key, and a parameter takes one of its columns only where the `argMapping` path names that column after the id. Nothing infers it, not even for a key of one column: a path ending on the id hands over the whole key, which lands only on the node's own record or a jOOQ `RecordN` or `RowN` of the key's columns. A `@routine` parameter takes one value, so a path ending on the id there always needs the column, and so does a `$tenant` pair, whose value is read as the tenant column's.

*Next step.* Add the key column after the id, as in `pActorId: filter.actorRef.actor_id`, or declare a `@service` or `@condition` parameter as the node's record. A `String` or `Object` parameter does not take the id as the client sent it: a `@nodeId` is decoded into its key, so to pass the id as sent, drop `@nodeId` from the argument. See xref:directives/nodeId.adoc#key-column-projection[Projecting one key column into an `argMapping` parameter].
