Each list is read in an order the build states: the one `@defaultOrder` writes, the primary key of the table the list's type is bound to where none is written, or the one a client picks through `@orderBy`. Where that table has no primary key, or the type is a function's result bound to no table, there is nothing to fall back on, and an `@orderBy` argument a client may leave out needs a `@defaultOrder` beside it. An ordering whose keys cannot be stated would sort by fewer keys than were written, or by none, so the build stops instead. An ordering is refused at the `@defaultOrder`, `@order`, `@orderBy` or `fields` element written, or at the list field; an `index` the table does not have is `ELEMENT_UNRESOLVED`, and a `fields` element's `name` matching no one column of the table is `COLUMN_UNRESOLVED`, the codes every name claimed in vain and every missing column draw.

*Next step.* Write one surface, name a column, index or primary key the table has, or add `@defaultOrder` to the list. For a `path`, name keys that join to one row each, from the field's table onward, and a column of the table it lands on; a value the path cannot reach, or one computed from several rows, goes in a view or a jOOQ computed column on the field's table, named with `name`. xref:directives/defaultOrder.adoc#constraints[`@defaultOrder` constraints] and xref:directives/order.adoc[`@order`] list the rules.
